# Story 33.2 — Add DB CHECK Constraint for Engagement Rate

## Story

**Como** engenheiro de dados responsavel pela integridade do banco,
**Quero** que o banco rejeite valores invalidos de `engagement_rate`, `total_leads` e `engaged_leads`,
**Para que** bugs futuros no app sejam detectados imediatamente no INSERT/UPDATE em vez de corromper dados silenciosamente.

## Contexto

A tabela `store_revenue_summary` armazena metricas de audiencia sem nenhuma validacao no nivel do banco:

- `total_leads` — deveria ser >= 0
- `engaged_leads` — deveria ser >= 0
- `engagement_rate` — deveria estar entre 0 e 100

A coluna `engagement_rate` foi originalmente `numeric(5,2)` (maximo 999.99), mas a migration `20260305_widen_numeric_rate_columns.sql` removeu a restricao de tamanho para `numeric` sem adicionar CHECK constraints. Isso permite que valores como 324% sejam persistidos sem erro.

### DEPENDENCIA CRITICA

> **Esta story so pode ser implementada APOS a Story 33.1 estar deployada em producao.**
>
> Se o CHECK constraint `engagement_rate <= 100` for aplicado antes do fix no app, o cron vai falhar com constraint violations para todas as lojas onde o rate ultrapassa 100%.

## Acceptance Criteria

### 33.2.1 — Corrigir dados existentes antes do constraint

- [x] A migration DEVE comecar com UPDATE para corrigir rows existentes que violam os constraints:
  ```sql
  -- Cap engagement_rate at 100 for existing rows
  UPDATE store_revenue_summary
    SET engagement_rate = 100
    WHERE engagement_rate > 100;

  -- Ensure no negative values
  UPDATE store_revenue_summary
    SET total_leads = 0
    WHERE total_leads < 0;

  UPDATE store_revenue_summary
    SET engaged_leads = 0
    WHERE engaged_leads < 0;

  UPDATE store_revenue_summary
    SET engagement_rate = 0
    WHERE engagement_rate < 0;
  ```

### 33.2.2 — Adicionar CHECK constraints

- [x] Criar migration `supabase/migrations/20260310_check_constraints_engagement.sql`
- [x] Adicionar constraint: `CHECK (total_leads >= 0)`
- [x] Adicionar constraint: `CHECK (engaged_leads >= 0)`
- [x] Adicionar constraint: `CHECK (engagement_rate >= 0 AND engagement_rate <= 100)`
- [x] Usar `ALTER TABLE ... ADD CONSTRAINT ... CHECK (...)` com nomes descritivos:
  ```sql
  ALTER TABLE store_revenue_summary
    ADD CONSTRAINT chk_total_leads_non_negative CHECK (total_leads >= 0);

  ALTER TABLE store_revenue_summary
    ADD CONSTRAINT chk_engaged_leads_non_negative CHECK (engaged_leads >= 0);

  ALTER TABLE store_revenue_summary
    ADD CONSTRAINT chk_engagement_rate_range CHECK (engagement_rate >= 0 AND engagement_rate <= 100);
  ```

### 33.2.3 — Idempotencia

- [x] A migration deve ser idempotente — usar `DO $$ ... IF NOT EXISTS` ou `ADD CONSTRAINT IF NOT EXISTS` (Postgres 12+):
  ```sql
  DO $$
  BEGIN
    IF NOT EXISTS (
      SELECT 1 FROM pg_constraint WHERE conname = 'chk_total_leads_non_negative'
    ) THEN
      ALTER TABLE store_revenue_summary
        ADD CONSTRAINT chk_total_leads_non_negative CHECK (total_leads >= 0);
    END IF;
    -- ... repeat for other constraints
  END $$;
  ```

### 33.2.4 — NOT NULL constraints nas colunas de audiencia

- [x] Backfill NULLs existentes para 0: `UPDATE ... SET COALESCE(..., 0)`
- [x] Adicionar `NOT NULL` em `total_leads`, `engaged_leads`, `engagement_rate`
- [x] Migration idempotente (so altera colunas que ainda sao nullable)
- [x] Verificado: zero NULLs e `is_nullable = NO` para as 3 colunas

### 33.2.5 — Validar pre-condicao (Story 33.1 deployed)

- [x] Antes de aplicar a migration em producao, confirmar que Story 33.1 ja esta deployada
- [x] Documentar no Change Log a data de deploy da 33.1

## Ordem de Implementacao
