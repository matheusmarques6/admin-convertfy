## Story

**As a** desenvolvedor da API,
**I want** endpoints que suportem criacao de loja sem `client_id` e vinculacao posterior,
**so that** o frontend possa implementar os novos fluxos de cadastro rapido e vinculacao.

## Acceptance Criteria

1. `POST /api/client-stores/credentials` aceita body sem `client_id` (campo opcional)
2. Quando `client_id` ausente, `org_id` e capturado do usuario autenticado via Supabase Auth (trigger `set_store_org_id` garante fallback no banco)
3. Quando `client_id` presente, comportamento identico ao atual (retrocompativel)
4. Novo endpoint `PATCH /api/client-stores/[id]/link` com body `{ client_id: string | null }`
5. Endpoint de link valida permissao: `is_admin()` ou usuario tem acesso a loja (`can_access_store`)
6. Endpoint de link valida que `client_id` (quando informado) pertence a mesma `org_id` da loja
7. Zod schema criado para validacao de input no POST (store create) e PATCH (link)
8. **[ARCH-AD2]** Audit trail registrado na tabela `activities` com tipos `store_linked`/`store_unlinked` (metadata inclui store_id, previous_client_id, new_client_id)
9. Retorno do PATCH inclui loja atualizada com dados do cliente (ou null)
10. **[ARCH-AD3]** Ao vincular/desvincular, cascata de `client_id` nas tabelas satelite: `store_alerts`, `store_onboarding_data` e `client_onboardings` sao atualizadas para manter consistencia
11. **[GAP-G4]** Ao criar loja avulsa via POST, auto-criar registro em `agent_store_access` para o usuario criador com `can_view = true, can_edit = true` — senao o criador perde acesso a loja
12. **[GAP-G2]** Cadastro rapido de loja avulsa permitido para qualquer membro autenticado da org (MVP) — RLS valida via `client_id IS NULL` + trigger `org_id`

## Dev Notes

### Arquivos Relevantes

**API Route atual (POST/PUT):**
- `src/app/api/client-stores/credentials/route.ts`
  - POST handler: Linha que valida `client_id` — `if (!client_id) { throw new AppError("client_id is required", 400) }`
  - `client_id` NAO esta em `ALLOWED_FIELDS` — e extraido e atribuido separadamente
  - PUT handler: NAO usa `client_id` — ja e imutavel no update

**Services:**
- `src/lib/services/credentials.service.ts` — `getStoreCredentials()` retorna `client_id` no resultado
- `src/lib/api/` — Helpers de resposta e erro (`AppError`, etc.)

**Schemas existentes:**
- `src/lib/schemas/common.ts` — Nao tem schema de store. Tem `campaignCreateSchema` e `taskCreateSchema` como referencia de padrao

**Supabase clients:**
- `src/lib/supabase/client.ts` — Client-side (usa JWT do usuario, RLS aplica)
- `src/lib/supabase/server.ts` — Server-side com `createAdminClient()` (bypassa RLS)

**Audit trail (ARCH-AD2) — Usar tabela `activities`:**
O projeto tem 3 sistemas de audit separados. Para vinculo/desvinculo de lojas, usar a tabela `activities` (de `00001_initial_schema.sql`):
- Novos tipos de enum adicionados na Story 1.1: `store_created`, `store_linked`, `store_unlinked`
- `activities.client_id` e nullable — funciona para lojas avulsas (setar como `new_client_id` ou NULL)
- `activities.metadata JSONB` armazena detalhes: `{ store_id, store_name, previous_client_id, new_client_id, new_client_name }`
- `client.service.ts` usa `publishEvent()` e `logActivity()` — reutilizar esse padrao

**Cascata em tabelas satelite (ARCH-AD3):**
Ao vincular/desvincular, atualizar `client_id` tambem em:
- `store_alerts` — para que alertas reflitam o cliente atual (ou NULL se avulsa)
- `store_onboarding_data` — para consistencia de dados
Usar `adminClient` (service role) para bypassar RLS nessas updates satelite.

**Ponto critico — org_id no POST:** Quando `client_id` e NULL, o `org_id` deve ser buscado do usuario autenticado. O helper RLS `current_org_id()` funciona no banco, mas no API route (server-side) precisa buscar via:
```ts
const { data: { user } } = await supabase.auth.getUser()
// Buscar org_id do usuario via org_members
```
