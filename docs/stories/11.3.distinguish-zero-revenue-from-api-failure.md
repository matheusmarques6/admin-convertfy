**Prioridade:** P1 (Alta — previne falhas mascaradas como dados validos)

## Contexto

A funcao `getKlaviyoRevenueForStore` em `src/lib/integrations/klaviyo/report-summary.ts` tem dois problemas:

1. **Falha mascarada como zero:** O catch block (linha 130-133) retorna `{ totalRevenue: 0, campaignRevenue: 0, flowRevenue: 0, currency: "BRL" }` para QUALQUER erro (timeout, rate limit, credencial invalida). Apos a Story 11.1, esses "zeros falsos" serao cacheados no `store_revenue_summary` com `sync_status: 'ok'`, poluindo o cache.

2. **Currency hardcoded no erro:** O catch retorna `currency: "BRL"` mesmo para lojas USD/EUR. Se o cache gravar isso, a conversao de moeda via `convertToBRL()` vai usar a taxa errada.

3. **Null silencioso do `klaviyoRequest()`:** Quando a API retorna 400/500, `klaviyoRequest()` retorna `null`. A funcao trata `null` como "zero revenue" (linhas 104-106 logam warn mas continuam).

---

## Objetivo

Fazer `getKlaviyoRevenueForStore` retornar um resultado tipado que distingue "zero real" de "falha API", para que o caller possa decidir se deve cachear ou nao. Usar o type `SyncResult<T>` de `src/lib/shared/data-status.ts` (criado no Epic 10, Story 10.1).

## Arquitetura Tecnica

### Fluxo Antes vs Depois

**Antes:**
```
getKlaviyoRevenueForStore() -> { totalRevenue: 0 }  (falha mascarada)
  caller: cacheia com sync_status: 'ok' -> poluicao do cache
```

**Depois:**
```
getKlaviyoRevenueForStore() -> { success: false, error: "rate limit" }
  caller: cacheia com sync_status: 'error', expires_at: +5min
  proximo request: ve error no cache, tenta live fetch novamente
```

### Impacto no `buildResponse()`

A funcao `buildResponse` em `total-revenue/route.ts` recebe `rows` que incluem `sync_status`. O campo `hasPartialData` ja verifica `sync_status === "error"`:
```typescript
const hasPartialData = rows.some(
  (s) => s.sync_status === "error" || s.sync_status === "partial"
)
```
Isso vai funcionar corretamente com lojas que falharam.
