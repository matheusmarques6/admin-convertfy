# Story 40.10 — Edge Cases and Guards

## Story

**Como** sistema robusto,
**Quero** que os casos de borda do sync onboarding<->board sejam tratados gracefully,
**Para que** o pipeline nao quebre em cenarios inesperados.

## Contexto

O fluxo de sync tem varios cenarios que precisam de tratamento especial:

1. Step sem assignee (role nao preenchido, membro nao existe na org)
2. Step bloqueado manualmente (override do DAG)
3. Step skipado (nao precisa ser executado)
4. Task deletada do board enquanto step ainda ativo
5. Membro desativado apos task ser criada
6. Multiplos onboardings com steps paralelos completados simultaneamente
7. Template step adicionado a um onboarding ja em andamento
8. Ciclos de dependencia inseridos via admin direto no banco

## Acceptance Criteria

### Assignee ausente
- [x] **AC 40.10.1**: Se step fica `pending` mas nao tem `assigned_to` e nao tem `default_assignee_role`, logar warning e criar task para o `assigned_to` do onboarding (fallback para o responsavel geral)
- [x] **AC 40.10.2**: Se o role existe mas nenhum membro ativo com esse role na org, logar warning e criar notificacao para owners/managers: "Etapa '{step.name}' pronta mas sem membro com role '{role}'"

### Step bloqueado manualmente
- [x] **AC 40.10.3**: Step com status `blocked` e `blocked_reason` preenchido NAO e transicionado automaticamente pelo DAG resolver (mesmo que dependencias estejam satisfeitas)
- [x] **AC 40.10.4**: Para desbloquear, usuario deve explicitamente mudar status de `blocked` para `pending` via UI

### Step skipado
- [x] **AC 40.10.5**: Quando um step e marcado como `skipped`, o sistema trata como dependencia satisfeita e executa `handleNewlyPendingSteps` para desbloquear downstream
- [x] **AC 40.10.6**: Se step tem `task_id`, a task correspondente e cancelada (`status = 'cancelled'`)

### Task deletada
- [x] **AC 40.10.7**: Se task e deletada do board (via UI ou API), o `client_onboarding_steps.task_id` e limpo (ON DELETE SET NULL ja garante isso via FK)
- [x] **AC 40.10.8**: Step permanece no status atual — nao reverte para `waiting`. Membro pode completar via kanban de onboarding diretamente

### Membro desativado
- [x] **AC 40.10.9**: Se membro e desativado (`org_members.is_active = false`), tasks existentes permanecem mas novas tasks NAO sao criadas para ele
- [x] **AC 40.10.10**: Na resolucao de assignee por role, filtrar por `is_active = true`

### Race conditions
- [x] **AC 40.10.11**: Se dois steps paralelos sao completados simultaneamente e ambos desbloqueiam o mesmo step downstream, apenas UMA task e criada (dedup via `source_type + source_id + assignee_id`)
- [x] **AC 40.10.12**: O `StepDependencyService.transitionToPending()` usa `UPDATE ... WHERE status = 'waiting'` para garantir que nao transiciona um step ja transicionado por outro request

### Validacao de ciclos
- [x] **AC 40.10.13**: Ao criar um onboarding a partir de template, validar DAG do template com `StepDependencyService.validateDag()`. Se ciclo detectado, rejeitar criacao com erro descritivo

### Step reassignment
- [x] **AC 40.10.14**: Quando um step e reatribuido a um membro diferente (`assigned_to` muda), atualizar ou recriar a task vinculada no board do novo assignee
- [x] **AC 40.10.15**: Ao reatribuir step, notificar o novo assignee sobre a tarefa

## Technical Notes

### Guard para assignee ausente

```typescript
// Em TaskAutomationService.onOnboardingStepPending():
async function resolveAssignee(params: {
  assignedTo?: string
  defaultAssigneeRole?: string
  orgId: string
  onboardingAssignedTo?: string // fallback
}): Promise<string | null> {
  // 1. Assignee direto
  if (params.assignedTo) return params.assignedTo

  // 2. Por role
  if (params.defaultAssigneeRole) {
    const member = await findActiveMemberByRole(params.orgId, params.defaultAssigneeRole)
    if (member) return member.id

    // Role existe mas nao tem membro → notificar
    await notifyNoMemberForRole(params.orgId, params.defaultAssigneeRole, params.stepName)
  }

  // 3. Fallback: responsavel geral do onboarding
  if (params.onboardingAssignedTo) return params.onboardingAssignedTo

  return null
}
```

### Guard para skip

```typescript
// Em OnboardingSyncService:
static async onStepSkipped(stepId: string): Promise<void> {
  const supabase = await createAdminClient()

  // 1. Buscar step
  const { data: step } = await supabase
    .from("client_onboarding_steps")
    .select("id, onboarding_id, task_id, status")
    .eq("id", stepId)
    .single()

  if (!step) return

  // 2. Cancelar task se existir
  if (step.task_id) {
    await supabase
      .from("tasks")
      .update({ status: "cancelled", metadata: { _syncOrigin: "step_skipped" } })
      .eq("id", step.task_id)
  }

  // 3. Marcar step como skipped
  await supabase
    .from("client_onboarding_steps")
    .update({ status: "skipped" })
    .eq("id", stepId)

  // 4. Cascade — skip satisfaz dependencias
  await OnboardingSyncService.handleNewlyPendingSteps(step.onboarding_id)
}
```
