# Story 5.1 - Fix Dashboard Total Revenue: Lojas Avulsas Excluidas do Calculo

**Prioridade:** Alta
**Sprint:** Current
**Assignee:** @dev
**Revisao:** @sm (River)
**Status:** In Progress

---

## Contexto

O endpoint `GET /api/dashboard/total-revenue` busca lojas de forma indireta: primeiro busca `clients` por `org_id`, depois busca `client_stores` filtrando por `.in("client_id", clientIds)`. Esse caminho exclui **todas as lojas com `client_id = NULL`** (lojas avulsas criadas sem vinculo a um cliente).

Resultado: o dashboard mostra receita parcial. Apenas lojas vinculadas a um cliente aparecem. Lojas avulsas com Klaviyo configurado e gerando receita sao completamente ignoradas.

O endpoint `/api/stores/control` ja usa o padrao correto: `.eq("org_id", orgId)` diretamente na tabela `client_stores`, sem passar por `clients`.

---

## Objetivo

Simplificar a query de lojas no endpoint `total-revenue` para usar `org_id` diretamente, garantindo que **todas as lojas da organizacao** (com e sem `client_id`) sejam incluidas no calculo de receita.

## Arquitetura Tecnica

### Arquivo Principal: `src/app/api/dashboard/total-revenue/route.ts`

#### Mudanca 1 — Remover dependencia de clientIds para buscar lojas

**ANTES (linhas ~120-165):**
```typescript
// Fetch clients in user's org, then their stores with Klaviyo keys
const { data: orgClients } = await admin
  .from("clients")
  .select("id, name")
  .eq("org_id", orgId)

const clientIds = orgClients?.map((c) => c.id) || []

if (clientIds.length === 0) {
  // retorna vazio — BUG: org pode ter lojas sem clientes
}

// ...

const { data: stores } = await admin
  .from("client_stores")
  .select("id, store_name, client_id")
  .or("klaviyo_private_key.not.is.null,klaviyo_api_key.not.is.null")
  .eq("is_active", true)
  .in("client_id", clientIds)  // <-- EXCLUI lojas avulsas
```

**DEPOIS:**
```typescript
// Fetch stores directly by org_id (includes stores with AND without client_id)
const [{ data: stores, error: storesError }, { data: orgClients }] = await Promise.all([
  admin
    .from("client_stores")
    .select("id, store_name, client_id")
    .or("klaviyo_private_key.not.is.null,klaviyo_api_key.not.is.null")
    .eq("is_active", true)
    .eq("org_id", orgId),
  admin
    .from("clients")
    .select("id, name")
    .eq("org_id", orgId),
])

if (!stores || stores.length === 0) {
  // retorna vazio — mas agora corretamente: nenhuma loja ativa com Klaviyo
}

// clientNameMap para display (fallback para store_name se client_id = null)
const clientNameMap = new Map(orgClients?.map((c) => [c.id, c.name]) || [])
```

#### Mudanca 2 — Fallback no clientName

Onde `clientNameMap.get(s.client_id)` eh usado, adicionar fallback:
```typescript
const clientName = s.client_id
  ? (clientNameMap.get(s.client_id) || "Cliente desconhecido")
  : s.store_name  // Loja avulsa: usar nome da loja
```

#### Mudanca 3 — Debug query consistente

A query de debug (`allStoresCount`) tambem deve usar `.eq("org_id", orgId)` em vez de `.in("client_id", clientIds)`.

#### Mudanca 4 — Remover early return por clientIds.length === 0

O check `if (clientIds.length === 0) return empty` deve ser removido ou movido para checar `stores.length === 0` em vez disso.

### Code Review Findings

**1. Correctness of the Fix -- PASS**
- The root cause (filtering via `.in("client_id", clientIds)`) has been correctly replaced with `.eq("org_id", orgId)`
- The early return on `clientIds.length === 0` has been properly removed
- The new early return on `filteredStores.length === 0` (line 169) is correct and covers both empty-org and store-ids-filter-miss scenarios
- `StoreInput.client_id` type correctly changed from `string` to `string | null`

**2. Regression Analysis -- PASS**
- `store_ids` filter (lines 163-167): untouched, works as before
- `clientNameMap` (line 146): still built from `orgClients`, now with safe fallback `|| []`
- API response format (`TotalRevenueResponse` interface): unchanged
- Klaviyo revenue fetching (`getKlaviyoRevenueForStore`): call signature unchanged
- Cache key construction: unchanged, still includes `user.id` for tenant isolation

**3. Security -- PASS**
- `orgId` is resolved from authenticated user via `resolveOrgId()` using RLS-protected `createClient()`
- `createAdminClient()` is used appropriately -- only after `orgId` is securely resolved
- All three parallel queries scope to `orgId`, preventing cross-tenant data leakage
- No SQL injection vectors (Supabase query builder with parameterized values)
- Cache key includes `user.id` to prevent cross-tenant cache poisoning

**4. Performance -- PASS**
- Three queries now run in parallel via `Promise.all` (stores, clients, debug) -- improvement over sequential original
- No N+1 queries introduced
- Chunk processing (CHUNK_SIZE = 2) remains for Klaviyo rate limit management
- Cache mechanism unchanged (10-minute TTL)

**5. Code Quality -- PASS**
- TypeScript types are correct (`client_id: string | null`)
- No dead code or unused imports
- Error handling follows codebase pattern (`errorResponse` + `AppError`)
- Debug logging improved with `"(avulsa)"` annotation for standalone stores
- Consistent use of `log.info` / `log.error` / `log.warn`

**6. Wise Reconcile Analysis -- PASS (no fix needed)**
- `wise/reconcile/route.ts` uses `.in("client_id", orgClientIds)` intentionally
- Reconciliations are inherently per-client operations (POST requires `client_id`)
- The `wise_reconciliations` table has a `client_id` foreign key -- stores without clients cannot have reconciliations
- This is semantically correct and does NOT need the same fix

### Observations (non-blocking)

1. **Debug query in production**: The `allStoresDebug` query (lines 141-143) fetches ALL stores including sensitive field names (`klaviyo_private_key`, `klaviyo_api_key`) for logging. The values are only checked as booleans (`!!s.klaviyo_private_key`), so no credential leakage, but the debug query adds latency. Consider removing or gating behind a `DEBUG` flag in future.

2. **Non-null assertion removed**: The original `orgClients!.map(...)` was replaced with `orgClients?.map(...) || []` -- safer and correct.

3. **AC 5.1.8 (manual testing)**: Marked as not checked in the story. This requires runtime validation with actual stores that have `client_id = NULL` and Klaviyo keys configured. Recommend verifying before merge.

### Summary

The fix is clean, correct, and well-scoped. It addresses the root cause (stores excluded by `client_id` indirection), improves performance (parallel queries), maintains backward compatibility (same API response format, same `store_ids` filter), and follows established codebase patterns. The Wise reconcile route was correctly assessed as not needing the same fix.
