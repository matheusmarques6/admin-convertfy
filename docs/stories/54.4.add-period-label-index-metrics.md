# Story 54.4 — Add Missing Index on `period_label` for Metrics Tables

## Story

**Como** engenheiro de performance,
**Quero** que as queries por `period_label` em `klaviyo_flow_metrics` e `klaviyo_campaign_metrics` usem indice,
**Para que** as operacoes de DELETE e SELECT por periodo nao degradem com o crescimento dos dados.

## Contexto

### Problema

Ambas as tabelas sao consultadas frequentemente com `.eq("period_label", period)`:

**Leitura (portal):**
```typescript
// portal/dashboard/route.ts
.from("klaviyo_flow_metrics").select("*").eq("store_id", storeId).eq("period_label", period)
.from("klaviyo_campaign_metrics").select("*").eq("store_id", storeId).eq("period_label", period)
```

**Escrita (cron):**
```typescript
// sync-persistence.service.ts
.from("klaviyo_flow_metrics").delete().eq("store_id", storeId).eq("period_label", period)
.from("klaviyo_campaign_metrics").delete().eq("store_id", storeId).eq("period_label", period)
```

O UNIQUE constraint existente e `(store_id, flow_id, period_start, period_end)` — **nao inclui `period_label`**. Queries por `(store_id, period_label)` fazem scan sequencial dentro do partition de store_id.

### Estimativa de impacto

Com 50 lojas x 4 periodos x ~30 campaigns = ~6000 rows. Sequential scan ainda e rapido, mas com crescimento para 200+ lojas + historico, se torna gargalo. O indice custa quase nada e previne degradacao futura.

## Acceptance Criteria

### 54.4.1 — Index composto para flow metrics

- [x] Criar migration com indice:
  ```sql
  CREATE INDEX IF NOT EXISTS idx_flow_metrics_store_period
    ON klaviyo_flow_metrics(store_id, period_label);
  ```

### 54.4.2 — Index composto para campaign metrics

- [x] Na mesma migration:
  ```sql
  CREATE INDEX IF NOT EXISTS idx_campaign_metrics_store_period
    ON klaviyo_campaign_metrics(store_id, period_label);
  ```

### 54.4.3 — Validacao

- [x] Migration e idempotente (`IF NOT EXISTS`)
- [x] `npm run build` passa
