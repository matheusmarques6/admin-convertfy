## Story

**Como** operador do sistema que gerencia multiplas lojas com integracoes Klaviyo,
**Quero** que API keys contendo caracteres invalidos (nao-ASCII) sejam sanitizadas na entrada e tratadas defensivamente na execucao,
**Para que** uma loja com key corrompida nao cause crashes silenciosos no cron sync, desperdice retries e fique permanentemente sem dados.

---

## Contexto

### Problema observado em producao (2026-03-05)

O cron `sync-reports` processa 8 lojas x 4 periodos. Uma loja especifica (key terminando em `...7466`) falha 100% das chamadas com o erro:

```
TypeError: Cannot convert argument to a ByteString because the character at
index 16 has a value of 8226 which is greater than 255.
```

O caractere Unicode `8226` e `bullet` (ponto marcador). Ele esta na posicao 16 da API key Klaviyo salva no banco. Quando o Node.js `fetch()` tenta montar o header `Authorization: Klaviyo-API-Key <key>`, falha porque HTTP headers so aceitam bytes 0-255 (ByteString / ASCII estendido).

### Causa raiz

A API key foi salva no banco com um caractere `bullet` (`U+2022`). Provavelmente veio de um copy-paste de PDF, email formatado ou pagina com bullet points decorativos. A funcao `updateStoreCredentials()` em `credentials.service.ts` nao valida o formato da key antes de encriptar e salvar.

### Impacto atual

1. **Loja afetada**: 100% das chamadas Klaviyo falham — nenhum dado e sincronizado
2. **Desperdicio de recursos**: cada chamada esgota 3 retries + backoff exponencial (~10.5s por tentativa), desperdicando tempo precioso do cron de 300s
3. **Cascata silenciosa**: o erro e logado como `REQUEST ERROR` generico sem indicar que a key e invalida — dificulta diagnostico
4. **Sem recuperacao**: como a key invalida esta persistida no banco, o erro se repete a cada execucao do cron indefinidamente

### Stack trace


O crash ocorre no construtor de `Headers` do `undici` (fetch nativo do Node.js), antes mesmo de a requisicao ser enviada. Por isso retries sao inuteis — vao falhar no mesmo ponto.

## Acceptance Criteria

### 16.6.1 — Validacao na entrada (credentials.service.ts)

- [x] Em `updateStoreCredentials()`, antes de encriptar e salvar qualquer campo de API key (`klaviyo_api_key`, `klaviyo_private_key`, `klaviyo_public_key`, `shopify_access_token`, `shopify_api_key`, `shopify_api_secret`), validar que o valor contem apenas caracteres ASCII printaveis (range `0x20`-`0x7E`)
- [x] Se a validacao falhar, lancar `AppError` com status 400 e mensagem clara
- [x] Aplicar `.trim()` antes da validacao para remover espacos/newlines acidentais de copy-paste
- [x] A validacao deve estar ANTES da chamada a `encrypt()` — nao adianta validar depois de encriptado
- [x] O campo `meta_access_token` (presente em `ENCRYPTED_FIELDS`) NAO precisa de validacao — tokens Meta vem de OAuth callback, nao de input manual do usuario. Documentar com comentario inline no codigo.

**Arquivo:** `src/lib/services/credentials.service.ts`

**Cobertura de pontos de entrada (QA Ressalva 1):**

Todos os caminhos de codigo que salvam credenciais passam por `updateStoreCredentials()`:
- `api/integrations/save/route.ts` (formulario manual)
- `api/integrations/shopify/callback/route.ts` (OAuth)
- `api/integrations/google/callback/route.ts` (OAuth)
- `api/integrations/meta/callback/route.ts` (OAuth)

Edicao direta via Supabase dashboard NAO e coberta, mas o AC 16.6.2 (fail-fast no client) serve como defense-in-depth para esse caso.

**Implementacao sugerida:**

```typescript
const ASCII_PRINTABLE = /^[\x20-\x7E]+$/

// meta_access_token nao precisa de validacao — vem de OAuth, nao de input manual
const FIELDS_TO_VALIDATE: ReadonlySet<string> = new Set([
  "shopify_access_token",
  "shopify_api_key",
  "shopify_api_secret",
  "klaviyo_api_key",
  "klaviyo_private_key",
  "klaviyo_public_key",
])

function validateCredentialField(field: string, value: string): string {
  const trimmed = value.trim()
  if (!trimmed) return trimmed
  if (!ASCII_PRINTABLE.test(trimmed)) {
    throw new AppError(
      `O campo ${field} contem caracteres invalidos. Copie a API key novamente sem formatacao.`,
      400
    )
  }
  return trimmed
}
```

### 16.6.2 — Defesa no client.ts (fail-fast sem retry)

- [x] Criar `KlaviyoInvalidKeyError` no `client.ts` (similar a `KlaviyoPermissionError`)
- [x] Exportar `KlaviyoInvalidKeyError` pelo barrel `src/lib/integrations/klaviyo/index.ts`
- [x] Em `_klaviyoRequestInner()` no `client.ts`, detectar o `TypeError` de ByteString no catch e lancar `KlaviyoInvalidKeyError` (fail-fast, sem retry)
- [x] Este check deve ficar no bloco catch, DEPOIS dos checks de `KlaviyoPermissionError`, `KlaviyoRateLimitError` e `AbortError`, e ANTES do `if (attempt < maxRetries) continue` generico
- [x] Adicionar re-throw de `KlaviyoInvalidKeyError` junto com os outros re-throws no topo do catch
  ```typescript
  if (error instanceof KlaviyoInvalidKeyError) {
    throw error  // not retryable — permanent key error
  }
  ```

**Arquivo:** `src/lib/integrations/klaviyo/client.ts`

**QA Ressalva 2 — Por que throw em vez de return null:**

Retornar `null` faria o cron registrar "No Placed Order metric" — semanticamente incorreto, pois o problema e key corrompida, nao ausencia de dados. Lancar `KlaviyoInvalidKeyError` permite que o cron (`sync-reports/route.ts`) capture e registre `sync_error: "Klaviyo API key is invalid: ..."` no `store_revenue_summary`, distinguindo claramente de outros erros. O `Promise.allSettled` no cron ja trata rejeicoes sem crashar o batch inteiro.

### 16.6.3 — Correcao da key no banco (one-time fix)

**Status: BLOCKED/OPS** — tarefa operacional, nao de codigo.

- [ ] Identificar a loja com key terminando em `...7466` no banco de dados (requer acesso ao Supabase)
- [ ] Verificar o conteudo decriptado da key e remover o caractere bullet (`U+2022`) manualmente
- [ ] Re-encriptar e atualizar o registro
- [ ] Confirmar que o cron sync passa para essa loja apos a correcao

**Por que esta bloqueado:**

Keys estao encriptadas com AES-256-GCM (`enc:v1:...`). Nao e possivel identificar ou corrigir via SQL puro. Requer acesso ao `ENCRYPTION_KEY` de producao + runtime Node.js para decrypt/encrypt.

**Opcoes de resolucao (escolher uma):**

1. **Pedir ao cliente** para re-salvar a key pelo portal — a validacao do AC 16.6.1 agora rejeita caracteres invalidos
2. **Script one-off** (`scripts/fix-corrupted-key.ts`) — dado `ENCRYPTION_KEY` + `storeId`, decripta, limpa bullet, re-encripta e salva via `updateStoreCredentials()`
3. **Supabase Edge Function** — mesma logica do script, mas executada no ambiente Supabase com acesso ao secret

> Nota: a opcao 1 e a mais simples e segura. As opcoes 2 e 3 requerem acesso ao ambiente de producao.

## Notas Tecnicas

### Por que nao sanitizar silenciosamente no client?

Uma opcao seria fazer `apiKey.replace(/[^\x20-\x7E]/g, "")` no `client.ts` e continuar. Isso e **perigoso** porque:

1. Remover caracteres da key produz uma key diferente — que sera rejeitada pelo Klaviyo com 401/403
2. Isso mascararia o problema real (key salva errada) gerando erros confusos de autenticacao
3. Melhor falhar rapido com mensagem clara do que falhar com erro ambiguo

### Riscos e mitigacoes

| Risco | Mitigacao |
|-------|-----------|
| Regex de validacao rejeita keys legitimas com caracteres especiais | API keys Klaviyo/Shopify sao sempre alfanumericas — regex `[\x20-\x7E]` cobre todo ASCII printavel incluindo `_`, `-`, `.` |
| Correcao manual da key errada no banco | Fazer backup do valor encriptado atual antes de alterar. Usar `updateStoreCredentials()` (com validacao) para garantir que a key nova e limpa |
| `updateStoreCredentials()` e usado em multiplos lugares (OAuth callback, admin UI, portal) | A validacao e transparente — keys validas passam sem modificacao, so rejeita invalidas |
| Edicao direta no Supabase dashboard bypassa validacao | AC 16.6.2 (fail-fast no client) serve como defense-in-depth — key invalida nao vai crashar o cron |
| `KlaviyoInvalidKeyError` nao tratada por algum caller | `Promise.allSettled` no cron ja trata rejeicoes. Callers manuais (portal, admin) recebem 500 generico via `errorResponse()` — aceitavel |
