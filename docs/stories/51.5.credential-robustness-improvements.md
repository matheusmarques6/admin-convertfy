# Story 51.5 — Melhorias de Robustez do Sistema de Credenciais

## Story

**Como** engenheiro de plataforma,
**Quero** que o sistema de credenciais tenha tratamento de erros consistente, validacao robusta e documentacao de key rotation,
**Para que** falhas sejam diagnosticaveis e o sistema esteja preparado para operacoes futuras.

## Contexto

### Problemas identificados pelo QA

1. **Decryption error handling inconsistente**: `decryptStoreCredentials()` em `crypto.ts` silently swallows decryption errors (log + continua com ciphertext). Isso causa erros cripticos downstream quando a API Klaviyo/Shopify recebe `enc:v1:...` como token.

2. **Sem validacao de tamanho**: `validateCredentialField()` verifica ASCII printable mas nao limita tamanho. Um usuario pode colar 1MB de texto.

3. **Sem mecanismo de key rotation**: `enc:v1:` prefix sugere versionamento, mas nao ha `v2` nem procedimento documentado.

## Acceptance Criteria

### 51.5.1 — Decryption error handling consistente

> **QA C10:** `_decryption_errors` NAO deve ser adicionado ao return type de `decryptStoreCredentials()`. Isso polui o contrato de tipos — se o resultado for passado para `.update()`, a coluna desconhecida causa erro. Usar logging interno no service.

- [ ] Em `decryptStoreCredentials()` (`crypto.ts`), quando decryption falha para um campo:
  - Logar `console.error` com o nome do campo (NAO o valor)
  - Setar o campo como `null` (NAO manter o ciphertext)
  - **NAO adicionar campos extras ao return type** — manter a mesma signature `T`
- [ ] Em `getStoreCredentials()` (`credentials.service.ts`), apos decriptar:
  - Verificar quais campos de `ENCRYPTED_FIELDS` sao `null` quando o raw value era non-null (indica falha de decryption)
  - Logar warning com store ID e campos afetados: `console.warn(\`[Credentials] Decryption failed for store ${storeId}: ${fields.join(", ")}\`)`
  - Continuar normalmente (nao lanca erro — permite que o sistema funcione para as outras integracoes)
- [ ] **Comportamento resultante:** campo corrompido retorna `null` → `deriveStatus()` retorna `not_configured` → UI mostra "credencial nao configurada" (acao clara para o usuario)

**Arquivos:** `src/lib/crypto.ts`, `src/lib/services/credentials.service.ts`

### 51.5.2 — Validacao de tamanho em `validateCredentialField()`

- [ ] Adicionar limite de tamanho maximo: 2048 caracteres para campos simples, 16384 para JSON blobs (`google_ads_credentials`, `google_calendar_credentials`)
- [ ] Adicionar limite minimo: 1 caractere apos trim (rejeitar strings vazias/whitespace-only)
- [ ] Retornar mensagem de erro clara: `"Credential field '${name}' exceeds maximum length of ${max} characters"`

**Arquivo:** `src/lib/services/credentials.service.ts`

### 51.5.3 — Documentar key rotation

- [ ] Criar `docs/guides/credential-key-rotation.md` com:
  - Quando fazer rotation (key comprometida, compliance, rotina)
  - Procedimento step-by-step:
    1. Gerar novo ENCRYPTION_KEY
    2. Setar como ENCRYPTION_KEY_NEW no env
    3. Rodar `/api/admin/encrypt-credentials` para re-encriptar com novo key
    4. Substituir ENCRYPTION_KEY pelo novo
    5. Remover ENCRYPTION_KEY_NEW
  - Rollback procedure
  - Verificacao pos-rotation

**Arquivo:** `docs/guides/credential-key-rotation.md`

### 51.5.4 — Validacao

- [ ] `npm run typecheck` passa sem erros
- [ ] `npm run lint` passa sem erros
- [ ] Testar: inserir `enc:v1:GARBAGE` em um campo no banco → `getStoreCredentials()` retorna `null` para aquele campo e loga warning (nao lanca erro)
- [ ] Testar: enviar string de 5000 chars como API key → deve rejeitar com mensagem clara

## Riscos

| Risco | Mitigacao |
|-------|----------|
| Setar campo como `null` quando decryption falha pode quebrar codigo que assume non-null | Auditar consumidores de `getStoreCredentials()` — maioria ja verifica `!!creds.field`. `deriveStatus()` retorna `not_configured` para null (comportamento correto). Documentar esta mudanca de behavior |
| Key rotation procedure manual e propenso a erro | Documentar claramente com checklist e rollback. Considerar automacao futura |
