# Story 22.1 — Fix Campaign Revenue = 0 + Period Alignment Bug

## Status: In Review

## Contexto

Dois bugs interligados foram identificados na pipeline de sync Klaviyo que afetam o portal do cliente e o dashboard admin:

1. **Campaign revenue = 0 no summary**: A tabela `store_revenue_summary` tem `klaviyo_campaign_revenue = 0` para TODAS as stores, apesar de `klaviyo_campaign_metrics` ter dados reais de receita por campanha.

2. **Period dates desalinhadas**: O JOIN entre `store_revenue_summary` e `klaviyo_campaign_metrics` usa `period_start = X AND period_end = Y`, mas as datas nunca coincidem porque cada execucao do cron gera timestamps ligeiramente diferentes.

### Impacto

- **Portal Dashboard**: Cards de campanhas vazios (0 campanhas mostradas)
- **Portal Analytics**: Secao de campanhas vazia
- **Lucro Estimado**: Valor subestimado (falta campaign revenue no total)
- **Dashboard Admin**: `campaignRevenue = 0` no banner de resultado total
- **Afeta**: 100% das stores com Klaviyo

## Evidencia (SQL + Diagnostico)

### Bug 1 — campaign_revenue = 0 no summary

```sql
-- TODAS as stores com sync_status="ok" tem campaign_revenue=0
SELECT store_id, period_label, sync_status, klaviyo_campaign_revenue, klaviyo_flow_revenue
FROM store_revenue_summary WHERE sync_status = 'ok';
-- RESULTADO: klaviyo_campaign_revenue = 0.00 em TODOS os rows
-- Enquanto klaviyo_campaign_metrics tem R$80k+ em conversion_value
```

**Evidencia critica**: Flow_metrics foram atualizados na rodada das 17:30 (28 flows, R$142k). Mas ZERO campaign_metrics foram criados apos 10:00 daquele dia. O summary foi atualizado as 17:30 com `sync_status = "ok"` e `campaign_revenue = 0`.

### Bug 2 — period dates nunca alinham

```sql
-- 100% MISMATCH entre summary e campaign_metrics period dates
SELECT s.period_start, c.period_start,
  CASE WHEN s.period_start = c.period_start THEN 'MATCH' ELSE 'MISMATCH' END
FROM store_revenue_summary s
LEFT JOIN (SELECT DISTINCT store_id, period_start, period_end FROM klaviyo_campaign_metrics) c
  ON c.store_id = s.store_id
WHERE s.period_label = '30d';
-- RESULTADO: MISMATCH em quase todas as combinacoes
```

## Analise da Causa Raiz (Verificada por Diagnostico)

### Bug 1: Array vazio tratado como "dados disponiveis"

O Campaign Values Report da Klaviyo API retorna intermitentemente `{ data: { attributes: { results: [] } } }`. O codigo em `klaviyo-sync.service.ts:563`:

```typescript
if (campaignResponse?.data?.attributes?.results) {  // BUG: [] e truthy em JS!
  campaignDataAvailable = true
```

Um array vazio `[]` e **truthy** em JavaScript. Consequencias:
1. `campaignDataAvailable = true` (incorreto — nao ha dados reais)
2. O loop `for (const r of results)` nao executa (array vazio)
3. `campRows` permanece `[]`
4. `totalCampaignRevenue = campRows.reduce(...) = 0`
5. O persistence service salva `klaviyo_campaign_revenue = 0` com `sync_status = "ok"`
6. Valor anterior correto e **sobrescrito com 0**

**Por que funciona para flows mas nao campaigns?** O Flow Values Report e mais estavel e retorna `results` consistentemente. O Campaign Values Report tem rate limiting mais restrito (~1 req/s para reporting endpoints) e pode retornar `results: []` quando sobrecarregado.

**Arquivo**: `src/lib/services/klaviyo-sync.service.ts` linha 563

### Bug 2: Datas calculadas em momentos diferentes + acumulo de rows antigos

Cada execucao do cron calcula `period_start`/`period_end` baseado no `now()` via `parseDateRangeInTimezone()`. O cron roda periodicamente:
- Rodada 05:57 UTC: `period_start = 2026-02-03` → salva campaign_metrics com essas datas
- Rodada 17:30 UTC: `period_start = 2026-02-03` → summary com essas datas, mas campaign_metrics nao foi salvo (campRows vazio)
- Rodada anterior: `period_start = 2026-02-01` → campaign_metrics com datas diferentes

O UPSERT key e `(store_id, campaign_id, period_start, period_end)`, entao rows antigos com period_start diferente **nunca sao deletados** e acumulam. O JOIN exato no portal/performance falha porque busca campaign_metrics com as datas do summary mais recente, mas os dados disponiveis sao de rodadas anteriores.

**Arquivo**: `src/app/api/clients/[id]/performance/route.ts` linhas 62-64
**Arquivo**: `src/app/api/portal/dashboard/route.ts` linhas 181-186

## Proposta Tecnica

### Fix 1: campaignDataAvailable (sync service)

```typescript
// ANTES (bugado):
if (campaignResponse?.data?.attributes?.results) {  // [] e truthy!
  campaignDataAvailable = true

if (campaignResponse?.data?.attributes?.results?.length) {
  campaignDataAvailable = true
```

### Fix 2: Preservar revenue existente (persistence)

```typescript
// Em upsertSyncResults, quando campaignDataAvailable = false:
// Ler o valor existente do banco e preservar em vez de sobrescrever com 0
if (!data.campaignDataAvailable) {
  const { data: existing } = await supabase
    .from("store_revenue_summary")
    .select("klaviyo_campaign_revenue")
    .eq("store_id", store.id).eq("period_label", period).single()
  if (existing && Number(existing.klaviyo_campaign_revenue) > 0) {
    summaryPayload.klaviyo_campaign_revenue = existing.klaviyo_campaign_revenue
  }
}
```

### Fix 3: Period alignment (portal/performance)

```typescript
// ANTES:
.eq("period_start", summary.period_start)
.eq("period_end", summary.period_end)

// DEPOIS (com period_label adicionado via migration):
.eq("period_label", period)
.order("fetched_at", { ascending: false })
```

### Fix 4: Cleanup rows antigos (persistence)

```typescript
// Antes do upsert de campaign_metrics:
await supabase
  .from("klaviyo_campaign_metrics")
  .delete()
  .eq("store_id", store.id)
  .neq("period_start", data.startDateStr)  // Delete rows com datas diferentes
```

### Fix 1 -- `.length` guard (klaviyo-sync.service.ts) -- PASS

**Lines 484, 563:** Changed `if (flowResponse?.data?.attributes?.results)` to `if (flowResponse?.data?.attributes?.results?.length)`.

- Correctness: Using `.length` on an array returns `0` for `[]`, which is falsy. This correctly prevents `dataAvailable = true` when API returns empty results. Applied symmetrically to both flow and campaign checks.
- Edge cases verified: `null` response handled (`.length` on `undefined` returns `undefined` which is falsy -- safe). Non-empty arrays (`length > 0`) remain truthy -- correct.
- Risk: None. This is a minimal, surgical fix.

**Verdict: PASS**

---

### Fix 2 -- Preserve revenue existente (sync-persistence.service.ts) -- PASS

**Lines 91-125:** The partial-data logic already existed and correctly:
1. Only sets `klaviyo_campaign_revenue` when `campaignDataAvailable = true` (line 94-96)
2. When partial, reads existing DB value and uses it for total calculation (lines 107-120)
3. Sets `sync_status = "partial"` with descriptive `sync_error`

- Correctness: With Fix 1 now correctly setting `campaignDataAvailable = false` for empty results, this existing logic will be properly triggered. The campaign_revenue field is omitted from the upsert payload (not set to 0), so the DB value is preserved.
- Edge case: If no prior DB row exists, `existing` is null, and `campRev` falls back to `0` -- correct for first sync.
- Risk: None. No new code was added for this fix.

**Verdict: PASS**

### Fix 3 -- period_label JOIN (portal/dashboard + performance routes) -- PASS

**Migration `add_period_label_to_metrics_tables`:** Confirmed applied. Both tables have `period_label TEXT NULL` column with composite indexes `(store_id, period_label)`.

**Portal dashboard (route.ts):** All queries now use `.eq("period_label", period)` instead of `.eq("period_start", ...)`. Applied consistently in:

**Verdict: PASS**

### Fix 4 -- Cleanup rows orfaos (sync-persistence.service.ts) -- CONCERNS

**Lines 35-50, 52-68:** DELETE by `(store_id, period_label)` before upsert.

- Correctness: The DELETE + upsert pattern works correctly: it removes ALL rows for that store+period, then inserts fresh ones. This prevents orphan accumulation (confirmed: some stores had up to 145 flow_metrics rows and 11 distinct `period_start` values for a single `store_id + period_label`).
- DB evidence confirms the orphan problem is real and will be cleaned on next cron run.

**CONCERN 1 (RESOLVED): Unit tests fixed.**
Re-review 2026-03-05: `createMockSupabase()` now implements `deleteFn -> deleteEqFn` chain with `deleteEqFn.mockReturnValue({ eq: deleteEqFn })` for recursive `.eq()` chaining. All 27 tests pass (`npx vitest run`). TypeScript typecheck passes (`npx tsc --noEmit`). Mock correctly returns from `from()` as `{ upsert: upsertFn, delete: deleteFn }` for non-`client_stores` tables.

**CONCERN 2 (Non-blocking, accepted): `savePerfDataToCache` does NOT have the cleanup logic.**
The `upsertSyncResults` function (cron path) correctly does DELETE before upsert. But `savePerfDataToCache` (live path, lines 189-213) still uses plain `upsert` with `onConflict: "store_id,campaign_id,period_start,period_end"`. Since live fetches also generate different `period_start` values, the live path can still accumulate orphan rows. This is lower risk because the cron path runs more frequently and will clean up, but it is an inconsistency.

**CONCERN 3 (Non-blocking): No NOT NULL constraint on period_label.**
The column is `TEXT NULL`. A `NOT NULL DEFAULT` or at least a `NOT NULL` constraint would prevent accidental insertions without `period_label`, which would make rows invisible to all queries. Low risk since all code paths set it, but a defensive measure.

**Verdict: PASS (blocking issue resolved)**
