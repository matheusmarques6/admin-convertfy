## Contexto

Apos Story 8.16, o portal dashboard le revenue, campaigns e flows do cache. Porem, audience metrics (`totalLeads`, `engagedLeads`, `engagementRate`) ainda requerem chamadas LIVE a Klaviyo API:

- `totalLeads`: busca todas as lists da conta e pega o profile count da maior list (3-5 API calls: paginar `/lists/` + individual fetch para lists com count 0)
- `engagedLeads`: busca todos os segments e procura por "Engaged" no nome (3-5 API calls: paginar `/segments/` + individual fetch para segments com count 0)

Essa logica esta em `fetchAudienceMetrics()` no `klaviyo-performance.service.ts` (linhas 127-230). Sao as ULTIMAS chamadas live que o portal faz apos Story 8.16.

### Opcoes de Arquitetura

**Opcao A: Adicionar colunas a `store_revenue_summary`**
- Pros: simples, sem nova tabela, dados ja associados ao store+period
- Contras: audience metrics nao variam por periodo (list count e segment count sao snapshots atuais, nao historicos)

**Opcao B: Criar tabela `klaviyo_audience_cache`**
- Pros: semanticamente correto (audience nao depende de periodo), schema limpo
- Contras: nova tabela, nova migration

**Recomendacao:** Opcao A (adicionar colunas a `store_revenue_summary`). Audience metrics sao um snapshot "atual" que muda lentamente. Gravar junto com o revenue summary a cada sync e suficiente. O cron ja processa cada store — adicionar 2-3 API calls extras por store e aceitavel.

---

## Objetivo

Cachear audience metrics (totalLeads, engagedLeads) no cron sync para eliminar as ultimas chamadas live Klaviyo do portal dashboard, atingindo zero API calls no page load.

## Arquitetura Tecnica

### Audience Fetch no Cron

Extrair `fetchAudienceMetrics` do `klaviyo-performance.service.ts` para um modulo reutilizavel, ou copiar a logica simplificada no cron:

```typescript
// Em syncStore, ANTES do loop de periodos:
let audience = { totalLeads: 0, engagedLeads: 0, engagementRate: 0 }
try {
  audience = await fetchAudienceForStore(apiKey)
} catch (err) {
  log.warn(`[Cron] Failed to fetch audience for ${store.store_name}:`, err)
  // Continue with 0s — audience is optional
}

// Depois, no upsert de store_revenue_summary para cada periodo:
total_leads: audience.totalLeads,
engaged_leads: audience.engagedLeads,
engagement_rate: audience.engagementRate,
```

### Funcao `fetchAudienceForStore`

```typescript
async function fetchAudienceForStore(apiKey: string): Promise<{
  totalLeads: number
  engagedLeads: number
  engagementRate: number
}> {
  // 1. Fetch all lists, find largest by profile count
  const allLists: Array<{ id: string; profileCount: number }> = []
  let listPage: string | null = "/lists/"
  while (listPage) {
    const resp = await klaviyoRequest<{
      data: Array<{ id: string; attributes: { profile_count?: number } }>
      links?: { next?: string }
    }>(apiKey, listPage)
    if (!resp?.data) break
    for (const l of resp.data) {
      allLists.push({ id: l.id, profileCount: l.attributes.profile_count || 0 })
    }
    listPage = resp.links?.next ? resp.links.next.replace(KLAVIYO_API_URL, "") : null
    if (listPage) await sleep(500)
  }

  // Individual fetch for lists with 0 count (API quirk: collection endpoint may not return count)
  if (allLists.length > 0 && allLists.every(l => l.profileCount === 0)) {
    for (const list of allLists.slice(0, 5)) {
      const detail = await klaviyoRequest<{
        data: { attributes: { profile_count?: number } }
      }>(apiKey, `/lists/${list.id}/?additional-fields[list]=profile_count`)
      if (detail?.data?.attributes?.profile_count) {
        list.profileCount = detail.data.attributes.profile_count
      }
      await sleep(500)
    }
  }

  const largestList = allLists.reduce((max, l) => l.profileCount > max.profileCount ? l : max, { id: "", profileCount: 0 })
  const totalLeads = largestList.profileCount

  // 2. Fetch segments, find "Engaged" segment
  const allSegments: Array<{ id: string; name: string; profileCount: number }> = []
  let segPage: string | null = "/segments/"
  while (segPage) {
    const resp = await klaviyoRequest<{
      data: Array<{ id: string; attributes: { name: string; profile_count?: number } }>
      links?: { next?: string }
    }>(apiKey, segPage)
    if (!resp?.data) break
    for (const s of resp.data) {
      allSegments.push({ id: s.id, name: s.attributes.name, profileCount: s.attributes.profile_count || 0 })
    }
    segPage = resp.links?.next ? resp.links.next.replace(KLAVIYO_API_URL, "") : null
    if (segPage) await sleep(500)
  }

  // Find engaged segment
  const engagedSegment = allSegments.find(s =>
    s.name.toLowerCase().includes("engaged") && s.name.toLowerCase().includes("90")
  ) || allSegments.find(s => s.name.toLowerCase().includes("engaged"))

  // Individual fetch if needed
  if (engagedSegment && engagedSegment.profileCount === 0) {
    const detail = await klaviyoRequest<{
      data: { attributes: { profile_count?: number } }
    }>(apiKey, `/segments/${engagedSegment.id}/?additional-fields[segment]=profile_count`)
    if (detail?.data?.attributes?.profile_count) {
      engagedSegment.profileCount = detail.data.attributes.profile_count
    }
  }

  const engagedLeads = engagedSegment?.profileCount || 0
  const engagementRate = totalLeads > 0 ? (engagedLeads / totalLeads) * 100 : 0

  return { totalLeads, engagedLeads, engagementRate }
}
```

## Riscos e Mitigacoes

| Risco | Mitigacao |
|-------|-----------|
| Audience fetch adiciona tempo ao cron | ~2-3s por store; para 10 stores = ~25s extra (dentro do budget de 240s) |
| Lists/segments com 0 profile count (API quirk) | Individual fetch com `additional-fields` como fallback (ja implementado no performance service) |
| Segment "Engaged 90d" nao encontrado | Busca por nome com fallback; se nao achar, engaged = 0 (comportamento atual) |
| Migration falha se coluna ja existe | `ADD COLUMN IF NOT EXISTS` e seguro |
| audience metrics iguais para todos os periodos | Correto — audience e snapshot atual, nao historico por periodo |
