# Story 58.3 — Propagar falha parcial ao processador e UI

## Executor Assignment

executor: "@dev"
quality_gate: "@qa"
quality_gate_tools: ["typecheck", "lint", "unit-tests"]

## Story

**Como** operador do admin,
**Quero** que o relatorio indique claramente quando dados de flow ou campanha estao faltando,
**Para que** eu saiba que o relatorio esta incompleto e possa reprocessar.

## Contexto

### Problema

Atualmente, quando o flow-values-reports falha mas campaign-values-reports funciona, a cadeia de dados e:

```
report-summary.ts → success: true, flowReportAvailable: false
     ↓
process/route.ts → result.success === true → marca loja como "completed"
     ↓
report-jobs/[id]/page.tsx → mostra loja como "OK" com flow=R$0
```

O campo `flowReportAvailable` existe em `KlaviyoRevenueSummary` (report-summary.ts:46-47) mas:
- O processador de reports (`process/route.ts:135`) nunca o verifica
- A UI do relatorio (`report-jobs/[id]/page.tsx`) nunca o exibe
- Nao existe um status intermediario entre "completed" e "failed"

### Resultado

O operador ve "Receita Flows: R$0" e uma badge "OK" na loja, sem saber que o dado esta errado. Nao ha como distinguir "loja sem flows" de "API falhou".

## Acceptance Criteria

### 58.3.1 — Retornar flag `partial` quando um dos reports falhar

- [ ] Em `src/lib/integrations/klaviyo/report-summary.ts`:
  - Quando `campaignReport === null` XOR `flowReport === null` (um falhou, outro ok):
    - Retornar `success: true` (para que o caller ainda receba os dados parciais)
    - Adicionar campo `partial: true` ao `KlaviyoRevenueSummary`
    - Manter `flowReportAvailable` e `campaignReportAvailable` como ja existem
  - Quando ambos ok: `partial: false`
  - Quando ambos null: continua retornando `success: false`

### 58.3.2 — Processador detectar dados parciais

- [ ] Em `src/app/api/reports/process/route.ts`:
  - Quando `result.success && result.data`:
    - Verificar `result.data.partial === true`
    - Se partial: marcar store progress como `{ status: "partial", missing: ["flow"] | ["campaign"] | ["metric-aggregates"] | ["flow", "metric-aggregates"] }` (array de strings, pois multiplas fontes podem falhar simultaneamente)
    - NOTA: `"partial"` deve ser adicionado ao type union `ReportJobStoreProgress['status']` em `src/types/report.ts` (atualmente: `'pending' | 'processing' | 'completed' | 'failed'`)
    - Se nao partial: manter `{ status: "completed" }` como hoje
  - Ao determinar status final do job:
    - Se alguma loja tem status "partial": job status = `"partial"` (nao "completed")
    - Adicionar campo `stores_partial` ao resultado do job

### 58.3.3 — UI indicar dados parciais por loja

- [ ] Em `src/app/admin/report-jobs/[id]/page.tsx`:
  - Na tabela de breakdown por loja:
    - Se loja tem status "partial": mostrar badge amarela "Parcial" em vez de "OK"
    - Ao lado do valor R$0 de flow (ou campanha), mostrar icone de warning com tooltip: "Dado indisponivel — API nao respondeu"
  - No card de KPI "Receita Flows" no topo:
    - Se alguma loja tem flow partial: mostrar asterisco ou badge "Dados incompletos"

### 58.3.4 — Permitir reprocessamento de lojas parciais

- [ ] Na tabela de breakdown, lojas com status "partial" devem mostrar botao "Tentar novamente" (identico ao botao de lojas "failed")
- [ ] O botao ja existe para lojas failed — reutilizar o mesmo handler `handleRetryStore`

## Tarefas Tecnicas

- O status "partial" do JOB ja existe (para quando lojas falham). Agora ele tambem cobre lojas com dados parciais.

### Dependencias

- **Depende de 58.1**: Apos o fix de quota, falhas parciais serao muito mais raras. Mas esta story e necessaria como defesa em profundidade para qualquer falha transitoria (timeout, 500, etc).
- **Depende de 58.2**: Sem o fix de cache, dados parciais seriam cacheados mesmo com o flag. Com 58.2, dados parciais nao sao cacheados, e com 58.3, o usuario sabe que precisa reprocessar.
