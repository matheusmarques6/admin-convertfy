# Story 44.1 — Fix 10 Broken CI Tests in Cron Sync-Reports

## Story

**Como** desenvolvedor que depende do CI para validar PRs,
**Quero** que os 10 testes quebrados em `route.test.ts` do cron sync-reports sejam corrigidos,
**Para que** o pipeline de CI volte a passar e PRs possam ser mergeados com confianca.

## Contexto

### Problema

O CI pipeline esta falhando ha 11 runs consecutivos (#412 a #422). Todos os 10 testes em `src/app/api/cron/sync-reports/route.test.ts` falham porque os mocks nao correspondem ao comportamento real da rota.

### Causa raiz primaria: mock do `rpc` retorna valor errado

O mock do Supabase na **linha 43** do arquivo de teste retorna:
```typescript
rpc: () => ({ data: 0, error: null })
```

Porem a rota chama `supabase.rpc("acquire_sync_lock", ...)` e verifica (route.ts linhas 59-76):
```typescript
async function acquireSyncLock(supabase: SupabaseClient): Promise<boolean> {
  const { data, error } = await supabase.rpc("acquire_sync_lock", {
    p_lock_name: "sync_reports",
    p_stale_ms: STALE_LOCK_MS,
  })
  // ...
  if (data === true) {   // <-- 0 !== true, lock NUNCA e adquirido
    return true
  }
  log.warn("[Cron] Another sync is running, skipping")
  return false           // <-- sempre retorna false
}
```

Como `0 !== true`, `acquireSyncLock()` retorna `false`, a rota retorna `{ status: "skipped", reason: "another instance running" }` com HTTP 409 — **nunca chega ao processamento de lojas**. Por isso `body.stores` e `undefined` e `mockSyncKlaviyoForPeriod` nunca e chamado.

### Causa raiz secundaria: mock de `upsertAudiences` ausente

A rota importa `upsertAudiences` do `sync-persistence.service` (linha 23 do route.ts), mas o teste so mocka `upsertSyncResults` (linhas 89-91 do teste). `upsertAudiences` NAO esta mockado, causando potencial erro quando audience fetch tem sucesso.

### Causa raiz terciaria: testes com timers podem precisar ajuste

Testes para rate limit handling (AC 16.8.2) usam `vi.useFakeTimers()` e `vi.runAllTimersAsync()` porque a rota tem delays com `setTimeout` (linhas 334-336, 561, 591 do route.ts). Estes precisam do fix do `rpc` primeiro e depois verificacao.

## Objetivo

Corrigir os mocks em `route.test.ts` para que todos os 10 testes passem novamente, sem modificar nenhum arquivo de implementacao.

## Arquitetura Tecnica

### Task 1: Fix mock do `rpc` para tratar `acquire_sync_lock` corretamente

**Arquivo:** `src/app/api/cron/sync-reports/route.test.ts` — linha 43

```typescript
// ANTES (bug): retorna 0, que falha no check `data === true`
rpc: () => ({ data: 0, error: null }),

// DEPOIS (fix): retorna true para acquire_sync_lock, 0 para outros RPCs
rpc: (fnName: string) => {
  if (fnName === "acquire_sync_lock") return { data: true, error: null }
  return { data: 0, error: null }
},
```

### Task 2: Adicionar mock de `upsertAudiences`

**Arquivo:** `src/app/api/cron/sync-reports/route.test.ts` — linhas 89-91

```typescript
// ANTES (bug): upsertAudiences nao mockado
vi.mock("@/lib/services/sync-persistence.service", () => ({
  upsertSyncResults: vi.fn().mockResolvedValue(undefined),
}))

// DEPOIS (fix): ambas funcoes mockadas
vi.mock("@/lib/services/sync-persistence.service", () => ({
  upsertSyncResults: vi.fn().mockResolvedValue(undefined),
  upsertAudiences: vi.fn().mockResolvedValue(undefined),
}))
```

### Task 3: Fix `chainable()` para queries em `store_revenue_summary`

O helper `upsertSyncError` (route.ts linhas 94-151) faz:
```typescript
supabase.from("store_revenue_summary").select(...).eq(...).eq(...).single()
```

O mock `chainable()` tem `.single()` que sempre retorna `{ data: { is_running: false } }`. Para `store_revenue_summary`, deveria retornar `{ data: null }` (nenhuma row existente) para que o path de upsert funcione.

```typescript
// ANTES:
self.single = () => ({ data: { is_running: false }, error: null })

// DEPOIS: retornar dados contextuais por tabela
self.single = () => {
  if (table === "cron_locks") return { data: { is_running: false }, error: null }
  return { data: null, error: null }
}
```

## QA Review Concerns (Pre-Dev)

> Revisao feita por @qa em 2026-03-15. Gate: **PASS WITH CONCERNS**.

### C1 (MEDIUM): `getStoreCredentials` chamado 2x — dev deve estar ciente

`getStoreCredentials` e chamado uma vez durante o API key grouping (route.ts linha 493) e novamente dentro de `syncStore` (route.ts linha 165). O mock resolve ambas as chamadas corretamente, mas o dev deve estar ciente dessa duplicacao ao tracar o fluxo do codigo. Nao requer fix, apenas awareness.

### C2 (LOW): `.update().eq().eq()` chain nao suportado no mock

O mock de `update` retorna `{ eq: () => { push; return ok } }` — um unico `.eq()` retorna `ok`, que nao tem metodo `.eq()`. A rota (route.ts linhas 122-124) encadeia `.update({}).eq("store_id", ...).eq("period_label", ...)` dentro do branch "preserve valid revenue" do `upsertSyncError`. Esse branch NAO e exercitado nos testes atuais (porque `existing.sync_status` nunca e `"ok"` ou `"partial"`), entao nao causa falha agora. **Backlog**: se testes futuros exercitarem esse path, o mock de `update` precisara retornar um objeto chainable.

### C3 (LOW): Sem cobertura de teste para `KlaviyoInvalidKeyError`

Route.ts linhas 220-242 e 369-387 tratam `KlaviyoInvalidKeyError`, mas nenhum teste cobre esse path. Fora do escopo da story 44.1 (que so corrige testes existentes). **Backlog**: criar testes para `KlaviyoInvalidKeyError` em story futura.

### C4 (LOW): Timer tests — sensibilidade com `Promise.allSettled`

Se `Promise.allSettled` interagir com fake timers de forma inesperada, chamadas adicionais de `vi.advanceTimersByTimeAsync()` podem ser necessarias. A abordagem "verificar e ajustar se necessario" da Task 5 e adequada.
