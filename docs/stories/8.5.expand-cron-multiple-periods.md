---

## Contexto

O cron `sync-reports/route.ts` atualmente sincroniza apenas o periodo de 30d (hardcoded na linha 74: `parseDateRange("30d")`). Para que a tabela `store_revenue_summary` (Fase 3) tenha dados para todos os periodos usados no dashboard (7d, 15d, 30d, 90d), o cron precisa ser expandido.

Alem disso, o cron processa lojas sequencialmente (`for...of`), o que eh ineficiente. Com 30+ lojas e 4 periodos, o tempo total pode exceder o `maxDuration=300` do Vercel Functions.

O cron roda a cada 2 horas (`0 */2 * * *`), mas com dados pre-computados, a frequencia ideal eh 30 minutos para manter staleness < 30min.

---

## Objetivo

1. Expandir o cron para sincronizar 4 periodos: 7d, 15d, 30d, 90d
2. Priorizar 30d (mais usado) antes dos outros periodos
3. Processar lojas em batches com `Promise.allSettled`
4. Adicionar lock de idempotencia para evitar execucoes paralelas
5. Aumentar frequencia do cron de 2h para 30min

## Arquitetura Tecnica

### Processamento por Periodo com Priorizacao

```typescript
const PERIODS = ['30d', '7d', '15d', '90d'] as const
const BATCH_SIZE = 10
const MAX_DURATION_MS = 240_000 // 80% de 300s

export async function GET(request: NextRequest) {
  // ... auth check ...

  const supabase = createAdminClient()
  const startTime = Date.now()

  // Lock de idempotencia
  const canRun = await acquireSyncLock(supabase)
  if (!canRun) {
    return NextResponse.json({ status: "skipped", reason: "another instance running" }, { status: 409 })
  }

  try {
    const stores = await getStoresWithKlaviyo(supabase)
    const results: SyncResult[] = []

    for (const period of PERIODS) {
      // Check timeout antes de cada periodo
      if (Date.now() - startTime > MAX_DURATION_MS) {
        log.warn(`[Cron] Timeout approaching, stopping at period ${period}`)
        break
      }

      // Processar lojas em batches
      for (let i = 0; i < stores.length; i += BATCH_SIZE) {
        if (Date.now() - startTime > MAX_DURATION_MS) break

        const batch = stores.slice(i, i + BATCH_SIZE)
        const batchResults = await Promise.allSettled(
          batch.map(store => syncStoreForPeriod(store, period, supabase))
        )

        for (let j = 0; j < batchResults.length; j++) {
          const result = batchResults[j]
          results.push({
            storeId: batch[j].id,
            storeName: batch[j].store_name,
            period,
            status: result.status === 'fulfilled' ? result.value.status : 'error',
            error: result.status === 'rejected' ? result.reason?.message : undefined,
          })
        }
      }
    }

    const elapsed = Date.now() - startTime
    return NextResponse.json({
      status: results.some(r => r.status === 'error') ? 'partial' : 'ok',
      elapsed: `${elapsed}ms`,
      results,
    })
  } finally {
    await releaseSyncLock(supabase)
  }
}
```

### Lock de Idempotencia

```typescript
async function acquireSyncLock(supabase: SupabaseClient): Promise<boolean> {
  // Verificar lock existente
  const { data: config } = await supabase
    .from('klaviyo_sync_config')
    .select('is_running, started_at')
    .eq('config_key', 'sync_revenue')
    .single()

  if (config?.is_running) {
    const startedAt = new Date(config.started_at).getTime()
    const staleLockMs = 10 * 60 * 1000 // 10 minutos
    if (Date.now() - startedAt < staleLockMs) {
      log.warn('[Cron] Another sync is running, skipping')
      return false
    }
    log.warn('[Cron] Stale lock detected, proceeding')
  }

  // Adquirir lock
  await supabase
    .from('klaviyo_sync_config')
    .upsert({
      config_key: 'sync_revenue',
      is_running: true,
      started_at: new Date().toISOString(),
    }, { onConflict: 'config_key' })

  return true
}

async function releaseSyncLock(supabase: SupabaseClient): Promise<void> {
  await supabase
    .from('klaviyo_sync_config')
    .update({ is_running: false })
    .eq('config_key', 'sync_revenue')
}
```

**Nota:** Se a tabela `klaviyo_sync_config` nao existir, criar uma migration simples. Alternativa: usar a propria `store_revenue_summary` com um registro especial de controle.

## Riscos e Mitigacoes

| Risco | Mitigacao |
|-------|-----------|
| Cron excede maxDuration=300 com muitas lojas | Timeout check a 80% + processamento parcial com status |
| Rate limit da Klaviyo com batches paralelos | Rate limiter existente por API key eh respeitado; cada loja tem sua propria key |
| Lock stale bloqueia execucoes futuras | Auto-release apos 10 minutos de inatividade |
| 30min de frequencia aumenta custo Vercel | Execucao rapida quando dados estao atualizados (skip lojas ja sincronizadas) |
