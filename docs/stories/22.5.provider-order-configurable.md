# Story 22.5 -- Refatorar Cascade para Provider Registry

## Status
Done

## Story

**Como** desenvolvedor,
**Quero** que o cascade de providers use um registry dinamico em vez de if-chain hardcoded,
**Para que** seja facil adicionar novos providers e, futuramente, permitir configuracao por loja.

---

## Dependencia

> **Pre-requisito:** 22.4 (Correios integrado) — para que Correios esteja no registry.
> **Pre-requisito:** 22.1 e 22.2 (cascade + freshness + indexes).

## Contexto

Hoje `trackWithBestProvider()` usa uma cadeia de `if/else` para cada provider. Funciona, mas adicionar um novo provider exige mexer na logica do cascade. Com um registry, adicionar provider e apenas uma entrada no objeto.

**Escopo reduzido (decisao arquitetural):** A revisao do Arquiteto concluiu que migration SQL, API endpoint e UI de drag-and-drop sao over-engineering para o momento atual. O cascade com `canRun` + deteccao automatica (Correios para BR, PostNL para EU) ja resolve ~95% dos casos. Esta story implementa **apenas o registry** como refatoracao interna. Migration/API/UI ficam para demanda futura.

### O que esta story FAZ
- Refatora `trackWithBestProvider()` de if-chain para loop sobre registry
- Cria `PROVIDER_REGISTRY` com `canRun`/`execute` por provider
- Mantem `DEFAULT_PROVIDER_ORDER` hardcoded
- 17track SEMPRE forcado como ultimo

### O que esta story NAO FAZ (adiado)
- ~~Migration SQL com `provider_order text[]`~~
- ~~API endpoint para salvar provider_order~~
- ~~UI com drag-and-drop no portal~~
- ~~CHECK constraint no DB~~

- [x] Criar registry em `carriers.ts`:
  ```typescript
  const PROVIDER_REGISTRY: Record<string, {
    label: string
    canRun: (keys: CarrierKeys, carrier: CarrierInfo) => boolean
    execute: (tn: string, keys: CarrierKeys, carrier: CarrierInfo) => Promise<TrackingResult | null>
  }> = {
    correios:        { label: "Correios", canRun: (_, c) => c.code === "correios", execute: (tn) => trackViaCorreios(tn) },
    postnl:          { label: "PostNL", canRun: (k, c) => c.provider === "postnl" && !!k.postnl, execute: (tn, k) => trackViaPostNL(tn, k.postnl!) },

  ```

### 22.5.2 -- Refatorar trackWithBestProvider() para loop

- [x] Definir `DEFAULT_PROVIDER_ORDER`:
  ```typescript
  const DEFAULT_PROVIDER_ORDER = ["correios", "postnl", "cainiao", "trackingmore", "seventeen_track"]
  ```
- [x] Implementar `resolveProviderOrder()`:
  ```typescript
  function resolveProviderOrder(configOrder: string[] | null): string[] {
    const order = configOrder ?? DEFAULT_PROVIDER_ORDER
    const without17 = order.filter(p => p !== "seventeen_track")
    return [...without17, "seventeen_track"]
  }
  ```
- [x] Refatorar `trackWithBestProvider()` para usar loop:
  ```typescript
  export async function trackWithBestProvider(
    trackingNumber: string,
    keys: CarrierKeys,
    trackVia17track: (...) => Promise<any[]>,
    providerOrder?: string[]
  ): Promise<TrackingResult | null> {
    const carrier = detectCarrierProvider(trackingNumber)
    const order = resolveProviderOrder(providerOrder ?? null)

    for (const providerName of order) {
      const provider = PROVIDER_REGISTRY[providerName]
      if (!provider) { log.warn("Unknown provider", { provider: providerName }); continue }
      if (!provider.canRun(keys, carrier)) continue

      const t0 = Date.now()
      log.info(`Trying ${provider.label}`, { trackingNumber })
      const result = await provider.execute(trackingNumber, keys, carrier)
      const found = !!(result && result.events.length > 0)
      log.info("Provider attempt", { provider: providerName, trackingNumber, durationMs: Date.now() - t0, found })

      if (found) {
        if (providerName !== "seventeen_track") {
          log.debug("17track avoided", { trackingNumber, resolvedBy: providerName })
        }
        return result
      }
    }

    return null
  }
  ```
- [x] 17track SEMPRE forcado como ultimo via `resolveProviderOrder()`
- [x] Resultado identico ao if-chain atual para `providerOrder = null`

## Dev Notes

### Nota: Paridade com if-chain

A refatoracao DEVE produzir comportamento identico ao if-chain atual. A unica diferenca e estrutural (loop vs if). Se qualquer cenario divergir, e um bug de regressao.

### Nota: PostNL tem condicao especial

PostNL so executa se `carrier.provider === "postnl"` (detectado por regex). Mesmo numa ordem customizada futura, PostNL so tenta para tracking numbers PostNL. Isso fica no `canRun`, transparente.

### Nota: trackVia17track como parametro

`trackWithBestProvider()` recebe `trackVia17track` como parametro (nao importa diretamente). O registry precisa de uma referencia a essa funcao. Opcao: closure ou parametro passado ao registry. A abordagem mais limpa e armazenar a referencia no escopo do `trackWithBestProvider`.

### Nota: Futuro (quando houver demanda)

Quando surgir necessidade real de configuracao por loja:
1. Migration: `ALTER TABLE tracking_stores ADD COLUMN provider_order text[] DEFAULT NULL`
2. `resolveCarrierKeys()` busca `provider_order` e passa para `trackWithBestProvider()`
3. API endpoint PATCH para salvar
4. UI no portal

O registry ja esta pronto para isso — basta passar o `providerOrder` do DB.
