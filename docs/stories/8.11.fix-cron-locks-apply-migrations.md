## Contexto

O Epic 8 (Performance: Cache de Revenue) foi merged na main mas as 3 migrations NAO foram aplicadas no Supabase de producao. Isso causou uma queda total do dashboard: todos os componentes de revenue mostram zero/vazio porque a tabela `store_revenue_summary` (fonte unica de dados para o novo endpoint) nao existe.

Alem disso, a migration `20260228_cron_locks.sql` tem um bug de seguranca: a RLS policy `service_cron_locks_all` usa `FOR ALL USING (true)` sem restringir a `TO service_role`, permitindo que qualquer usuario autenticado leia/escreva na tabela de locks.

### Bug na Migration Atual

```sql
-- ANTES (BUGADO) - 20260228_cron_locks.sql linha 25-26
CREATE POLICY "service_cron_locks_all" ON cron_locks
  FOR ALL USING (true) WITH CHECK (true);

-- DEPOIS (CORRETO) - deve ser restrito a service_role
CREATE POLICY "service_cron_locks_all" ON cron_locks
  FOR ALL TO service_role
  USING (true) WITH CHECK (true);
```

## Arquitetura Tecnica

### Fix do cron_locks RLS

O problema esta na migration `supabase/migrations/20260228_cron_locks.sql`. A policy precisa do `TO service_role` para restringir o acesso:

```sql
-- ANTES (linha 25-26):
CREATE POLICY "service_cron_locks_all" ON cron_locks
  FOR ALL USING (true) WITH CHECK (true);

-- DEPOIS:
CREATE POLICY "service_cron_locks_all" ON cron_locks
  FOR ALL TO service_role
  USING (true) WITH CHECK (true);
```

### Ordem de Aplicacao das Migrations

A ordem importa porque `dashboard_cache_org_id` referencia `organizations(id)` e assume que a tabela `dashboard_cache` ja existe:

1. **cron_locks** - Tabela independente, sem FK externas
2. **store_revenue_summary** - Depende de `client_stores(id)` e `organizations(id)` (ambas ja existem)
3. **dashboard_cache_org_id** - ALTER TABLE na `dashboard_cache` existente

### Aplicacao no Supabase

Usar o SQL Editor do Supabase Dashboard ou CLI:
```bash
# Via CLI (se configurado)
supabase db push

# Ou via SQL Editor: copiar e executar cada migration na ordem
```
