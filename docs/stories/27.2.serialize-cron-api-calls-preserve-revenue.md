## Story

**Como** sistema que sincroniza dados do Klaviyo via cron,
**Quero** que as chamadas a API de reporting sejam serializadas (nao paralelas),
**Para que** campaign reports nao sejam rate-limited e retornem null, causando $0 em campaign revenue.

---

## Contexto

O cron dispara 3 chamadas em paralelo via `Promise.all`:
1. `POST /flow-values-reports/`
2. `POST /campaign-values-reports/`
3. `POST /metric-aggregates/`

Com burst rate limit do Klaviyo (~1 req/s), a 2a ou 3a chamada frequentemente e rate-limited e retorna `null` (via `klaviyoRequest()` que retorna `null` em erros nao-permission/nao-rate-limit).

Quando `campaignResponse` e null:
- `campaignDataAvailable = false`
- `campRows = []`

**Nota importante (QA review):** A logica de preservacao de revenue quando `campaignDataAvailable === false` **ja existe** em `sync-persistence.service.ts` (linhas 91-125). O `upsertSyncResults` ja le o valor anterior e preserva `klaviyo_campaign_revenue`. O DELETE de `klaviyo_campaign_metrics` tambem so roda quando `campRows.length > 0` (linha 53). Portanto, o fix real e **impedir que o report retorne null** — serializando as chamadas.

Evidencia do banco: todas as 15 rows "ok" em `store_revenue_summary` tem `klaviyo_campaign_revenue = 0.00`, enquanto `klaviyo_flow_revenue` esta populado corretamente. Isso sugere que o campaign report falha TODA vez (rate limit consistente por causa do `Promise.all`).

### Arquivos afetados

- `src/lib/services/klaviyo-sync.service.ts` (funcao `syncKlaviyoForPeriod`, linha ~421: `Promise.all`)

## Acceptance Criteria

### 27.2.1 — Serializar chamadas API no sync service

- [x] Em `syncKlaviyoForPeriod()`, trocar `Promise.all([flowReport, campaignReport, metricAgg])` por chamadas **sequenciais**
- [x] Ordem recomendada: (1) flow-values-reports, (2) sleep 1500ms, (3) campaign-values-reports, (4) sleep 1500ms, (5) metric-aggregates
- [x] Definir constante `REPORT_API_DELAY_MS = 1500` (a constante `MIN_REQUEST_INTERVAL` existente e para REST API geral e provavelmente 500ms — insuficiente para reporting API que tem rate limit mais restritivo ~1 req/s)
- [x] Manter o timeout individual por chamada (15s)

### 27.2.2 — Log de observabilidade

- [x] Apos cada chamada API serializada, logar: `"[CronSync] {report_type} completed for store {id} in {ms}ms"`
- [x] Se uma chamada falha (retorna null), logar: `"[CronSync] {report_type} FAILED for store {id}: null response (likely rate-limited)"` com level `warn`
- [x] No final do sync de cada store, logar quais reports tiveram sucesso e quais falharam

## Notas Tecnicas

- `klaviyoRequest()` retorna `null` em erros que nao sao `KlaviyoPermissionError` ou `KlaviyoRateLimitError`. Isso inclui timeouts (AbortError), erros de rede, e respostas 5xx. O null masking e intencional (story 16.4), mas o consumidor precisa tratar null como "falha" e nao como "vazio".
- O rate limit da Klaviyo Reporting API e mais restritivo (~1 req/s burst) que a API REST geral (~2 req/s). Sleep de 1500ms e conservador e seguro.
- A funcao `fetchFlowNames()` e `fetchCampaignNames()` ja rodam ANTES do `syncKlaviyoForPeriod` e tambem consomem rate limit. O sleep adicional e necessario.
