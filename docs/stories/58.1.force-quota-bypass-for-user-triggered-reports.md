# Story 58.1 — Force quota bypass para reports user-triggered

## Executor Assignment

executor: "@dev"
quality_gate: "@qa"
quality_gate_tools: ["typecheck", "lint", "unit-tests"]

## Story

**Como** operador do admin,
**Quero** que relatorios de periodo personalizado sempre busquem dados reais da API Klaviyo,
**Para que** os dados de flow e campanha estejam corretos no relatorio gerado.

## Contexto

### Problema

O rate limiter diario (`rate-limiter.ts:339-348`) tem um soft halt em 220 chamadas XS/dia por API key. Quando o processador de reports gera relatorios para N lojas sequencialmente (3 XS calls/loja: campaign + flow + metric-aggregates), a quota pode esgotar no meio do processamento.

O bug critico: campaign e flow sao enqueued sequencialmente no report-summary.ts. Se a quota esta em 219:

```
1. Campaign enqueue → count=219, check PASSA → increment → count=220 → REQUEST OK
2. Flow enqueue     → count=220 >= 220 → EXHAUSTED → retorna null SILENCIOSAMENTE
```

A campanha ganha a ultima vaga, o flow e descartado com `null`. Em `report-summary.ts:273-277`:
```typescript
let flowRevenue = 0
const flowResults = flowReport?.data?.attributes?.results || []
for (const r of flowResults) {
  flowRevenue += Number(r.statistics?.conversion_value) || 0
}
// flowReport era null → flowResults = [] → flowRevenue = 0
```

A funcao retorna `success: true` com `flowRevenue: 0`, e o relatorio mostra "R$0" para flows.

### Por que o cron nao sofre isso

O cron usa freshness skip (consome 6-12 XS calls/ciclo) e nunca chega perto do threshold de 220. Reports customizados para 15+ lojas consomem 45+ XS calls de uma vez.

### Impacto

- Flows representam 40-70% da receita Klaviyo tipica
- Relatorios subestimam drasticamente a contribuicao do email marketing
- Dados errados sao cacheados (ver story 58.2)
- Operadores tomam decisoes com dados falsos

## Acceptance Criteria

### 58.1.1 — Passar `force: true` em chamadas do report-summary para custom periods

- [ ] Em `src/lib/integrations/klaviyo/report-summary.ts`, na funcao `getKlaviyoRevenueForStore`:
  - Quando `isCustomPeriod(period)` for true, passar `force: true` nas options de `klaviyoRequest` para AMBAS as chamadas (campaign-values-reports e flow-values-reports)
  - Tambem passar `force: true` na chamada indireta via `fetchStoreRevenueFromMetricAggregates` (que internamente chama `klaviyoRequest` para `/metric-aggregates/`)
- [ ] Em `src/lib/services/klaviyo-sync.service.ts`, na funcao `fetchStoreRevenueFromMetricAggregates`:
  - Adicionar parametro opcional `force?: boolean` e propagar para `klaviyoRequest`
- [ ] Reports de periodos padrao (7d, 30d, etc.) e 1d devem continuar respeitando a quota (NAO passar force)

### 58.1.2 — Reserva de quota em batch (defesa em profundidade)

- [ ] Em `src/lib/integrations/klaviyo/rate-limiter.ts`, criar funcao:
  ```typescript
  export function reserveReportQuota(apiKey: string, count: number): boolean
  ```
  - Verifica se ha `count` vagas disponiveis antes do threshold
  - Incrementa atomicamente (check + increment na mesma operacao)
  - Retorna `false` se nao houver quota suficiente
- [ ] Em `report-summary.ts`, ANTES das chamadas de API:
  - Quando NÃO for custom period (ou seja, para periodos padrao que nao usam `force`):
    - Chamar `reserveReportQuota(apiKey, 3)` (campaign + flow + metric-agg)
    - Se retornar false, pular para cache fallback imediatamente
  - Quando FOR custom period, o `force: true` ja bypassa a quota

### 58.1.3 — Logging melhorado

- [ ] Quando `force: true` for usado, logar: `[KlaviyoReportSummary] Custom period: bypassing daily quota for store ${storeId}`
- [ ] Quando batch reservation falhar, logar: `[KlaviyoReportSummary] Quota insufficient for store ${storeId} (need 3, available X)`

### Riscos

- `force: true` em custom periods pode gerar 429 do Klaviyo se muitas lojas forem processadas rapidamente. O rate limiter de tier (2s entre XS calls) ainda esta ativo — `force` so bypassa o DAILY QUOTA soft halt, nao o spacing entre requests.
- A reserva em batch para periodos padrao e defensiva — nao muda o comportamento para custom periods.

### Testes esperados

1. `reserveReportQuota(key, 3)` retorna true quando count < threshold - 3
2. `reserveReportQuota(key, 3)` retorna false quando count >= threshold - 3
3. `reserveReportQuota` incrementa atomicamente (nao ha gap entre check e increment)
4. Custom period calls passam `force: true` e nao sao bloqueados pela quota
