# Story 51.3 — Consolidar Leituras no `getStoreCredentials()`

## Story

**Como** engenheiro de backend,
**Quero** que toda leitura de credenciais que precisa do valor decriptado passe pelo `getStoreCredentials()`,
**Para que** mudancas no modelo de encryption (key rotation, novo formato) sejam aplicadas automaticamente.

## Contexto

### Problema

4 endpoints decriptam credenciais diretamente chamando `decryptStoreCredentials()` ou `decrypt()` ao inves de usar `getStoreCredentials()`. Outros 12 endpoints leem campos de credenciais para boolean flags (`!!field`) — esses sao aceitaveis e NAO precisam migrar.

### Endpoints que decriptam diretamente

| # | Arquivo | Linha | Metodo atual | Problema |
|---|---------|-------|-------------|---------|
| 1 | `src/app/api/portal/dashboard/route.ts` | L530 | `decryptStoreCredentials(s)` em batch | Decripta tudo para extrair boolean flags — wasteful e risco de leak |
| 2 | `src/app/api/clients/[id]/performance/route.ts` | L206 | `decryptStoreCredentials(rawStore)` | Idem |
| 3 | `src/app/api/portal/tracking/route.ts` | L60-61 | `decrypt(store.shopify_access_token)` | Decrypt direto para copiar para tracking_stores |
| 4 | `src/app/api/portal/tracking/config/route.ts` | L58-59 | `decrypt(store.shopify_access_token)` | Idem |
| 5 | `src/app/api/stores/route.ts` | L100 | `decrypt(_kpub)` em `klaviyo_public_key` | Decrypt direto de campo em client_stores |

### Out of scope (decrypt em outras tabelas — `tracking_stores`)

> **QA C6:** Os seguintes endpoints fazem `decrypt()` em credenciais da tabela `tracking_stores`, NAO `client_stores`. Lifecycle de credenciais diferente — documentado como out-of-scope para esta story.

- `src/app/api/integrations/tracking/test/route.ts` L84, L102, L619, L620
- `src/app/api/tracking/lookup/route.ts` L328
- `src/app/api/tracking/debug-live/route.ts` L48, L56

### Endpoints com boolean flag reads (NAO precisam migrar)

Estes leem `!!store.klaviyo_api_key` ou similar — apenas checam existencia, nao decriptam:
- `/api/portal/stores` GET
- `/api/portal/integrations` GET
- `/api/portal/onboarding/wizard` GET
- `/api/stores` GET
- `/api/stores/control`
- E outros

## Acceptance Criteria

### 51.3.1 — Criar `getMultipleStoreCredentials()`

- [ ] Adicionar ao `credentials.service.ts`:
  ```typescript
  export async function getMultipleStoreCredentials(
    storeIds: string[]
  ): Promise<Map<string, DecryptedStoreCredentials>>
  ```
- [ ] Deve fazer um unico `SELECT * FROM client_stores WHERE id = ANY($1)` (batch)
- [ ] Decriptar cada store via `decryptStoreCredentials()`
- [ ] Retornar Map indexado por store ID

**Arquivo:** `src/lib/services/credentials.service.ts`

### 51.3.2 — Migrar `/api/portal/dashboard`

> **DBM C6-DB:** O dashboard usa credenciais APENAS para boolean checks (`!!store.klaviyo_private_key`) e passa `store.id` para funcoes downstream que chamam `getStoreCredentials()` internamente. Boolean checks funcionam em ciphertext (`!!("enc:v1:...")` e `true`). A decryption e desnecessaria — performance e security win.

- [ ] Ler `src/app/api/portal/dashboard/route.ts`
- [ ] **Opcao preferida (zero decryption):** Remover a chamada `decryptStoreCredentials()` por completo. Usar os raw stores diretamente — boolean checks (`!!store.field`) funcionam em ciphertext
- [ ] **Opcao alternativa:** Substituir por `getMultipleStoreCredentials(storeIds)` se alguma chamada downstream precisar do valor decriptado
- [ ] Verificar que `fetchShopifyData()` e `fetchKlaviyoData()` usam `store.id` (nao o token diretamente) — confirmado: chamam `syncShopifyForStore(store.id)` que chama `getStoreCredentials()` internamente
- [ ] Se usar opcao preferida, descartar o import de `decryptStoreCredentials` se nao for mais usado

**Arquivo:** `src/app/api/portal/dashboard/route.ts`

### 51.3.3 — Migrar `/api/clients/[id]/performance`

- [ ] Ler `src/app/api/clients/[id]/performance/route.ts`
- [ ] Substituir `decryptStoreCredentials(rawStore)` por `getStoreCredentials(storeId)`
- [ ] Ajustar o restante do codigo para usar o retorno do service

**Arquivo:** `src/app/api/clients/[id]/performance/route.ts`

### 51.3.4 — Migrar `/api/portal/tracking` e `/api/portal/tracking/config`

- [ ] Ler ambos os arquivos
- [ ] Substituir `decrypt(store.shopify_access_token)` por:
  ```typescript
  const creds = await getStoreCredentials(store.id)
  const token = creds.shopify_access_token
  ```
- [ ] Manter a logica de copiar o token para `tracking_stores` (encrypt no destino)

**Arquivos:** `src/app/api/portal/tracking/route.ts`, `src/app/api/portal/tracking/config/route.ts`

### 51.3.5 — Migrar `/api/stores` GET

- [ ] Ler `src/app/api/stores/route.ts`
- [ ] L100: substituir `decrypt(_kpub)` direto por `getStoreCredentials(store.id)` e extrair `klaviyo_public_key`
- [ ] Ou se o campo e usado apenas para display no frontend, considerar se o boolean flag e suficiente

**Arquivo:** `src/app/api/stores/route.ts`

### 51.3.6 — Validacao

- [ ] `npm run typecheck` passa sem erros
- [ ] `npm run lint` passa sem erros
- [ ] Grep por `decryptStoreCredentials(` fora de `credentials.service.ts` e `crypto.ts` → deve retornar 0
- [ ] Grep por `decrypt(` em arquivos de route (excluindo `crypto.ts`, `credentials.service.ts`, e routes de `tracking_stores`) → deve retornar 0

## Riscos

| Risco | Mitigacao |
|-------|----------|
| `getMultipleStoreCredentials()` com muitas stores pode ser lento | Usar `WHERE id = ANY($1)` (batch) ao inves de N queries. Para dashboards com 50+ stores, considerar paginacao |
| Portal dashboard pode precisar de campos nao-credenciais alem das credenciais | `getMultipleStoreCredentials` deve retornar a store completa decriptada, nao apenas campos de credenciais |
