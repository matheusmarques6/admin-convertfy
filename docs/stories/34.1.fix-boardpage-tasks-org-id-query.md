# Story 34.1 — Fix BoardPage tasks.org_id Query

## Story

**Como** usuario do dashboard que acessa a pagina Board,
**Quero** que as tarefas carreguem corretamente sem erro de query,
**Para que** eu possa gerenciar meu kanban sem pagina quebrada.

## Contexto

### Problema observado em producao

A query em `src/app/(dashboard)/board/page.tsx:99` usa `.eq("org_id", orgId)` mas a tabela `tasks` NAO tem coluna `org_id`. A tabela tem `client_id`, `store_id`, `assignee_id` e `created_by`, mas nunca recebeu a migration de multi-tenant que adicionou `org_id` as demais tabelas.

Erro Postgres: **42703** (undefined_column).

### Codigo atual (bug)

**Arquivo:** `src/app/(dashboard)/board/page.tsx` (linhas 86-102)

```typescript
const { data: tasks, error } = await adminClient
  .from("tasks")
  .select(`
    *,
    assignee:org_members(
      id,
      role,
      profile:profiles!org_members_profile_id_fkey(id, name, email, avatar_url)
    ),
    creator:profiles!tasks_created_by_fkey(id, name, email, avatar_url),
    client:clients(id, name, company),
    store:client_stores(id, store_name, platform)
  `)
  .eq("org_id", orgId)  // BUG: coluna org_id nao existe na tabela tasks
  .in("status", KANBAN_FETCH_STATUSES)
  .or(`source_type.in.(${allowedSourceTypes.join(",")}),assignee_id.eq.${orgMemberId}`)
  .order("position", { ascending: true })
```

### Estrutura da tabela tasks

A tabela `tasks` tem estas colunas de contexto:
- `client_id` UUID REFERENCES clients(id)
- `store_id` UUID REFERENCES client_stores(id)
- `assignee_id` UUID REFERENCES org_members(id)
- `created_by` UUID REFERENCES profiles(id)

A relacao com org e INDIRETA: `tasks.assignee_id` → `org_members.org_id`.

### Fix proposto

Substituir `.eq("org_id", orgId)` por um filtro que usa `assignee_id` via join com `org_members`, OU buscar os `org_member` IDs da org e filtrar por `assignee_id.in.(...)`.

**Opcao recomendada:** Filtrar por `assignee_id` IN (org_member IDs da org). A funcao `resolveCurrentUser()` ja busca o `orgId` na linha 28-34. Podemos buscar todos os org_member IDs e filtrar:

```typescript
// Buscar todos os org_member IDs da org
const { data: orgMembers } = await adminClient
  .from("org_members")
  .select("id")
  .eq("org_id", orgId)
  .eq("is_active", true)

const orgMemberIds = (orgMembers || []).map(m => m.id)

const { data: tasks, error } = await adminClient
  .from("tasks")
  .select(`...`)
  .in("assignee_id", orgMemberIds)  // FIX: filtrar por assignees da org
  .in("status", KANBAN_FETCH_STATUSES)
  .or(`source_type.in.(${allowedSourceTypes.join(",")}),assignee_id.eq.${orgMemberId}`)
  .order("position", { ascending: true })
```

**NOTA:** O trigger `copy_pipeline_auto_tasks` (migration `20260226_04_copy_pipeline.sql`) faz INSERT em `tasks` com `org_id`, o que indica que a coluna pode existir em producao adicionada manualmente. O dev DEVE verificar o schema real antes de implementar. Se `org_id` existir em producao, o fix e diferente (pode ser que a migration nao foi aplicada neste ambiente).

### Alternativa: Adicionar migration para org_id

Se preferirmos alinhar `tasks` com as demais tabelas multi-tenant:

```sql
ALTER TABLE tasks ADD COLUMN IF NOT EXISTS org_id UUID REFERENCES organizations(id);
CREATE INDEX IF NOT EXISTS idx_tasks_org_id ON tasks(org_id);
-- Backfill via assignee
UPDATE tasks SET org_id = om.org_id FROM org_members om WHERE tasks.assignee_id = om.id AND tasks.org_id IS NULL;
```

O dev deve decidir qual abordagem e mais adequada apos verificar o schema de producao.
