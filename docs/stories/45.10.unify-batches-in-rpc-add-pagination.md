# Story 45.10 — Unify Campaign Batches Into RPC + Add Pagination

## Status: Ready for Dev
## Effort: HIGH (4-5h)
## Priority: MEDIUM

## Context

The portal campaigns API makes 2 separate queries:
1. RPC `get_portal_campaigns_with_metrics` — individual campaigns with Klaviyo metrics
2. Supabase query on `campaign_batches` — batch SMS/WhatsApp campaigns

These are merged client-side in the API route with JS transform logic. This adds complexity and prevents server-side pagination.

Additionally, the `campaign_batches.store_ids` `overlaps()` query may not have a GIN index.

## Deliverables

### 1. Extend RPC to include batches via UNION

**Complexity note**: `campaign_batches` has fundamentally different structure than `campaigns`:
- `campaign_batches.store_ids` is a `UUID[]` array vs `campaigns.store_id` single UUID
- Batches lack ~20 columns present in campaigns (klaviyo_campaign_id, subject_line, segment_name, all metrics, etc.)
- The UNION branch must NULL-fill all missing columns to match the RETURNS TABLE schema

**Decision: store_ids array handling**: Use `unnest(store_ids)` to explode batches into one row per store (consistent with how the current JS merge works), OR return `store_ids[1]` as `store_id` if batches should appear once. Recommend `unnest` for correct store filtering.

```sql
-- UNION ALL branch skeleton for campaign_batches:
SELECT
  cb.id,
  unnest(cb.store_ids) AS store_id,
  NULL::UUID AS client_id,
  cb.name,
  NULL AS description,
  cb.campaign_type::TEXT AS channel,
  -- ... ~20 more NULL-filled columns ...
  CASE cb.status
    WHEN 'completed' THEN 'sent'
    WHEN 'failed' THEN 'cancelled'
    ELSE cb.status
  END AS status,
  'batch'::TEXT AS source,
  -- no Klaviyo metrics for batches
  NULL::NUMERIC AS open_rate,
  -- ...etc
FROM campaign_batches cb
WHERE cb.store_ids && p_store_ids
  AND cb.scheduled_at::DATE >= p_start_date
  AND cb.scheduled_at::DATE < (p_end_date + INTERVAL '1 day')
```

### 2. Add pagination parameters

```sql
CREATE OR REPLACE FUNCTION get_portal_campaigns_with_metrics(
  p_store_ids UUID[],
  p_start_date DATE,
  p_end_date DATE,
  p_status TEXT DEFAULT NULL,
  p_channel TEXT DEFAULT NULL,
  p_limit INT DEFAULT 500,     -- NEW
  p_offset INT DEFAULT 0       -- NEW
)
```

**totalCount mechanism**: Use `COUNT(*) OVER()` window function to include total count in each row without a separate query.

### 3. Add GIN index on campaign_batches.store_ids

```sql
CREATE INDEX IF NOT EXISTS idx_campaign_batches_store_ids
ON campaign_batches USING GIN (store_ids);
```

### 4. Consolidate batchStatusMap duplication

The API route currently has TWO divergent `batchStatusMap` definitions (lines ~139 and ~163). The UNION approach eliminates both — status mapping moves to SQL.

## Migration Safety

- Changing function signature creates a new overload in Postgres — **MUST DROP old signature first** with `DROP FUNCTION IF EXISTS get_portal_campaigns_with_metrics(UUID[], DATE, DATE, TEXT, TEXT)`
- Reemit REVOKE/GRANT for new signature
- This migration MUST incorporate changes from 45.4 (NULL rates) — do not revert those
