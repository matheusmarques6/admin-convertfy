## Contexto

A analise de seguranca revelou lacunas nos endpoints de settings existentes:

1. O endpoint de password change do portal (`/api/portal/settings/password/route.ts`) nao possui rate limiting, permitindo tentativas ilimitadas de brute force.
2. Os endpoints PUT do portal (profile e notifications) nao possuem validacao Zod.
3. O endpoint first-login (`/api/auth/change-password`) nao verifica o metadata `must_change_password`, permitindo uso indevido.
4. Mudancas de perfil nao sao registradas no log de atividades.
5. O settings hub (`/settings/page.tsx`) mostra todas as secoes para todos os roles, incluindo Equipe e Personalizacao para agentes que nao deveriam ver essas opcoes.
6. Switches de notificacoes e campo de email desabilitado nao possuem atributos de acessibilidade.

---

## Objetivo

1. Adicionar rate limiting ao endpoint de password do portal
2. Adicionar validacao Zod aos endpoints PUT do portal
3. Proteger endpoint first-login com guard `must_change_password`
4. Implementar activity logging para mudancas de perfil
5. Filtrar settings hub por role
6. Corrigir acessibilidade

---

## Acceptance Criteria

- [ ] **9.5.1** Rate limiting adicionado ao endpoint `/api/portal/settings/password/route.ts`:
  - Usar mesmo pattern de rate limiting dos endpoints admin
  - Limite adequado para prevenir brute force (ex: 5 tentativas por minuto por IP/user)

- [ ] **9.5.2** Validacao Zod adicionada aos endpoints PUT do portal:
  - `/api/portal/settings/route.ts` (profile update): name string min 2 max 100, phone string opcional
  - `/api/portal/settings/notifications/route.ts` (notifications update): preference_key string, enabled boolean
  - Retornar 400 com detalhes de validacao em caso de erro

- [ ] **9.5.3** Guard `must_change_password` adicionado ao `/api/auth/change-password/route.ts`:
  - Verificar `user.user_metadata?.must_change_password === true`
  - Se false ou ausente, retornar 403 com mensagem "Este endpoint eh exclusivo para primeiro login"
  - NOTA: Se ja implementado na Story 9.2, verificar e confirmar neste item

- [ ] **9.5.4** Activity logging implementado para mudancas de perfil:
  - Ao atualizar perfil via `/api/settings/profile`, registrar na tabela `activities`
  - Seguir pattern existente do `/api/auth/change-password` que ja loga atividades
  - Campos: user_id, action ("profile_updated"), details (campos alterados), timestamp
  - Tambem registrar mudancas de senha ("password_changed")

- [ ] **9.5.5** Settings hub (`/settings/page.tsx`) filtrado por role:
  - Admin (owner/admin): ve todas as secoes
  - Agent: NAO ve secoes "Equipe" (users/permissions) e "Personalizacao" (appearance/custom-fields/email-templates/tags)
  - Buscar role via `org_members` no server component
  - Filtragem ocorre no servidor (nao apenas CSS hide)

- [ ] **9.5.6** Acessibilidade corrigida:
  - Switches de notificacoes: `aria-label="Ativar/desativar notificacao de {nome}"`
  - Campo email desabilitado: `aria-describedby` apontando para texto explicativo
  - Botoes de password toggle: `aria-label="Mostrar senha"` / `aria-label="Ocultar senha"`

- [ ] **9.5.7** Run `npm run lint` passa sem erros
- [ ] **9.5.8** Run `npm run typecheck` passa sem erros

### Settings Hub Role Filtering

```typescript
// src/app/(dashboard)/settings/page.tsx
// Este eh um server component — buscar role no servidor

const supabase = await createClient();
const { data: { user } } = await supabase.auth.getUser();

const { data: membership } = await supabase
  .from("org_members")
  .select("role")
  .eq("user_id", user.id)
  .single();

const isAdmin = membership?.role === "owner" || membership?.role === "admin";

// Definir secoes visiveis
const settingSections = [
  // Sempre visivel
  { group: "Conta", items: ["profile", "notifications"] },
  // Apenas admin/owner
  ...(isAdmin ? [
    { group: "Equipe", items: ["users", "permissions"] },
    { group: "Personalizacao", items: ["appearance", "custom-fields", "email-templates", "tags"] },
  ] : []),
  // Sempre visivel
  { group: "Integracao", items: ["integrations"] },
];
```

## Riscos e Mitigacoes

| Risco | Mitigacao |
|-------|-----------|
| Rate limiting in-memory eh volatil em serverless | Usar pattern persistente se disponivel; caso contrario, in-memory com window curta ainda oferece protecao |
| Activity logging pode aumentar latencia | Insert eh rapido e nao eh critico; pode ser fire-and-forget |
| Role filtering pode esconder settings para roles customizados futuros | Usar whitelist de roles que TEM acesso (owner, admin) em vez de blacklist |
| Tabela activities pode nao existir | Verificar existencia antes de implementar; a tabela ja eh usada pelo change-password |
