## Story

**Como** operador do sistema que gerencia multiplas lojas com integracoes Klaviyo,
**Quero** que lojas com API keys sem os scopes necessarios sejam tratadas graciosamente no cron sync,
**Para que** o erro 403 seja registrado de forma clara no `store_revenue_summary`, os scopes faltantes sejam visiveis, e o cron nao desperdice tempo retentando lojas com erro permanente de permissao.

---

## Contexto

### Problema observado em producao

O cron `sync-reports` processa multiplas lojas. Duas lojas especificas retornam 403 `permission_denied` do Klaviyo, indicando que a API key nao tem os scopes necessarios (ex: `metrics:read`, `campaigns:read`).

### Causa raiz

A `KlaviyoPermissionError` e lancada corretamente pelo `client.ts` (L188), mas o cron tem um gap critico:

1. **Pre-fetch sem try-catch**: `getCachedAccountInfo()` e `fetchFlowNames()`/`fetchCampaignNames()` sao chamados FORA do try-catch por periodo (linhas 107-119 do `sync-reports/route.ts`). Se lancam `KlaviyoPermissionError`, o erro pula direto pro `Promise.allSettled` no nivel do batch.
2. **Sem registro no banco**: Como o erro ocorre antes do loop de periodos, NENHUM `store_revenue_summary` e atualizado — o erro fica invisivel no dashboard.
3. **Re-tentativa a cada execucao**: Sem mecanismo de cooldown, o cron tenta a mesma loja com a mesma key a cada execucao, desperdicando tempo e requests.

### Impacto atual

1. **Lojas afetadas**: 0% de dados sincronizados — nenhum periodo e processado
2. **Erro invisivel**: `store_revenue_summary` nao tem registro de erro — parece que a loja nunca foi sincronizada
3. **Desperdicio**: Cada execucao gasta tempo fazendo requests que vao falhar com 403
4. **Diagnostico dificil**: Erro so aparece em logs do serverless, nao no dashboard

## Acceptance Criteria

### 16.7.1 — Wrap pre-fetch em try-catch no cron

- [x] Em `sync-reports/route.ts`, envolver as chamadas de pre-fetch (`getCachedAccountInfo`, `getCachedPlacedOrderMetric`, `fetchFlowNames`, `fetchCampaignNames`) em um try-catch
- [x] Se `KlaviyoPermissionError` for capturada:
  - Registrar `sync_error` em `store_revenue_summary` para TODOS os periodos da loja, com mensagem clara incluindo os scopes faltantes (ex: `"[PERMISSION] API key missing scopes: metrics:read, campaigns:read"`)
  - Atualizar `klaviyo_validation_error` em `client_stores` com os scopes faltantes
  - Atualizar `klaviyo_missing_scopes` em `client_stores` com array dos scopes
  - Fazer `continue` para pular a loja inteira (nao processar periodos)
  - Logar warning com store_name e scopes faltantes

**Arquivo:** `src/app/api/cron/sync-reports/route.ts`

### 16.7.2 — Registrar KlaviyoPermissionError no store_revenue_summary

- [x] Ao capturar `KlaviyoPermissionError` no pre-fetch, fazer upsert em `store_revenue_summary` para cada periodo configurado (`periods` array), com:
  - `sync_status: "error"`
  - `sync_error: "[PERMISSION] Klaviyo API key missing scopes: ${missingScopes.join(', ')}"`
  - `synced_at: new Date().toISOString()`
  - Demais campos de receita zerados
- [x] Isso garante que o dashboard mostra o erro para todos os periodos, nao apenas silencio

**Arquivo:** `src/app/api/cron/sync-reports/route.ts`

### 16.7.3 — Atualizar campos de validacao em client_stores

- [x] Ao capturar `KlaviyoPermissionError`, atualizar `client_stores` com:
  - `klaviyo_validation_error`: mensagem do erro (scopes faltantes)
  - `klaviyo_missing_scopes`: array dos scopes faltantes
  - `klaviyo_validated_at`: timestamp atual
  - `klaviyo_has_reporting_access`: `false`
- [x] Isso faz com que `getStoreIntegrationStatus()` retorne `status: "error"` com os scopes faltantes, visivel na UI de configuracao

**Arquivo:** `src/app/api/cron/sync-reports/route.ts`

### 16.7.4 — Propagar custom errors no service layer (re-throw seletivo)

Tres pontos do codigo tem catches genericos que engolem TODAS as excecoes, incluindo `KlaviyoPermissionError` e `KlaviyoRateLimitError`. Corrigir todos:

- [x] **`getCachedPlacedOrderMetric`** em `cached-metadata.ts` (L76-81): O catch generico retorna `null`, fazendo o cron tratar como "No Placed Order metric" em vez de permission error. Adicionar re-throw de `KlaviyoPermissionError` ANTES do catch generico
- [x] **`syncKlaviyoForPeriod`** em `klaviyo-sync.service.ts` (L652-662): O catch generico converte tudo em `{ success: false }`. Adicionar re-throw de `KlaviyoPermissionError` e `KlaviyoRateLimitError` ANTES do return generico
- [x] **`fetchStoreRevenueFromMetricAggregates`** em `klaviyo-sync.service.ts` (L382-392): O catch generico engole rate limit errors. Adicionar re-throw de `KlaviyoRateLimitError` (opcional — `KlaviyoPermissionError` ja seria pega antes no pre-fetch)

**Arquivos:**
- `src/lib/integrations/klaviyo/cached-metadata.ts`
- `src/lib/services/klaviyo-sync.service.ts`

**Padrao de implementacao:**
```typescript
} catch (err) {
  // Re-throw non-retryable errors — must not be silenced
  if (err instanceof KlaviyoPermissionError) throw err
  if (err instanceof KlaviyoRateLimitError) throw err
  // ... existing generic handling
}
```

### 16.7.5 — Tratar KlaviyoPermissionError no loop de periodos

- [x] No loop de periodos do cron (`sync-reports/route.ts`), adicionar catch especifico para `KlaviyoPermissionError` no bloco catch existente (linhas 198-229)

## Notas Tecnicas

### Fluxo proposto

```
syncStore() {
  // 1. Get credentials
  const apiKey = ...

  // 2. Pre-fetch with permission error handling
  try {
    accountInfo = await getCachedAccountInfo(apiKey, ...)
    metricId = await getCachedPlacedOrderMetric(apiKey, ...)
    [flowNames, campNames] = await Promise.all([...])
  } catch (err) {
    if (err instanceof KlaviyoPermissionError) {
      // Record error for ALL periods
      for (const period of periods) {
        await upsertSyncError(store, period, err.message)
      }
      // Update client_stores validation fields
      await updateKlaviyoValidation(store.id, err.missingScopes)
      return  // skip this store entirely
    }
    throw err  // re-throw other errors
  }

  // 3. Continue with per-period sync as before
  for (const period of periods) { ... }
}
```

### Arquivos impactados

| Arquivo | Mudanca |
|---------|---------|
| `src/app/api/cron/sync-reports/route.ts` | Try-catch no pre-fetch + upsert erro + update client_stores + catch no loop + `upsertSyncError()` |
| `src/lib/services/klaviyo-sync.service.ts` | Re-throw seletivo de `KlaviyoPermissionError` e `KlaviyoRateLimitError` em `syncKlaviyoForPeriod` e `fetchStoreRevenueFromMetricAggregates` |
| `src/lib/integrations/klaviyo/cached-metadata.ts` | Re-throw de `KlaviyoPermissionError` em `getCachedPlacedOrderMetric` |

### Riscos e mitigacoes

| Risco | Mitigacao |
|-------|-----------|
| Upsert em store_revenue_summary para todos os periodos pode ser lento | Usar Promise.all para paralelizar os upserts |
| Campo klaviyo_validation_error pode ficar stale se key for corrigida | Proximo sync bem-sucedido limpa o campo (ja feito por updateStoreCredentials com integrationKey=klaviyo) |
| Outras exceptions no pre-fetch (ex: timeout) nao devem ser tratadas como permission | Catch especifico para KlaviyoPermissionError, re-throw para outros |
