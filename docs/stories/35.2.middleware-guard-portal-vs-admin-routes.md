# Story 35.2 — Middleware Guard Portal vs Admin Routes

## Story

**Como** portal user que acessa a aplicacao,
**Quero** ser redirecionado para `/portal/dashboard` se tentar acessar rotas admin,
**Para que** eu nao veja uma pagina quebrada com erro PGRST116.

## Contexto

### Problema observado

O middleware (`src/lib/supabase/middleware.ts`) so verifica se o usuario tem sessao autenticada (`getUser()`). Nao diferencia portal users de admin users. Um portal user autenticado consegue navegar para `/dashboard`, `/clients`, etc., e ve erros porque essas paginas fazem queries em `org_members` que nao existem para portal users.

### Codigo atual do middleware (relevante)

```typescript
// src/lib/supabase/middleware.ts - linhas 53-56
const protectedPaths = ["/dashboard", "/clients", "/pipeline", "/automations",
  "/settings", "/reports", "/tools", "/team", "/financial", "/meetings",
  "/stores", "/onboarding", "/notifications", "/campaigns"]
const isProtectedPath = protectedPaths.some(path =>
  request.nextUrl.pathname.startsWith(path))

// linhas 76-78 - so checa se user existe
if (isProtectedPath && !user) {
  return NextResponse.redirect(new URL("/login", request.url))
}
```

### Caso especial: usuarios dual

Existem usuarios que sao TANTO portal users quanto admin users:
- `matheus@convertfy.me` — tem `is_portal_user: true` no metadata MAS tambem tem registro em `org_members`
- `ryan@convertfy.me` — mesmo caso

Esses usuarios DEVEM continuar acessando rotas admin normalmente. O guard NAO pode simplesmente checar `is_portal_user` no metadata — precisa verificar se o user TEM `org_members`.

### Estrategia proposta

No middleware, apos confirmar que o user tem sessao e esta acessando rota protegida admin:

1. Checar `user.user_metadata.is_portal_user`
2. Se `true`, fazer query leve em `org_members` para verificar se o user tambem e admin
3. Se NAO tem `org_members` → redirect para `/portal/dashboard`
4. Se TEM `org_members` → permitir acesso (usuario dual)

**IMPORTANTE:** O middleware ja pula API routes (linha 9: `if (pathname.startsWith('/api/')) return NextResponse.next()`). O guard so precisa atuar em paginas.

### Preocupacao de performance

O middleware executa em TODA request para rotas protegidas. A query `org_members` adicional so executa quando `is_portal_user === true`, o que e um subset pequeno de usuarios. Para a maioria dos admin users, o metadata NAO tem `is_portal_user`, entao o guard e um no-op.

## Acceptance Criteria

### 35.2.1 — Extrair helper `isPortalOnlyUser` e adicionar guard no middleware

- [x] Criar funcao helper `isPortalOnlyUser(supabase, user)` que:
  1. Checa `user.user_metadata?.is_portal_user === true` — se false, retorna false (fast path)
  2. Se true, faz query em `org_members` para verificar se user tambem e admin:
```typescript
// RLS note: portal users sem org_members recebem null de current_org_id(),
// fazendo org_id = NULL ser falso para todas as rows. Query retorna 0 rows (nao erro).
const { data: orgMember } = await supabase
  .from("org_members")
  .select("id")
  .eq("profile_id", user.id)
  .eq("is_active", true)
  .maybeSingle()
```
  3. Se `orgMember` e null → retorna true (e portal-only)
  4. Se `orgMember` existe → retorna false (usuario dual)
- [x] Usar o helper em DOIS pontos do middleware (ver AC 35.2.2 e 35.2.6)

**Arquivo:** `src/lib/supabase/middleware.ts`

## Riscos

| Risco | Mitigacao |
|-------|----------|
| Query `org_members` no middleware adiciona latencia | Query so executa para users com `is_portal_user: true` (minoria). Query e leve (1 row, index em profile_id). Helper extrai logica para reuso |
| Supabase client no middleware pode ter limitacoes | O middleware ja cria `createServerClient` na linha 19 e faz `getUser()`. Query em `org_members` usa o mesmo client |
| Usuario dual que perde acesso admin (org_member desativado) fica redirecionando | Comportamento desejado: se `is_active: false`, nao deve acessar admin |
| RLS em `org_members` pode bloquear query para portal users | Dev confirmou: `current_org_id()` retorna NULL para portal users sem org_members, fazendo a query retornar 0 rows (nao erro). User client funciona corretamente. NAO precisa de `createAdminClient()` |
| Double-redirect em `/` para portal users | Coberto no AC 35.2.6: helper reutilizado no root path handler evita hop desnecessario |
