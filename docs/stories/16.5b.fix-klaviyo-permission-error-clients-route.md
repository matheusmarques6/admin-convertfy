## Story

**Como** administrador que configura uma API key da Klaviyo com scopes insuficientes,
**Quero** que o erro de permissao seja identificado de forma clara no relatorio de performance do cliente (com os scopes especificos que faltam),
**Para que** eu possa corrigir a configuracao da API key sem precisar interpretar mensagens genericas de erro.

---

## Contexto

A story 16.5 corrige a propagacao de `KlaviyoPermissionError` no fluxo do portal dashboard — o service re-throw o erro e o portal o loga com os scopes faltando.

Porem, `src/app/api/clients/[id]/performance/route.ts` e um segundo caller de `fetchKlaviyoPerformance` e usa um padrao de catch diferente: **string matching fragilizado** no `err.message` para identificar tipos de erro.

**Problema identificado no catch existente (linhas ~314-328):**

```typescript
} catch (err) {
  // ... tenta cache ...
  const rawMsg = err instanceof Error ? err.message : String(err)
  let message = rawMsg
  let code: string | undefined

  if (rawMsg.includes("401") || rawMsg.includes("403") || rawMsg.toLowerCase().includes("unauthorized")) {
    message = "API Key sem permissão para métricas. Verifique os scopes da chave Klaviyo."
    code = "AUTH_ERROR"
  } else if (rawMsg.includes("429")) {
    message = "Limite de requisições Klaviyo excedido. Tente novamente em alguns minutos."
    code = "RATE_LIMIT"
  } else if (rawMsg.includes("Falha ao conectar")) {
    message = "Falha ao conectar com a API do Klaviyo. Verifique as credenciais."
    code = "CONNECTION_ERROR"
  }
  // ...
}
```

Com `KlaviyoPermissionError` propagada pelo service (story 16.5), essa excecao chega ao catch do route. O catch pode captura-la via `rawMsg.includes("403")` dependendo da mensagem do erro, mas:

1. **Nao ha garantia** — `KlaviyoPermissionError` nao precisa incluir "403" na sua mensagem
2. **Os scopes especificos sao perdidos** — `err.missingScopes[]` nunca e lido
3. **O code retornado e generico** — `"AUTH_ERROR"` nao informa scopes ao frontend

**Comportamento desejado:** Detectar `KlaviyoPermissionError` via `instanceof` (tipado, sem depender de string matching) e construir uma mensagem clara com os scopes faltando.

### Localizacao exata do catch block

O catch relevante esta em `src/app/api/clients/[id]/performance/route.ts`, dentro do bloco que processa dados Klaviyo por store. A estrutura atual (linhas ~297-329):

```typescript
} catch (err) {
  // On error, try cache tables first, then stale dashboard_cache
  klaviyoData = await readKlaviyoFromCacheTables(adminClient, store.id, period).catch(() => null)

  if (!klaviyoData) {
    const stale = await getStaleCache<KlaviyoPerformanceData>(adminClient, store.id, "klaviyo_perf", period)
    if (stale) {
      log.info(`[ClientPerf] Using stale cache for store ${store.id} after error`)
      klaviyoData = stale.data
    }
  }

  if (klaviyoData) {
    log.info(`[ClientPerf] Recovered from error with cached data for store ${store.id}`)
  } else {
    const rawMsg = err instanceof Error ? err.message : String(err)
    let message = rawMsg
    let code: string | undefined

    if (rawMsg.includes("401") || rawMsg.includes("403") || rawMsg.toLowerCase().includes("unauthorized")) {
      message = "API Key sem permissão para métricas. Verifique os scopes da chave Klaviyo."
      code = "AUTH_ERROR"
    } else if (rawMsg.includes("429")) {
      message = "Limite de requisições Klaviyo excedido. Tente novamente em alguns minutos."
      code = "RATE_LIMIT"
    } else if (rawMsg.includes("Falha ao conectar")) {
      message = "Falha ao conectar com a API do Klaviyo. Verifique as credenciais."
      code = "CONNECTION_ERROR"
    }

    log.warn("Failed to fetch Klaviyo data for store", { storeId: store.id, error: err })
    errors.push({ integration: "klaviyo", message, code })
  }
}
```
