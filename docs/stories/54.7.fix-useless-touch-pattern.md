# Story 54.7 — Fix Useless Touch Pattern (`expires_at` vs `fetched_at`)

## Story

**Como** engenheiro de performance,
**Quero** que o mecanismo de "touch" do cache realmente previna refreshes desnecessarios,
**Para que** o portal nao dispare live API calls contra o Klaviyo a cada acesso.

## Contexto

### Problema

Em `portal/dashboard/route.ts` (linhas ~178-192), quando dados sao considerados "stale" (>5min), o codigo faz um "touch":

```typescript
if (isStale && summary.sync_status === "ok") {
  Promise.resolve(
    adminForTouch
      .from("store_revenue_summary")
      .update({ expires_at: new Date(Date.now() + 24 * 60 * 60 * 1000).toISOString() })
      .eq("store_id", storeId)
      .eq("period_label", period)
  ).catch(() => {})
}
```

**Mas a verificacao de staleness usa `fetched_at`, nao `expires_at`:**
```typescript
const dataAgeMs = summary.fetched_at ? Date.now() - new Date(summary.fetched_at).getTime() : Infinity
const isStale = dataAgeMs > PORTAL_STALENESS_MS  // 5 min
```

O touch atualiza `expires_at` mas nunca atualiza `fetched_at`. Resultado: o dado continua "stale" em todos os acessos subsequentes, e o touch roda repetidamente sem efeito util.

### Problemas adicionais

1. `Promise.resolve()` wrapper desnecessario (Supabase query ja e Promise)
2. `.catch(() => {})` engole todos os erros silenciosamente
3. Cria novo `adminClient` a cada cache read stale — desperdicio de recursos
4. `PORTAL_STALENESS_MS = 5 * 60 * 1000` (5min) e muito agressivo — cron roda a cada ~30min

## Acceptance Criteria

### 54.7.1 — Corrigir touch para atualizar `fetched_at`

- [x] Touch deve atualizar `fetched_at` (nao `expires_at`) para que a proxima leitura nao considere stale:
  ```typescript
  .update({ fetched_at: new Date().toISOString() })
  ```
- [ ] ~~Ou alternativamente, mudar o stale check para usar `expires_at`~~ (nao necessario, opcao A implementada)

### 54.7.2 — Ajustar staleness threshold

- [x] Aumentar `PORTAL_STALENESS_MS` para ser proporcional ao intervalo do cron (~30min):
  ```typescript
  const PORTAL_STALENESS_MS = 45 * 60 * 1000  // 45 min (1.5x cron interval)
  ```
- [ ] ~~Ou usar `expires_at` que ja e definido com TTL adequado pelo cron~~ (nao necessario)

### 54.7.3 — Cleanup do touch code

- [x] Remover `Promise.resolve()` wrapper
- [x] Adicionar logging minimo no `.catch()` em vez de engolir erros
- [x] Reusar adminClient existente em vez de criar novo (reusa `supabase` param)

### 54.7.4 — Validacao

- [x] `npm run build` passa
- [x] Portal nao marca dados como stale desnecessariamente
