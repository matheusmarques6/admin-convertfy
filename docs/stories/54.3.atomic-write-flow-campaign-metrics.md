# Story 54.3 — Atomic Write for Flow/Campaign Metrics (Eliminate Race Condition)

## Story

**Como** usuario do portal,
**Quero** que os dados de flows e campanhas nunca desaparecam momentaneamente durante o sync,
**Para que** eu nao veja "0 flows" ou "0 campanhas" ao acessar o dashboard durante uma sincronizacao.

## Contexto

### Problema

Em `sync-persistence.service.ts`, o padrao de escrita para `klaviyo_flow_metrics` e `klaviyo_campaign_metrics` e:

```typescript
// Passo 1: DELETE todas as rows do periodo
await supabase
  .from("klaviyo_flow_metrics")
  .delete()
  .eq("store_id", store.id)
  .eq("period_label", period)

// Passo 2: UPSERT novas rows
const { error } = await supabase
  .from("klaviyo_flow_metrics")
  .upsert(flowRows, { onConflict: "store_id,flow_id,period_start,period_end" })
```

**Entre o DELETE e o UPSERT**, uma leitura do portal (`fetchKlaviyoFromCache()`) ve zero rows. Essa janela e pequena (ms) mas real, especialmente com cron + portal refresh concorrentes.

### Mesmo pattern para campaigns

```typescript
// DELETE + UPSERT separados para klaviyo_campaign_metrics
```

### Impacto

- Portal mostra momentaneamente 0 flows/campaigns com receita $0
- Se o processo morrer entre DELETE e UPSERT, dados ficam perdidos ate proximo cron

## Acceptance Criteria

### 54.3.1 — Substituir DELETE+UPSERT por UPSERT puro

- [x] Remover o `DELETE` pre-upsert para `klaviyo_flow_metrics`
- [x] Remover o `DELETE` pre-upsert para `klaviyo_campaign_metrics`
- [x] Usar apenas UPSERT com `onConflict` — rows que nao existem mais na fonte simplesmente nao sao atualizadas
- [x] Adicionar um cleanup posterior: deletar rows que nao foram tocadas neste sync (por `fetched_at` < timestamp do sync)

**Abordagem:**
```typescript
const syncTimestamp = new Date().toISOString()

// 1. UPSERT todas as rows (cada row tem fetched_at = syncTimestamp)
const { error: flowErr } = await supabase
  .from("klaviyo_flow_metrics")
  .upsert(
    flowRows.map(r => ({ ...r, fetched_at: syncTimestamp })),
    { onConflict: "store_id,flow_id,period_start,period_end" }
  )

// 2. CLEANUP: deletar rows antigas deste store+period que nao foram atualizadas
if (!flowErr) {
  await supabase
    .from("klaviyo_flow_metrics")
    .delete()
    .eq("store_id", store.id)
    .eq("period_label", period)
    .lt("fetched_at", syncTimestamp)
}
```

**Arquivo:** `src/lib/services/sync-persistence.service.ts`

### 54.3.2 — Mesmo pattern para campaign metrics

- [x] Aplicar a mesma abordagem (UPSERT + cleanup posterior) para `klaviyo_campaign_metrics`

### 54.3.3 — Manter audiences com DELETE+INSERT

- [x] O pattern DELETE+INSERT para `klaviyo_audiences` pode ser mantido (tabela nao e lida pelo dashboard durante sync — nao ha race condition critica)
- [x] Documentar no codigo o motivo da diferenca

| Risco | Mitigacao |
|-------|----------|
| Rows orfas se cleanup falhar | Cleanup e best-effort; 54.9 (TTL) serve como safety net |

| Flows removidos do Klaviyo persistem no cache | Cleanup por `fetched_at` remove flows que nao vieram no sync |
