# Story 19.1 - Fix Partial Sync Overwriting Valid Revenue Data

**Prioridade:** P0 (Critica - causa dados de receita incorretos na dashboard)
**Sprint:** Current
**Assignee:** @dev
**Revisao:** @qa, @data-engineer
**Status:** Ready
**Epic:** 19 - Dashboard Revenue Data Integrity

---

## Contexto

O diagnostico da dashboard admin revelou que `klaviyo_campaign_revenue = 0.00` para TODAS as lojas no `store_revenue_summary`, mesmo quando `klaviyo_campaign_metrics` tem campanhas com `conversion_value > 0`.

### Causa Raiz

Em `syncKlaviyoForPeriod()` (`klaviyo-sync.service.ts`), os 3 requests Klaviyo (flow-values-reports, campaign-values-reports, metric-aggregates) sao enviados via `Promise.all`. Quando `campaignResponse` retorna `null` (erro transiente do `klaviyoRequest` apos retries), o bloco de processamento de campanhas e simplesmente pulado:

```typescript
// Se campaignResponse e null, este bloco nao executa
if (campaignResponse?.data?.attributes?.results) {
  // ... processa campanhas
  totalCampaignRevenue = campRows.reduce(...)
}
// totalCampaignRevenue permanece 0, campRows permanece []
```

### Heuristica Existente e Por Que Falha

O `upsertSyncResults()` em `sync-persistence.service.ts` JA possui uma heuristica de preservacao (linhas 54-80):

```typescript
const campaignReportMissing = data.campaignRevenue === 0 && data.campRows.length === 0
if (campaignReportMissing && existing.klaviyo_campaign_revenue > 0) {
  effectiveCampaignRevenue = existing.klaviyo_campaign_revenue
}
```

Esta heuristica **falha em cadeia** nos seguintes cenarios:

1. **Primeira sync da loja:** Nao existe registro anterior no DB. O SELECT retorna null, e `effectiveCampaignRevenue` permanece 0. Esse zero e gravado com `sync_status: "ok"`.

2. **Falhas consecutivas:** Se o cron falhou na sync anterior E nessa, o DB ja tem `klaviyo_campaign_revenue = 0`. A condicao `> 0` nao e satisfeita, e o zero e mantido perpetuamente.

3. **`sync_status: "ok"` sempre gravado:** Linha 99 grava `sync_status: "ok"` mesmo quando um dos reports nao foi obtido. Isso mascara a falha parcial — o frontend nao sabe que os dados estao incompletos.

4. **Condicao `campaignRevenue === 0 && campRows.length === 0`:** Nao distingue "zero real" (nenhuma campanha enviou no periodo) de "report falhou". Uma loja que REALMENTE tem zero campanhas no periodo ativaria a mesma condicao, causando um SELECT desnecessario.

### Problema Secundario: Blue Wolf Missing

Blue Wolf tem chave Klaviyo valida mas nao aparece no cache 30d/90d:
1. Rate limit em 7d (Retry-After: 20,860,000ms = 5.8h)
2. Rate limit em 15d (Retry-After: 20,856,000ms)
3. `consecutiveRateLimits >= 2` causa `break` no loop em `syncStore()` (`sync-reports/route.ts`)
4. 30d e 90d nunca sao tentados
5. Dashboard padrao (30d) nao mostra Blue Wolf

### Evidencia no Banco

```
store_revenue_summary (30d):
  Blessed Choice: campaign=0.00, flow=209922.06, status=ok
  Karm:           campaign=0.00, flow=25871.44,  status=ok
  Innova Bay:     campaign=0.00, flow=3042.24,   status=ok

klaviyo_campaign_metrics:
  Blessed Choice: 10 campanhas, max conversion_value=4999.16
  Karm:           36 campanhas, max conversion_value=1673.45
  (dados de syncs anteriores que funcionaram para outros periodos)
```

---

## Objetivo

1. Substituir a heuristica fragil por flags explicitas (`campaignDataAvailable`/`flowDataAvailable`) que distinguem "zero real" de "report indisponivel"
2. Gravar `sync_status: "partial"` quando apenas um report funciona (nao "ok")
3. Nao sobrescrever campos de receita com zero quando o report correspondente falhou
4. Priorizar o periodo 30d no cron e nao bloquear periodos maiores por rate limit em menores

- [x] **19.1.5** Quando sync e parcial (so um report disponivel), recalcular `klaviyo_total_revenue` somando o campo novo + o valor existente no DB:

  ```typescript
  // Somente no caso parcial (um report obtido, outro nao):
  if ((data.flowDataAvailable && !data.campaignDataAvailable) ||
      (!data.flowDataAvailable && data.campaignDataAvailable)) {
    const { data: existing } = await supabase
      .from("store_revenue_summary")
      .select("klaviyo_campaign_revenue, klaviyo_flow_revenue")
      .eq("store_id", store.id)
      .eq("period_label", period)
      .single()

    const campRev = data.campaignDataAvailable
      ? data.campaignRevenue
      : (existing ? Number(existing.klaviyo_campaign_revenue) || 0 : 0)
    const flowRev = data.flowDataAvailable
      ? data.flowRevenue
      : (existing ? Number(existing.klaviyo_flow_revenue) || 0 : 0)
  ```

  **Edge case - primeira sync (sem registro anterior):** Se nao existe registro, `existing` e null e o campo indisponivel fica como 0. Isso e aceitavel: total = campo_disponivel + 0. Na proxima sync completa, o total sera corrigido.

## Arquitetura Tecnica

### Fluxo Antes

```
Cron sync-reports:
  1. Promise.all([flowReport, campaignReport, metricAgg])
  2. campaignReport = null (rate limit/timeout)
  3. totalCampaignRevenue = 0, campRows = []
  4. upsertSyncResults():
     - Heuristica: campaignRevenue===0 && campRows.length===0 → "missing"
     - SELECT existing: klaviyo_campaign_revenue = 0 (da falha anterior)
     - Condicao > 0 NAO satisfeita → effectiveCampaignRevenue = 0
     - Upsert: campaign_revenue=0, sync_status="ok" (ERRADO!)
  5. Dashboard mostra: Campaign Revenue = R$ 0
```

### Fluxo Depois

```
Cron sync-reports:
  1. Promise.all([flowReport, campaignReport, metricAgg])
  2. campaignReport = null (rate limit/timeout)
  3. campaignDataAvailable = false (flag explicita)
  4. upsertSyncResults():
     - Flag false → NAO inclui klaviyo_campaign_revenue no payload
     - SELECT existing para recalcular total
     - Upsert: preserva campaign_revenue anterior, sync_status="partial"
  5. Dashboard mostra: Campaign Revenue = valor da ultima sync completa
```

## Riscos e Mitigacoes

| Risco | Mitigacao |
|-------|-----------|
| `sync_status: "partial"` novo para o frontend | Ja suportado: `hasPartialData` verifica `status === "error" \|\| status === "partial"` no `total-revenue/route.ts` (confirmado no codigo) |
| SELECT previo no upsert parcial adiciona latencia | Query indexada por PK `(store_id, period_label)`, <1ms |
| Race condition no SELECT-then-upsert | Mitigado pelo cron_lock (impede execucao concorrente) |
| Reordenar CACHED_PERIODS afeta consumidores | Verificado via grep: 16 arquivos usam CACHED_PERIODS, nenhum depende da ordem |
| `consecutiveRateLimits >= 3` (antes 2) pode causar mais requests em lojas rate-limited | Mitigado pelo backoff (aguarda ate 15s entre periodos) |
| Interface change em `KlaviyoSyncData` (campos required) | TypeScript garante que `syncKlaviyoForPeriod` (unico produtor) e atualizado |
| Interface change em `KlaviyoRevenueSummary` (campos opcionais) | Backward compatible — callers existentes nao precisam mudar |
| Primeira sync de uma loja com partial: total = campo_disponivel + 0 | Aceitavel: corrigido na proxima sync completa. Melhor que total = 0 permanente |
