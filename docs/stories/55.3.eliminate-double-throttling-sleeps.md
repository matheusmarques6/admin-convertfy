# Story 55.3 — Eliminar Double-Throttling nos Sleeps

## Story

**Como** engenheiro de performance,
**Quero** remover os sleeps manuais redundantes no sync de periodos,
**Para que** o cron nao desperdice ~18s por loja em idle puro quando o rate limiter global ja controla o ritmo.

## Contexto

### Problema

`syncKlaviyoForPeriod` em `klaviyo-sync.service.ts` tem sleeps manuais entre as 3 API calls de reporting:

```typescript
// Linha 478: ANTES do flow-values-report
await sleep(MIN_REQUEST_INTERVAL) // 1000ms

// Linha 508: ENTRE flow e campaign reports
await sleep(REPORT_API_DELAY_MS)  // 1500ms

// Linha 540: ENTRE campaign e metric-aggregates
await sleep(REPORT_API_DELAY_MS)  // 1500ms
```

**Total por periodo**: 1000 + 1500 + 1500 = **4000ms de idle**

Porem, `klaviyoRequest()` ja tem um rate limiter global de **1200ms** entre chamadas (implementado em `src/lib/integrations/klaviyo/client.ts`). Os sleeps manuais sao **redundantes** — adicionam 4s extras de idle ALEM do rate limiter.

### Impacto

- 4 periodos por loja x 4s = **16s de idle por loja** (4s extras, nao 18s — os sleeps se sobrepoe parcialmente ao rate limiter)
- 42 lojas = **~672s de idle puro** por run
- Mesmo com 2 grupos em paralelo: **~336s de idle**

Alem disso, `INTRA_GROUP_DELAY_MS = 2500ms` no cron route (linha 32) adiciona delay entre lojas do mesmo grupo. Esse delay pode ser reduzido para 1000ms porque o rate limiter global ja garante spacing.

### Cuidado

O rate limiter global em `klaviyoRequest` e **por processo**, nao por API key. Em paralelo (2 grupos), cada grupo tem seu proprio ritmo. Os sleeps originais foram adicionados porque a reporting API do Klaviyo e mais restritiva (~1 req/s burst). O rate limiter global usa 1200ms — suficiente.

## Acceptance Criteria

### 55.3.1 — Remover sleep antes do flow-values-report

- [x] Removido `await sleep(MIN_REQUEST_INTERVAL)` antes do flow report
- [x] O rate limiter global em `klaviyoRequest` ja garante spacing minimo

### 55.3.2 — Reduzir sleep entre reports

- [x] Reduzido `REPORT_API_DELAY_MS` de 1500ms para 300ms (safety margin para reporting API)
- [x] Rate limiter global (1200ms) + 300ms = 1500ms efetivo entre reports
- [ ] Se rate limits aumentarem apos deploy, incrementar para 500ms

### 55.3.3 — Reduzir INTRA_GROUP_DELAY_MS

- [x] Em `route.ts`, reduzido `INTRA_GROUP_DELAY_MS` de 2500ms para 1000ms
- [x] O delay entre lojas do mesmo grupo nao precisa ser maior que o rate limiter

### 55.3.4 — Rate limiter global intacto

- [x] **NAO** removido/alterado o rate limiter em `rate-limiter.ts` (MIN_INTERVAL_MS = 1200ms)
- [x] O rate limiter continua sendo a protecao principal contra 429s

### 55.3.5 — Monitoramento pos-deploy

- [ ] Apos deploy, verificar nos logs do proximo run:
  - Numero de `sync_error RATE_LIMIT` nao aumentou
  - Tempo total do run diminuiu significativamente
- [ ] Se rate limits aumentarem, adicionar backoff adaptativo em vez de sleep fixo

### 55.3.6 — Sem regressao

- [x] `npx tsc --noEmit` passa sem erros
- [ ] Dados de flow/campaign/metric-aggregates continuam corretos — verificar em producao

## Riscos

| Risco | Mitigacao |
|-------|----------|
| Aumento de rate limits 429 | Rate limiter global (1200ms) continua ativo; REPORT_API_DELAY de 300ms adiciona safety margin |
| Reporting API mais restritiva que esperado | Se 429s aumentarem, incrementar REPORT_API_DELAY_MS para 500ms via config |
| Remocao de sleep causa race condition | Nao ha race condition — chamadas sao sequenciais (await) |

## Notes

- O rate limiter global em `klaviyoRequest` usa `MIN_REQUEST_INTERVAL = 1000ms` (definido em `src/lib/integrations/klaviyo/index.ts`)
- A reporting API do Klaviyo (flow-values-reports, campaign-values-reports) tem burst limit mais restritivo (~1 req/s) — o safety margin de 300ms entre reports garante 1300ms total (1000ms rate limiter + 300ms delay)
- O delay entre batches de grupos (linha 592 do route: `3000ms`) tambem pode ser reduzido, mas isso e menos impactante — deixar para observacao pos-deploy
