## Story

**Como** usuario do portal do cliente,
**Quero** que os dados do dashboard carreguem corretamente apos refresh (F5),
**Para que** eu possa visualizar metricas de campanhas, flows e receita sem dados zerados ou tela vazia.

---

## Contexto

### Problema Observado
Ao dar F5 no portal, todos os dados somem. O dashboard mostra valores zerados ou tela vazia.

### Causa Raiz Identificada (Diagnostico 2026-03-05)

O cron `sync-reports` processa 8 lojas x 4 periodos = 32 sync jobs a cada 30 minutos.
O Klaviyo rate limita agressivamente (Retry-After: 24-37 segundos), causando uma cascata:

1. Cron processa lojas em batches de 10
2. Apos 1-2 lojas com sucesso, Klaviyo retorna HTTP 429 (rate limit)
3. Logica de consecutive-break: 2+ rate limits seguidos -> pula periodos restantes da loja
4. `upsertSyncError()` grava rows com `sync_status = "error"` e **receita ZERO**
5. Periodos que nunca foram alcancados ficam **sem row nenhuma**

### Estado do Banco (2026-03-05 02:00 UTC)

| Loja (portal user) | 7d | 15d | 30d | 90d |
|---------------------|-----|------|------|------|
| Blessed Choice      | ok  | ok   | ok   | ok   |
| Innova Bay          | ok  | ok   | RATE_LIMIT (zero) | RATE_LIMIT (zero) |
| Blue Wolf           | RATE_LIMIT | RATE_LIMIT | *sem row* | *sem row* |
| **Karm** (portal)   | *sem row* | *sem row* | RATE_LIMIT (zero) | RATE_LIMIT (zero) |

| Almira              | PERMISSION | PERMISSION | PERMISSION | PERMISSION |
| ToysLand            | PERMISSION | PERMISSION | PERMISSION | PERMISSION |
| BRINQUEMAIS         | *sem row* | *sem row* | *sem row* | *sem row* |

### 3 Problemas Combinados

**P1 - Rate limit no cron**: O cron nao consegue sincronizar 8 lojas sem bater no rate limit.
As lojas processadas por ultimo (Karm, Vivazz) sao as mais afetadas.

**P2 - Error rows com dados zerados**: Quando rate limited, `upsertSyncError()` grava rows
com receita zero. O portal le esses zeros como dados reais.

**P3 - fetchKlaviyoFromCache nao distingue ok de error**: A funcao retorna dados do summary
independentemente de `sync_status`, mostrando zeros como se fossem receita real.

### Fluxo do Bug (periodo 30d, loja Karm)

```
1. Cron roda -> Karm 30d -> Klaviyo 429 rate limit
2. upsertSyncError() -> grava row: sync_status="error", receita=0, expires_at=+6h
3. Portal carrega -> fetchKlaviyoFromCache("941c124b", "30d")
4. Encontra row (sync_status="error") -> retorna dados com receita=0
5. Dashboard mostra: Receita R$0, Pedidos 0, etc.
```

### Fluxo do Bug (periodo 7d, loja Karm)

```
1. Cron roda -> Karm 7d -> nunca alcancado (consecutive-break apos 30d+90d falharem)
2. Nenhuma row existe
3. Portal carrega -> fetchKlaviyoFromCache("941c124b", "7d") -> null
4. Tenta liveFetchKlaviyoForPortal() -> funciona 1a vez
5. savePerfDataToCache() -> fire-and-forget (pode falhar)
6. Usuario da F5 -> cache pode estar vazio + cooldown 60s bloqueia re-fetch
7. Dashboard mostra: tela vazia
```

## Criterios de Aceitacao

### Camada 1: Cron mais resiliente ao rate limit

- [x] **CA1**: Cron deve processar lojas com **delay entre stores** (ex: 2-3s) para
      reduzir probabilidade de rate limit. Avaliar se `BATCH_SIZE = 10` em paralelo
      e agressivo demais para o rate limit do Klaviyo reporting API (~1 req/s)
- [x] **CA2**: Quando rate limited, cron deve **preservar dados anteriores validos** em vez
      de sobrescrever com zeros. `upsertSyncError()` NAO deve sobrescrever um row
      `sync_status = "ok"` existente com `sync_status = "error"` e receita zero
- [x] **CA3**: Aumentar intervalo entre periodos da mesma loja (atualmente sequencial
      sem delay) para respeitar o Retry-After retornado pelo Klaviyo

### Camada 2: Portal resiliente a dados de erro

- [x] **CA4**: `fetchKlaviyoFromCache()` deve ignorar rows com `sync_status = "error"` e
      tratar como cache miss (tentar live fetch ou mostrar "dados indisponiveis")
- [x] **CA5**: Quando summary tem `sync_status = "error"` mas `campaign_metrics`/`flow_metrics`
      existem com dados reais (de um sync anterior bem-sucedido), construir summary
      sintetico a partir dos dados de detalhe

### Camada 3: Logging e observabilidade

- [x] **CA6**: `savePerfDataToCache()` deve logar erros em vez de `.catch(() => {})`
- [x] **CA7**: Cron deve logar resumo de rate limits: quantas lojas afetadas, quantos
      periodos perdidos, para facilitar tuning futuro

### Validacao

## Riscos

- **R1**: Reduzir batch size ou adicionar delays pode fazer o cron exceder o timeout de 300s
  do Vercel (MAX_DURATION_MS = 240s). Mitiga: monitorar elapsed time, processar lojas
  mais criticas primeiro (as que tem portal users), pular lojas menos prioritarias se timeout.
- **R2**: O fallback de summary sintetico (CA5) pode ter valores imprecisos comparado ao
  que o Klaviyo retornaria (ex: audience metrics nao estao nas detail tables).
  Mitiga: marcar como "parcial" e mostrar aviso ao usuario.
- **R3**: Lojas com PERMISSION errors (Almira, ToysLand) continuarao sem dados ate
  as API keys serem corrigidas -- isso e esperado e NAO e bug desta story.
