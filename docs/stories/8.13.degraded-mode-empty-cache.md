## Contexto

O endpoint `/api/dashboard/total-revenue` (`src/app/api/dashboard/total-revenue/route.ts`) atualmente retorna `storesCount: 0` quando a tabela `store_revenue_summary` esta vazia. Os componentes do dashboard interpretam `storesCount === 0` como "usuario nao tem lojas conectadas" e mostram a mensagem "Conecte lojas com Klaviyo para ver a receita gerada".

Isso e incorreto quando o usuario TEM lojas com Klaviyo — o problema e apenas que o cache ainda nao foi populado (cold-start, primeira deploy, ou migrations recentes). Precisamos distinguir entre:

1. **Sem lojas**: Usuario realmente nao tem stores com Klaviyo -> manter mensagem "Conecte lojas"
2. **Cache vazio / sincronizando**: Tem stores com Klaviyo mas `store_revenue_summary` esta vazio -> mostrar "Dados sendo sincronizados..."
3. **Tabela nao existe**: Erro 42P01 (relation does not exist) -> retornar HTTP 503 com `Retry-After`

### Estado Atual do Codigo

```typescript
// src/app/api/dashboard/total-revenue/route.ts — linhas 77-97
if (rows.length === 0) {
  // PROBLEMA: retorna storesCount: 0 sem verificar se usuario tem stores
  const emptyResult: TotalRevenueResponse = {
    period,
    totalRevenue: 0,
    storesCount: 0,       // <-- Frontend interpreta como "sem lojas"
    storesWithRevenue: 0,
    // ...
  }
}
```

```typescript
// src/components/dashboard/total-revenue-banner.tsx — linhas 169-183
if (data && data.storesCount === 0) {
  return (
    // "Conecte lojas com Klaviyo para ver a receita gerada"
    // INCORRETO quando lojas existem mas cache esta vazio
  )
}
```

---

## Objetivo

Implementar degraded-mode responses no backend e syncing states no frontend para que o dashboard mostre informacoes uteis durante o periodo de cold-start do cache, em vez de mensagens enganosas.

## Arquitetura Tecnica

### Backend: Deteccao de Syncing State

Modificar `src/app/api/dashboard/total-revenue/route.ts`:

```typescript
// ANTES (linhas 68-97):
const { data: summaries, error } = await query
if (error) { throw error }
const rows = summaries || []
if (rows.length === 0) {
  // retorna storesCount: 0
}

// DEPOIS:
const { data: summaries, error } = await query

// Handle table-not-exists (42P01)
if (error) {
  if (error.code === '42P01') {
    return NextResponse.json(
      { error: "Cache table not ready", retryAfter: 300 },
      { status: 503, headers: { "Retry-After": "300" } }
    )
  }
  throw error
}

const rows = summaries || []

if (rows.length === 0) {
  // Check if user actually has stores with Klaviyo
  const { count: klaviyoStoresCount } = await supabase
    .from("client_stores")
    .select("id", { count: "exact", head: true })
    .eq("org_id", orgId)
    .not("klaviyo_private_key", "is", null)

  if (klaviyoStoresCount && klaviyoStoresCount > 0) {
    // Stores exist but cache is empty — syncing state
    const emptyResult: TotalRevenueResponse = {
      period,
      totalRevenue: 0,
      campaignRevenue: 0,
      flowRevenue: 0,
      storesCount: klaviyoStoresCount,
      storesWithRevenue: 0,
      topStores: [],
      bottomStores: [],
      storeBreakdown: [],
      hasPartialData: false,
      lastFetchedAt: null,
      cachedAt: new Date().toISOString(),
      dataStatus: "syncing",
    }
    return successResponse(request, emptyResult)
  }

  // No stores at all — existing behavior
  // ... (manter codigo existente com storesCount: 0)
}
```

### SWR: Polling Acelerado no Syncing State

No `TotalRevenueBanner`, ajustar o SWR config:

```typescript
const { data, error, isLoading, isValidating, mutate } = useSWR<TotalRevenueData>(
  swrKey,
```

## Riscos e Mitigacoes

| Risco | Mitigacao |
|-------|-----------|
| SWR polling de 30s gera muitas requests | Apenas ativo no syncing state; quando dados aparecem, para automaticamente |
| Query adicional de `client_stores` adiciona latencia | So executa quando cache vazio (cold path, nao hot path); query e rapida (count com index) |
| 503 confunde o frontend SWR | SWR por default nao retenta 503; fetcher ja lanca Error no `!res.ok` |
| Componentes fora destes 3 tambem afetados | TopStoresCard e WorstPerformersCard usam `useStoreRevenue` que consome o mesmo endpoint |
