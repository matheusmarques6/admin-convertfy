# Story 16.1 — Integrar Multi-Carrier Engine no Sync Pipeline

## Status
Ready for Review

## Story

**Como** sistema de rastreio do admin-convertfy,
**Quero** usar o engine multi-carrier (`trackWithBestProvider`) no sync pipeline ao invés do 17track global,
**Para que** cada loja utilize o melhor provider disponível (Cainiao grátis, PostNL direto, TrackingMore ou 17track como fallback), reduzindo custos e melhorando cobertura.

---

## Contexto

O engine multi-carrier foi implementado em `src/lib/tracking/carriers.ts` (Story 4.1 / merge da branch `claude/fix-shopify-tracking-config-mUJiW`) e contém:

- `detectCarrierProvider(trackingNumber)` — detecta carrier por regex
- `trackWithBestProvider(trackingNumber, keys, trackVia17track)` — fallback chain:
  1. PostNL direto (se `postnl` key configurada na loja)
  2. Cainiao (grátis, sem API key, para carriers chineses)
  3. 17track (se `seventeen_track` key configurada — ou `SEVENTEEN_TRACK_API_KEY` global como fallback)
  4. TrackingMore (se `trackingmore` key configurada na loja)

Atualmente o `syncTrackingCode()` em `tracking.service.ts` chama `trackNumber()` que usa **apenas** 17track via `SEVENTEEN_TRACK_API_KEY` env var global — ignorando completamente as chaves por loja e o engine multi-carrier.

A tabela `tracking_stores` já possui a coluna `carrier_api_keys JSONB` (migration `20260227_carrier_api_keys.sql` aplicada) para armazenar chaves encriptadas por loja.

- [ ] `syncTrackingCode()` deve buscar o `tracking_store_id` do `tracking_code` e a partir dele resolver o `client_store_id`

- [ ] Montar o objeto `CarrierKeys` com todas as chaves disponíveis

### 16.1.2 — Substituir `trackNumber()` por `trackWithBestProvider()`

- [ ] `syncTrackingCode()` deve chamar `trackWithBestProvider()` passando:
  - `trackingNumber` — número do rastreio
  - `keys: CarrierKeys` — chaves resolvidas da loja
  - `trackVia17track` — função de 17track existente em `tracking.service.ts`
- [ ] O retorno de `TrackingResult` (de `carriers.ts`) deve ser mapeado para o formato de `TrackResult` via `mapCarriersResultToTrackResult()` — ver Dev Notes para o mapeamento explícito de status
- [ ] Fallback: se `trackWithBestProvider()` retornar `null` **e** existir `SEVENTEEN_TRACK_API_KEY` global, chamar `trackNumber()` original como último recurso
- [ ] **Mock data NÃO é resultado aceitável no sync pipeline em produção**: se `trackNumber()` for chamado como fallback mas a API key global não existir (modo mock), o sync deve logar um warning e retornar sem atualizar o banco — não gravar dados fictícios no tracking_codes

### 16.1.3 — Extrair função `trackVia17track` reutilizável

- [ ] Extrair a lógica de chamada HTTP ao 17track de `trackNumber()` em uma função standalone `trackVia17track(trackingNumbers: string[], apiKey: string)` compatível com a assinatura esperada por `trackWithBestProvider()`
- [ ] `trackNumber()` existente deve continuar funcionando (usa a nova função internamente)
- [ ] Não quebrar os callers existentes: `syncTrackingCode()`, `syncAllPendingCodes()`, rota `/api/tracking/sync`

### 16.1.4 — Manter fallback para env var global

- [ ] Se `tracking_stores.seventeen_track_api_key` estiver vazio **e** `SEVENTEEN_TRACK_API_KEY` env var existir, usar a env var como fallback para 17track
- [ ] Se a query de `tracking_stores` falhar (erro de DB ou loja deletada): logar com `log.warn("tracking_store not found, using global fallback", { trackingCodeId })` e montar `CarrierKeys` apenas com a env var global — não abortar o sync
- [ ] Emitir log do provider no `tracking.service.ts` após resultado bem-sucedido, com estrutura:
  ```typescript

    trackingCodeId,
    trackingNumber: code.tracking_number,
    provider: result.carrier_code || "unknown",  // ex: "postnl", "cainiao", "17track"
    status: result.status,

  ```
  — esse log é adicional ao que já existe em `carriers.ts` e serve para rastreabilidade no nível do serviço

### 16.1.5 — Testes e validação

### Mapeamento TrackingResult → TrackResult

⚠️ **ATENÇÃO:** `carriers.ts` retorna status como `string` livre. Os valores `"pick_up"`, `"undelivered"` e `"alert"` **não existem** em `TrackingStatus` — usar `as TrackingStatus` diretamente causaria valores inválidos no banco. Usar o mapeamento explícito abaixo:

```typescript
// Mapa de status dos providers → TrackingStatus válido
const CARRIER_STATUS_MAP: Record<string, TrackingStatus> = {
  delivered:        "delivered",
  in_transit:       "in_transit",
  out_for_delivery: "out_for_delivery",
  pending:          "pending",
  info_received:    "info_received",
  failed_attempt:   "failed_attempt",
  exception:        "exception",
  expired:          "expired",
  // Status exclusivos de alguns providers — normalizar:
  pick_up:          "in_transit",      // Cainiao/PostNL: coletado = em trânsito
  undelivered:      "failed_attempt",  // TrackingMore: não entregue = tentativa falha
  alert:            "exception",       // TrackingMore: alerta = exceção
}

function mapCarriersResultToTrackResult(result: TrackingResult): TrackResult {
  return {
    status: CARRIER_STATUS_MAP[result.status] ?? "pending",
    statusDescription: result.status_detail || result.last_event || "",
    location: result.events[0]?.location || null,
    events: result.events,
    carrier: result.carrier_name || null,
    estimatedDelivery: result.estimated_delivery,
  }
}
```

### Query para resolver carrier_api_keys por tracking_code

```typescript
// 1. Buscar tracking_store_id do code (já está em tracking_codes)
const { data: code } = await admin
  .from("tracking_codes")
  .select("*, tracking_store_id")
  .eq("id", trackingCodeId)
  .single()

// 2. Buscar chaves da loja
const { data: store } = await admin
  .from("tracking_stores")
  .select("seventeen_track_api_key, carrier_api_keys")
  .eq("id", code.tracking_store_id)
  .single()

// 3. Montar CarrierKeys
const keys: CarrierKeys = {
  seventeen_track: store?.seventeen_track_api_key
    ? decrypt(store.seventeen_track_api_key)
    : process.env.SEVENTEEN_TRACK_API_KEY,
  trackingmore: store?.carrier_api_keys?.trackingmore
    ? decrypt(store.carrier_api_keys.trackingmore)
    : undefined,
  postnl: store?.carrier_api_keys?.postnl
    ? decrypt(store.carrier_api_keys.postnl)
    : undefined,
  cainiao: true, // sempre habilitado (gratuito)
}
```

### Cuidados

- `decrypt()` retorna a string original se não tiver prefixo `enc:v1:` — safe de chamar mesmo em valores já em plain text
- `tracking_codes` já tem coluna `tracking_store_id` (verificar se está populada — pode ser null em códigos antigos; nesses casos usar fallback global sem erro)
- Não alterar a assinatura pública de `syncTrackingCode(trackingCodeId: string)` — callers não devem precisar de mudança
- Se `trackWithBestProvider()` retornar `TrackingResult` com `events: []` (array vazio), o mapeamento ainda é válido: `location` será `null`, `statusDescription` virá de `status_detail` — comportamento correto para pacotes sem histórico ainda
- **Mock data no sync:** `trackNumber()` retorna dados fictícios quando `API_KEY` é undefined. Antes de chamar como fallback final, verificar se há API key disponível. Se não houver, logar `log.warn("No API key available, skipping sync", { trackingCodeId })` e retornar sem atualizar o banco
