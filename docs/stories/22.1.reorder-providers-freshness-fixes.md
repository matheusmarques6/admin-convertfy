# Story 22.1 -- Reordenar Providers + Freshness Guard + Fixes

## Status
Done

## Story

**Como** sistema de rastreio,
**Quero** que a ordem dos providers seja PostNL -> Cainiao -> TrackingMore -> 17track, com freshness check e timeout,
**Para que** 17track seja chamado apenas como ultimo recurso e chamadas desnecessarias sejam evitadas.

**ANTES:**

## Acceptance Criteria

### 22.1.1 -- Freshness guard em syncTrackingCode()

- [ ] Antes de chamar `trackWithBestProvider()`, verificar se dados sao frescos
- [ ] Implementar funcao `isWithinFreshness(lastCheckedAt: string, status: string | null): boolean`
- [ ] Thresholds por status:

| Status | Threshold |
|--------|-----------|
| `pending` / `info_received` | 6 horas |
| `in_transit` | 4 horas |
| `out_for_delivery` | 30 minutos |
| `delivered` | 30 dias |
| `exception` / `expired` | 24 horas |
| Status desconhecido / null | fallback para `pending` (6h) |

- [ ] Se dados frescos: logar `log.info("Skipping sync, data is fresh", { trackingCodeId, status, lastCheckedAt, thresholdMs })` e retornar sem chamar APIs
- [ ] Se dados stale ou nunca sincronizados (`last_checked_at` null): continuar normalmente

```typescript
// Freshness guard (NOVO -- antes da linha 509):
const FRESHNESS_MS: Record<string, number> = {
  pending:          6 * 3600_000,
  info_received:    6 * 3600_000,
  in_transit:       4 * 3600_000,
  out_for_delivery: 30 * 60_000,
  delivered:        30 * 86400_000,
  exception:        24 * 3600_000,
  expired:          24 * 3600_000,
}

function isWithinFreshness(lastCheckedAt: string | null, status: string | null): boolean {
  if (!lastCheckedAt) return false
  const threshold = FRESHNESS_MS[status || "pending"] ?? FRESHNESS_MS.pending
  return Date.now() - new Date(lastCheckedAt).getTime() < threshold
}

// Em syncTrackingCode(), apos buscar o code:
```

### Nota: Timeout real do 17track

`trackVia17track()` faz 2 fetches sequenciais (register + gettrackinfo) com 300ms de sleep entre eles.
Com AbortController de 8s em cada fetch, o worst case e ~16.3s (8s + 0.3s + 8s).
Somado aos 3 providers anteriores (3x8s = 24s worst case), o pior caso total e ~40s.
Em Vercel Pro (60s timeout), cabe, mas e apertado para o batch `syncAllPendingCodes()`.
Na pratica, providers respondem em < 2s ou fazem timeout. Monitorar via logs de latencia.

### Nota: Cainiao para todos os tracking numbers

Ao remover `isChinese`, Cainiao tentara para tracking brasileiros, europeus, americanos etc.
Cainiao responde rapido com null para tracking nao-chineses (~200-500ms).
Risco baixo de latencia, mas monitorar via logs se Cainiao retorna dados INCORRETOS
para carriers como DHL/UPS (falso positivo). Se isso acontecer, adicionar blocklist.

### Conflito YT prefix (Yanwen vs YunExpress)

A funcao `detectCarrierProvider()` (carriers.ts) checa Yanwen: `/^(LP|LV|UG|YT|YW)\d{9}(YP|CN)$/`
A funcao `detectCarrier()` (tracking.service.ts) checa YunExpress: `tn.startsWith("YT")`

Na pratica: `YT1234567890CN` bate Yanwen (regex completo) ANTES de YunExpress (prefix simples) porque `detectCarrierProvider` e chamada primeiro no cascade. Nao ha conflito real no fluxo de execucao.
