# Story 50.6 — Webhook: Update Handler para Refund Completion

## Story

**Como** sistema que recebe webhooks do Asaas quando um reembolso e processado,
**Quero** que o handler PAYMENT_REFUNDED atualize o registro de refund e determine se a invoice foi totalmente reembolsada,
**Para que** o status da invoice e dos refunds reflita corretamente o que aconteceu no Asaas.

## Contexto

O webhook handler em `src/app/api/integrations/asaas/webhook/route.ts` ja trata o evento `PAYMENT_REFUNDED` (linha 77) chamando `handlePaymentEvent(payload)` que atualiza `invoices.status`.

Esta story **adiciona** uma chamada a `handleRefundCompletion(payload)` que:
1. Atualiza o refund record de 'requested' para 'processed'
2. Cria refund retroativo se nao houve trigger admin previo
3. Verifica se a invoice foi totalmente reembolsada (para partial refunds, o status pode permanecer 'paid')

### Codigo atual (linha 77-80)

```typescript
case "PAYMENT_REFUNDED":
case "PAYMENT_DELETED":
  await handlePaymentEvent(payload)
  break
```

### Codigo desejado

```typescript
case "PAYMENT_REFUNDED":
  await handlePaymentEvent(payload)      // ja existe — atualiza invoice.status
  await handleRefundCompletion(payload)   // NOVO — atualiza refunds + checa total
  break
case "PAYMENT_DELETED":
  await handlePaymentEvent(payload)
  break
```

**IMPORTANTE**: Separar PAYMENT_REFUNDED de PAYMENT_DELETED no switch/case. Antes estavam agrupados — agora PAYMENT_REFUNDED tem logica adicional.

### Referencia: Arquitetura

Ver secao 5.2 de `docs/architecture/refund-processing-architecture.md`.

## Acceptance Criteria

### AC 50.6.1 — Separar PAYMENT_REFUNDED de PAYMENT_DELETED

- [ ] No switch/case do webhook handler, separar os dois eventos
- [ ] PAYMENT_REFUNDED: `handlePaymentEvent` + `handleRefundCompletion`
- [ ] PAYMENT_DELETED: apenas `handlePaymentEvent` (sem mudanca)

### AC 50.6.2 — Criar funcao handleRefundCompletion

- [ ] Adicionar funcao `handleRefundCompletion(payload)` no mesmo arquivo do webhook
- [ ] Importar `handleAsaasRefundWebhook` de `@/lib/services/refund.service`
- [ ] Extrair `asaasPaymentId` e `refundedValue` do payload
- [ ] Chamar `handleAsaasRefundWebhook({ asaasPaymentId, refundedValue })`

```typescript
async function handleRefundCompletion(payload: AsaasWebhookPayload) {
  const payment = payload.payment
  if (!payment) return

  await handleAsaasRefundWebhook({
    asaasPaymentId: payment.id,
    refundedValue: payment.value,  // Asaas envia o valor total do payment
  })
}
```

### AC 50.6.3 — Ajustar logica de status na handlePaymentEvent (se necessario)

- [ ] Verificar que `handlePaymentEvent` NAO seta incondicionalmente `status = 'refunded'` para PAYMENT_REFUNDED
- [ ] Se a logica atual seta status baseado no mapping `mapAsaasStatusToInternal()` (REFUNDED -> refunded), isso pode conflitar com partial refunds
- [ ] Para partial refunds, o `handleAsaasRefundWebhook` (no service) e que determina se o status final deve ser 'refunded' ou permanecer 'paid'
- [ ] Se `handlePaymentEvent` seta status incondicionalmente, **ajustar**: mover a decisao de status para o `handleRefundCompletion`, ou fazer `handlePaymentEvent` nao alterar status quando evento e PAYMENT_REFUNDED (delegar ao service)

**NOTA para o dev**: Este AC requer leitura cuidadosa do `handlePaymentEvent` existente. O comportamento correto e:
- Partial refund: status permanece 'paid' (service decide)
- Full refund: status muda para 'refunded' (service decide)
- Se `handlePaymentEvent` ja seta 'refunded' antes do service rodar, pode causar inconsistencia

### AC 50.6.4 — Idempotencia

- [ ] Se o webhook chega duplicado, o service usa `INSERT ... ON CONFLICT (asaas_refund_id) DO NOTHING`
- [ ] Nenhum erro deve ser lancado em caso de duplicata — operacao e silenciosamente ignorada
- [ ] Log info quando duplicata e detectada: `[Refund Webhook] Duplicate webhook for asaas_refund_id ${id} — skipping`

### AC 50.6.5 — Error handling no webhook

- [ ] Se `handleRefundCompletion` falhar, o erro NAO deve impedir o response 200 ao Asaas
- [ ] Wrap em try/catch: log error e continuar (Asaas reenviara o webhook se receber non-200)
- [ ] Ou: tratar como error silencioso e deixar o Asaas reenviar

```typescript
case "PAYMENT_REFUNDED":
  await handlePaymentEvent(payload)
  try {
    await handleRefundCompletion(payload)
  } catch (error) {
    console.error('[Refund Webhook] Error processing refund completion:', error)
    // Nao re-throw — Asaas reenviara se necessario
  }
  break
```

## Riscos

| Risco | Mitigacao |
|-------|----------|
| handlePaymentEvent seta status 'refunded' incondicionalmente para partial refunds | AC 50.6.3 cobre este caso — dev deve analisar e ajustar |

| payload.payment.value pode ser o valor total (nao o refunded) | Verificar documentacao Asaas — se necessario, calcular a partir de outros campos |
