## Contexto

O QA finding H3 identifica um problema critico: o portal dashboard faz HTTP self-call para buscar dados Shopify:

```typescript
// src/app/api/portal/dashboard/route.ts (linhas 458-472)
const shopifyResponse = await fetch(
  `${baseUrl}/api/integrations/shopify/report?store_id=${store.id}&period=${period}`,
  { headers: { Cookie: cookieHeader } }
)
```

Problemas com este approach:
1. **Round-trip desnecessario**: request HTTP para o mesmo servidor (latencia extra ~50-100ms)
2. **Cookie forwarding fragil**: se auth mudar (token rotation, SameSite), quebra silenciosamente
3. **Rate limiting self-inflicted**: conta como request contra rate limits internos
4. **Serverless cold start**: pode triggar outro cold start no Vercel

A boa noticia e que `generateShopifyReport()` ja foi extraido para `src/lib/integrations/shopify/report.ts` (nota no cabecalho desse arquivo: "Extracted from the API route handler so it can be called directly"). Porem o portal AINDA usa o HTTP self-call em vez de importar diretamente.

---

## Objetivo

Eliminar o HTTP self-call no portal dashboard substituindo por import direto de `generateShopifyReport()`, e garantir que o service esteja preparado para ser chamado pelo live fallback (Stories 10.5/10.6).

  import { generateShopifyReport, ShopifyFullReportData } from "@/lib/integrations/shopify/report"
  import { SyncResult } from "@/lib/shared/data-status"

  export async function syncShopifyForStore(
    storeId: string,
    period: string,
    options?: { customStartDate?: string; customEndDate?: string },
  ): Promise<SyncResult<ShopifyFullReportData>> {
    try {

        customStartDate: options?.customStartDate || null,
        customEndDate: options?.customEndDate || null,

        data: data.success && data.connected ? data : null,
        source: "live",
        fetchedAt: new Date().toISOString(),
      }
    } catch (err) {
      return {
        success: false,
        data: null,
        error: err instanceof Error ? err.message : "Unknown Shopify error",
        source: "live",
        fetchedAt: new Date().toISOString(),
      }
    }
  }

## Arquitetura Tecnica

### Antes vs Depois

```
ANTES:
  Portal Dashboard → HTTP fetch() → /api/integrations/shopify/report → generateShopifyReport()
                                                                          ↑
                                                            (round-trip desnecessario)

DEPOIS:
  Portal Dashboard → syncShopifyForStore() → generateShopifyReport()
                     (import direto, zero HTTP overhead)
```

### Novo Arquivo: `src/lib/services/shopify-sync.service.ts`

Wrapper fino sobre `generateShopifyReport` que:
1. Retorna `SyncResult<T>` padronizado
2. Trata erros com mensagens explicitas
3. Sera reutilizado por Stories 10.5/10.6 para live fallback

### Cache Behavior

O cache Shopify (via `dashboard_cache` table) permanece inalterado:
- Portal checa `dashboard_cache` primeiro
- Se miss, chama `syncShopifyForStore()` → salva em `dashboard_cache`
- Este e o comportamento atual, apenas sem HTTP self-call

**Nota M1:** Shopify usa `dashboard_cache` (nao `store_revenue_summary`). Isso e intencional:
- `store_revenue_summary` so tem `shopify_total_revenue` (campo unico vindo do Klaviyo metric-aggregates)
- Shopify full report (orders, products, customers) e muito mais detalhado
- `dashboard_cache` persiste o JSON completo do report
