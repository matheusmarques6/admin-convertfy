## Contexto

Dois problemas de performance identificados:

**1. Query duplicada de meetings em `stores/control/route.ts`:** A mesma query de meetings eh executada duas vezes (linhas 169-179 para summary e 287-299 para enrichment). Ambas buscam meetings do mesmo escopo e podem ser consolidadas em uma unica chamada.

**2. Metadados Klaviyo sem cache:** As funcoes `getAccountInfo()` e `findPlacedOrderMetric()` sao chamadas para cada loja em cada request. Esses metadados mudam rarissimamente (timezone da conta e ID da metrica "Placed Order") mas consomem 2 API calls por loja por request. Com 30 lojas, sao 60 calls desperdicadas.

---

## Objetivo

1. Consolidar as queries de meetings em `stores/control/route.ts` em uma unica chamada
2. Implementar cache para `getAccountInfo()` e `findPlacedOrderMetric()` com TTL de 30 minutos

## Arquitetura Tecnica

### Meetings - Consolidacao

A query de meetings deve ser extraida para uma chamada no inicio do handler, e o resultado passado como parametro para as funcoes de summary e enrichment.

```typescript
// Buscar meetings UMA VEZ
const { data: meetingsData } = await supabase
  .from('meetings')
  .select('client_id, status, date')
  .eq('status', 'completed')
  .order('date', { ascending: false })

// Construir map de last meeting por client
const lastMeetingByClient = new Map<string, string>()
if (meetingsData) {
  for (const m of meetingsData) {
    if (m.client_id && !lastMeetingByClient.has(m.client_id)) {
      lastMeetingByClient.set(m.client_id, m.date)
    }
  }
}

// Usar lastMeetingByClient tanto no summary quanto no enrichment
```

### Metadados Klaviyo - Cache via dashboard_cache

```typescript
// Em src/lib/integrations/klaviyo/index.ts ou arquivo dedicado

import { getCache, setCache } from "@/lib/cache"
import { createAdminClient } from "@/lib/supabase/server"

export async function getCachedAccountInfo(
  apiKey: string,
  orgId?: string
): Promise<AccountInfo> {
  const supabase = createAdminClient()
  const cacheKey = hashApiKey(apiKey) // SHA256 parcial para nao expor key

  const cached = await getCache<AccountInfo>(supabase, cacheKey, "klaviyo_metadata", "account_info")
  if (cached) return cached.data

  const accountInfo = await getAccountInfo(apiKey)
  await setCache(supabase, cacheKey, "klaviyo_metadata", "account_info", accountInfo as any, orgId)
  return accountInfo
}

export async function getCachedPlacedOrderMetric(
  apiKey: string,
  orgId?: string
): Promise<string | null> {
  const supabase = createAdminClient()
  const cacheKey = hashApiKey(apiKey)

  const cached = await getCache<{ metricId: string }>(supabase, cacheKey, "klaviyo_metadata", "placed_order_metric")
  if (cached) return cached.data.metricId

  const metricId = await findPlacedOrderMetric(apiKey)
  if (metricId) {
    await setCache(supabase, cacheKey, "klaviyo_metadata", "placed_order_metric", { metricId }, orgId)
  }
  return metricId
}

function hashApiKey(apiKey: string): string {
  // Usar primeiros/ultimos chars + hash para identificacao sem expor
  return `kl_${apiKey.slice(-8)}`
}
```

**Nota:** Usar `createAdminClient()` aqui eh aceitavel porque o cache de metadados eh por API key (nao por user), e a funcao eh chamada pelo cron e pelo backend, nunca exposta diretamente ao usuario.

## Riscos e Mitigacoes

| Risco | Mitigacao |
|-------|-----------|
| Cache de metadados com key errada serve dados de outra conta | Cache key usa hash da API key, que eh unica por conta Klaviyo |
| Metadados mudam (ex: timezone) e cache serve valor antigo | TTL de 30min limita staleness; mudancas de timezone sao extremamente raras |
