## Story

**Como** administrador do sistema,
**Quero** que todas as rows em klaviyo_campaign_metrics e klaviyo_flow_metrics tenham org_id preenchido,
**Para que** as RLS policies funcionem corretamente e dados nao fiquem invisiveis para queries com user RLS client.

---

## Contexto

A investigacao revelou que **100% dos rows** nas tabelas de metricas Klaviyo tem `org_id = NULL`:

| Tabela | Rows com org_id NULL | Rows com org_id |
|--------|---------------------|-----------------|
| klaviyo_campaign_metrics | 67 (100%) | 0 |
| klaviyo_flow_metrics | 863 (100%) | 0 |
| store_revenue_summary | 0 | 8 (OK) |

As RLS policies usam: `(org_id = current_org_id()) OR can_access_store(store_id)`

Com org_id NULL, a comparacao `NULL = current_org_id()` sempre retorna falso.
O fallback `can_access_store()` depende de `org_members`, que portal users puros nao tem.

Atualmente o portal usa `adminClient` (service role) que bypassa RLS, entao o impacto
e indireto. Porem e um bug de dados que pode causar problemas futuros e ja quebra
qualquer query via user RLS client.

---

## Causa Raiz

Existem **dois code paths** que inserem dados sem `org_id`:

### Path 1: Portal live fallback (`savePerfDataToCache`)
`src/lib/services/sync-persistence.service.ts` — funcao `savePerfDataToCache()` (linhas 125-162)
constroi rows de campaign e flow SEM incluir `org_id`, embora o parametro `orgId` seja recebido.
Apenas `store_revenue_summary` recebe `org_id` (linha 105).

Chamada em `src/app/api/portal/dashboard/route.ts:369`:
```typescript
savePerfDataToCache(createAdminClient(), store.id, store.org_id || null, period, perfData, startDateStr, endDateStr).catch(() => {})
```

### Path 2: Cron sync (`upsertSyncResults`)
`src/lib/services/sync-persistence.service.ts` — funcao `upsertSyncResults()` (linhas 35-46)
recebe `data.flowRows` e `data.campRows` do `klaviyo-sync.service.ts`. Os tipos `FlowMetricRow`
(linha 38) e `CampaignMetricRow` (linha 66) em `klaviyo-sync.service.ts` NAO incluem campo `org_id`.
Todo row inserido via cron tera `org_id = NULL`.

## Criterios de Aceitacao

- [ ] **CA1**: Todas as rows em `klaviyo_campaign_metrics` com org_id NULL sao atualizadas
      com o org_id correto (derivado de `client_stores.org_id` via `store_id`)
- [ ] **CA2**: Todas as rows em `klaviyo_flow_metrics` com org_id NULL sao atualizadas
      com o org_id correto
- [ ] **CA3**: `savePerfDataToCache()` inclui `org_id` em todos os upserts de campaign e flow metrics
- [ ] **CA4**: `upsertSyncResults()` (path do cron) inclui `org_id` nos rows de campaign e flow.
      Tipos `FlowMetricRow` e `CampaignMetricRow` em `klaviyo-sync.service.ts` devem incluir `org_id`
- [ ] **CA5**: Migration de backfill aplicada e verificada (zero rows com org_id NULL)
- [ ] **CA6**: NOT NULL constraint adicionada em migration SEPARADA, apos verificar que todos os
      callers estao corrigidos (CA3 + CA4). Aplicar somente quando backfill + code fix estiverem em prod
- [ ] **CA7**: Migration e reversivel (DOWN migra de volta se necessario)

## Tarefas

- [ ] T1: Ler `src/lib/services/sync-persistence.service.ts` e identificar onde org_id e (ou nao e) passado
- [ ] T2: Ler o cron sync que popula essas tabelas e verificar se tambem omite org_id
- [ ] T3: Criar migration SQL para backfill org_id usando JOIN com client_stores:
      ```sql
      UPDATE klaviyo_campaign_metrics kcm
      SET org_id = cs.org_id
      FROM client_stores cs
      WHERE kcm.store_id = cs.id AND kcm.org_id IS NULL;
      ```

- [ ] T5: Corrigir `upsertSyncResults()` e tipos `FlowMetricRow`/`CampaignMetricRow` em
      `src/lib/services/klaviyo-sync.service.ts` para incluir org_id
- [ ] T6: Criar segunda migration (aplicar APOS deploy do code fix): NOT NULL constraint
- [ ] T7: Verificar com query que nao restam rows com org_id NULL
- [ ] T8: Rodar typecheck + lint
