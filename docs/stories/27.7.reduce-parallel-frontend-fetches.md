## Story

**Como** sistema que consome a API Klaviyo via multiplos endpoints,
**Quero** que o frontend nao dispare chamadas desnecessarias quando o cache ja tem dados,
**Para que** o rate limit do Klaviyo nao seja atingido em cascata e os dados carreguem de forma confiavel.

---

## Contexto

O hook `useStorePerformance` dispara 3 requests **paralelos**:
1. `useKlaviyoCampaigns()` → `/api/integrations/klaviyo/campaigns`
2. `useKlaviyoFlows()` → `/api/integrations/klaviyo/flows`
3. `useKlaviyoReport()` → `/api/integrations/klaviyo/report`

Quando o cache esta populado (apos stories 27.1-27.3), todos retornam do cache e nao ha problema.

Mas quando o cache esta vazio ou stale, os 3 endpoints fazem live fetch ao Klaviyo **simultaneamente**, disparando ~9 chamadas API (3 endpoints × ~3 calls cada). Com rate limit de ~1 req/s, pelo menos 6 desses requests vao ser rate-limited, causando erro em cascata.

---

## Acceptance Criteria

### 27.7.1 — Avaliar necessidade dos 3 endpoints separados

- [ ] Verificar se o endpoint `/api/integrations/klaviyo/report` ja retorna dados suficientes para eliminar a necessidade de chamar campaigns e flows separadamente
- [ ] Se sim: refatorar `useStorePerformance` para usar apenas 1 endpoint
- [ ] Se nao: manter 3 endpoints mas implementar stagger (27.7.2)

### 27.7.2 — Stagger frontend requests (se manter 3 endpoints)

- [ ] No hook `useStorePerformance`, implementar cascata:
  1. Fetch campaigns primeiro
  2. Quando campaigns retorna, fetch flows
  3. Quando flows retorna, fetch report
- [ ] Usar SWR `dependency` pattern ou `useSWR` com key condicional
- [ ] Manter loading progressivo (mostrar campanhas antes dos flows)

### 27.7.3 — Dedup SWR mais agressivo

- [ ] Aumentar `dedupingInterval` de SWR para campanhas/flows de 60s para 300s (5 min) — alinhado com `PORTAL_STALENESS_MS`
- [ ] **NAO** usar `revalidateOnMount: false` globalmente — isso impede o fetch no primeiro mount quando nao ha dados anteriores. Se necessario, usar condicionalmente: `revalidateOnMount: !hasPreviousData`
- [ ] Verificar que `errorRetryCount: 2` esta configurado (evitar retry storms)

### 27.7.4 — Cache-hit fast path no backend

- [ ] Nos endpoints de campaigns e flows, quando cache hit acontece (`fromCache: true`):
  - Garantir que nenhuma chamada externa e feita (apenas DB read)
  - Adicionar header `X-Cache: HIT` para debug
- [ ] Quando cache miss:
  - Adicionar header `X-Cache: MISS`
  - Log com tempo de live fetch
- [ ] **Nota**: NAO definir threshold de tempo (<50ms) — latencia depende de Supabase e nao e controlavel. O objetivo e minimizar, nao garantir.

## Notas Tecnicas

- Apos stories 27.1-27.3, o cache hit rate deve ser ~100% para periodos padrao. Esta story e uma camada de protecao para quando cache miss inevitavel acontecer (primeiro load, custom period).
- O SWR `keepPreviousData: true` ja esta configurado — o usuario ve dados antigos enquanto revalida. O stagger nao afeta UX perceptivelmente.
- Headers `X-Cache` sao uteis para debug em produção mas nao devem expor informacao sensivel.
