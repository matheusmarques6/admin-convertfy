## Story

**Como** sistema que calcula date ranges para queries Klaviyo,
**Quero** que todos os endpoints usem `parseDateRangeInTimezone()` com o timezone da conta Klaviyo,
**Para que** datas calculadas sejam consistentes entre cron e live endpoints, evitando mismatch de 1 dia.

---

## Contexto

Existem duas funcoes para calcular date ranges:

| Funcao | Onde usa | Timezone |
|--------|----------|----------|
| `parseDateRangeInTimezone(period, tz)` | Cron sync | Timezone da conta Klaviyo (ex: `America/Sao_Paulo`) |
| `parseDateRange(period)` | Live campaigns, flows, report endpoints | UTC do servidor (Vercel) |

No Vercel (UTC), para uma conta em `America/Sao_Paulo` (UTC-3):
- Entre 00:00-02:59 UTC (21:00-23:59 SP), `parseDateRange("30d")` calcula "hoje" como dia UTC, que e "amanha" em Sao Paulo.
- Resultado: `period_start` e `period_end` diferem em **1 dia** entre cron e live.

Mesmo com a story 27.1 (cache lookup por `period_label`), o mismatch de timezone ainda afeta:
- Os timestamps enviados a API Klaviyo (janela de dados diferente)
- O `period_start`/`period_end` gravados no cache (inconsistencia entre rows do cron e live)

### Arquivos afetados

- `src/app/api/integrations/klaviyo/flows/route.ts` (usa `parseDateRange`)

## Notas Tecnicas

- `getCachedAccountInfo(apiKey)` ja faz cache em memoria (Map) por apiKey. Nao ha custo adicional em chama-la.
- A funcao `parseDateRangeInTimezone(period, timezone)` retorna `{ startDate, endDate }` como strings `YYYY-MM-DD` no timezone especificado. Verificar se tambem aceita `customStartDate`/`customEndDate` como parametros (os endpoints passam esses para `parseDateRange`).
- O timezone da conta Klaviyo e tipicamente `America/Sao_Paulo` para lojas BR, mas pode variar. Sempre usar o da conta, nao hardcodar.
- **Ordering**: Nos endpoints, `parseDateRange` e chamado ANTES do cache check (linha ~414 campaigns), mas `getCachedAccountInfo` e chamado DEPOIS (linha ~464, no live fetch path). Com a story 27.1 (cache lookup por `period_label`), `period_start/period_end` so sao necessarios no live fetch path — entao o timezone so precisa ser obtido quando cache miss. Isso resolve o ordering problem.
