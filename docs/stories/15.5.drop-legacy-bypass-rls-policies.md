# Story 15.5 — Drop Legacy Bypass RLS Policies (USING: true / WITH CHECK: true)

## Contexto

Uma auditoria de QA identificou políticas RLS legadas com `USING: true` e/ou `WITH CHECK: true` que concedem acesso irrestrito a qualquer usuário autenticado (ou público, no caso da role `public`).

**Problema central: semântica OR do PostgreSQL em políticas PERMISSIVE**

O PostgreSQL avalia múltiplas políticas PERMISSIVE com semântica OR. Isso significa que **se qualquer política PERMISSIVE retornar `true`, o acesso é concedido** — independentemente de quantas políticas mais restritivas existam. Portanto, as políticas de hardening criadas nas Stories anteriores (15.1, 15.4, etc.) são **completamente anuladas** pela coexistência dessas políticas bypass.

Exemplo do impacto:

```sql
-- Policy hardened (do Epic 15):
CREATE POLICY "clients_insert_org_member" ON clients
  FOR INSERT WITH CHECK (is_org_member());

-- Policy bypass (legacy, ainda existe):
CREATE POLICY "Authenticated users can insert clients" ON clients
  FOR INSERT WITH CHECK (true);  -- ← anula a policy acima completamente
```

O resultado é que qualquer usuário autenticado pode inserir, atualizar ou deletar clientes de qualquer organização, contornando todo o isolamento multi-tenant.

**Tabelas e políticas afetadas identificadas pela auditoria:**

| Tabela | Policy Bypass | Operação | Role | Risco |
|--------|--------------|----------|------|-------|
| `clients` | "Authenticated users can insert clients" | INSERT | `authenticated` | HIGH |
| `clients` | "Authenticated users can delete clients" | DELETE | `authenticated` | HIGH |
| `clients` | "Authenticated users can update clients" | UPDATE | `authenticated` | HIGH |
| `client_stores` | "Allow all on client_stores" | ALL | `public` | HIGH |
| `client_stores` | "Authenticated users can manage client_stores" | ALL | `authenticated` | HIGH |
| `invoices` | "Authenticated users can manage invoices" | ALL | `authenticated` | HIGH |
| `invoices` | "Allow all operations on invoices" | ALL | `public` | HIGH |
| `meetings` | "Authenticated users can manage meetings" | ALL | `authenticated` | HIGH |
| `reports` | "Authenticated users can manage reports" | ALL | `authenticated` | HIGH |

## Objetivo

**Como** engenheiro de segurança,
**Quero** remover todas as políticas RLS com `USING: true` / `WITH CHECK: true` das tabelas de negócio,
**Para que** as políticas de hardening multi-tenant sejam efetivamente aplicadas e o isolamento por `org_id` funcione corretamente.

## Arquitetura Técnica

### Por que políticas PERMISSIVE com `true` são perigosas

No PostgreSQL, quando RLS está habilitado, o acesso a uma linha é determinado por:

```
Acesso concedido SE:
  - Usuário é proprietário da tabela (bypassses RLS), OU
  - Usuário tem BYPASSRLS privilege, OU
  - Qualquer política PERMISSIVE retorna TRUE (para SELECT/USING)
  - Qualquer política PERMISSIVE retorna TRUE (para INSERT/UPDATE/WITH CHECK)
```

A presença de `WITH CHECK (true)` em uma policy PERMISSIVE significa que **qualquer** `WITH CHECK` de qualquer outra policy é ignorado na prática, pois o OR lógico sempre resolve para `true`.

Referência: [PostgreSQL Docs — Row Security Policies](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)

### Políticas de substituição esperadas

**`client_stores`:**

**`invoices`, `meetings`, `reports`:**

## Dev Notes — Semântica OR e Por Que Isso é Crítico

```
Cenário atual (INSEGURO):
  Policy A: "clients_insert_org_member" → WITH CHECK (org_id = get_user_org())
  Policy B: "Authenticated users can insert clients" → WITH CHECK (true)

  Resultado: qualquer usuário autenticado pode inserir em clients de QUALQUER org
  porque Policy B retorna true e PostgreSQL faz: (false OR true) = true

Cenário após a fix (SEGURO):
  Policy A: "clients_insert_org_member" → WITH CHECK (org_id = get_user_org())

  Resultado: apenas membros da org correta podem inserir
```

Esta é uma vulnerabilidade de controle de acesso crítica em sistemas multi-tenant. O isolamento por `org_id` que protege dados de clientes entre agências diferentes está completamente comprometido enquanto essas políticas bypass existirem.
