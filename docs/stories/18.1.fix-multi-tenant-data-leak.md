## Story

**Como** usuario do portal do cliente,
**Quero** que meus dados sejam visiveis APENAS para mim,
**Para que** nenhum outro cliente consiga ver receita, campanhas, flows ou faturas da minha loja.

## Contexto

### Problema Observado
O portal do cliente mostra dados de lojas de OUTROS clientes. Vazamento de dados multi-tenant.

### Causa Raiz (Auditoria 2026-03-05)

3 problemas combinados:

**P1 - 11 RLS policies legacy com `USING(true)`**
Tabelas criticas (`client_stores`, `clients`, `client_portal_users`, `invoices`, `client_charges`,
`client_subscriptions`, `client_reports`) possuem policies PERMISSIVE com `USING(true)` que
anulam TODAS as policies de isolamento corretas (PostgreSQL usa OR para PERMISSIVE policies).

**P2 - Portal usa `adminClient` (service role) para queries de dados**
`src/app/api/portal/dashboard/route.ts` usa `createAdminClient()` que bypassa RLS.
Mesmo com RLS correto, o service role ignora tudo.

**P3 - `dashboard_cache` SELECT permite cross-org**
Policy usa `is_org_member()` sem filtrar QUAL org -- qualquer membro de qualquer org le todo cache.

### O que JA esta correto
- API routes do portal filtram por `client_id` no codigo aplicacional
- `store_id` e validado contra lojas do cliente antes do uso
- Tabelas `klaviyo_*_metrics` e `store_revenue_summary` tem policies RLS corretas
- Policies hardened existem em `client_stores`, `clients`, `client_portal_users` (mas sao anuladas pelas legacy)

#### GAP-2: CRITICO -- `invoices` route QUEBRARA para portal users apos P0-Step 2

`src/app/api/portal/invoices/route.ts` usa `supabase` (createClient / user RLS) para:
1. Buscar `client_portal_users` (linha 26) -- OK, coberto por `auth_user_id = auth.uid()`
2. Buscar `invoices` (linha 48-64) -- **QUEBRARA**
3. Buscar `integrations` (linha 72-77) -- Funciona por acaso (bypass `integrations` nao e dropada)
4. Inserir `client_portal_activity` (linha 183) -- Falha silenciosamente (tabela nao existe)

Apos dropar a bypass `"Allow all operations on invoices"` e `"Authenticated users can manage invoices"`,
as policies restantes sao:
- `"Access invoices by client"`: requer `can_access_client(client_id)` -- portal users NAO sao org_members, retorna FALSE
- `"Admin can manage invoices"`: requer `is_admin()` ou `is_org_owner()` -- FALSE para portal
- `"Users can view invoices"`: requer `is_admin()` ou `can_access_client()` -- FALSE para portal

**Resultado:** Portal users verao 0 invoices apos P0-Step 2. O plano NAO trata este caso.

**Fix necessario (ANTES de P0-Step 2):** Uma das opcoes:
- (A) Migrar `invoices/route.ts` para usar `adminClient` em vez de `supabase` (mais seguro, consistente com outras rotas portal)
- (B) Criar RLS policy para portal users: `CREATE POLICY "portal_invoices_select" ON invoices FOR SELECT TO authenticated USING (client_id IN (SELECT client_id FROM client_portal_users WHERE auth_user_id = auth.uid() AND is_active = true))`

Opcao (A) e preferivel por consistencia com o padrao das demais rotas portal.

A rota de invoices (linha 72) consulta `integrations` via `supabase` sem `org_id` --

O plano cobre apenas as tabelas que o portal acessa diretamente. As demais tabelas
sao igualmente vulneraveis a leitura cross-org por qualquer usuario autenticado
(incluindo portal users via Supabase JS client no browser).

**Recomendacao:** Incluir estas tabelas no P2-Step 3 (auditoria completa) e criar
um Story separado (18.2?) para remediacao sistematica das tabelas admin-only.

#### GAP-5: MEDIO -- Settings routes usam `supabase` para `client_notification_preferences`

`settings/route.ts` (linha 45) e `settings/notifications/route.ts` (linha 75) usam
`supabase` para operar em `client_notification_preferences`. Esta tabela NAO EXISTE
no banco (apenas `notification_preferences` existe, com policies `user_id = auth.uid()`).

**Impacto:** Estas queries ja falham silenciosamente HOJE. Nao e um risco de seguranca,
mas indica dead code / feature nao funcional. Deve ser documentado como tech debt.

#### GAP-6: MEDIO -- `client_portal_activity` tabela NAO EXISTE

A tabela `client_portal_activity` nao existe no banco de dados. Todas as insercoes
nesta tabela (em auth, change-password, invoices, dashboard, report) falham silenciosamente.

O P2-Step 1 propoe criar uma policy para esta tabela, mas a tabela em si nao existe.
O step precisa incluir `CREATE TABLE` antes de `CREATE POLICY`.

### 3. Analise de Sequencia e Dependencias

**P0-Step 1 antes de P0-Step 2: CORRETO e CRITICO.**
Confirmado que sem o fix no auth POST, o login portal quebraria imediatamente.

**P0-Step 2 e P0-Step 3 em paralelo: SEGURO.**

- P0-Step 2 COM P0-Step 1: QUEBRA invoices portal (GAP-2). NAO documentado.
- P0-Step 3 sozinho: SEGURO. `client_reports`, `client_charges`, `client_subscriptions` nao
  sao acessados pelo portal via user RLS.

### 6. Riscos Adicionais Identificados

**R4 (nao mapeado):** `client_reports` ja tem policies hardened (`org_client_reports_*`).
O plano propoe criar novas policies (`client_reports_select/insert/delete`) que seriam
duplicatas. Isto cria confusao e policies sobrepostas. Verificar antes de executar.

**R5 (nao mapeado):** A policy `"Users can update client reports"` em `client_reports`
(roles: public, cmd: UPDATE, qual: `auth.role() = 'authenticated'`) tambem e uma bypass
disfaracada -- permite UPDATE a qualquer authenticated user. Nao e dropada no plano.

**R6 (nao mapeado):** `dashboard_cache` tem policy `"Users can access cache for their
client stores"` (roles: public, cmd: ALL) que faz JOIN com `client_portal_users`.
Se a bypass de `client_portal_users` for removida, este JOIN pode ser impactado
dependendo de como o Postgres avalia policies recursivamente.
