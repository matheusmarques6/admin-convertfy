# Story 12.1 — Briefing gerado pelo N8N não aparece na UI

## User Story

**Como** agente de onboarding (COO/gestor),
**quero** que o briefing gerado pelo N8N apareça automaticamente na aba Briefing da loja
**para que** eu possa validar e utilizar o briefing sem precisar recarregar manualmente a página ou investigar o banco de dados.

---

## Contexto

O fluxo de geração de briefing é:

```
COO aprova onboarding
  → onboardingPhaseService.transition("generating_copies")
    → n8nTriggerService.triggerCopyGeneration(callback_url: APP_URL/api/onboarding/webhook)
      → N8N processa (IA gera briefing)
        → POST /api/onboarding/webhook { type: "briefing_generated", data: BriefingData }
          → Salva em store_briefings com status: "current" ✅
            → UI NÃO ATUALIZA ❌
```

O dado chega ao banco corretamente. O problema está em 4 camadas: (1) a UI não escuta mudanças, (2) possível incompatibilidade de estrutura entre o que o N8N envia e o que o tipo `BriefingData` espera, (3) o `callback_url` pode estar inacessível pelo N8N em certos ambientes, e (4) o `callback_secret` é enviado no body pelo serviço mas o webhook exige no header `X-Webhook-Secret`.

```typescript

  setLoading(true)
  // ... fetch
}, [storeId])

// DEPOIS — silent=true omite setLoading(true), atualiza briefing em background

  if (!silent) setLoading(true)
  // ... fetch (setLoading(false) no finally sempre executa)
}, [storeId])
```

Adicionar polling condicional usando fetch silencioso:

```typescript
// ANTES — fetch apenas no mount

  fetchBriefing()
}, [fetchBriefing])

// DEPOIS — polling de 10s enquanto sem briefing, sem spinner
useEffect(() => {
  fetchBriefing()
}, [fetchBriefing])

useEffect(() => {
  if (briefing !== null) return // já tem briefing, não pollar
  if (loading) return           // aguarda fetch inicial

  const interval = setInterval(() => {
    fetchBriefing(true) // silent=true: sem setLoading, sem spinner
  }, 10_000)

  return () => clearInterval(interval)
}, [briefing, loading, fetchBriefing])
```

## Arquitetura Tecnica

### Contrato N8N → Webhook

O N8N deve chamar o callback com:

```http
POST {APP_URL}/api/onboarding/webhook
X-Webhook-Secret: {valor de ONBOARDING_WEBHOOK_SECRET}
Content-Type: application/json

{
  "onboarding_id": "uuid-do-onboarding",
  "type": "briefing_generated",
  "data": {
    "dados_loja": {
      "nome": "Loja Exemplo",
      "url": "https://loja.myshopify.com",
      "plataforma": "shopify",
      "nicho": "moda feminina",
      "pais": "BR",
      "idioma": "pt-BR",
      "frete_gratis": "acima de R$150"
    },
    "codigo_colaborador": {
      "shopify_code": null
    },
    "materiais_identidade": {
      "logo_url": null,
      "design_direction": "minimalista",
      "design_file_url": null,
      "brand_manual_url": null
    },
    "foco_campanhas": {
      "abordagem": "remarketing",
      "descricao": "Foco em recuperacao de carrinhos abandonados e recompra"
    },
    "publico": {
      "target_audience": "mulheres 25-40 anos",
      "price_sensitivity": "balanced",
      "perfil": "Consumidoras que buscam moda casual com custo-beneficio"
    },
    "perfil_marca": {
      "tipo": "lifestyle",
      "descricao": "Marca que conecta estilo de vida com praticidade"
    },
    "detalhes_adicionais": {
      "notas": null,
      "conceito_frete": null
    },
    "resumo_performance": {},
    "analise_anuncios": {}
  }
}
```

**IMPORTANTE:** O campo `callback_secret` é enviado no body do trigger pelo backend (para que o N8N possa lê-lo), mas deve ser retransmitido como header `X-Webhook-Secret` no callback. O endpoint rejeita requests sem esse header com `401`.

### Polling Strategy

- Intervalo: 10 segundos (evita rate limit, N8N tipicamente processa em 30-120s)
- Condição de parada: `briefing !== null`
- Cleanup: `clearInterval` no return do `useEffect`
- Sem Supabase Realtime para esta story (Realtime adicionaria complexidade de subscriptions desnecessária para um evento de baixa frequência)

### Variavel de Ambiente

| Variavel | Uso | Prioridade |
|----------|-----|-----------|
| `APP_URL` | Server-side, para callback_url | 1 (preferida) |
| `NEXT_PUBLIC_APP_URL` | Client + server, existente no projeto | 2 (fallback) |

Em producao, definir `APP_URL` com a URL publica da aplicacao (ex: `https://admin.convertfy.com`).

## Notas de Implementacao

### Causa Raiz Principal (Causa 1)
O `useEffect` em `store-briefing-tab.tsx` (linha 40-42) faz fetch unico no mount. Como o N8N pode demorar entre 30 segundos e varios minutos para processar, o usuario abre a aba e ve o estado vazio permanentemente. A solucao de polling de 10s e intencional — Supabase Realtime seria overkill para um evento de baixa frequencia (uma geracao de briefing por onboarding).

### Causa Raiz Secundaria (Causa 4)
Em `n8n-trigger.service.ts` linha 92, o `callback_secret` e enviado no body do payload enviado ao N8N. O endpoint `/api/onboarding/webhook` linha 24 exige o secret no **header** `X-Webhook-Secret`. Isso significa que o N8N precisa extrair `callback_secret` do body recebido e repassar como header `X-Webhook-Secret` no callback. Esta e uma convencao comum em N8N — o workflow N8N deve ser configurado para isso. Nao ha mudanca de codigo necessaria aqui, apenas documentacao e confirmacao com o time de N8N.

### Por que `APP_URL` ao inves de apenas `NEXT_PUBLIC_APP_URL`
Variaveis `NEXT_PUBLIC_*` sao expostas no bundle do cliente (Next.js as injeta em tempo de build). Para URLs de callback server-to-server, e melhor usar uma variavel exclusivamente server-side (`APP_URL`) que pode diferir do URL publico em alguns deploys. O fallback garante compatibilidade retroativa.
