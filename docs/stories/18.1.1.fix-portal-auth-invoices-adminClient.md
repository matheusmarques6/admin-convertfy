## Story

**Como** usuario do portal do cliente,
**Quero** que o login e as faturas funcionem corretamente mesmo apos a remocao das bypass policies,
**Para que** o sistema possa ser protegido contra vazamento de dados sem quebrar funcionalidades.

---

## Contexto

### Problema

Duas rotas portal usam `supabase` (createClient / user RLS) para queries em tabelas que dependem de bypass policies `USING(true)`. Quando essas bypass policies forem removidas na Story 18.1.2, essas rotas QUEBRAM:

1. **`POST /api/portal/auth`** (linha 105): Busca `client_portal_users` via `supabase`. Apos remover bypass `"Allow all for authenticated users"`, o SELECT falharia. Porem a policy `"Portal users can view own record"` com `auth_user_id = auth.uid()` COBRIRIA o SELECT. O UPDATE (linha 128) e INSERT em `client_portal_activity` (linha 138) tambem usam `supabase`.

2. **`GET /api/portal/invoices`** (linha 48): Busca `invoices` via `supabase`. Apos remover bypass `"Allow all operations on invoices"`, as policies restantes (`"Access invoices by client"`, `"Admin can manage invoices"`) requerem `can_access_client()` ou `is_admin()` -- portal users NAO sao org_members, retorna FALSE. **Resultado: 0 invoices.**

3. **`GET /api/portal/invoices`** (linha 72): Busca `integrations` via `supabase` sem filtro `org_id`. Funciona por acaso (bypass de `integrations` nao e dropada nesta fase).

### Decisao

Migrar as queries problematicas para `adminClient` (service role), consistente com o padrao das demais rotas portal que ja usam `adminClient` + filtro por `client_id`.

### Por que adminClient e seguro aqui

- O `client_id` vem do lookup de `client_portal_users` (autenticado via `auth.uid()`)
- Queries de `invoices` e `integrations` sao filtradas por esse `client_id`
- Nao ha risco de escalacao: portal user so ve dados do seu proprio client

  - DEPOIS: `let query = adminClient.from("invoices").select(...)`
  - O filtro `.eq("client_id", portalUser.client_id)` JA EXISTE — mantem isolamento

- [x] **AC 18.1.1.9** — GET handler (linha 72): Mudar query de `integrations` de `supabase` para `adminClient` + adicionar filtro `org_id`
  - ANTES: `await supabase.from("integrations").select("credentials, is_active").eq("type", "asaas").eq("is_active", true).single()`
  - DEPOIS: Precisa obter `org_id` do client. Adicionar lookup:
    ```typescript
    // Get org_id for scoping
    const { data: clientData } = await adminClient
      .from("clients")
      .select("org_id")
      .eq("id", portalUser.client_id)
      .single()
    ```
  - Depois usar:
    ```typescript
    const { data: integration } = await adminClient
      .from("integrations")
      .select("credentials, is_active")
      .eq("type", "asaas")
      .eq("is_active", true)
      .eq("org_id", clientData?.org_id)
      .single()
    ```
  - Se `clientData` for null, pular a query de integrations (sem Asaas = sem payment links)

- [x] **AC 18.1.1.10** — GET handler (linha 183): Mudar INSERT em `client_portal_activity` de `supabase` para `adminClient`
