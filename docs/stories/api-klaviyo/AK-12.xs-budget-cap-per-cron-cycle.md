# Story AK-12 — XS Budget Cap por Ciclo de Cron

## Story

**Como** operador do sistema,
**Quero** que cada invocacao do cron tenha um limite maximo de chamadas XS (Reporting API),
**Para que** o sistema nao esgote o cap diario de 225/key em poucas invocacoes, garantindo distribuicao uniforme ao longo do dia.

## Contexto

### Problema

Sem um budget cap por ciclo, o cron pode consumir dezenas de chamadas XS numa unica invocacao — especialmente apos deploy (cache frio) ou apos periodo de downtime. Isso esgota o cap diario rapidamente, deixando invocacoes subsequentes sem budget.

### Calculo

```
Cap diario por key: ~225 (estimado, nao confirmado oficialmente)
Cron roda: a cada 5 min = 288 invocacoes/dia

Budget ideal por invocacao: 225 / 288 = ~0.78/invocacao (muito baixo!)

Na pratica, com freshness skip (AK-10):
  Maioria das invocacoes: 0 calls XS (tudo fresh)
  Invocacoes com sync: 3-6 lojas x 2 calls = 6-12 calls XS

Budget seguro por ciclo: 60 (cobre pico + margem)
  Worst case: 225 / 60 = 3.75 invocacoes/dia consumindo budget total
  Normal case: ~120 calls/dia distribuidos em ~10-15 invocacoes
```

### Integracao com AK-2

AK-2 ja implementou `getReportQuotaUsage(apiKey)` que rastreia consumo diario por key. Esta story adiciona o conceito de budget POR CICLO — complementar ao cap diario.

## Acceptance Criteria

### AK-12.1 — Constante de budget

- [ ] Adicionar constante em `src/lib/shared/data-status.ts` ou `rate-limiter.ts`:
  ```typescript
  /** Max XS (reporting) calls per cron cycle per API key group.
   *  Prevents single invocation from exhausting daily cap. */
  export const XS_BUDGET_PER_CYCLE = 60
  ```
- [ ] Exportar constante para uso no cron route

### AK-12.2 — Tracking no cron

- [ ] No loop principal do cron (`sync-reports/route.ts`), antes de sincronizar cada loja/periodo:
  - Consultar `getReportQuotaUsage(apiKey)` do AK-2 para obter `used` no ciclo atual
  - Se `used >= XS_BUDGET_PER_CYCLE` para aquele API key group: **skip** a loja/periodo
  - Marcar como `"skipped:budget"` no summary (distinto de `"skipped:fresh"`)
- [ ] O tracking deve ser por API key group (lojas que compartilham a mesma key)

### AK-12.3 — Round-robin prioridade

- [ ] Lojas skipped por budget devem ser priorizadas na proxima invocacao
  - Se Epic 55.5 (round-robin por freshness) ja estiver implementado: verificar que lojas skipped naturalmente ficam no topo da fila (menos fresh = maior prioridade)
  - Se 55.5 NAO estiver implementado: adicionar campo `skippedAt` ou similar para priorizar na proxima run
- [ ] Logar quantas lojas foram skipped por budget no summary

### AK-12.4 — Logging

- [ ] No summary JSON do cron, incluir por API key group:
  ```json
  {
    "apiKeyGroup": "...XXXX",
    "xsBudget": { "used": 42, "limit": 60, "skipped": 3 }
  }
  ```
- [ ] Se budget foi atingido, logar warning: `[Cron] API key ...XXXX hit XS budget cap (60) — 3 stores skipped, will retry next cycle`

### AK-12.5 — Testes

- [ ] Testar que sync para em `XS_BUDGET_PER_CYCLE` calls para um API key group
- [ ] Testar que lojas de OUTRO key group continuam sincronizando (budget e por key, nao global)
- [ ] Testar que lojas skipped aparecem no summary com motivo `"skipped:budget"`
- [ ] Testar que `XS_BUDGET_PER_CYCLE` pode ser overridden via env var (opcional, nice-to-have)

## Riscos

- **Cache frio pos-deploy**: 42 lojas x 4 periodos x 2 calls = ~336 calls XS necessarias. Com budget de 60/ciclo, levara ~6 invocacoes (30 min) para popular todo o cache. Aceitavel.
- **Contagem de XS**: Depende de AK-2 (`getReportQuotaUsage`) estar funcional. Se AK-2 nao estiver mergeado, esta story fica bloqueada.
- **Granularidade**: Budget e por API key group. Se uma key tem 10 lojas e outra tem 2, a key com 10 sera mais restrita. Isso e intencional — protege keys com mais carga.

## Arquivos Afetados

- `src/lib/shared/data-status.ts` (ou `rate-limiter.ts`) — constante `XS_BUDGET_PER_CYCLE`
- `src/app/api/cron/sync-reports/route.ts` — logica de budget check + logging
- `src/lib/integrations/klaviyo/rate-limiter.ts` — integracao com `getReportQuotaUsage()`

## Revisao Multi-Agente

### @dev — Anotacoes de Implementacao

- **Complexidade: LOW-MEDIUM**. A logica principal e um `if (used >= budget) skip` no loop do cron. A parte mais complexa e decidir ONDE colocar o check — antes do sync de cada period ou antes do sync de cada store.
- **Recomendacao**: Check antes de cada chamada XS individual (nao por store inteira). Assim, se uma store precisa de 4 calls e so restam 2, ela faz os 2 possiveis.
- **AK-2 dependency**: `getReportQuotaUsage()` ja existe e rastreia por key. Reutilizar — NAO duplicar.
- Considerar constante `XS_BUDGET_PER_CYCLE` configuravel via `process.env.XS_BUDGET_PER_CYCLE` com fallback para 60.

### @qa — Anotacoes de Qualidade

- **Teste critico**: Simular 42 lojas com cache frio. Verificar que budget cap limita a 60 calls por key e o restante e marcado "skipped:budget".
- **Teste de isolamento**: 2 key groups — esgotar budget de um, verificar que o outro continua.
- **Monitoramento**: Apos deploy, verificar que `xsBudget.skipped` e 0 na maioria das invocacoes (steady state). Se > 0 frequentemente, budget pode estar muito baixo.

### @data-engineer — Anotacoes de Dados

- **Trade-off**: Budget mais baixo = dados atualizam mais devagar apos cache frio. 60 e conservador. Se necessario, aumentar para 80-100.
- **Observabilidade**: Os logs de `xsBudget` por key group sao essenciais para calibrar o valor. Monitorar por 1 semana apos deploy.

### @architect — Anotacoes Arquiteturais

- **Pattern**: Budget cap por ciclo e complementar ao cap diario (AK-2). Um protege dentro do ciclo, outro protege ao longo do dia.
- **Escalabilidade**: Quando escalar para queue-based workers, o budget cap migra para o worker level. A constante isolada facilita essa migracao.
- **Configuravel**: Recomendar env var override para ajuste sem redeploy.

### @analyst — Anotacoes de Impacto

- **Protecao futura**: Com crescimento de ~5 lojas/mes, sem budget cap, picos pos-deploy podem esgotar o cap diario em 1-2 invocacoes. O cap distribui o consumo.
- **Recovery time**: Cache frio recovery de 30min (6 ciclos) e aceitavel. Operadores verao dados "syncing" por ~30min — documentar esse comportamento.
