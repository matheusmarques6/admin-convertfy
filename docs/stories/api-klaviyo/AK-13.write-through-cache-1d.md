# Story AK-13 — Write-Through Cache para Periodo 1d

## Story

**Como** operador do portal,
**Quero** que quando eu consulto dados de 1 dia, o resultado seja salvo no cache para os proximos operadores,
**Para que** multiplos operadores consultando a mesma loja/1d nao disparem live fetches redundantes.

## Contexto

### Problema

O periodo "1d" e `LIVE_ONLY` — nunca e pre-populado pelo cron. Cada consulta no portal dispara um live fetch (2-3 chamadas XS a Reporting API). Se 3 operadores consultam a mesma loja em 5 minutos:

```
3 operadores x 3 calls XS = 9 calls (6 desnecessarias)
```

O `LIVE_FETCH_COOLDOWN_MS` atual de 60s impede re-fetch dentro de 1 minuto, mas nao entre operadores (cooldown e por session/invocation no serverless).

### Solucao: Write-Through

Quando `report-summary.ts` faz live fetch para 1d, **persistir o resultado** em `store_revenue_summary` com `period_label = "1d"` e `sync_source = "live"`. O proximo operador que consultar 1d dentro de `LIVE_FETCH_CACHE_TTL_MS` (5 min) recebe o cached result.

### Por que NAO mover 1d para CACHED_PERIODS

Dados de 1 dia mudam muito rapido (pedidos das ultimas horas). Cachear via cron a cada 3h (como 7d) seria desatualizado demais. Write-through com TTL de 5min e o equilibrio ideal: dados frescos + sem duplicacao.

## Acceptance Criteria

### AK-13.1 — Persistir resultado de live fetch

- [ ] Em `src/lib/integrations/klaviyo/report-summary.ts`, apos live fetch bem-sucedido para periodo "1d":
  - Inserir/atualizar `store_revenue_summary` com:
    - `period_label = "1d"`
    - `sync_source = "live"`
    - `fetched_at = now()`
    - Dados de revenue/flows/campaigns como nos periodos cached
  - Usar `upsert` com chave `(store_id, period_label)` para evitar duplicatas

### AK-13.2 — Ler do cache antes de live fetch

- [ ] Antes de disparar live fetch para "1d", verificar se existe row em `store_revenue_summary` com:
  - `period_label = "1d"`
  - `fetched_at` dentro de `LIVE_FETCH_CACHE_TTL_MS` (5 min, constante ja existente em data-status.ts)
- [ ] Se existir e estiver fresh: retornar cache hit com `source: "cache"`
- [ ] Se nao existir ou estiver stale: fazer live fetch + write-through

### AK-13.3 — Aumentar cooldown de 1d

- [ ] Aumentar `LIVE_FETCH_COOLDOWN_MS` para 1d especificamente de 60s para 5 minutos:
  - Opcao A: Usar `LIVE_FETCH_CACHE_TTL_MS` (ja 5 min) como cooldown para 1d
  - Opcao B: Criar `PERIOD_COOLDOWNS: Record<string, number>` com override para "1d"
  - Escolher a opcao que gera menos complexidade

### AK-13.4 — Testes

- [ ] Testar que live fetch de 1d persiste resultado no DB
- [ ] Testar que segunda consulta dentro de 5 min retorna cache (nao faz live fetch)
- [ ] Testar que consulta apos 5 min faz novo live fetch
- [ ] Testar que `sync_source = "live"` e gravado corretamente
- [ ] Testar que write-through NAO afeta periodos cached (7d, 15d, etc.)

## Riscos

- **Race condition**: Dois operadores consultando 1d simultaneamente podem ambos fazer live fetch antes do cache ser populado. Aceitavel — e o mesmo comportamento atual, apenas sem cache.
- **Storage growth**: +1 row por loja por consulta de 1d. Com 42 lojas e TTL de 5min, rows de 1d sao efemeras. Considerar cleanup (ou confiar no TTL check na leitura).
- **Cooldown vs cache**: O cooldown (`live_fetch_cooldowns` table) e o cache (`store_revenue_summary`) sao mecanismos diferentes. O cache persiste dados, o cooldown bloqueia re-fetch. Ambos devem estar alinhados (5 min).

## Arquivos Afetados

- `src/lib/integrations/klaviyo/report-summary.ts` — write-through logic + cache check
- `src/lib/shared/data-status.ts` — possivelmente novo cooldown especifico para 1d

## Revisao Multi-Agente

### @dev — Anotacoes de Implementacao

- **Complexidade: LOW**. A logica de upsert em `store_revenue_summary` ja existe para periodos cached. Reutilizar.
- O cache-first check tambem ja existe em `report-summary.ts` — estender para "1d" condicionalmente.
- **Cuidado**: `store_revenue_summary` pode ter CHECK constraint em `period_label`. Verificar se "1d" e aceito.
- NAO alterar `CACHED_PERIODS` — 1d continua live-only. O write-through e uma otimizacao transparente.

### @qa — Anotacoes de Qualidade

- **Teste E2E**: Abrir portal como operador 1, consultar 1d para loja X. Verificar que row aparece em `store_revenue_summary`. Abrir como operador 2, consultar mesma loja/1d dentro de 5min — verificar que nao houve live fetch (log).
- **Teste de TTL**: Aguardar > 5min, re-consultar — verificar que live fetch e disparado novamente.

### @data-engineer — Anotacoes de Dados

- **Schema**: Verificar que `period_label` aceita "1d". Se for enum/CHECK, adicionar migration.
- **Cleanup**: Rows de 1d com `fetched_at` > 5min sao "mortas". Considerar cron de cleanup ou simplesmente ignorar (overhead minimo).
- **Observabilidade**: Adicionar log "1d cache hit" vs "1d live fetch" para medir hit rate apos deploy.

### @architect — Anotacoes Arquiteturais

- **Pattern correto**: Write-through cache e o pattern ideal para dados volateis que multiplos consumidores leem. NAO e caching agressivo — e deduplicacao de fetches.
- **Nao complicar**: A implementacao mais simples e a melhor. Upsert no mesmo path de retorno, check antes do fetch. Sem infra nova.

### @analyst — Anotacoes de Impacto

- **Economia**: Com 3 operadores ativos, reduz ~6 calls/loja/dia para 1d. Economia modesta mas contribui para budget.
- **UX**: Segundo operador ve dados em <100ms (cache hit) em vez de 5-15s (live fetch). Melhoria perceptivel.
