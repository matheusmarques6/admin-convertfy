# Story AK-11 — Adicionar 12m ao CACHED_PERIODS com Threshold 24h

## Story

**Como** operador do sistema,
**Quero** que o periodo de 12 meses seja pre-populado pelo cron com freshness de 24h,
**Para que** operadores do portal que consultam dados anuais recebam resposta instantanea do cache em vez de live fetch lento.

## Contexto

### Problema

O periodo "12m" esta hoje em `LIVE_ONLY_PERIODS` — cada consulta no portal dispara um live fetch (3-5 chamadas XS a Reporting API). Com 42 lojas, se varios operadores consultam 12m:

```
10 lojas consultadas/dia x 3 calls XS = 30 calls/dia (desnecessarias)
```

Dados de 12 meses mudam minimamente ao longo de um dia — re-fetch diario e mais que suficiente.

### Impacto no Cron

O cron (`sync-reports/route.ts`) ja itera `CACHED_PERIODS`:
```typescript
for (const period of CACHED_PERIODS) {
  // sync each period per store
}
```

Adicionar "12m" ao array faz o cron automaticamente sincronizar esse periodo. Com threshold de 24h, cada loja sincroniza 12m apenas 1x/dia.

### Custo Estimado

```
42 lojas x 1 sync/dia x 2 calls XS (flow-values + campaign-values) = ~84 calls/dia
Distribuido em ~15 keys = ~6 calls/key/dia (negligivel)
```

### Cache-First Path

`report-summary.ts` ja tem logica cache-first baseada em `isCachedPeriod()`:
```typescript
if (isCachedPeriod(period)) {
  // try cache first, fallback to live
}
```

Ao mover "12m" para `CACHED_PERIODS`, essa logica passa a servir 12m do cache automaticamente.

## Acceptance Criteria

### AK-11.1 — Mover 12m para CACHED_PERIODS

- [ ] Em `src/lib/shared/data-status.ts`:
  - Adicionar `"12m"` ao array `CACHED_PERIODS`: `["30d", "7d", "15d", "90d", "12m"] as const`
  - Remover `"12m"` de `LIVE_ONLY_PERIODS`: `["1d", "custom"] as const`
- [ ] O tipo `CachedPeriod` sera atualizado automaticamente (const assertion)
- [ ] O tipo `LiveOnlyPeriod` sera atualizado automaticamente

### AK-11.2 — Adicionar threshold de 24h

- [ ] Adicionar entrada em `PERIOD_FRESHNESS_THRESHOLDS`:
  ```typescript
  "12m": 24 * 60 * 60_000,  // 24 hours — annual data barely changes intra-day
  ```
- [ ] Verificar que `isCachedPeriod("12m")` retorna `true`
- [ ] Verificar que `isCachedPeriod("1d")` ainda retorna `false`

### AK-11.3 — Thundering herd (opcional mas recomendado)

- [ ] Considerar adicionar jitter ao cron sync para 12m:
  - Quando 42 lojas todas expiram 12m ao mesmo tempo (24h), o cron tentara sincronizar todas de uma vez
  - Opcao A: Adicionar `Math.random() * 2 * 60 * 60_000` (ate 2h de jitter) ao threshold de 12m
  - Opcao B: O round-robin por freshness (Epic 55.5) ja distribui naturalmente — verificar se e suficiente
  - Se 55.5 ja resolve, documentar e nao implementar jitter
- [ ] Se implementar jitter, adicionar como funcao `getJitteredThreshold(period)` reutilizavel

### AK-11.4 — Testes

- [ ] Testar que `CACHED_PERIODS` inclui "12m"
- [ ] Testar que `LIVE_ONLY_PERIODS` NAO inclui "12m"
- [ ] Testar que `isCachedPeriod("12m")` retorna `true`
- [ ] Testar freshness: `isFresh("12m", fetchedAt)` com fetchedAt < 24h (true) e > 24h (false)
- [ ] Verificar que `ALL_PERIODS` ainda contem todos os 7 periodos

## Riscos

- **Thundering herd**: 42 lojas expirando 12m simultaneamente = burst de ~84 calls XS. Com tiered limiter (AK-1, 4s/call), isso levaria ~336s — EXCEDE timeout de 240s. Mitigacao: round-robin (55.5) distribui ao longo de varias invocacoes, ou jitter no threshold.
- **Timeout do cron**: Primeira execucao apos deploy sincroniza 12m para TODAS as lojas (nenhuma tem cache). Sera distribuido em multiplas invocacoes pelo round-robin.
- **Cross-story**: Mesmo arquivo que AK-10. Se ambas em progresso simultaneo, coordenar merge.

## Revisao Multi-Agente

### @dev — Anotacoes de Implementacao

- **Complexidade: LOW**. Mover string entre arrays + adicionar entrada no Record.
- O cron ja itera `CACHED_PERIODS` — nenhuma mudanca em `sync-reports/route.ts`.
- `report-summary.ts` ja tem cache-first para `isCachedPeriod()` — nenhuma mudanca.
- **Cuidado**: Verificar se `store_revenue_summary` aceita `period_label = "12m"` (coluna varchar, deve aceitar qualquer string). Se houver CHECK constraint, ajustar migration.
- **TypeScript**: Apos mover "12m", qualquer codigo que faz `as LiveOnlyPeriod` com "12m" vai dar erro de tipo — buscar no codebase.

### @qa — Anotacoes de Qualidade

- **Teste end-to-end**: Apos deploy, verificar que o cron popula `store_revenue_summary` com `period_label = "12m"` para pelo menos 1 loja na primeira invocacao.
- **Teste de regressao**: Verificar que "1d" e "custom" continuam como live-only.
- **Monitoramento**: Verificar que 12m aparece nos logs do cron summary como periodo sincronizado.

### @data-engineer — Anotacoes de Dados

- **Schema**: `store_revenue_summary.period_label` e varchar — aceita "12m" sem migration.
- **Volume**: +1 row por loja por sync de 12m = ~42 rows/dia adicionais. Negligivel.
- **Staleness**: 24h de atraso para dados de 12 meses e excelente. A maioria dos dashboards anuais atualiza 1x/dia.

### @architect — Anotacoes Arquiteturais

- **Design validado**: O sistema de CACHED_PERIODS + LIVE_ONLY_PERIODS foi projetado exatamente para esse tipo de extensao. Mover entre arrays e a operacao prevista.
- **Jitter**: Preferir verificar se round-robin (55.5) resolve antes de implementar jitter. Evitar complexidade prematura.

### @analyst — Anotacoes de Impacto

- **Custo**: ~6 calls/key/dia para 12m. Com budget de ~120/key/dia (pos AK-10), sobra folga.
- **UX**: Consulta de 12m que hoje leva 5-15s (live fetch) passara a ser instantanea (cache hit).
- **Adocao**: Operadores provavelmente consultam 12m no inicio do mes para reports mensais — cache sera especialmente util nesses picos.
