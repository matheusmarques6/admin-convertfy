# Story 42.3 — Refatorar OAuth flow: separar Calendar (per-user) de Ads (per-store)

## Story

**Como** admin user da plataforma,
**Quero** conectar minha conta Google Calendar de forma segura,
**Para que** minhas reunioes sejam sincronizadas com meu calendario pessoal.

## Contexto

### Estado atual

- `GET /api/integrations/google/authorize` ja suporta `scope=calendar` nos scopes
- `GET /api/integrations/google/callback` salva tokens em `client_stores` via `updateStoreCredentials()` — **incorreto para Calendar**
- State do OAuth usa `Buffer.from(JSON.stringify({...})).toString('base64')` com `timestamp` para CSRF — **sem nonce criptografico (C2)**
- Ja usa `prompt: 'consent'` e `access_type: 'offline'` (bom)
- Redirect pos-callback vai para `/settings/integrations` fixo

### O que precisa mudar

1. State incluir `crypto.randomUUID()` como nonce anti-CSRF (C2)
2. State incluir `user_type` (profile/portal_user) e `org_id`
3. Callback validar nonce e roteiar tokens para `user_google_tokens` quando `scope=calendar`
4. Redirect pos-callback depender do contexto (admin vs portal)
5. Fluxo existente (Ads/per-store) continuar funcionando sem regressao

## Acceptance Criteria

- [x] **AC 42.3.1**: `GET /api/integrations/google/authorize` aceita parametro `context=admin|portal` alem do existente `scope=calendar|ads|all`

- [x] **AC 42.3.2**: **[C2]** State do OAuth inclui `crypto.randomUUID()` como nonce anti-CSRF:
  ```typescript
  const state = {
    user_id: user.id,
    user_type: 'profile', // ou 'portal_user' se context=portal
    scope,
    org_id: orgMember.org_id, // buscar do org_members (admin) ou client_portal_users -> clients (portal)
    store_id: storeId || '',
    nonce: crypto.randomUUID(), // NOVO - C2
    timestamp: Date.now(),
  }
  ```
  - **[M1] NOTA:** Quando `context=portal`, o user NAO esta em `org_members`. Resolver `org_id` via: `client_portal_users.client_id -> clients.org_id`. Implementar lookup condicional:
    ```typescript
    let orgId: string
    if (context === 'portal') {
      const { data: portalUser } = await adminClient
        .from('client_portal_users')
        .select('clients(org_id)')
        .eq('auth_user_id', user.id)
        .single()
      orgId = portalUser?.clients?.org_id
    } else {
      const { data: orgMember } = await supabase
        .from('org_members')
        .select('org_id')
        .eq('user_id', user.id)
        .single()
      orgId = orgMember?.org_id
    }
    ```

- [x] **AC 42.3.3**: State serializado e salvo em cookie `google_oauth_state` (ja existe, manter padrao)

- [x] **AC 42.3.4**: **[C2]** Callback valida nonce: decodifica state do query param E do cookie, compara `nonce` campo a campo (nao apenas comparacao de string do state inteiro — embora a comparacao inteira tambem funcione como fallback)

- [x] **AC 42.3.5**: Quando `scope=calendar`: callback salva tokens em `user_google_tokens` via `google-auth.service.saveTokens()` (NAO em `client_stores`)
  - Busca userinfo do Google para obter email e account_id
  - Chama `saveTokens(userId, userType, orgId, tokens, userInfo)`

- [x] **AC 42.3.6**: **[C6]** Authorize route usa `prompt: 'consent'` + `access_type: 'offline'` para garantir refresh_token (ja existe, confirmar que continua)

- [x] **AC 42.3.7**: Fluxo existente (scope != calendar) continua salvando em `client_stores` via `updateStoreCredentials()` sem nenhuma regressao

- [x] **AC 42.3.8**: Redirect pos-callback:
  - Quando `scope=calendar` + `context=admin` (ou sem context): redirect para `/admin/settings?tab=integrations&success=google_calendar_connected`
  - Quando `scope=calendar` + `context=portal`: redirect para `/client/settings?success=google_calendar_connected`
  - Quando `scope=ads`: redirect para `/settings/integrations?success=google_connected` (comportamento atual)
