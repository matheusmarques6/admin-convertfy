## Contexto

Apos as migrations (8.11) e o seed (8.12), o dashboard deve estar mostrando dados parciais baseados no seed SQL. Agora precisamos:

1. Disparar o cron `sync-reports` manualmente para popular `store_revenue_summary` com dados frescos para TODOS os 4 periodos (`7d`, `15d`, `30d`, `90d`)
2. Monitorar a execucao do cron (verificar que nao da timeout, que processa todas as stores)
3. Validar que o dashboard mostra dados corretos em todos os componentes
4. Comparar numeros com o que era mostrado antes do Epic 8

### Cron Endpoint

- Rota: `src/app/api/cron/sync-reports/route.ts`
- Metodo: `GET`
- Auth: `Authorization: Bearer {CRON_SECRET}`
- maxDuration: 300s (5 minutos)
- Processa stores em batches de 10, timeout interno de 240s
- Popula `store_revenue_summary` para periodos: `30d`, `7d`, `15d`, `90d` (nessa ordem de prioridade)

### Componentes do Dashboard para Validar

| Componente | Arquivo | O que mostra |
|------------|---------|--------------|
| `TotalRevenueBanner` | `src/components/dashboard/total-revenue-banner.tsx` | Revenue total agregado (campaign + flow) |
| `TopStoresCard` | `src/components/dashboard/top-stores-card.tsx` | Top 5 lojas por revenue |
| `WorstPerformersCard` | `src/components/dashboard/worst-performers-card.tsx` | Bottom 5 lojas ("Atencao Necessaria") |

## Arquitetura Tecnica

### Trigger Manual do Cron

O cron e protegido por `CRON_SECRET`. Para disparar manualmente:

1. Obter o `CRON_SECRET` das environment variables do Vercel
2. Fazer GET request com o header Authorization

```bash
# Opção 1: curl direto
curl -v "https://{DOMAIN}/api/cron/sync-reports" \
  -H "Authorization: Bearer {CRON_SECRET}"

# Opção 2: via Vercel Dashboard > Functions > Invoke
```

### Interpretacao do Response

```typescript
// Response do cron
{
  status: "ok" | "partial",          // "partial" = timeout ou erros em algumas stores
  elapsed: "180000ms",               // Tempo total de execucao
  cleanedCacheEntries: 5,            // Entradas de cache expiradas limpas
  summary: {
    ok: 40,                          // Store-periods sincronizados com sucesso
    error: 2,                        // Store-periods com erro
    skipped: 0                       // Store-periods pulados (timeout)
  },
  stores: [                          // Detalhes por store-period
    { storeId: "...", storeName: "...", period: "30d", status: "ok", campaignRevenue: 1234.56, flowRevenue: 789.01 },
    // ...
  ]
}
```

### Queries de Validacao

```sql
-- 1. Cobertura: stores com 4 periodos
SELECT cs.store_name, COUNT(srs.period_label) AS periods
FROM client_stores cs
LEFT JOIN store_revenue_summary srs ON srs.store_id = cs.id
WHERE cs.klaviyo_private_key IS NOT NULL AND cs.org_id IS NOT NULL
GROUP BY cs.store_name
ORDER BY periods ASC;
-- Todas devem ter periods = 4

-- 2. Erros de sync
SELECT store_id, period_label, sync_status, sync_error
FROM store_revenue_summary
WHERE sync_status IN ('error', 'partial');
-- Idealmente vazio; se nao, investigar

-- 3. Revenue total 30d
SELECT
  SUM(klaviyo_total_revenue) AS total,
  SUM(klaviyo_campaign_revenue) AS campaigns,
  SUM(klaviyo_flow_revenue) AS flows,
  COUNT(*) AS stores
FROM store_revenue_summary
WHERE period_label = '30d';
```

## Riscos e Mitigacoes

| Risco | Mitigacao |
|-------|-----------|
| Cron timeout em 300s com muitas stores | Cron tem batching + timeout interno de 240s; stores nao processadas ficam para o proximo run |
| Rate limit da Klaviyo API | Cron ja implementa `sleep(MIN_REQUEST_INTERVAL)` entre requests |
| CRON_SECRET nao encontrado | Verificar env vars no Vercel Dashboard > Settings > Environment Variables |
| Revenue diverge > 5% do pre-Epic 8 | Investigar: pode ser dados mais frescos, stores novas, ou sync parcial; documentar decisao |
| Cron schedule nao ativado | Verificar `vercel.json` na raiz do projeto; deploy pode ser necessario para ativar crons |
