# Story 33.6 — Fallback para Cache em Rate Limit Klaviyo

## Story

**Como** usuario do dashboard (admin ou portal),
**Quero** que ao ocorrer rate limit da Klaviyo os dados mais recentes do cache sejam exibidos,
**Para que** eu nao veja erro e possa continuar tomando decisoes com dados recentes.

## Contexto

### Problema

Quando a Klaviyo retorna 429 (rate limit), as API routes (`flows`, `campaigns`, `report`, `report-summary`) retornam erro direto para o frontend. O usuario ve tela de erro, mesmo que o cron ja tenha populado dados frescos nas tabelas `store_revenue_summary`, `klaviyo_flow_metrics` e `klaviyo_campaign_metrics`.

### Solucao

**Somente quando der rate limit:** no `catch` de `KlaviyoRateLimitError`, consultar o cache existente (< 48h). Se tiver dados, retornar com flag `rateLimited: true`. Se nao tiver, retornar mensagem amigavel.

### O que ja existe

- Tabelas `store_revenue_summary`, `klaviyo_flow_metrics`, `klaviyo_campaign_metrics` ja populadas pelo cron a cada ~6h
- `readFlowsFromCache()` e `readCampaignsFromCache()` ja implementadas em `flows/route.ts` e `campaigns/route.ts` (ATENCAO: usam `CACHE_MAX_AGE_MS = 6h` hardcoded — para o fallback de rate limit, passar `RATE_LIMIT_MAX_CACHE_AGE_MS` como parametro ou fazer query direta com 48h)
- Campo `fromCache: boolean` ja retornado pelas routes
- `fetched_at` disponivel em todas as tabelas para verificar freshness
- `DataStatusMeta` e `SyncResult` ja modelam source/status

### O que NAO muda

- Cron sync — ja trata rate limit corretamente (marca partial, preserva dados)
- Fluxo normal sem rate limit — continua identico
- Nenhuma tabela nova, nenhum schema novo
- Nenhum circuit breaker, nenhum rate limit tracker no banco

## Acceptance Criteria

### 33.6.1 — Fallback em `flows/route.ts`

- [x] No catch de `KlaviyoRateLimitError`, buscar cache com freshness de 48h (NAO 6h)
- [x] **IMPORTANTE:** `readFlowsFromCache()` usa `CACHE_MAX_AGE_MS = 6h` hardcoded. Para o fallback, adicionar parametro opcional `maxAgeMs` com default 6h, e passar `RATE_LIMIT_MAX_CACHE_AGE_MS` (48h) no catch de rate limit
- [x] Retornar com campos adicionais: `rateLimited: true`, `fromCache: true`, `fetchedAt: string`
- [x] Se cache inexistente ou > 48h: retornar JSON com `{ error: "rate_limited_no_cache", message: "Dados temporariamente indisponiveis por limitacao da Klaviyo." }` e status 200 (NAO 429)

**Arquivo:** `src/app/api/integrations/klaviyo/flows/route.ts`

- [x] Mesmos campos de resposta: `rateLimited: true`, `fromCache: true`, `fetchedAt: string`

**Arquivo:** `src/app/api/integrations/klaviyo/campaigns/route.ts`

### 33.6.3 — Fallback em `report/route.ts`

## Regras

- **SOMENTE quando der rate limit** — fluxo normal nao muda em nada
- **Cache < 48h** — dados mais antigos que 2 dias NAO sao exibidos
- **Status 200** — mesmo quando rate limited, retornar 200 (nao 429) para o frontend renderizar corretamente
- **Periodos sem cache (1d, 12m, custom)**: o cron nao popula esses periodos. Se rate limited, mostrar mensagem amigavel diretamente

## Riscos

| Risco | Mitigacao |
|-------|----------|
| Periodos 1d/12m/custom sem cache | Mostrar mensagem amigavel, sem fallback |
| Cache com `sync_status=error` e revenue=0 | Verificar `sync_status` antes de usar — se `error` e revenue=0, tratar como sem cache |
| Dados parciais (flow OK, campaign rate limited) | Cada route tem fallback independente — OK ter mix de live e cache |
| Usuario nao percebe que dados sao cached | Banner obrigatorio com timestamp |
| report/route.ts retorna response complexa mas cache so tem revenue | Retornar `partial: true`, frontend esconde secoes detalhadas |
| `report-summary.ts` usa `Promise.all` — rate limit em 1 request mata ambos | OK — o catch captura e faz fallback para o par inteiro |
