# Story 56.5 — Adicionar requireStoreAccess Granular em /api/integrations/save

## Story

**Como** engenheiro de seguranca,
**Quero** que o endpoint `/api/integrations/save` valide permissao granular (`can_edit`) antes de salvar credenciais,
**Para que** membros sem permissao de edicao em uma loja nao possam sobrescrever credenciais de integracao.

## Contexto

### Problema

O endpoint `src/app/api/integrations/save/route.ts` ja tem protecao parcial:
- Chama `resolveOrgId(user.id)` (linha 57) — verifica que usuario pertence a ALGUMA org
- Passa `orgId` para `updateStoreCredentials` (linha 74) — defense-in-depth cross-org

**O que falta:** `requireStoreAccess(store_id, user.id, "can_edit")` NAO e chamado. Isso significa que qualquer membro da org (mesmo sem `can_edit` na loja especifica) pode salvar credenciais em qualquer loja da org.

### Severidade: MEDIUM

A mitigacao cross-org ja existe (via `orgId`). O risco residual e **escalacao intra-org**: um membro com acesso limitado (ex: so `can_view` em 2 lojas) pode salvar credenciais em lojas que nao deveria editar.

### Codigo atual

```typescript
export async function POST(request: Request) {
  // ...
  const user = await requireAuth(supabase)
  const orgId = await resolveOrgId(user.id) // OK: cross-org check
  // ...
  if (store_id) {
    // FALTA: requireStoreAccess(store_id, user.id, "can_edit")
    await updateStoreCredentials(store_id, credentials, { orgId })
  }
}
```

## Acceptance Criteria

### 56.5.1 — Adicionar requireStoreAccess com can_edit

- [x] Quando `store_id` e fornecido no body, chamar:
  ```typescript
  const storeAccess = await requireStoreAccess(store_id, user.id, "can_edit")
  ```
- [x] Usar `storeAccess.orgId` em vez de chamar `resolveOrgId` separadamente (evita TOCTOU):
  ```typescript
  // ANTES (2 chamadas separadas):
  const orgId = await resolveOrgId(user.id)
  await updateStoreCredentials(store_id, credentials, { orgId })

  // DEPOIS (1 chamada, orgId vem do requireStoreAccess):
  const storeAccess = await requireStoreAccess(store_id, user.id, "can_edit")
  await updateStoreCredentials(store_id, credentials, { orgId: storeAccess.orgId })
  ```

**Given-When-Then:**

```
GIVEN User A is member of Org A
AND User A has can_view (but NOT can_edit) on Store S1
WHEN User A calls POST /api/integrations/save with { store_id: S1_id, klaviyo_private_key: "pk_xxx" }
THEN response is 403 Forbidden with message about can_edit permission
AND credentials are NOT modified

GIVEN User A is member of Org A
AND User A has NO access row for Store S2
WHEN User A calls POST /api/integrations/save with { store_id: S2_id, ... }
THEN response is 403 Forbidden
AND credentials are NOT modified

GIVEN User A is member of Org A
AND User A has can_edit on Store S3
WHEN User A calls POST /api/integrations/save with { store_id: S3_id, klaviyo_private_key: "pk_xxx" }
THEN credentials are saved and encrypted correctly

GIVEN User A is admin or owner of Org A
AND Store S4 belongs to Org A
WHEN User A calls POST /api/integrations/save with { store_id: S4_id, ... }
THEN credentials are saved (admin/owner has full access)
```

### 56.5.2 — Salvar integracoes org-level sem store_id

- [x] Quando `store_id` NAO e fornecido (integracao org-level como Asaas, Wise):
  - Manter `resolveOrgId(user.id)` como esta
  - NAO chamar `requireStoreAccess` (nao ha store para validar)
  - O fluxo org-level nao e afetado por esta story

**Given-When-Then:**

```
GIVEN User A is member of Org A
WHEN User A calls POST /api/integrations/save with { asaas_api_key: "xxx" } (sem store_id)
THEN org-level integration is saved normally (sem requireStoreAccess)
```

### 56.5.3 — Typecheck

- [x] `npm run typecheck` passa sem erros novos

## Ordem de Implementacao

1. Adicionar import de `requireStoreAccess`
2. No handler POST, quando `store_id` presente: substituir `resolveOrgId` por `requireStoreAccess` com `"can_edit"` (AC 56.5.1)
3. Quando `store_id` ausente: manter fluxo org-level inalterado (AC 56.5.2)
4. Rodar typecheck (AC 56.5.3)
