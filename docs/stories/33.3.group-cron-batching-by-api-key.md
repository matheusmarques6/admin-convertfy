# Story 33.3 — Group Cron Batching by API Key

## Story

**Como** engenheiro de infraestrutura responsavel pelo cron de sync,
**Quero** que lojas compartilhando a mesma API key do Klaviyo sejam processadas sequencialmente,
**Para que** nao esgotemos o rate limit da Klaviyo com chamadas paralelas para a mesma key.

## Contexto

### Problema observado em producao

O cron `sync-reports` processa lojas em batches de `BATCH_SIZE = 3` em paralelo, com 3s entre batches. O rate limit da Klaviyo e **por API key**, nao por loja. Quando multiplas lojas compartilham a mesma key (comum em agencias com varias lojas), chamadas paralelas esgotam o rate limit rapidamente.

### Evidencias de producao (2026-03)

```
[Cron] Karm/15d: [RATE_LIMIT] Retry-After: 12s
[Cron] Vivazz/15d: [RATE_LIMIT] Retry-After: 24s
[Cron] Blue Wolf/15d: [RATE_LIMIT] Retry-After: 36s
[Cron] Blue Wolf/90d: [RATE_LIMIT] Retry-After: 18s
```

Karm, Vivazz e Blue Wolf compartilham a mesma API key → processadas em paralelo → 429 para todas.

### Comportamento atual (bug)

```
Batch 1: [Karm, Vivazz, Blue Wolf]  ← mesma API key, paralelo = 429!
          3s delay
Batch 2: [StoreD, StoreE, StoreF]
```

### Comportamento desejado (fix)

```
API Key Group A (3 stores): Karm → 2s → Vivazz → 2s → Blue Wolf  (sequencial)
API Key Group B (2 stores): StoreD → 2s → StoreE                  (sequencial)
API Key Group C (1 store):  StoreF                                 (sozinha)

Groups A, B, C processados em paralelo (max 2 groups simultaneos)
```

## Arquitetura Tecnica

### Pseudo-codigo da solucao

```typescript
const MAX_PARALLEL_GROUPS = 2
const INTRA_GROUP_DELAY_MS = 2500

// Step 1: Build API key groups
const apiKeyGroups = new Map<string, StoreWithKey[]>()
for (const store of stores) {
  const credentials = await getStoreCredentials(store.id)
  const apiKey = credentials.klaviyo_private_key || credentials.klaviyo_api_key
  if (!apiKey) {
    // skip store, log it
    continue
  }
  if (!apiKeyGroups.has(apiKey)) apiKeyGroups.set(apiKey, [])
  apiKeyGroups.get(apiKey)!.push({ ...store, apiKey })
}

const groups = Array.from(apiKeyGroups.entries())
log.info(`[Cron] ${stores.length} stores grouped into ${groups.length} API key groups: [${groups.map(g => g[1].length).join(", ")}]`)

// Step 2: Process groups in batches of MAX_PARALLEL_GROUPS
for (let i = 0; i < groups.length; i += MAX_PARALLEL_GROUPS) {
  if (Date.now() - startTime > MAX_DURATION_MS) { timedOut = true; break }

  const groupBatch = groups.slice(i, i + MAX_PARALLEL_GROUPS)

  const groupResults = await Promise.allSettled(
    groupBatch.map(async ([_apiKey, groupStores], groupIdx) => {
      const results: CronSyncResult[] = []
      for (let j = 0; j < groupStores.length; j++) {
        if (Date.now() - startTime > MAX_DURATION_MS) break
        const storeResults = await syncStore(groupStores[j], CACHED_PERIODS, supabase, startTime)
        results.push(...storeResults)
        // Delay between stores in same group
        if (j < groupStores.length - 1) {
          await new Promise(r => setTimeout(r, INTRA_GROUP_DELAY_MS))
        }
      }
      return results
    })
  )

  // Collect results...

  // Delay between group batches
  if (i + MAX_PARALLEL_GROUPS < groups.length) {
    await new Promise(r => setTimeout(r, 3000))
  }
}
```

### Nota sobre getStoreCredentials (double fetch)

`getStoreCredentials` faz uma query ao banco por store. Para construir o mapa de grupos, precisamos chamar `getStoreCredentials` para TODAS as lojas antes de iniciar o processamento. Isso adiciona N queries upfront.

**Double fetch:** `syncStore` internamente tambem chama `getStoreCredentials` (linha 165-166), resultando em 2 chamadas por loja. Duas opcoes:

- **(a) Passar a API key pre-fetched para `syncStore`** — adicionar parametro opcional `apiKey?: string` para que `syncStore` pule a segunda chamada quando ja tem a key. Requer refatorar a assinatura de `syncStore`.
- **(b) Aceitar o double fetch** — sao apenas queries simples de DB (SELECT por id), nao chamadas de API externa. O overhead e ~200ms total para 8 lojas. Aceitavel como tradeoff pela simplicidade.

**Recomendacao:** opcao (b) para a implementacao inicial. Se a performance se tornar preocupante (muitas lojas), refatorar para opcao (a) em story futura.

### Nota sobre worst-case: todas as lojas com mesma API key

Se todas as 8 lojas compartilham a mesma API key, formam um unico grupo processado sequencialmente. Estimativa de duracao:

- Cada loja leva ~10-15s para sync completo (4 periodos x queries)
- Com `INTRA_GROUP_DELAY_MS = 2500`: 8 lojas * ~12s + 7 delays * 2.5s = ~113s total
- Bem dentro do `MAX_DURATION_MS` (tipicamente 180-240s para Vercel Pro)
- Nao ha paralelismo neste caso, mas a reducao de 429s compensa o tempo total

## Riscos

| Risco | Mitigacao |
|-------|----------|
| Chamadas a `getStoreCredentials` upfront adicionam latencia | Queries simples (SELECT por id). N=8 stores = ~200ms total. Double fetch aceitavel (ver nota acima) |
| Todas as lojas com mesma API key → processamento sequencial | Estimativa ~113s para 8 lojas. Dentro do MAX_DURATION_MS. Tradeoff aceitavel vs 429s |
| API key em logs | AC 33.3.5 exige log apenas do index do grupo, NAO do API key |
| Cron timeout com grupos grandes sequenciais | `MAX_DURATION_MS` check entre cada loja. Timeout graceful |
