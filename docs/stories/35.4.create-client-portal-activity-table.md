# Story 35.4 — Criar tabela client_portal_activity

## Story

**Como** administrador do sistema,
**Quero** que os logins e acoes de portal users sejam registrados em audit trail,
**Para que** eu tenha visibilidade de atividade dos usuarios portal e possa auditar acessos.

## Contexto

### Problema observado

**7 endpoints** fazem INSERT na tabela `client_portal_activity` que NAO existe no banco:

| # | Endpoint | Arquivo | Linha | Acao registrada | Client usado |
|---|----------|---------|-------|-----------------|-------------|
| 1 | POST `/api/portal/auth` | `src/app/api/portal/auth/route.ts` | 141 | `login` | `adminClient` |
| 2 | POST `/api/portal/auth/verify` | `src/app/api/portal/auth/verify/route.ts` | 68 | `login` | `adminClient` |
| 3 | POST `/api/admin/portal-users/[id]/send-invite` | `src/app/api/admin/portal-users/[id]/send-invite/route.ts` | 132 | `invite_sent` | `supabase` (user) |
| 4 | GET `/api/portal/stores/[id]/report` | `src/app/api/portal/stores/[id]/report/route.ts` | 118 | `view_report` | `adminClient` |
| 5 | GET `/api/portal/invoices` | `src/app/api/portal/invoices/route.ts` | 201 | `view_invoices` | `adminClient` |
| 6 | GET `/api/portal/dashboard` | `src/app/api/portal/dashboard/route.ts` | 983 | `view_dashboard` | `adminClient` |
| 7 | POST `/api/portal/change-password` | `src/app/api/portal/change-password/route.ts` | 78 | `password_changed` | `supabase` (user) |

Os inserts falham silenciosamente (nenhum dos endpoints faz `.throwOnError()` ou checa o `error` do insert de activity). Resultado: dados de audit trail de login e atividade estao sendo perdidos desde o deploy da feature portal.

**Nota sobre clients:** Endpoints #3 e #7 usam `supabase` (user client) em vez de `adminClient`. Para padronizar e evitar problemas com RLS, esses 2 endpoints devem ser alterados para usar `adminClient` no INSERT de activity (ver AC 35.4.5). Activity logging e operacao do sistema, faz sentido usar service_role.

### Comentario no codigo

O endpoint `/api/portal/auth/route.ts` tem um comentario na linha 140:
```typescript
// Log activity (table does not exist yet -- GAP-6 / Story 18.1.6)
```

Isso confirma que a tabela foi planejada (GAP-6 no security audit, Story 18.1.6) mas nunca criada.

### Estrutura proposta

Baseado nos INSERT statements existentes no codigo:

```sql
CREATE TABLE client_portal_activity (
  id UUID DEFAULT gen_random_uuid() PRIMARY KEY,
  portal_user_id UUID NOT NULL REFERENCES client_portal_users(id) ON DELETE CASCADE,
  client_id UUID NOT NULL REFERENCES clients(id) ON DELETE CASCADE,
  action TEXT NOT NULL,                    -- 'login', 'invite_sent', etc.
  metadata JSONB DEFAULT '{}'::jsonb,      -- user_agent, sent_by, etc.
  created_at TIMESTAMPTZ DEFAULT now() NOT NULL
);

-- Index para queries por portal user (historico de atividade)
CREATE INDEX idx_portal_activity_portal_user
  ON client_portal_activity(portal_user_id, created_at DESC);

-- Index para queries por client (auditoria por cliente)
CREATE INDEX idx_portal_activity_client
  ON client_portal_activity(client_id, created_at DESC);

-- RLS
ALTER TABLE client_portal_activity ENABLE ROW LEVEL SECURITY;

-- Admins podem ler toda atividade da org (via adminClient, sem policy necessaria)
-- Portal users podem inserir sua propria atividade
CREATE POLICY "Portal users insert own activity"
  ON client_portal_activity FOR INSERT
  TO authenticated
  WITH CHECK (
    portal_user_id IN (
      SELECT id FROM client_portal_users WHERE auth_user_id = auth.uid()
    )
  );

-- Admins leem via adminClient (service_role bypasses RLS)
-- Se necessario no futuro, adicionar SELECT policy para portal users verem proprio historico
```

### Nota sobre os INSERT statements existentes

5 dos 7 endpoints usam `adminClient` (service_role, bypassa RLS). Os endpoints #3 (`send-invite`) e #7 (`change-password`) usam `supabase` (user client). A RLS INSERT policy proposta NAO funcionaria para o endpoint #3 porque `auth.uid()` e o admin user que envia o convite, nao o portal user. Por isso, AC 35.4.5 padroniza todos para usar `adminClient`. A policy e mantida como safety net para futuro uso.

## Riscos

| Risco | Mitigacao |
|-------|----------|
| Inserts atuais nao checam erro do activity insert | Comportamento intencional: activity logging e best-effort, nao deve bloquear login. Manter como esta |
| Tabela pode crescer rapidamente com muitos logins | Index `(portal_user_id, created_at DESC)` otimiza queries. Considerar retention policy no futuro |
| FK para client_portal_users com ON DELETE CASCADE | Correto: se portal user e deletado, activity logs tambem sao removidos |
| RLS INSERT policy nao funciona para `send-invite` (admin user, nao portal user) | Resolvido no AC 35.4.5: padronizar para `adminClient` (service_role bypassa RLS) |
