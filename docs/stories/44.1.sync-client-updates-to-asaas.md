# Story 44.1 — Propagar alterações de cliente para Asaas no save

**Epic:** 44 — Asaas Customer Bidirectional Sync
**Prioridade:** P0 (bug reportado em produção)
**Esforço:** MEDIUM
**Status:** Done

---

## Problema

No `src/app/admin/clients/[id]/edit/page.tsx`, a função `onSubmit` (linha 158) contém um bloco de criação Asaas (linhas 208-250) que só executa quando `asaasCustomerId` não existe. Quando o cliente já tem `asaas_customer_id`, o código pula direto para o update local. Todos os campos sincronizáveis (email, nome, telefone, cpf_cnpj, endereço) ficam desatualizados no Asaas.

O método `AsaasService.updateCustomer()` existe em `src/lib/integrations/asaas.ts:68` mas tem **zero chamadas** em todo o codebase.

## Solução

### Fase 1: API Route para update de customer no Asaas

Criar `PATCH /api/integrations/asaas/customers/update` que:
1. Recebe `clientId`
2. Busca o cliente no banco **com scoping por `org_id`** (segurança multi-tenant)
3. Extrai `asaas_customer_id` de `custom_fields`
4. Busca credenciais Asaas da org
5. Envia **TODOS os campos sincronizáveis** para `asaas.updateCustomer()` (não computa diff — simplicidade)
6. Sanitiza inputs antes de enviar (strip non-digits de cpfCnpj, phone, postalCode — mesmo padrão de `create/route.ts`)
7. Retorna sucesso/erro

### Fase 2: Integrar no edit form

No `edit/page.tsx`, após o bloco de criação (linha 208-250), adicionar:
- Se `asaasCustomerId` existe E campos sincronizáveis mudaram → chamar `PATCH /api/integrations/asaas/customers/update`
- Se Asaas falhar → save local continua + toast de aviso
- Se Asaas suceder → toast de confirmação

## Riscos e Mitigações

| Risco | Mitigação |
|-------|-----------|
| Asaas API fora do ar | Save local continua, toast de aviso (graceful degradation) |
| Rate limit Asaas | `fetchWithRetry` já implementado no AsaasService |
| Cliente deletado no Asaas (404) | Capturar 404, logar, não bloquear save |
| Dados inválidos rejeitados pela Asaas (400) | Mostrar erro descritivo da Asaas no toast |
| Edição concorrente por 2 admins | Last-write-wins (aceitável para P0, sem lock) |
| Cross-tenant client update | Mitigado por `.eq("org_id", orgId)` no fetch do cliente |

## Problemas Adjacentes (fora do escopo, registrar para futuro)

1. **`asaas_customer_id` em `custom_fields` JSONB** — deveria ser coluna própria (já existe coluna `asaas_customer_id` na tabela mas app usa `custom_fields`)
2. **Import de clientes sobrescreve dados locais** — `POST /customers` faz overwrite unidirecional Asaas→local
3. **Zero testes para integração Asaas** — nenhum test file existe
4. **Webhook Asaas só processa PAYMENT events** — não há handler para CUSTOMER events
