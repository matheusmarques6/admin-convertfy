# Story 5.2 - Validacao Real de Credenciais no Fluxo de Save

**Prioridade:** Alta
**Sprint:** Current
**Assignee:** @dev
**Revisao:** @sm (River)
**Status:** Ready for Review

---

## Contexto

Atualmente, o sistema salva credenciais de integracao (Shopify, Klaviyo) sem verificar se elas funcionam. O status "Conectado" na UI eh baseado apenas na **existencia** do campo no banco de dados — uma chave invalida ou expirada aparece como "Conectado".

Endpoints de teste ja existem (`/api/integrations/klaviyo/test`, `/api/integrations/shopify/test`), mas estao **desconectados** do fluxo de save. Alem disso, credenciais salvas sao encriptadas (`enc:v1:`), o que impede testes pelo browser (o componente ClientStores tem botoes "Testar Conexao" que falham porque enviam o valor encriptado).

O `getStoreIntegrationStatus()` em `credentials.service.ts` retorna `connected: true` se o campo existir, mesmo com valor invalido.

---

## Objetivo

Implementar validacao real de credenciais no momento do save e um sistema de status que reflita o estado real da conexao, com campos `last_validated_at` e `last_validation_error` persistidos no banco.

## Arquitetura Tecnica

### Fluxo de Save com Validacao

```
Usuario salva credenciais
        |
        v
  POST/PUT /api/client-stores/credentials
        |
        v
  Encripta credenciais (AES-256-GCM)
        |
        v
  Valida credenciais (chama APIs externas)
  - Shopify: GET /admin/api/2024-10/shop.json
  - Klaviyo: GET /api/accounts/
        |
        +-- Sucesso: validated_at = now(), error = null
        +-- Falha: validated_at = now(), error = "mensagem"
        |
        v
  Salva no banco (credenciais + resultado validacao)
        |
        v
  Retorna resposta com validation_results
```

### Notas Importantes

1. **Validacao NAO bloqueia o save** — credenciais sao salvas mesmo se invalidas, mas o status reflete o erro
2. **Descriptografar para testar**: o validator precisa do valor plain-text. Como o `processFields()` ja encriptou, o validator deve receber os valores ANTES da encriptacao (do body original)
3. **Rate limits**: as APIs de teste (Shopify shop.json, Klaviyo accounts) sao leves e nao devem causar rate limiting
4. **Credenciais encriptadas existentes**: o botao "Revalidar" na UI deve chamar os endpoints de teste que ja sabem descriptografar via `getStoreCredentials()`

### Findings

**HIGH -- Security surface (advisory, not blocking):**
- GET `/api/client-stores/credentials` returns plain-text credentials (shopify_access_token, klaviyo_private_key) to the browser for the revalidation flow. This exposes credentials in browser memory/network tab. Recommend follow-up story to refactor to a server-side `/api/client-stores/credentials/revalidate` endpoint.

**MEDIUM -- Code duplication:**
- Shopify domain normalization logic duplicated between `credential-validator.service.ts` and `shopify/test/route.ts`. Should be extracted to shared utility.

**LOW -- UX:**
- `handleRevalidate` catch block silently swallows errors; user gets no feedback on network failure.
- Shopify test endpoint logs token prefix (10 chars) -- pre-existing, not introduced by this story.

### Recommendation
Story may proceed to deployment. Create follow-up story for server-side revalidation endpoint (HIGH priority backlog item).
