# Story 35.1 — Fix trigger handle_new_user + Limpar Profiles Orfaos

## Story

**Como** administrador do sistema,
**Quero** que o trigger `handle_new_user` nao crie profiles para portal users,
**Para que** usuarios de portal nao fiquem com profiles orfaos que poluem o banco e causam erros PGRST116.

## Contexto

### Problema observado em producao

O trigger `handle_new_user` (definido em `supabase/migrations/00001_initial_schema.sql`) executa em TODOS os `INSERT` na tabela `auth.users`, criando um registro em `profiles` para todo usuario — incluindo portal users que sao gerenciados exclusivamente via `client_portal_users`.

Resultado: portal users ficam com:
- Profile com `role: 'sdr'` (hardcoded em producao — migration original usava `'cs'`)
- `account_type: 'admin'` (default da coluna)
- Sem registro em `org_members` (nunca sao adicionados a uma org)
- Erro PGRST116 ao tentar acessar rotas admin (query `.single()` em `org_members` retorna 0 rows)

### Trigger atual em producao (BUG)

```sql
CREATE OR REPLACE FUNCTION handle_new_user()
RETURNS TRIGGER AS $$
BEGIN
  INSERT INTO profiles (id, email, name, role)
  VALUES (
    NEW.id,
    NEW.email,
    COALESCE(NEW.raw_user_meta_data->>'name', split_part(NEW.email, '@', 1)),
    COALESCE((NEW.raw_user_meta_data->>'role')::user_role, 'sdr')
  );
  RETURN NEW;
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;
```

### Fix proposto

```sql
CREATE OR REPLACE FUNCTION handle_new_user()
RETURNS TRIGGER AS $$
BEGIN
  -- Portal users are managed via client_portal_users, not profiles
  IF (NEW.raw_user_meta_data->>'is_portal_user')::boolean IS TRUE THEN
    RETURN NEW;
  END IF;

  INSERT INTO profiles (id, email, name, role)
  VALUES (
    NEW.id,
    NEW.email,
    COALESCE(NEW.raw_user_meta_data->>'name', split_part(NEW.email, '@', 1)),
    COALESCE((NEW.raw_user_meta_data->>'role')::user_role, 'sdr')
  );
  RETURN NEW;
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;
```

### Verificacao de seguranca

Portal auth (`/api/portal/auth/route.ts`) usa APENAS `client_portal_users` para validar sessao. A tabela `profiles` NUNCA e consultada no fluxo portal. Safe to skip profile creation para portal users.

## Riscos

| Risco | Mitigacao |
|-------|----------|
| Cast `(->>'is_portal_user')::boolean` pode falhar se metadata tiver valor invalido | PostgreSQL cast de NULL retorna NULL, e `NULL IS TRUE` = false. Safe. Valores nao-booleanos dariam erro, mas todos os call sites enviam `true` como boolean |
| Profiles orfaos podem ter sido referenciados em outros lugares | Verificar FK constraints antes do DELETE. Esses profiles nunca tiveram org_members, entao nao devem ter sido usados |
| Trigger em producao usa `'sdr'` mas migration original usava `'cs'` | Migration faz `CREATE OR REPLACE` que substitui a funcao inteira. Manter `'sdr'` para alinhar com producao |
