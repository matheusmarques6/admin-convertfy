## Story

**Como** operador do sistema que gerencia multiplas lojas com integracoes Klaviyo,
**Quero** que o cron sync trate rate limits (429) de forma resiliente e registre o erro corretamente,
**Para que** lojas afetadas por rate limiting tenham dados parciais salvos e o cron maximize a quantidade de dados sincronizados dentro do timeout de 300s.

---

## Contexto

### Problema observado em producao

O cron `sync-reports` processa 8 lojas x 4 periodos. Em execucoes com muitas lojas, o Klaviyo retorna 429 (rate limit) com `Retry-After` de ate 3723 segundos (~62 minutos). O client.ts lanca `KlaviyoRateLimitError` quando o wait excede 10s (`MAX_RETRY_AFTER_MS`).

### Infraestrutura existente (ja funciona)

O rate limiter (`rate-limiter.ts`) ja implementa:
- **Fila por API key**: Requests serializadas com 1200ms entre elas
- **Concurrency limiter**: `withConcurrencyLimit()` processa N lojas simultaneamente
- **Fail-fast**: `KlaviyoRateLimitError` e lancada (nao engolida) quando Retry-After > 10s

### Gap atual

1. **`KlaviyoRateLimitError` no pre-fetch**: Assim como `KlaviyoPermissionError`, se `getCachedAccountInfo()` ou `fetchFlowNames()` lanca rate limit error, o erro pula o try-catch por periodo e nao registra nada no `store_revenue_summary`
2. **Sem fallback parcial**: Se o rate limit ocorre no meio do sync de uma loja (ex: 2/4 periodos ok, 3o falha), os periodos restantes nao sao tentados
3. **Sem registro claro**: O `sync_error` generico nao distingue rate limit de outros erros — dificulta diagnostico
4. **Log de retry-after nao mostra contexto**: Log diz "Rate limited" mas nao indica qual loja/periodo

### Impacto atual

1. **Dados parciais perdidos**: Se rate limit ocorre no periodo 3/4, o periodo 4 nem e tentado (porque o erro crashou a loja inteira)
2. **Diagnostico**: `store_revenue_summary.sync_error` tem mensagem generica, sem indicar que foi rate limit
3. **Metricas**: Sem visibilidade de quantas lojas sao afetadas por rate limit por execucao

## Acceptance Criteria

### 16.8.1 — Tratar KlaviyoRateLimitError no pre-fetch

- [x] Em `sync-reports/route.ts`, no try-catch do pre-fetch (AC 16.7.1), tambem capturar `KlaviyoRateLimitError`
- [x] Se capturado no pre-fetch:
  - Registrar `sync_error` em `store_revenue_summary` para TODOS os periodos com mensagem `"[RATE_LIMIT] Klaviyo rate limited during pre-fetch (Retry-After: ${retryAfterMs}ms)"`
  - `sync_status: "error"`
  - Logar warning com store_name e retry-after
  - `continue` para pular a loja inteira

**Arquivo:** `src/app/api/cron/sync-reports/route.ts`

### 16.8.2 — Continuar periodos restantes apos rate limit por periodo

**Pre-requisito:** AC 16.7.4 deve estar implementado (re-throw de `KlaviyoRateLimitError` em `syncKlaviyoForPeriod` e `fetchStoreRevenueFromMetricAggregates`). Sem isso, `syncKlaviyoForPeriod` engole o rate limit error no catch generico (L652-662) e retorna `{ success: false }` — o cron nunca ve `KlaviyoRateLimitError`.

- [x] No loop de periodos, se `syncKlaviyoForPeriod()` lanca `KlaviyoRateLimitError`, capturar e registrar o erro no `store_revenue_summary` para aquele periodo, mas **continuar** com os periodos restantes (nao `break`)
- [x] Motivacao: rate limit pode ser transiente — o proximo request (apos o backoff do rate limiter) pode funcionar
- [x] Se **2 ou mais** periodos consecutivos falham com rate limit, fazer `break` (requisito firme, nao opcional). Logar warning indicando skip dos periodos restantes
- [x] Resetar contador `consecutiveRateLimits` a zero apos periodo bem-sucedido

**Arquivo:** `src/app/api/cron/sync-reports/route.ts`

### 16.8.3 — Prefixar sync_error com tipo de erro

- [x] Quando `KlaviyoRateLimitError` e capturada no catch por periodo, prefixar a mensagem com `[RATE_LIMIT]`
- [x] Quando `KlaviyoPermissionError` e capturada (se chegar aqui), prefixar com `[PERMISSION]`
- [x] Erros genericos mantem sem prefixo (compatibilidade)
- [x] Isso permite que o dashboard/UI filtre e destaque erros por tipo

**Arquivo:** `src/app/api/cron/sync-reports/route.ts`

### 16.8.4 — Testes

- [x] Teste: mock `getCachedAccountInfo` lancando `KlaviyoRateLimitError` → verificar upsert em todos os periodos com `[RATE_LIMIT]` prefix
- [x] Teste: mock `syncKlaviyoForPeriod` lancando `KlaviyoRateLimitError` no periodo 2 → verificar que periodo 3 e 4 ainda sao tentados (requer AC 16.7.4 — re-throw no service)
- [x] Teste: 2 periodos consecutivos com rate limit → verificar `break` (requisito firme)
- [x] Teste: verificar que `consecutiveRateLimits` reseta a zero apos periodo bem-sucedido (ex: periodo 1 = rate limit, periodo 2 = sucesso, periodo 3 = rate limit → NAO faz break)
- [x] Teste: verificar prefixo `[PERMISSION]` quando `KlaviyoPermissionError` e capturada no loop de periodos (AC 16.8.3)

## Notas Tecnicas

### Fluxo proposto (integrado com 16.7)

```typescript
// Pre-fetch (extends 16.7.1)
try {
  accountInfo = await getCachedAccountInfo(apiKey, ...)
  metricId = await getCachedPlacedOrderMetric(apiKey, ...)
  [flowNames, campNames] = await Promise.all([...])
} catch (err) {
  if (err instanceof KlaviyoPermissionError) {
    // ... (16.7 handling)
  }
  if (err instanceof KlaviyoRateLimitError) {
    for (const period of periods) {
      await upsertSyncError(store, period,
        `[RATE_LIMIT] Rate limited during pre-fetch (${err.retryAfterMs}ms)`)
    }
    return  // skip store
  }
  throw err
}

// Per-period sync
let consecutiveRateLimits = 0
for (const period of periods) {
  try {
    const result = await syncKlaviyoForPeriod(...)
    consecutiveRateLimits = 0  // reset on success
    // ... handle result
  } catch (err) {
    if (err instanceof KlaviyoRateLimitError) {
      consecutiveRateLimits++
      await upsertSyncError(store, period,
        `[RATE_LIMIT] ${err.message}`)
      if (consecutiveRateLimits >= 2) {
        log.warn(`[Cron] 2+ consecutive rate limits for ${store.store_name}, skipping remaining periods`)
        break
      }
      continue  // try next period
    }
    // ... handle other errors as before
  }
}
```

### Dependencias

- **Story 16.7** deve ser implementada primeiro:
  - AC 16.7.1: try-catch no pre-fetch (16.8.1 estende esse catch)
  - AC 16.7.4: re-throw seletivo no service layer (sem isso, `syncKlaviyoForPeriod` engole `KlaviyoRateLimitError` e AC 16.8.2 nao funciona)
  - AC 16.7.6: funcao `upsertSyncError()` (16.8 reutiliza)

### Arquivos impactados

| Arquivo | Mudanca |
|---------|---------|
| `src/app/api/cron/sync-reports/route.ts` | Catch de KlaviyoRateLimitError no pre-fetch e por periodo + prefixo [RATE_LIMIT] |

### Riscos e mitigacoes

| Risco | Mitigacao |
|-------|-----------|
| Continuar apos rate limit pode gerar mais 429s | Contador de consecutivos com break apos 2 |
| Rate limiter ja serializa — rate limit no cron indica saturacao real | Aceitar e registrar; melhorar concorrencia e outra story (se necessario) |
| Prefixo [RATE_LIMIT] pode quebrar UI que parseia sync_error | sync_error e free-text, UI mostra como string — sem risco |
