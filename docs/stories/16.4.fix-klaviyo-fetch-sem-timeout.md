## Story

**Como** sistema serverless rodando no Vercel,
**Quero** que requests para a Klaviyo tenham um timeout maximo configuravel,
**Para que** falhas de rede ou lentidao da API nao consumam todo o tempo disponivel da funcao e disparem retries desnecessarios com backoff exponencial.

---

## Contexto

O `fetch()` em `src/lib/integrations/klaviyo/client.ts` linha 97 e chamado sem `AbortSignal.timeout()`. Em ambiente Vercel (serverless), se a Klaviyo nao responder:

1. O `fetch` fica pendurado ate o timeout do SO ou da funcao Vercel (10-60s dependendo do plano)
2. Durante esse tempo, o backoff exponencial do loop de retry continua agendando novas tentativas
3. Multiplas requests em paralelo (flows, campaigns, metrics) ficam todas penduradas simultaneamente
4. O resultado e que a funcao Vercel expira sem retornar nada — sem log de timeout, sem fallback

**Padrao observado nos logs** (timestamps revelam backoff exponencial de requests em paralelo falhando por timeout):

```
17:51:25 → 17:51:27 → 17:51:30 → 17:51:36 → 17:51:36 → 17:51:37 → 17:51:40 → 17:51:46
```

Os intervalos (2s, 3s, 6s, 0s, 1s, 3s, 6s) correspondem a 2 grupos de requests em paralelo com backoff 1.5s/3s/6s — exatamente o comportamento de requests penduradas que expiram simultaneamente e disparam todos os seus retries.

**Codigo atual (sem timeout)**:

```typescript
const response = await fetch(url, {
  method,
  headers: {
    "Authorization": `Klaviyo-API-Key ${apiKey}`,
    "Accept": "application/json",
    "Content-Type": "application/json",
    "revision": KLAVIYO_REVISION,
  },
  ...(body && { body: JSON.stringify(body) }),
})
```

`AbortSignal.timeout()` e suportado no Node.js 17.3+ e no Vercel Edge/Serverless runtime sem necessidade de polyfill. E a solucao idiomatica para timeout em `fetch` no ecossistema Node/Next.js moderno.

```typescript
} catch (error) {
  if (error instanceof KlaviyoRateLimitError) {
    log.warn(`[${logTag}] Rate limited after all retries for ${endpoint}`)
  } else {
    log.error(`[${logTag}] REQUEST ERROR:`, error)
  }
  if (attempt < maxRetries) continue
  return null
}
```

#### AFTER — catch block com deteccao de AbortError

```typescript
} catch (error) {
  if (error instanceof KlaviyoPermissionError) {
    throw error  // nao retryar — erro de configuracao permanente (story 16.3)
  }
  if (error instanceof KlaviyoRateLimitError) {
    log.warn(`[${logTag}] Rate limited after all retries for ${endpoint}`)
    throw error
  }
  if (error instanceof Error && error.name === "AbortError") {
    log.error(`[${logTag}] REQUEST TIMEOUT after ${KLAVIYO_FETCH_TIMEOUT_MS}ms: ${endpoint}`)
    if (attempt < maxRetries) continue  // timeout e recuperavel — retry
    return null
  }
  log.error(`[${logTag}] REQUEST ERROR:`, error)
  if (attempt < maxRetries) continue
  return null
}
```

### Nota sobre a ordem dos checks no catch

A ordem importa: `KlaviyoPermissionError` e `KlaviyoRateLimitError` sao re-lancados antes de qualquer verificacao de `attempt < maxRetries`. `AbortError` e um erro recuperavel — continua no loop de retry ate esgotar tentativas. Erros genericos seguem o mesmo padrao de `AbortError`.

### Por que AbortSignal.timeout() e a abordagem correta

Alternativas consideradas e descartadas:

| Alternativa | Problema |
|-------------|----------|
| `Promise.race([fetch(), new Promise(reject => setTimeout(reject, 15000))])` | Nao cancela o fetch subjacente — continua consumindo recursos de rede |
| `AbortController` com `setTimeout` manual | Mais verboso, requer limpeza manual do timer, propenso a memory leak |
| `AbortSignal.timeout()` | API nativa do Node.js 17.3+, cancela o fetch no nivel do motor HTTP, sem boilerplate |

## Riscos

| Risco | Probabilidade | Impacto | Mitigacao |
|-------|--------------|---------|-----------|
| Timeout de 15s muito baixo para reporting endpoints | Baixa | Medio | Reporting API da Klaviyo tem p99 de ~3-5s em condicoes normais. 15s e 3-5x o p99. Se necessario, a constante pode ser parametrizada por endpoint no futuro |
| AbortSignal.timeout() indisponivel em runtime legado | Muito Baixa | Alto | Node.js 17.3+ e requerido. O projeto usa Next.js 15 que requer Node.js 18.17+. Sem risco real |
| Timeout aborta request no meio de uma operacao de escrita | Muito Baixa | Baixo | Klaviyo requests sao idempotentes (GET + POST de relatorios sem efeitos colaterais). Nao ha mutacoes de dados |
| Efeito cascata na fila do `enqueueKlaviyoRequest` | Media | Medio | Quando um request fica pendurado por 15s aguardando timeout, todos os outros requests enfileirados para a mesma API key ficam bloqueados nesse slot durante todo o periodo. O timeout reduz o impacto de potencialmente infinito (ate o timeout da funcao Vercel de 60s) para no maximo 15s por slot de fila. Em cenarios de instabilidade da API Klaviyo, multiplos slots consecutivos podem encadear bloqueios de 15s cada. |
