# Story 37.1 — Confirmacao Obrigatoria na Rejeicao

## Contexto

O frontend ja tem modal de confirmacao com textarea obrigatoria (botao desabilitado se vazio). Porem o backend aceita rejeicao/revisao sem comentarios — qualquer chamada direta a API (curl, Postman) consegue rejeitar sem justificativa. Alem disso, o modal nao deixa claro que a rejeicao DELETA todos os dados do cliente.

## Objetivo

Garantir que rejeicao/revisao sempre tenha justificativa (frontend + backend), e que o COO entenda as consequencias antes de confirmar.

## Criterios de Aceitacao

- [x] **AC 37.1.1**: Backend rejeita `POST /api/onboarding/[id]/approve` com `action: "rejected"` ou `"revision_requested"` se `comments` for vazio, null ou whitespace-only. Retornar 400 com mensagem clara.
- [x] **AC 37.1.2**: Backend aceita `action: "approved"` com `comments` vazio ou null (comentarios opcionais para aprovacao).
- [x] **AC 37.1.3**: Backend limita `comments` a 2000 caracteres. Retornar 400 se exceder.
- [x] **AC 37.1.4**: No modal de rejeicao, adicionar `Alert` de warning: "Esta acao ira apagar todos os dados do formulario. O cliente precisara preencher novamente."
- [x] **AC 37.1.5**: Botao de confirmacao no modal de rejeicao muda de "Confirmar" para "Rejeitar Onboarding" com estilo destrutivo (vermelho).
- [x] **AC 37.1.6**: Botao de confirmacao no modal de revisao muda para "Solicitar Revisao".
- [x] **AC 37.1.7**: Textarea do modal tem `maxLength={2000}` e contador de caracteres visivel.
- [x] **AC 37.1.8**: Textarea tem `aria-required="true"` e `id` linkado ao `label` via `htmlFor` para rejeicao/revisao (acessibilidade).
- [x] **AC 37.1.9**: Migration: adicionar `NOT NULL` + `CHECK(trim(comments) <> '')` na coluna `comments` de `onboarding_rejection_log` para garantir integridade no banco (defesa em profundidade alem do backend guard).

## Concerns (levantados na analise)

| # | Concern | Severidade | Origem | Acao |
|---|---------|-----------|--------|------|
| P1-1 | Backend aceita comments vazio para reject/revision | HIGH | QA | Resolver em AC 37.1.1 |
| P1-2 | Sem max-length no comments (payload abuse) | MEDIUM | QA | Resolver em AC 37.1.3 e 37.1.7 |
| P1-3 | Double-click no botao de confirmacao | LOW | QA | Ja mitigado: `processing` state + `FOR UPDATE` na RPC |
| P1-4 | Stale state: COO A abre dialog, COO B aprova | MEDIUM | QA | Aceito como known limitation — erro 400 retornado no segundo request. Melhorar UX em epic futuro (polling/refresh). |
| CC-3 | Textarea sem `id` linkado ao `label` via `htmlFor` | MEDIUM | QA | Resolver em AC 37.1.8 |
| CC-4 | Falta `aria-required` no textarea obrigatorio | LOW | QA | Resolver em AC 37.1.8 |

## Impacto por Disciplina

- **Dev**: 2 arquivos editados (~20 linhas backend, ~30 linhas frontend)
- **Arquiteto**: Validacao dual (frontend + backend) — padrao correto
- **DB**: Nenhuma mudanca necessaria (comments ja e TEXT nullable no `onboarding_rejection_log`)
- **QA**: Testar chamada direta a API sem comments; testar whitespace-only; testar max-length

## Arquivos Envolvidos

- `src/app/api/onboarding/[id]/approve/route.ts` (backend guard)
- `src/components/onboarding/onboarding-approvals.tsx` (UX do modal)

## Cenarios de Teste

1. `POST approve` com `action: "rejected"`, `comments: null` → deve retornar 400
2. `POST approve` com `action: "rejected"`, `comments: "   "` (whitespace) → deve retornar 400
3. `POST approve` com `action: "revision_requested"`, sem campo `comments` → deve retornar 400
4. `POST approve` com `action: "approved"`, sem comments → deve funcionar (200)
5. `POST approve` com `comments` de 2001 caracteres → deve retornar 400
6. Modal de rejeicao mostra warning sobre delecao de dados
7. Botao diz "Rejeitar Onboarding" (nao "Confirmar")
