## Contexto

A solucao de performance requer uma tabela dedicada `store_revenue_summary` que armazena revenue pre-agregado por loja e periodo. Esta tabela substitui as 120+ chamadas de API por uma unica query ao Supabase.

O schema completo esta definido no PRD (Secao 3.2) e inclui: revenue Klaviyo decomposto (total, campaign, flow), revenue Shopify (ground truth), controle de qualidade do sync (`sync_status`, `sync_error`), TTL explicito (`expires_at`), e isolamento multi-tenant via `org_id NOT NULL`.

---

## Objetivo

Criar a migration SQL para a tabela `store_revenue_summary` com todos os constraints, indices, RLS policies e funcao de cleanup definidos no PRD.

---

## Acceptance Criteria

- [x] **8.6.1** Migration SQL criada em `supabase/migrations/` com o schema completo:
  - Chave primaria composta: `(store_id, period_label)`
  - `org_id UUID NOT NULL REFERENCES organizations(id)`
  - Colunas de revenue: `klaviyo_total_revenue`, `klaviyo_campaign_revenue`, `klaviyo_flow_revenue`, `shopify_total_revenue` (NUMERIC(15,2), NOT NULL, DEFAULT 0)
  - `sync_status VARCHAR(20)` com CHECK constraint (`ok`, `partial`, `error`, `pending`)
  - `sync_error TEXT` nullable
  - `expires_at TIMESTAMPTZ NOT NULL`
  - `fetched_at TIMESTAMPTZ NOT NULL DEFAULT NOW()`
  - `created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()`
  - CHECK constraints: `valid_period_label`, `valid_period_range`, `klaviyo_revenue_non_negative`

- [x] **8.6.2** Indices criados:
  - `idx_revenue_summary_org` em `(org_id, period_label)` — para RLS e queries de overview
  - `idx_revenue_summary_expires` em `(expires_at) WHERE expires_at IS NOT NULL` — para cleanup
  - `idx_revenue_summary_sync_status` em `(sync_status) WHERE sync_status IN ('error', 'partial')` — para health check

- [x] **8.6.3** RLS habilitado com policies:
  - `org_revenue_summary_select`: SELECT para `authenticated` com `USING (org_id = current_org_id() OR can_access_store(store_id))`
  - `service_revenue_summary_all`: ALL para `service_role` com `USING (true) WITH CHECK (true)`
  - **NAO** criar policies de INSERT/UPDATE para `authenticated` (escrita exclusiva via service_role)

- [x] **8.6.4** Funcao `clean_expired_revenue_summaries()` criada como `SECURITY DEFINER`:
  - Deleta registros com `expires_at < NOW() - INTERVAL '1 hour'`
  - Retorna contagem de registros deletados

- [x] **8.6.5** Comment na tabela adicionado para documentacao

- [x] **8.6.6** Migration pode ser executada sem erros em banco limpo e em banco com dados existentes (idempotente onde possivel com `IF NOT EXISTS`)

- [x] **8.6.7** Run `npm run lint` passa sem erros
- [x] **8.6.8** Run `npm run typecheck` passa sem erros

## Arquitetura Tecnica

### Migration SQL Completa

O SQL esta definido integralmente no PRD, Secao 3.2. Copiar exatamente o schema, incluindo:

1. `CREATE TABLE IF NOT EXISTS store_revenue_summary` com todas as colunas e constraints
2. Os 3 indices (`idx_revenue_summary_org`, `idx_revenue_summary_expires`, `idx_revenue_summary_sync_status`)
3. `ALTER TABLE ... ENABLE ROW LEVEL SECURITY`
4. As 2 policies RLS (`org_revenue_summary_select`, `service_revenue_summary_all`)
5. `CREATE OR REPLACE FUNCTION clean_expired_revenue_summaries()`
6. `COMMENT ON TABLE store_revenue_summary`

### Verificacao de pre-requisitos

Antes de criar a migration, verificar que:
- A funcao `current_org_id()` existe no banco (usada pela RLS policy)
- A funcao `can_access_store(store_id)` existe no banco (usada pela RLS policy)
- A tabela `client_stores` existe e tem coluna `id UUID`
- A tabela `organizations` existe e tem coluna `id UUID`
