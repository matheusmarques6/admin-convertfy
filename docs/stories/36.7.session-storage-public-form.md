# Story 36.7 — sessionStorage no Form Publico

## Contexto

O form publico (`/cliente/onboarding`) usa `useState` para todo o estado. Se o usuario recarregar a pagina, perde TODOS os dados preenchidos. O formulario pode levar 5-10 minutos para preencher (especialmente com uploads).

O wizard portal nao tem este problema porque salva cada step via API.

## Objetivo

Persistir dados do formulario em `sessionStorage` para sobreviver a recarregamentos de pagina.

## Criterios de Aceitacao

- [x] **AC 36.7.1**: Ao montar o componente, verificar se existe draft em `sessionStorage` (key: `convertfy_onboarding_draft`) e restaurar `formData`
- [x] **AC 36.7.2**: A cada mudanca de `formData`, salvar em `sessionStorage` (debounce opcional)
- [x] **AC 36.7.3**: Persistir tambem `currentStepId` para restaurar o step correto
- [x] **AC 36.7.4**: NAO persistir `uploadedFiles` (paths de upload temporario podem expirar) — apenas os campos de texto
- [x] **AC 36.7.5**: Apos submit com sucesso, limpar `sessionStorage`
- [x] **AC 36.7.6**: Apos restaurar dados, se existirem uploads referenciados em `formData` (logo_url, etc.) mas sem entry em `uploadedFiles`, mostrar indicacao visual de que o upload precisa ser refeito

## Impacto por Disciplina

- **Dev**: 1 arquivo, ~25 linhas. `useEffect` para save + restore
- **Arquiteto**: `sessionStorage` (morre com a aba) vs `localStorage` com TTL — sessionStorage e suficiente para o caso de reload
- **DB**: Zero
- **QA**: Testar: preencher step 1 → reload → dados persistem? Submit → limpa? 2 abas → independentes? Modo anonimo?

## Risco

Baixo. Totalmente isolado ao form publico.
