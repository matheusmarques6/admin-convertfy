## Story

**Como** sistema em produção que depende de logs estruturados para diagnosticar falhas,
**Quero** que erros passados para `log.error()` (e demais níveis) sejam serializados corretamente,
**Para que** timeouts, API keys inválidas, rate limits e outros erros sejam visíveis nos logs ao invés de aparecerem como `data: {}`.

---

## Contexto

A função `normalizeData()` em `src/lib/logger.ts` (linhas 45-50) tem os checks na ordem errada.

`Error` é um subtype de `object`. O check genérico de object (`typeof data === "object"`) vem **antes** do `instanceof Error`, então todo objeto `Error` cai no branch genérico e é retornado diretamente como `Record<string, unknown>`. O problema é que `message` e `stack` são propriedades **não-enumeráveis** do `Error` — `JSON.stringify(new Error("x"))` retorna `"{}"`. O resultado é que qualquer `log.error("msg", err)` produz `data: {}` no output.

Código atual (bugado):

```typescript
function normalizeData(data: unknown): Record<string, unknown> | undefined {
  if (!data) return undefined
  if (typeof data === "object" && data !== null && !Array.isArray(data)) return data as Record<string, unknown>
  if (data instanceof Error) return { error: data.message, stack: data.stack }  // nunca alcancado
  return { value: data }
}
```

Impacto observado:
- `src/app/api/portal/dashboard/route.ts:375` — `[Portal LiveFetch] Error for store {id}:` aparece com `data: {}` em produção
- Qualquer falha de integração (Klaviyo, Shopify, Supabase) logada via `log.error(..., err)` perde o contexto de `message` e `stack`
- Debugging de produção fica cego para a causa raiz dos erros

## Arquitetura Tecnica

### Arquivo Unico Modificado

**`src/lib/logger.ts`** — apenas a funcao `normalizeData()` (linhas 45-50)

#### BEFORE (bugado)

```typescript
function normalizeData(data: unknown): Record<string, unknown> | undefined {
  if (!data) return undefined
  if (typeof data === "object" && data !== null && !Array.isArray(data)) return data as Record<string, unknown>
  if (data instanceof Error) return { error: data.message, stack: data.stack }
  return { value: data }
}
```

#### AFTER (correto)

```typescript
function normalizeData(data: unknown): Record<string, unknown> | undefined {
  if (!data) return undefined
  if (data instanceof Error) return { error: data.message, stack: data.stack }
  if (typeof data === "object" && data !== null && !Array.isArray(data)) return data as Record<string, unknown>
  return { value: data }
}
```

A unica mudanca e a inversao das linhas 47 e 48. Nenhuma outra logica e tocada.

### Comportamentos fora do escopo deste fix

**Primitivos falsy** (`0`, `false`, `""`): continuam retornando `undefined` pelo branch `if (!data) return undefined`. Este e um comportamento pre-existente e intencional — quem passa `0` ou `false` como data raramente quer logar esse valor como campo estruturado. Nao e um bug introduzido por este fix.

**Propriedades enumeraveis em subclasses de Error**: `{ error: data.message, stack: data.stack }` captura apenas as duas propriedades essenciais para debugging. Propriedades customizadas como `err.code` ou `err.statusCode` definidas em subclasses nao sao capturadas — decisao consciente para manter o fix minimo e seguro.

### Por que o bug existe

JavaScript serializa `Error` como `{}` porque `message` e `stack` sao definidos com `enumerable: false` no prototype. Isso significa:

```typescript
JSON.stringify(new Error("test"))         // "{}"
Object.keys(new Error("test"))            // []
new Error("test") instanceof Error        // true  (check correto)
typeof new Error("test") === "object"     // true  (check errado — mais amplo)
```

O check `instanceof Error` e mais especifico e deve sempre preceder o check generico de `typeof === "object"`.
