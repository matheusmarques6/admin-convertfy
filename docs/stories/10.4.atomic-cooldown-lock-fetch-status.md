## Contexto

Os QA findings H1 e H2 identificam problemas criticos que surgem quando multiplos serverless functions tentam fazer live fetch simultaneamente:

**H1 - Race Condition:** Sem mecanismo atomico, 10 requests simultaneos para a mesma store podem disparar 10 live fetches simultaneos para Klaviyo, causando rate limiting massivo.

**H2 - Rate Limit Amplification:** Em ambiente serverless (Vercel), cada request roda em isolamento. Nao ha shared state entre functions. Um simples `if (isRefreshing) return` nao funciona porque cada function tem seu proprio estado em memoria.

### Solucao: Database-level atomicity

Usar o banco (Supabase/PostgreSQL) como mecanismo de coordenacao:
1. **`live_fetch_cooldowns` table**: registro atomico de "quem esta buscando o que"
2. **PL/pgSQL function**: `try_acquire_live_fetch(store_id, period, cooldown_ms)` que usa `INSERT ... ON CONFLICT DO NOTHING` para garantir atomicidade
3. **Cooldown key**: `store_id + period` para cached periods, `store_id + md5(date_range)` para custom ranges (M2)

---

## Objetivo

Criar infraestrutura de banco para coordenar live fetches entre multiplas serverless functions, evitando race conditions e rate limit amplification.

- [x] **10.4.2** Criar PL/pgSQL function `try_acquire_live_fetch`:
  ```sql
  CREATE OR REPLACE FUNCTION try_acquire_live_fetch(
    p_store_id uuid,
    p_fetch_key text,
    p_cooldown_ms integer DEFAULT 60000,
    p_created_by text DEFAULT 'unknown'
  )
  RETURNS boolean
  LANGUAGE plpgsql
  AS $$
  DECLARE
    v_inserted boolean := false;
    v_expires_at timestamptz;
  BEGIN
    v_expires_at := now() + (p_cooldown_ms || ' milliseconds')::interval;

    -- Clean expired entries for this store+key first
    DELETE FROM live_fetch_cooldowns
    WHERE store_id = p_store_id
      AND fetch_key = p_fetch_key
      AND expires_at < now();

    -- Try atomic insert — fails silently if row exists (cooldown active)
    INSERT INTO live_fetch_cooldowns (store_id, fetch_key, status, expires_at, created_by)
    VALUES (p_store_id, p_fetch_key, 'in_progress', v_expires_at, p_created_by)
    ON CONFLICT (store_id, fetch_key) DO NOTHING
    RETURNING true INTO v_inserted;

    RETURN COALESCE(v_inserted, false);
  END;
  $$;
  ```

- [x] **10.4.3** Criar PL/pgSQL function `release_live_fetch`:

  ```sql
  CREATE OR REPLACE FUNCTION release_live_fetch(
    p_store_id uuid,
    p_fetch_key text,
    p_status text DEFAULT 'completed',
    p_result_summary jsonb DEFAULT NULL
  )
  RETURNS void
  LANGUAGE plpgsql
  AS $$
  BEGIN
    UPDATE live_fetch_cooldowns
    SET status = p_status,
        completed_at = now(),
        result_summary = COALESCE(p_result_summary, result_summary)
    WHERE store_id = p_store_id
      AND fetch_key = p_fetch_key;
  END;
  $$;
  ```

- [x] **10.4.5** Criar TypeScript helper `src/lib/services/fetch-cooldown.service.ts`:
  ```typescript
  import { SupabaseClient } from "@supabase/supabase-js"
  import { LIVE_FETCH_COOLDOWN_MS, CUSTOM_RANGE_COOLDOWN_MS } from "@/lib/shared/data-status"
  import { createHash } from "crypto"

  /** Generate fetch key for a period or custom date range */
  export function getFetchKey(period: string, startDate?: string, endDate?: string): string {
    if (period === "custom" && startDate && endDate) {
      const hash = createHash("md5").update(`${startDate}_${endDate}`).digest("hex").slice(0, 8)
      return `custom_${hash}`
    }
    return period
  }

  /** Try to acquire a live fetch lock. Returns true if acquired (proceed), false if cooldown active (skip). */
  export async function tryAcquireLiveFetch(
    supabase: SupabaseClient,
    storeId: string,
    fetchKey: string,
    createdBy: string = "unknown",
    cooldownMs?: number,
  ): Promise<boolean> {
    const cooldown = cooldownMs ?? (fetchKey.startsWith("custom_")
      ? CUSTOM_RANGE_COOLDOWN_MS
      : LIVE_FETCH_COOLDOWN_MS)

    const { data, error } = await supabase.rpc("try_acquire_live_fetch", {
      p_store_id: storeId,
      p_fetch_key: fetchKey,
      p_cooldown_ms: cooldown,
      p_created_by: createdBy,
    })

    if (error) {
      // If RPC fails, allow the fetch (fail-open)
      return true
    }
    return data === true
  }

  /** Release a live fetch lock after completion or failure. */
  export async function releaseLiveFetch(
    supabase: SupabaseClient,
    storeId: string,
    fetchKey: string,
    status: "completed" | "failed" = "completed",
    resultSummary?: Record<string, unknown>,
  ): Promise<void> {
    await supabase.rpc("release_live_fetch", {
      p_store_id: storeId,
      p_fetch_key: fetchKey,
      p_status: status,
      p_result_summary: resultSummary ?? null,
    })
  }
  ```

## Arquitetura Tecnica

### Fluxo de Live Fetch com Cooldown

```
Request 1 (portal, store_id=abc, period=30d):
  1. Check cache → MISS
  2. tryAcquireLiveFetch(abc, "30d") → true (inserted row)
  3. Call syncKlaviyoForPeriod(...)
  4. Save result to store_revenue_summary
  5. releaseLiveFetch(abc, "30d", "completed")
  6. Return data

Request 2 (portal, store_id=abc, period=30d, 5 seconds later):
  1. Check cache → HIT (from request 1)
  2. Return cached data

Request 3 (portal, store_id=abc, period=30d, concurrent with request 1):
  1. Check cache → MISS
  2. tryAcquireLiveFetch(abc, "30d") → false (cooldown active)
  3. Wait briefly, re-check cache → HIT (request 1 completed)
  4. Return cached data
  (OR: return "loading" status to frontend)
```

### Custom Date Range Key (M2)

```typescript
// Para custom date ranges, o fetch key inclui hash do date range
getFetchKey("custom", "2024-01-01", "2024-03-31")
// → "custom_a1b2c3d4"

// Cooldown de 30 minutos (CUSTOM_RANGE_COOLDOWN_MS)
// Impede re-fetch do mesmo range por 30min
```

### Fail-Open Strategy

Se o RPC falhar (conexao com banco, etc.), `tryAcquireLiveFetch` retorna `true` — permite o fetch. E melhor ter um fetch duplicado do que nenhum dado.

## Riscos e Mitigacoes

| Risco | Mitigacao |
|-------|-----------|
| PL/pgSQL function nao compilar | Testar migration localmente antes de merge |
| Race condition no proprio DELETE + INSERT | `ON CONFLICT DO NOTHING` e atomico no PostgreSQL — seguro |
| Cooldown table cresce infinitamente | `clean_expired_cooldowns` chamado pelo cron a cada 30min |
| Supabase RPC fail | Fail-open strategy — permite fetch se RPC falhar |
| `crypto.createHash` nao disponivel em Edge Runtime | `fetch-cooldown.service.ts` so e chamado em Node.js runtime (API routes) — seguro |
