# Story 22.2 -- Migration DB: Indexes + provider_used + HTTP Cache no Lookup

## Status
Done

## Story

**Como** sistema de rastreio,
**Quero** indexes otimizados, campo `provider_used` no banco, e cache HTTP no widget,
**Para que** o widget tenha performance adequada, possamos rastrear qual API retornou cada resultado, e respostas repetidas sejam cacheadas.

---

## Dependencia

> **22.2 Task 1 (migration) deve ser aplicada ANTES de 22.1.**
> O campo `provider_used` criado aqui e usado em 22.1.7.
> 22.2 Task 2 (Cache-Control) pode rodar em paralelo com 22.1.
>
> **Ordem de rollback:** Reverter 22.1 ANTES de reverter 22.2.
> Se reverter 22.2 com 22.1 ativa, o codigo tentara gravar em `provider_used` que nao existe (erro 400).

## Contexto

A migration de DB (Task 1) e pre-requisito de 22.1. O Cache-Control no endpoint (Task 2) e independente.

Combina a migration de DB (indexes + provider_used) com o Cache-Control no endpoint do widget. Ambos sao de baixo risco.

### Problemas identificados pelo DBA:
1. Index composto `(tracking_store_id, tracking_number)` faltando em `tracking_codes`
2. Index `idx_otc_email` no `order_tracking_cache` indexa `store_id`, NAO `customer_email` (nome enganoso)
3. Indexes faltando em `tracking_lookups` para email e order_number
4. Campo `provider_used` nao existe em `tracking_codes`
5. Endpoint `/api/tracking/lookup` sem `Cache-Control` header

## Acceptance Criteria

### 22.2.1 -- Criar migration Supabase

- [x] Migration SQL:
  ```sql
  -- 1. Campo provider_used em tracking_codes
  ALTER TABLE tracking_codes ADD COLUMN IF NOT EXISTS provider_used text;
  COMMENT ON COLUMN tracking_codes.provider_used IS
    'API provider that returned tracking data (cainiao, postnl, trackingmore, 17track)';

  -- 2. Index composto para widget lookup (tracking_number scoped by store)
  CREATE INDEX IF NOT EXISTS idx_tracking_codes_store_number
    ON tracking_codes (tracking_store_id, tracking_number);

  -- 3. Index de email no order_tracking_cache (corrige idx_otc_email que indexa store_id)
  CREATE INDEX IF NOT EXISTS idx_otc_customer_email
    ON order_tracking_cache (store_id, customer_email);

  -- 4. Indexes parciais em tracking_lookups
  CREATE INDEX IF NOT EXISTS idx_tracking_lookups_email
    ON tracking_lookups (customer_email)
    WHERE customer_email IS NOT NULL;

  CREATE INDEX IF NOT EXISTS idx_tracking_lookups_order_number
    ON tracking_lookups (order_number)
    WHERE order_number IS NOT NULL;

  -- 5. Index parcial para codigos ativos (usado por syncAllPendingCodes)
  CREATE INDEX IF NOT EXISTS idx_tracking_codes_active
    ON tracking_codes (last_checked_at ASC NULLS FIRST)
    WHERE status NOT IN ('delivered', 'expired');

  -- 6. Remover index antigo com nome enganoso (substituido por idx_otc_customer_email)
  DROP INDEX IF EXISTS idx_otc_email;
  ```
- [x] Todos os statements usam `IF NOT EXISTS` / `IF EXISTS` (idempotente)
- [x] NULL e aceitavel para `provider_used` em registros historicos (sem backfill)

### 22.2.4 -- Cache-Control no endpoint do widget

- [x] Adicionar `Cache-Control` header no response de `GET /api/tracking/lookup`:
  ```typescript
  const CACHE_TTL: Record<string, number> = {
    delivered: 3600,        // 1h
    in_transit: 300,        // 5min
    out_for_delivery: 120,  // 2min
    pending: 600,           // 10min
    info_received: 600,     // 10min
    exception: 900,         // 15min
    expired: 3600,          // 1h
  }
  ```
- [x] Se multiplos tracking codes no resultado com status diferentes: usar o MENOR TTL entre eles
- [x] Header format: `Cache-Control: public, s-maxage={ttl}, stale-while-revalidate=60`

## Dev Notes

### Migration

Aplicar via MCP Supabase `apply_migration`. Todos os statements sao idempotentes e nao-bloqueantes (CREATE INDEX nao faz lock exclusivo em Postgres para tabelas pequenas).

### Cache-Control no lookup

```typescript
// Em src/app/api/tracking/lookup/route.ts, antes do return final:

function getCacheTtl(results: WidgetResult[]): number {
  if (results.length === 0) return 60

  let minTtl = 3600
  for (const result of results) {
    for (const track of result.tracking) {
      const ttl = CACHE_TTL[track.status] ?? 300
      if (ttl < minTtl) minTtl = ttl
    }
  }
  return minTtl
}

// No return:
const cacheTtl = getCacheTtl(results)
return NextResponse.json(
  { results, query, found: results.length > 0 },
  {
    headers: {
      ...PUBLIC_CORS,
      "Cache-Control": `public, s-maxage=${cacheTtl}, stale-while-revalidate=60`,
    },
  }
)
```

### Nota: Sync-on-demand removido do escopo

A versao anterior (22.5) propunha "fire-and-forget sync em background" quando dados estavam stale. Isso foi removido porque:
1. Em Vercel serverless, fire-and-forget sem `after()` nao garante execucao
2. Race condition com sync batch (double API call + data overwrite)
3. O freshness guard da 22.1 + o cron existente ja cobrem a atualizacao de dados

Se no futuro quisermos sync-on-demand, usar `after()` do Next.js 15 com lock check.
