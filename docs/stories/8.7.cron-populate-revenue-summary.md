## Contexto

Com a tabela `store_revenue_summary` criada (Story 8.6) e o cron expandido para multiplos periodos (Story 8.5), o proximo passo eh fazer o cron popular a nova tabela com revenue agregado via upsert apos cada sync.

Atualmente o cron sincroniza metricas de flows e campaigns nas tabelas `klaviyo_flow_metrics` e `klaviyo_campaign_metrics`. Esta story adiciona um passo adicional: apos obter os dados de revenue de uma loja para um periodo, o cron faz upsert na `store_revenue_summary` com os totais agregados.

---

## Objetivo

Ao final de cada sync de loja+periodo, o cron deve agregar `conversion_value` de flows e campaigns e salvar na `store_revenue_summary` via upsert, incluindo `sync_status` e `expires_at`.

---

## Acceptance Criteria

- [x] **8.7.1** Apos cada sync de loja+periodo, o cron faz upsert na `store_revenue_summary` com:
  - `store_id`: ID da loja
  - `org_id`: org_id da loja (buscar de `client_stores.org_id`)
  - `period_label`: periodo sincronizado (7d, 15d, 30d, 90d)
  - `period_start` e `period_end`: datas reais do periodo calculadas por `parseDateRange()`
  - `klaviyo_total_revenue`: soma de campaign + flow revenue
  - `klaviyo_campaign_revenue`: soma de `conversion_value` de todas as campaigns
  - `klaviyo_flow_revenue`: soma de `conversion_value` de todos os flows
  - `shopify_total_revenue`: 0 (placeholder — Shopify revenue esta fora de escopo deste PRD, ver Secao 10)
  - `sync_status`: `'ok'` se todos os dados foram obtidos, `'partial'` se algum flow/campaign falhou, `'error'` se a loja inteira falhou
  - `sync_error`: mensagem de erro se `sync_status != 'ok'`, `NULL` caso contrario
  - `expires_at`: `NOW() + INTERVAL '6 hours'` (4x a frequencia do cron de 30min, margem para falhas)
  - `fetched_at`: `NOW()`

- [x] **8.7.2** O upsert usa `ON CONFLICT (store_id, period_label) DO UPDATE` conforme definido no PRD (Secao 3.3)

- [x] **8.7.5** O cron usa `createAdminClient()` (service_role) para escrita na `store_revenue_summary` — isso eh correto pois o cron nao eh um endpoint de usuario e a tabela so permite escrita via service_role

## Arquitetura Tecnica

### Upsert apos Sync

```typescript
async function upsertRevenueSummary(
  supabase: SupabaseClient,
  storeId: string,
  orgId: string,
  periodLabel: string,
  periodStart: Date,
  periodEnd: Date,
  klaviyoCampaignRevenue: number,
  klaviyoFlowRevenue: number,
  syncStatus: 'ok' | 'partial' | 'error',
  syncError: string | null
): Promise<void> {
  const { error } = await supabase
    .from('store_revenue_summary')
    .upsert({
      store_id: storeId,
      org_id: orgId,
      period_label: periodLabel,
      period_start: periodStart.toISOString(),
      period_end: periodEnd.toISOString(),
      klaviyo_total_revenue: klaviyoCampaignRevenue + klaviyoFlowRevenue,
      klaviyo_campaign_revenue: klaviyoCampaignRevenue,
      klaviyo_flow_revenue: klaviyoFlowRevenue,
      shopify_total_revenue: 0, // Placeholder
      sync_status: syncStatus,
      sync_error: syncError,
      expires_at: new Date(Date.now() + 6 * 60 * 60 * 1000).toISOString(),
      fetched_at: new Date().toISOString(),
    }, { onConflict: 'store_id,period_label' })

  if (error) {
    log.error(`[Cron] Failed to upsert revenue summary for store ${storeId} period ${periodLabel}:`, error)
  }
}
```

## Riscos e Mitigacoes

| Risco | Mitigacao |
|-------|-----------|
| Revenue calculado incorretamente (dupla contagem) | Agregar a partir dos dados retornados pela API, nao das tabelas de metricas |
| Loja sem org_id causa FK violation | Skip com warning; nao deveria acontecer em dados limpos |
| `expires_at` de 6h eh muito curto se cron falhar | 6h = 12x a frequencia (30min); se 12 execucoes consecutivas falharem, ha problemas maiores |
