# Story 55.1 — Period Rotation: Skip Fresh Periods

## Story

**Como** operador do sistema que gerencia 42 lojas,
**Quero** que o cron nao re-sincronize periodos que ja tem dados frescos no cache,
**Para que** o budget de tempo do cron seja gasto apenas em dados que realmente precisam de refresh.

## Contexto

### Problema

O cron sincroniza 4 periodos (7d, 15d, 30d, 90d) para CADA loja, sem verificar se os dados ja estao frescos. Periodos longos (30d, 90d) mudam pouco a cada 30 minutos — re-sincronizar a cada run desperdicea ~62% das API calls.

### Dados Atuais

- 42 lojas x 4 periodos = **168 syncs por run**
- Cada sync = 3 API calls (flow-values-report, campaign-values-report, metric-aggregates)
- Total: **~504 API calls** por run
- Com freshness check: **~190 API calls** (~62% reducao)

### Thresholds de Freshness

| Periodo | Freshness Threshold | Justificativa |
|---------|--------------------|-|
| 7d | Sempre sync | Dados mudam rapido (orders recentes) |
| 15d | 2 horas | Mudanca moderada, 2h e suficiente |
| 30d | 4 horas | Mudanca lenta, 4h e aceitavel |
| 90d | 8 horas | Quase estatico, 8h e conservador |

### Como Funciona

1. Antes de processar uma loja, o cron faz query em `store_revenue_summary` para buscar `fetched_at` de cada periodo
2. Para cada periodo, compara `fetched_at` com o threshold
3. Se `fetched_at` esta dentro do threshold, skip o periodo
4. Lojas novas (sem nenhum registro no cache) sincronizam TODOS os periodos

## Acceptance Criteria

### 55.1.1 — Consultar freshness antes de sincronizar

- [x] Antes de chamar `syncStore`, buscar `fetched_at` de cada store/period em `store_revenue_summary`
- [x] Query: `SELECT period_label, fetched_at FROM store_revenue_summary WHERE store_id = $1 AND sync_status IN ('ok', 'partial')`
- [x] Passar o mapa de freshness para `syncStore` como parametro

### 55.1.2 — Filtrar periodos frescos

- [x] Dentro de `syncStore`, para cada periodo, verificar se `fetched_at` esta dentro do threshold
- [x] Se fresco, adicionar ao resultado como `status: "skipped"` com `error: "fresh (fetched Xmin ago)"`
- [x] Periodos sem entrada no cache (NULL fetched_at) sao SEMPRE sincronizados

### 55.1.3 — Constantes configuraveis

- [x] Criar constante `PERIOD_FRESHNESS_THRESHOLDS` em `src/lib/shared/data-status.ts`:
  ```typescript
  /** How long each period's cache is considered "fresh enough" to skip re-sync */
  export const PERIOD_FRESHNESS_THRESHOLDS: Record<CachedPeriod, number> = {
    "7d":  0,              // always sync
    "15d": 2 * 60 * 60_000, // 2 hours
    "30d": 4 * 60 * 60_000, // 4 hours
    "90d": 8 * 60 * 60_000, // 8 hours
  }
  ```

### 55.1.4 — Lojas novas sincronizam tudo

- [x] Se uma loja nao tem NENHUM registro em `store_revenue_summary`, sincronizar todos os 4 periodos
- [x] Isso garante que lojas recem-adicionadas recebem dados completos no primeiro run

### 55.1.5 — Logging de skip vs sync

- [x] Log por loja: `"[Cron] StoreName: syncing 2/4 periods (skipped 15d=45min ago, 90d=2h ago)"`
- [x] Log resumo no final: `"[Cron] Total: 65/168 periods synced, 103 skipped (fresh)"`

### 55.1.6 — Sem regressao

- [x] Lojas existentes continuam recebendo dados (7d sempre synca)
- [x] `npm run build` passa sem erros

## Riscos

| Risco | Mitigacao |
|-------|----------|
| Freshness query adiciona latencia | Query simples (index em store_id + period_label ja existe) |
| Skip excessivo causa dados desatualizados | 7d SEMPRE synca; thresholds conservadores; pode ajustar via constantes |
| Bug no calculo de freshness | Fallback: se fetched_at e NULL ou invalido, sync normalmente |

## Notes

- A query de freshness pode ser feita em batch para todas as lojas de um grupo, evitando N queries individuais
- O campo `fetched_at` ja existe em `store_revenue_summary` e e populado pelo cron a cada sync
