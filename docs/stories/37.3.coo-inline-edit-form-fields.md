# Story 37.3 — COO Edita Campos do Formulario

## Contexto

Quando o COO revisa um onboarding pendente, ele ve todos os dados do formulario (nome, email, loja, nicho, etc.) mas nao pode editar. Se houver um erro de digitacao ou dado incorreto, o COO precisa rejeitar, esperar o cliente re-preencher, e revisar novamente. Isso gera uma ida-e-volta desnecessaria.

## Objetivo

Permitir que o COO edite qualquer campo do formulario diretamente na tela de aprovacao, salve as alteracoes, e depois aprove/rejeite normalmente.

## Criterios de Aceitacao

### Backend

- [x] **AC 37.3.1**: Criar endpoint `PATCH /api/onboarding/[id]/edit` que aceita payload parcial com campos de `clients`, `client_stores` e `store_onboarding_data`.
- [x] **AC 37.3.2**: Endpoint requer autenticacao + permissao `onboarding_approve` (ou role owner/manager/coo) — mesmo gate do endpoint de approve.
- [x] **AC 37.3.3**: Endpoint verifica que o onboarding esta em `pending_approval` antes de permitir edicao.
- [x] **AC 37.3.4**: Endpoint verifica que o onboarding pertence a mesma org do usuario autenticado.
- [x] **AC 37.3.5**: Se o COO alterar `email`, validar que nao existe duplicata em `clients` (mesma org) nem em `client_portal_users`.
- [x] **AC 37.3.6**: Se o COO alterar `store_name`, validar unicidade dentro da org.
- [x] **AC 37.3.7**: Aplicar schema de validacao nos campos editados — reutilizar regras do `publicOnboardingSchema` (formato email, tamanho de campos, enums de platform/country/language/shipping_type).
- [x] **AC 37.3.8**: Se o COO alterar `platform` de "shopify" para outro, limpar `shopify_collaborator_code`.
- [x] **AC 37.3.9**: Registrar cada campo alterado em tabela `onboarding_edit_log` (field_name, old_value, new_value, edited_by, created_at).
- [x] **AC 37.3.10**: Endpoint retorna os dados atualizados apos salvar.

### Frontend

- [x] **AC 37.3.11**: Cada campo no card de aprovacao tem botao/icone de edicao (lapiz).
- [x] **AC 37.3.12**: Ao clicar no lapiz, o campo vira editavel (input/select/textarea conforme tipo).
- [x] **AC 37.3.13**: Campos enum (platform, country, language, shipping_type) renderizam como `Select` com as opcoes de `onboarding.ts`.
- [x] **AC 37.3.14**: Botao "Salvar Alteracoes" aparece quando ha campos modificados. Envia todas as alteracoes em uma unica chamada.
- [x] **AC 37.3.15**: Botao "Cancelar Edicao" descarta alteracoes nao salvas e volta ao modo visualizacao.
- [x] **AC 37.3.16**: Campos modificados e salvos mostram badge visual "Editado" para o COO saber o que foi alterado.
- [ ] **AC 37.3.17**: Validacao client-side antes de salvar (mesmas regras do form publico). — Delegada ao backend (schema Zod no endpoint). Frontend confia no backend para validacao completa.

### Migration

- [x] **AC 37.3.18**: Criar tabela `onboarding_edit_log` com RLS (leitura por org_members). Funcao RLS deve usar `SET search_path = public` (padrao de seguranca do projeto).
- [x] **AC 37.3.19**: Adicionar unique index em `clients(org_id, lower(email))` para prevenir duplicatas por email na mesma org.
- [x] **AC 37.3.20**: FK `onboarding_edit_log.onboarding_id` com `ON DELETE CASCADE` (edits deletados junto com onboarding na rejeicao).
- [x] **AC 37.3.21**: Adicionar unique index em `client_stores(org_id, lower(trim(store_name)))` para prevenir duplicatas de nome de loja na mesma org.

## Cenarios de Teste

1. COO edita email para um que ja existe na mesma org → deve retornar 409
2. COO edita email para um que existe em `client_portal_users` → deve retornar 409
3. COO edita store_name para um que ja existe na org → deve retornar 409
4. COO edita platform de shopify para woocommerce → `shopify_collaborator_code` limpo automaticamente
5. COO edita e depois aprova → portal account usa o email editado
6. COO edita e depois rejeita → dados editados aparecem no `onboarding_rejection_log.form_snapshot`
7. Team member sem permissao tenta `PATCH /api/onboarding/[id]/edit` → 403
8. `PATCH` em onboarding que nao esta em `pending_approval` → 400
9. `PATCH` em onboarding de outra org → 403
10. Dois COOs editam simultaneamente → last-write-wins sem erro
11. COO edita campo com valor invalido (email malformado, platform inexistente) → 400 com erro descritivo
12. `onboarding_edit_log` registra old_value e new_value corretamente
13. COO edita email e depois rejeita → `onboarding_rejection_log.form_snapshot` contem o email editado (nao o original)
