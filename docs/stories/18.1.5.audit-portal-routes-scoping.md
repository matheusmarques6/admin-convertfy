## Story

**Como** administrador do sistema,
**Quero** que TODAS as rotas portal sejam auditadas para scoping correto por client_id,
**Para que** nenhuma rota permita acesso cross-tenant, mesmo com adminClient.

## Acceptance Criteria

### Auditoria

- [ ] **AC 18.1.5.1** — Auditar CADA rota portal e confirmar scoping. Para cada rota, verificar:
  1. Usa `adminClient` ou `supabase`?
  2. Se `adminClient`: tem filtro `.eq("client_id", ...)` ou equivalente?
  3. Se `supabase`: a policy RLS cobre o acesso (ex: `auth_user_id = auth.uid()`)?
  4. Resultado: OK, FIX NEEDED, ou DEAD CODE

- [ ] **AC 18.1.5.2** — Documentar resultado da auditoria na tabela acima (atualizar esta story)

### GAP-3: integrations bypass policy

- [ ] **AC 18.1.5.3** — Documentar status da bypass policy de `integrations`:
  - Policy: `"Authenticated users can manage integrations"` com `USING(true)`
  - Status apos 18.1.1: invoices usa `adminClient` com filtro `org_id` (fixado)
  - Portal `integrations/route.ts` ja usa `adminClient` com `.eq("client_id", ...)` (OK)
  - Risco residual: qualquer usuario autenticado pode ler integracoes via Supabase JS client
  - Decisao: documentar como candidata para Story 18.2 (remediacoes admin-only)

### Dead code

- [ ] **AC 18.1.5.4** — Documentar `settings/notifications/route.ts` como dead code:
  - Tabela `client_notification_preferences` NAO EXISTE no banco
  - Queries falham silenciosamente
  - NAO e risco de seguranca, mas e tech debt
  - Adicionar comentario `// TODO: Dead code — tabela client_notification_preferences nao existe` no topo do arquivo

### Rotas com supabase que dependem de policies

- [ ] **AC 18.1.5.5** — Confirmar que as seguintes rotas continuam funcionando apos P0:
  - `settings/route.ts` GET/PUT: usa `supabase` -> `client_portal_users` com policy `auth_user_id`
  - `settings/avatar/route.ts` POST/DELETE: usa `supabase` -> `client_portal_users` com policy `auth_user_id`
  - `settings/password/route.ts` PUT: usa `supabase` -> `client_portal_users` com policy `auth_user_id`
  - `change-password/route.ts` POST: SELECT via `supabase` (policy OK), UPDATE via `adminClient` (OK)
  - Todas funcionam porque dependem da policy `"Portal users can view/update own record"` que filtra por `auth_user_id = auth.uid()` — esta policy NAO e removida em P0
