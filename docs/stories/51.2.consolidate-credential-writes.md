# Story 51.2 — Consolidar Escritas no `updateStoreCredentials()`

## Story

**Como** engenheiro de backend,
**Quero** que toda escrita de credenciais passe pelo `updateStoreCredentials()`,
**Para que** validacao ASCII, encryption e futuras extensoes (audit log, webhooks) sejam aplicadas consistentemente.

## Contexto

### Problema

6 endpoints escrevem credenciais diretamente no banco com `encrypt()` manual, bypasando `validateCredentialField()` do `credentials.service.ts`. Isso ja causou o bug da BRINQUEMAIS (U+2022 bullet character na API key).

### Endpoints que bypasam o service

| # | Arquivo | Linha(s) | Integracao | Escrita atual |
|---|---------|----------|-----------|--------------|
| 1 | `src/app/api/portal/stores/route.ts` | PUT, L128-141 | Klaviyo + Shopify | `encrypt()` direto |
| 2 | `src/app/api/portal/integrations/route.ts` | PUT, L189-234 | Shopify + Klaviyo | `encrypt()` direto |
| 3 | `src/app/api/portal/onboarding/wizard/route.ts` | L395-406 | Klaviyo (step `klaviyo_keys`) | `encrypt()` direto |
| 4 | `src/app/api/client-stores/credentials/route.ts` | POST L242, PUT L344 | Todos | `processFields()` local com `encrypt()` |
| 5 | `src/app/api/cron/sync-reports/route.ts` | L208, L232, L356, L377 | Klaviyo | Validation metadata (nao credenciais) |
| 6 | `src/app/api/admin/encrypt-credentials/route.ts` | L63 | Migration tool | Re-encryption (OK manter) |

### O que NAO precisa migrar

- **#5 (cron sync-reports)**: Escreve apenas campos de validacao (`klaviyo_validation_error`, `klaviyo_missing_scopes`, etc.), NAO credenciais. Aceitavel como esta, mas idealmente criar `updateStoreValidationStatus()`.
- **#6 (encrypt-credentials)**: Migration tool de uso unico. Pode manter como esta.

## Acceptance Criteria

### 51.2.0 — Adicionar `resetValidation` option ao `updateStoreCredentials()` (PRE-REQUISITO)

> **QA C2/C3:** O portal seta `validated_at = NULL` (pending re-validation) ao salvar credenciais, mas `updateStoreCredentials()` com `integrationKey` seta `validated_at = NOW` (connected). Semantica oposta — precisa ser resolvido antes de migrar os endpoints.

- [ ] Adicionar parametro opcional `resetValidation?: boolean` ao `updateStoreCredentials()`:
  ```typescript
  export async function updateStoreCredentials(
    storeId: string,
    credentials: Partial<StoreCredentials>,
    integrationKey?: "shopify" | "klaviyo" | "meta",
    options?: { resetValidation?: boolean }
  ): Promise<void>
  ```
- [ ] Quando `resetValidation: true` e `integrationKey` e fornecido:
  - Setar `{integration}_validated_at = null` (pending)
  - Setar `{integration}_validation_error = null`
  - Setar `{integration}_missing_scopes = null` (se aplicavel)
  - Setar `{integration}_has_reporting_access = null` (se aplicavel)
- [ ] Quando `resetValidation: false` ou omitido: manter comportamento atual (`validated_at = NOW`)
- [ ] Endpoints do portal devem chamar com `{ resetValidation: true }`
- [ ] Endpoints do admin (OAuth callbacks, integrations/save) mantem `{ resetValidation: false }` (default)

**Arquivo:** `src/lib/services/credentials.service.ts`

### 51.2.4 — Migrar `/api/client-stores/credentials` POST/PUT

> **QA C3-DB:** O POST handler NAO deve ser separado em INSERT + UPDATE (two-phase). Isso cria risco de partial failure onde a store existe sem credenciais. Manter INSERT atomico.

- [ ] Ler `src/app/api/client-stores/credentials/route.ts`
- [ ] Remover `processFields()` local e `ENCRYPTED_FIELDS` local (ja removido em 51.1)
- [ ] **POST handler — manter INSERT atomico:**
  - Importar `ENCRYPTED_FIELDS` do constants file
  - Antes do INSERT, encriptar campos usando o service: chamar `encrypt()` para cada campo em `ENCRYPTED_FIELDS` que foi enviado no body
  - Ou criar `encryptCredentialFields(fields)` helper no service que recebe os campos e retorna encriptados + validados
  - O INSERT continua sendo uma unica operacao atomica com todos os campos (metadata + credenciais encriptadas)
  - NAO separar em INSERT + UPDATE
- [ ] **PUT handler:** substituir `processFields()` + `.update()` por `updateStoreCredentials()`
- [ ] Manter `validateShopifyCredentials()` e `validateKlaviyoCredentials()` existentes (eles testam a key contra a API)
- [ ] Testar: criar store com credenciais → verificar que sao encriptadas corretamente

**Arquivo:** `src/app/api/client-stores/credentials/route.ts`

## Riscos

| Risco | Mitigacao |
|-------|----------|
| `updateStoreCredentials()` pode nao suportar todos os campos que os endpoints enviam | Verificar a signature do service — pode precisar de extensao para campos como `shopify_store_domain` (nao e credencial, mas e enviado junto) |
| POST de client-stores cria a store + credenciais na mesma operacao | **NAO separar em two-phase** (QA C3-DB). Manter INSERT atomico: encriptar campos antes do INSERT usando helpers do service |
| Portal stores PUT envia campos mistos (credenciais + metadata) | Separar os campos: metadata via `.update()` direto, credenciais via `updateStoreCredentials()`. Documentar este pattern no AC |
| Portal seta `validated_at = NULL`, service seta `validated_at = NOW` | Resolvido em AC 51.2.0: parametro `resetValidation: true` para endpoints do portal (QA C2/C3) |
