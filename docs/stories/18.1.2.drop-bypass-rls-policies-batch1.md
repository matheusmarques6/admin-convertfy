## Story

**Como** administrador do sistema,
**Quero** remover todas as policies RLS bypass (`USING(true)`) das tabelas criticas do portal,
**Para que** o isolamento multi-tenant seja enforced pelo banco de dados e nao apenas pelo codigo aplicacional.

---

## Contexto

### Problema

PostgreSQL usa OR semantics para PERMISSIVE policies: se QUALQUER policy retorna true, o acesso e concedido. As policies legacy com `USING(true)` anulam TODAS as policies hardened existentes.

### Tabelas afetadas neste batch

| Tabela | Policies bypass | Policies hardened existentes |
|--------|----------------|------------------------------|
| `client_stores` | 2 | `org_client_stores_*` (SELECT/INSERT/UPDATE/DELETE com org_id) |
| `clients` | 4 | `org_clients_*` (SELECT/INSERT/UPDATE/DELETE com org_id) |
| `client_portal_users` | 1 | `"Portal users can view own record"`, `"Portal users can update own record"` |
| `invoices` | 1 | `"Access invoices by client"`, `"Admin can manage invoices"`, `"Users can view invoices"` |
| `meetings` | 1 (GAP-1 do QA) | Hardened policies existentes (verificar) |
| `meeting_participants` | 3 (GAP-1 do QA) | Nenhuma hardened (verificar) |

### Pre-requisito BLOQUEANTE

**Story 18.1.1 DEVE estar deployada em producao** antes de executar esta migration. Sem o fix de codigo:
- Login portal FUNCIONA (policy `auth_user_id = auth.uid()` cobre o SELECT)
- UPDATE de `last_login_at` via `supabase` FUNCIONA (policy `"Portal users can update own record"`)
- Invoices portal QUEBRA (policies restantes requerem `can_access_client()` -- portal users nao sao org_members)
