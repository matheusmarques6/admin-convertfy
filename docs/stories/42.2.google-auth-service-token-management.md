# Story 42.2 — Google Auth Service: token management per-user

## Story

**Como** desenvolvedor da plataforma,
**Quero** um service dedicado para gerenciar tokens Google OAuth per-user,
**Para que** todas as operacoes de Calendar usem tokens validos com refresh automatico e tratamento de revogacao.

## Contexto

### Estado atual

- Tokens Google sao salvos em `client_stores` via `credentials.service.ts` (per-store, incorreto para Calendar)
- Nao existe service dedicado para refresh automatico de tokens Google
- Nao existe deteccao de token revogado
- `@/lib/crypto` ja implementa AES-256-GCM com prefix `enc:v1:` (reusar)

### O que precisa mudar

Criar `google-auth.service.ts` que:
1. Salva tokens encriptados na tabela `user_google_tokens`
2. Busca e retorna access_token valido (refresh automatico se expirado)
3. Detecta revogacao (401 do Google) e marca `is_active = false`
4. Expoe status de conexao para UI
5. Permite desconexao (revoke + delete)

## Acceptance Criteria

- [x] **AC 42.2.1**: Service criado em `src/lib/services/google-auth.service.ts`

- [x] **AC 42.2.2**: Funcao `saveTokens(userId, userType, orgId, googleTokens, userInfo)`:
  - Encripta `access_token` e `refresh_token` com AES-256-GCM via `@/lib/crypto` (prefix `enc:v1:`)
  - Calcula `expires_at` a partir de `expires_in` do Google
  - Salva `google_email` e `google_account_id` (do userinfo)
  - Salva `scopes` recebidos como array
  - UPSERT: se user ja tem registro, atualiza tokens (reconexao)
  - Usa `createAdminClient()` para write (RLS nao permite INSERT de dados encriptados via user client)

- [x] **AC 42.2.3**: Funcao `getValidAccessToken(userId, userType)`:
  - Busca registro em `user_google_tokens`
  - Verifica `is_active` — se false, retorna null com erro
  - Verifica `expires_at` — se expirado (ou expira em < 5 min), faz refresh
  - Decripta e retorna `access_token` valido
  - Se nao encontrou registro, retorna null

- [x] **AC 42.2.4**: **[C3]** Token refresh com padrao 401 -> refresh -> retry:
  - Usa `refresh_token` para obter novo `access_token` via `https://oauth2.googleapis.com/token`
  - Atualiza `access_token`, `expires_at` no banco
  - Se refresh falha (400/401 do Google = token revogado):
    - Marca `is_active = false`
    - Popula `sync_error = 'Token revogado pelo usuario. Reconecte seu Google Calendar.'`
    - NAO deleta o registro (preserva google_email para UI)
  - Retorna novo `access_token` se sucesso, null se falhou

- [x] **AC 42.2.5**: Funcao `getConnectionStatus(userId, userType)`:
  - Retorna `{ connected: boolean, google_email: string | null, is_active: boolean, last_synced_at: string | null, sync_error: string | null }`
  - Se nao tem registro: `{ connected: false, ... }`
  - Se tem registro inativo: `{ connected: true, is_active: false, sync_error: '...' }`

- [x] **AC 42.2.6**: Funcao `disconnectGoogle(userId, userType)`:
  - Revoga token no Google: `POST https://oauth2.googleapis.com/revoke?token={access_token}`
  - Deleta registro de `user_google_tokens`
  - Nao falha se revoke no Google retorna erro (token pode ja estar revogado)

- [x] **AC 42.2.7**: **[C6]** Handle missing refresh_token:
  - Se ao fazer refresh, `refresh_token` esta vazio/null no banco:
    - Marca `sync_error = 'Refresh token ausente. Reconecte com prompt de consentimento.'`
    - Marca `is_active = false`
  - Isso forca o usuario a reconectar com `prompt: 'consent'` (tratado na story 42.3)

- [x] **AC 42.2.8**: Tokens nunca expostos em logs ou responses:
  - `log.info` usa apenas `{ userId, userType, google_email }`, nunca tokens
  - `getConnectionStatus` retorna status e email, nunca tokens
  - `getValidAccessToken` retorna apenas o access_token decriptado para uso interno

### Estrutura do service

```typescript
import { createAdminClient } from '@/lib/supabase/admin'
import { encrypt, decrypt } from '@/lib/crypto'

const log = logger.child('GoogleAuth')
const GOOGLE_TOKEN_URL = 'https://oauth2.googleapis.com/token'

interface GoogleTokens {
  access_token: string
  refresh_token?: string
  token_type: string

  email: string
  id: string // google account id (sub claim)
}

  google_email: string | null
  is_active: boolean
  last_synced_at: string | null
  sync_error: string | null

export async function saveTokens(
  userId: string,
  userType: 'profile' | 'portal_user',
  orgId: string,
  tokens: GoogleTokens,
  userInfo: GoogleUserInfo
): Promise<void> { ... }

export async function getValidAccessToken(
  userId: string,
  userType: 'profile' | 'portal_user'
): Promise<string | null> { ... }

export async function getConnectionStatus(
  userId: string,
  userType: 'profile' | 'portal_user'
): Promise<ConnectionStatus> { ... }

export async function disconnectGoogle(
  userId: string,
  userType: 'profile' | 'portal_user'
): Promise<void> { ... }
```

### Uso do adminClient

- `saveTokens` e `disconnectGoogle` usam `createAdminClient()` porque:
  1. Tokens sao encriptados (RLS user client nao consegue ler/escrever dados encriptados corretamente)
  2. Cron/background jobs precisam acessar tokens de qualquer user
- `getConnectionStatus` pode usar `createClient()` (RLS permite SELECT do proprio user)

### Integracao com crypto existente

- `encrypt(value)` retorna string com prefix `enc:v1:` (AES-256-GCM)
- `decrypt(value)` aceita string com prefix `enc:v1:` e retorna plaintext
- Mesmo padrao usado em `credentials.service.ts` para Klaviyo/Shopify keys

|-------|------|-----------|
