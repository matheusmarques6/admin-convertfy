# Story 14.2 — Email Logs: Remover Role 'coo' da Policy de Visualizacao

## Contexto

A migration `20260302_email_logs.sql` criou a tabela `email_logs` para rastrear todos os emails enviados via Resend. A policy RLS de SELECT (`email_logs_select_admin`) foi inicialmente criada permitindo acesso a usuarios com roles `admin`, `manager` e `coo`.

Apos revisao de seguranca e definicao de responsabilidades de roles, ficou determinado que a role `coo` nao deve ter acesso direto aos logs de email — o acesso a logs operacionais de sistema e restrito a `admin` e `manager`. A role `coo` tem permissoes de negocio (aprovacao de onboarding, visao estrategica), nao de auditoria tecnica.

## Objetivo

**Como** administrador de seguranca do sistema,
**Quero** que a visualizacao de email logs seja restrita apenas a `admin` e `manager`,
**Para que** a role `coo` nao tenha acesso a dados tecnicos de auditoria de emails, seguindo o principio do menor privilegio.

## Acceptance Criteria

- [x] **14.2.1** — A policy `email_logs_select_admin` permite SELECT apenas para usuarios com `profiles.role IN ('admin', 'manager')`.
- [x] **14.2.2** — A role `coo` NAO possui acesso de SELECT na tabela `email_logs` via RLS.
- [x] **14.2.3** — A policy de INSERT (`email_logs_insert_service`) permanece inalterada com `WITH CHECK (true)` (usado pelo service role via backend).
- [x] **14.2.4** — Os indices da tabela `email_logs` estao corretos: `to_email`, `status`, `created_at DESC`, `template_type`.
- [x] **14.2.5** — RLS esta habilitado na tabela (`ALTER TABLE email_logs ENABLE ROW LEVEL SECURITY`).

## Arquitetura Tecnica

### Arquivo Modificado

**`supabase/migrations/20260302_email_logs.sql`** — Migration que cria a tabela e suas policies. A mudanca foi feita diretamente na migration antes de aplicacao em producao.

### Schema da Tabela

```sql
CREATE TABLE IF NOT EXISTS email_logs (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  to_email TEXT NOT NULL,
  subject TEXT NOT NULL,
  template_type TEXT NOT NULL DEFAULT 'custom',
  resend_id TEXT,
  status TEXT NOT NULL DEFAULT 'pending',
  error_message TEXT,
  metadata JSONB DEFAULT '{}',
  sent_by UUID REFERENCES auth.users(id),
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

### Policy Corrigida (BEFORE vs AFTER)

**BEFORE (incorreto):**
```sql
CREATE POLICY "email_logs_select_admin" ON email_logs
  FOR SELECT
  USING (
    EXISTS (
      SELECT 1 FROM profiles
      WHERE profiles.id = auth.uid()
      AND profiles.role IN ('admin', 'manager', 'coo')  -- 'coo' removido
    )
  );
```

**AFTER (correto):**
```sql
CREATE POLICY "email_logs_select_admin" ON email_logs
  FOR SELECT
  USING (
    EXISTS (
      SELECT 1 FROM profiles
      WHERE profiles.id = auth.uid()
      AND profiles.role IN ('admin', 'manager')
    )
  );
```

### Roles e seus Acessos a email_logs

| Role | SELECT | INSERT |
|------|--------|--------|
| `admin` | Sim | Via service role |
| `manager` | Sim | Via service role |
| `coo` | Nao | Via service role |
| `agent` | Nao | Via service role |
| `client` | Nao | Via service role |

### Decisao de Design de Seguranca

A role `coo` (Chief Operating Officer) tem permissoes orientadas a negocio:
- Aprovacao de onboarding de clientes
- Visao de metricas de operacao
- Acesso ao kanban de onboarding

Logs tecnicos de email (Resend IDs, erros de entrega, metadata de templates) sao dados de auditoria tecnica, responsabilidade de `admin` e `manager` — nao do `coo`.
