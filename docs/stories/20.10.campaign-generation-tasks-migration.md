## Acceptance Criteria

### 20.10.1 -- Expandir org_role enum

- [x] Adicionar 'sdr' ao enum `org_role`
- [x] Adicionar 'techlead' ao enum `org_role`
- [x] Adicionar ao `user_role` se necessario
- [x] Atualizar `apply_board_config_preset()` para sdr e techlead

### 20.10.2 -- Expandir campaign_generations status

- [x] Expandir CHECK para incluir 'approved' e 'completed'
- [x] Adicionar colunas `approved_by` (FK org_members) e `approved_at`

### 20.10.3 -- Criar tabela campaign_generation_tasks

- [x] Campos: id, generation_id, org_id, role, assignee_id, status, started_at, completed_at, completed_by, notes, created_at, updated_at
- [x] CHECK role IN ('designer', 'techlead', 'sdr')
- [x] CHECK status IN ('pending', 'in_progress', 'completed', 'skipped')
- [x] UNIQUE(generation_id, role) -- uma task por role por geracao
- [x] ON DELETE CASCADE no generation_id

### 20.10.4 -- Triggers

- [x] `fn_create_generation_tasks()`: quando status muda para 'approved', cria 3 tasks automaticamente
- [x] `fn_check_generation_completion()`: quando todas tasks completed/skipped, marca generation como 'completed'
- [x] Ambos SECURITY DEFINER + idempotentes

### 20.10.5 -- RLS Policies

- [x] `cg_tasks_admin_all`: admin bypass
- [x] `cg_tasks_org_select`: org members veem tasks da sua org
- [x] `cg_tasks_owner_insert`: owner/manager/coo podem inserir
- [x] `cg_tasks_update`: assignee atualiza propria task; owner/manager/coo atualizam qualquer
- [x] `org_member_select_generations`: org members podem ver generations dos seus clientes
- [x] `org_member_update_generations`: owner/manager/coo podem atualizar generations (aprovar)

### 20.10.6 -- Indices

- [x] idx_cg_tasks_generation_id
- [x] idx_cg_tasks_org_id
