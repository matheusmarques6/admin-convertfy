# Story 42.5 — Integrar Calendar sync no CRUD de meetings (POST/PUT/DELETE)

## Story

**Como** admin user da plataforma,
**Quero** que ao criar, editar ou cancelar uma reuniao, o Google Calendar seja atualizado automaticamente,
**Para que** meu calendario esteja sempre sincronizado sem acao manual.

## Contexto

### Estado atual

- `POST /api/meetings` cria meeting + participantes + auto-task no board
- `PUT /api/meetings/[id]` atualiza meeting, suporta `participant_response` e reconciliacao de participantes
- `DELETE /api/meetings/[id]` exclui meeting
- Nenhuma dessas rotas interage com Google Calendar

### O que precisa mudar

Integrar chamadas ao `google-calendar-sync.service` nas rotas existentes:
1. POST: apos criar meeting local, chamar `syncMeetingToGoogle`
2. PUT: ao editar titulo/data/participantes, chamar `updateGoogleEvent`
3. DELETE/Cancel: chamar `deleteGoogleEvent` antes de deletar/cancelar

## Acceptance Criteria

- [x] **AC 42.5.1**: `POST /api/meetings` — apos criar meeting e participantes no banco:
  - **[H1]** POST body aceita campo opcional `timezone` (default: `'America/Sao_Paulo'`). Persistir em `meetings.timezone` no INSERT
  - Identifica o organizador (participant com `is_organizer = true`, ou o `user_id` da meeting)
  - Chama `syncMeetingToGoogle(meetingId, organizerUserId)`
  - Se sync retorna `{ synced: true }`: resposta normal com dados da meeting (incluindo meet_link)
  - Se sync retorna `{ synced: false }`: resposta normal com meeting criada + campo `google_sync_warning` no response (NAO falhar a criacao)

- [x] **AC 42.5.2**: `PUT /api/meetings/[id]` — ao editar titulo, scheduled_at, duration, participantes:
  - **[H1]** PUT body aceita campo opcional `timezone`. Se presente, persistir em `meetings.timezone` no UPDATE
  - **[M3]** O SELECT do existing meeting antes do update deve incluir `google_event_id, user_id, scheduled_at` (alem de `id`), pois sao necessarios para decidir se criar vs atualizar evento Google e para detectar reagendamento
  - Chama `updateGoogleEvent(meetingId)`
  - Se meeting nao tem `google_event_id` (nunca sincronizada): tenta `syncMeetingToGoogle` (criar)
  - Se sync falha: atualiza `google_sync_status = 'error'` mas nao falha o update local

- [x] **AC 42.5.3**: `PUT /api/meetings/[id]` com reagendamento (scheduled_at mudou):
  - Alem de chamar `updateGoogleEvent`, reset `response_status` para `'pending'` em todos os `meeting_participants`
  - Google Calendar notifica participantes automaticamente via `sendUpdates: "all"`

- [x] **AC 42.5.4**: `DELETE /api/meetings/[id]` — antes de deletar do banco:
  - Chama `deleteGoogleEvent(meetingId)` para deletar do Google Calendar
  - Se `deleteGoogleEvent` falha: log warning mas continua com delete local (Google pode limpar depois)
  - Ordem: delete Google -> delete local

- [x] **AC 42.5.5**: Status change para `'cancelled'` (via PUT com `status: 'cancelled'`):
  - Chama `deleteGoogleEvent(meetingId)` para cancelar no Google
  - Google notifica participantes automaticamente

- [x] **AC 42.5.6**: Se sync falha em qualquer operacao, response inclui warning mas NAO falha:
  - Response HTTP status permanece 200/201
  - Response body inclui `google_sync_status` e `google_sync_error` para informar a UI
  - Meeting local e SEMPRE a fonte de verdade

- [x] **AC 42.5.7**: `google_sync_status` atualizado em cada operacao:
  - Apos sync bem-sucedido: `'synced'`
  - Apos falha de sync: `'error'`
  - Meeting sem Calendar conectado: `'not_connected'`

- [x] **AC 42.5.8**: Sem regressao nas funcionalidades existentes:
  - Criar meeting sem Google Calendar conectado funciona normalmente
  - Editar meeting sem `google_event_id` funciona normalmente
  - Deletar meeting sem `google_event_id` funciona normalmente
  - `participant_response` (aceitar/recusar convite) no PUT continua funcionando

## Technical Notes

### Integracao no POST /api/meetings/route.ts

```typescript
// [H1] Incluir timezone no INSERT
const timezone = body.timezone || 'America/Sao_Paulo'
// ... no insert: { ...meetingData, timezone }

// Apos criar meeting e participantes...
try {
  const syncResult = await syncMeetingToGoogle(meeting.id, user.id)
  if (syncResult.synced) {
    meetingData = await fetchMeeting(meeting.id) // refresh com meet_link
  }
} catch (syncError) {
  log.warn('Google Calendar sync failed for new meeting', {
    meetingId: meeting.id,
    error: syncError,
  })
}
```

### Integracao no PUT /api/meetings/[id]/route.ts

```typescript
// [M3] Expandir SELECT do existing meeting para incluir campos necessarios ao sync
const { data: existingMeeting } = await supabase
  .from('meetings')
  .select('id, google_event_id, user_id, scheduled_at')
  .eq('id', meetingId)
  .single()

// Apos update local...
if (data.scheduled_at && data.scheduled_at !== existingMeeting.scheduled_at) {
  await supabase
    .from('meeting_participants')
    .update({ response_status: 'pending' })
    .eq('meeting_id', meetingId)
}

if (existingMeeting.google_event_id) {
  await updateGoogleEvent(meetingId)
} else {
  await syncMeetingToGoogle(meetingId, existingMeeting.user_id)
}
```

### Integracao no DELETE /api/meetings/[id]/route.ts

```typescript
if (existingMeeting.google_event_id) {
  try {
    await deleteGoogleEvent(meetingId)
  } catch (error) {
    log.warn('Failed to delete Google Calendar event', { meetingId, error })
  }
}
// Deletar do banco
```

## Riscos

| Risco | Prob | Mitigacao |
|-------|------|-----------|
| Latencia adicional no POST | Alta | Sync e rapido (1-2s) e meeting local ja esta salva |
| Erro de sync bloqueia criacao | Baixa | AC 42.5.6: try/catch garante que local sempre funciona |
| Race condition PUT concorrente | Baixa | Google Calendar e idempotente para PATCH |
