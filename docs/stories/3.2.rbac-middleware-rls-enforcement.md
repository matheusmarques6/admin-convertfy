# Story 3.2 - Enforcement de Permissões (Middleware + RLS)

## Contexto
As RLS policies e helpers já existem (`has_feature()`, `can_access_store()`, etc.), mas alguns endpoints da API não validam features adequadamente. O middleware atual só atualiza sessão sem checar roles/features.

## Objetivo
Garantir que TODAS as rotas API e páginas respeitem a matriz de permissões definida na Story 3.1.

## Acceptance Criteria

- [x] **3.2.1** Auditoria completa de 124 API routes — identificados gaps em rotas financeiras, reports e store control

- [x] **3.2.2** Criado helper `src/lib/api/check-permission.ts` com:
  - `requireFeature(supabase, userId, feature)` — checa feature individual
  - `requireAnyFeature(supabase, userId, features)` — checa qualquer feature do array
  - Admin e org owner sempre passam

- [x] **3.2.3** Aplicado `requireFeature()` nas API routes críticas:
  - `client-charges` (POST/PUT/DELETE/PATCH): `view_financial`
  - `client-subscriptions` (POST/DELETE/PATCH): `view_financial`
  - `client-reports` (POST/PUT/DELETE): `view_reports`
  - Onboarding approve: já tinha checagem de role (owner/manager) ✅
  - Campanhas: RLS já cobre via `can_manage_store_campaigns()` ✅

- [x] **3.2.4** RLS policies atualizadas:
  - `invoices` — `has_feature('view_financial')` ✅
  - `campaigns` — `can_access_store()` para SELECT ✅
  - `clients/stores` — Atualizado `can_access_client()` e `can_access_store()` para permitir que qualquer membro ativo da org veja (não mais dependente de agent_store_access para view)
  - `accessible_store_ids()` e `accessible_client_ids()` também atualizados

- [x] **3.2.5** Páginas já protegidas:
  - `/financial` — `PermissionGate requiredFeatures={["view_financial"]}` ✅
  - `/reports` — `PagePermissionWrapper requiredFeatures={["view_reports"]}` ✅
