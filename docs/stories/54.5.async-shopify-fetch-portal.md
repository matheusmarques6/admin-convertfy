# Story 54.5 — Async Shopify Fetch (Stop Blocking Portal Response)

## Story

**Como** usuario do portal,
**Quero** que o dashboard carregue rapido mesmo quando a Shopify estiver lenta ou com rate limit,
**Para que** eu nao fique esperando 10+ segundos por dados que poderiam ser carregados em background.

## Contexto

### Problema

Em `portal/dashboard/route.ts`, quando o cache Shopify esta vazio ou expirado, o endpoint faz um **live fetch sincrono** para a API da Shopify:

```typescript
// Dentro do GET handler — bloqueia a response
const shopifyData = await syncShopifyForStore(store, credentials, period)
await saveShopifyToCache(storeId, shopifyData)
```

Se a Shopify estiver lenta (2-10s), com rate limit, ou down, a response inteira do portal fica bloqueada. Isso afeta a percepcao de performance do portal.

### Comparacao com Klaviyo

O Klaviyo ja usa o pattern correto: dados sao populados pelo cron em background, e o portal **apenas le do cache**. Se o cache Klaviyo esta vazio, retorna `dataStatus: "syncing"`.

### Pattern desejado

Shopify deveria seguir o mesmo pattern:
1. Tentar ler do cache
2. Se cache miss/expirado, retornar `dataStatus: "syncing"` para Shopify
3. Disparar refresh em background (fire-and-forget ou via cron)
4. Frontend faz polling/retry apos alguns segundos

## Acceptance Criteria

### 54.5.1 — Remover fetch sincrono da Shopify no GET

- [x] Em `portal/dashboard/route.ts`, remover o `await syncShopifyForStore()` do path sincrono
- [x] Se cache Shopify esta vazio/expirado, retornar `shopify: null` com `shopifyStatus: "syncing"`
- [x] Disparar sync em background (sem await):
  ```typescript
  if (!cachedShopify || isExpired(cachedShopify)) {
    // Fire-and-forget — nao bloqueia response
    syncShopifyForStore(store, credentials, period)
      .then(data => saveShopifyToCache(storeId, data))
      .catch(err => console.error(`[Portal] Shopify background sync failed:`, err))
  }
  ```

**Arquivo:** `src/app/api/portal/dashboard/route.ts`

### 54.5.2 — Frontend graceful handling

- [x] Em `client/dashboard/page.tsx`, tratar `shopifyStatus: "syncing"` mostrando skeleton/spinner para a secao Shopify
- [x] Manter re-fetch automatico (ja existe via SWR ou polling) para atualizar quando dados chegarem

**Arquivo:** `src/app/client/dashboard/page.tsx`

### 54.5.3 — Considerar inclusao no cron

- [x] Avaliar se Shopify deve ser incluido no cron `sync-reports` (como Klaviyo ja e)
- [ ] Se sim, adicionar como task separada no cron (nao bloqueia sync Klaviyo)
- [x] Se nao (decisao de produto), documentar a razao

### 54.5.4 — Validacao

- [x] `npm run build` passa
- [x] Portal carrega em <2s mesmo com Shopify lenta
- [x] Dados Shopify aparecem apos background sync completo

## Riscos

| Risco | Mitigacao |
|-------|----------|
| Fire-and-forget pode perder erros | Catch com logging adequado |
| Primeira visita sempre mostra "syncing" | Aceitavel; dados aparecem em poucos segundos |
| Vercel pode matar background task | Fire-and-forget no edge roda ate o response terminar; alternativa: POST separado |
