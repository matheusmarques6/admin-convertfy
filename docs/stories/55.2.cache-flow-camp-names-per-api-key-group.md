# Story 55.2 — Cache flowNames/campNames por API Key Group

## Story

**Como** engenheiro de performance do cron,
**Quero** que lojas que compartilham a mesma API key Klaviyo reutilizem os dados de flow/campaign names,
**Para que** eliminemos ~38 API calls redundantes por run e economizemos ~100-160s de rate limiter budget.

## Contexto

### Problema

No `syncStore()` (linha 190 do cron route), cada loja faz:

```typescript
;[flowNames, campNames] = await Promise.all([
  fetchFlowNames(apiKey),
  fetchCampaignNames(apiKey),
])
```

Lojas que compartilham a mesma API key (mesma conta Klaviyo) fazem essas chamadas **redundantemente**. `fetchFlowNames` pagina por todos os flows da conta (~2-5 API calls), e `fetchCampaignNames` pagina por email + SMS (~3-6 API calls).

### Dados de Producao

- 42 lojas agrupadas em ~20 API key groups
- Grupos com 2+ lojas: ~10 grupos (media 3 lojas/grupo)
- ~19 lojas em grupos multi-loja = 19 x (5+6) = **~209 API calls para names**
- Com cache por grupo: ~10 x (5+6) = **~110 API calls** (economia de ~99 calls)
- Alem dos names, `accountInfo` e `metricId` tambem sao identicos por API key

### Solucao

Mover o pre-fetch de `flowNames`, `campNames`, `accountInfo`, e `metricId` para o **loop de grupos** no cron route. Buscar 1x por grupo e passar como parametro para `syncStore`.

## Acceptance Criteria

### 55.2.1 — Pre-fetch por grupo no cron route

- [x] No loop de grupos, antes de iterar as lojas, buscar accountInfo, metricId, flowNames, campNames
- [x] Usar o `orgId` e `storeId` da primeira loja do grupo para cache lookup

### 55.2.2 — Alterar syncStore para aceitar dados pre-fetched

- [x] `syncStore` aceita `preFetched?: PreFetchedGroupData` e `apiKeyOverride?: string`
- [x] Se `preFetched` fornecido, pula o bloco de pre-fetch interno
- [x] Se `preFetched` for undefined, mantém comportamento original (backward compatible)

### 55.2.3 — Error handling no pre-fetch do grupo

- [x] `KlaviyoPermissionError`: marca TODAS as lojas do grupo como error + atualiza client_stores
- [x] `KlaviyoInvalidKeyError`: marca TODAS as lojas do grupo como error + atualiza client_stores
- [x] `KlaviyoRateLimitError`: fallback para pre-fetch individual (groupData fica undefined)
- [x] Outros erros: fallback para pre-fetch individual

### 55.2.4 — Log de reuso

- [x] Log por grupo: `"Group ...key: pre-fetched N flows, M campaigns — sharing across X stores"`
- [x] Log por loja: `"StoreName: using shared group data (N flows, M campaigns)"`

## Dependencias

## Riscos

| Risco | Mitigacao |
|-------|----------|
| Grupo com lojas de orgs diferentes | `accountInfo` e por API key (conta Klaviyo), nao por org — safe |
| Pre-fetch falha e bloqueia todas lojas do grupo | Fallback para pre-fetch individual |
| flowNames/campNames muito grandes causam memory pressure | Maps sao leves (string → objeto simples), mesmo 100+ entries sao <50KB |

## Notes

- O agrupamento por API key ja existe (Epic 33, Story 33.3) — esta story reutiliza os grupos
- `getCachedAccountInfo` e `getCachedPlacedOrderMetric` ja usam DB cache com TTL — esta story beneficia duplamente com 55.4 (TTL 24h)
- O `storeId` usado para DB cache lookup pode ser qualquer loja do grupo (mesma API key = mesmos dados)
