## Contexto

Tres itens de tech debt e observability que nao sao bloqueantes mas melhoram a qualidade do sistema:

1. **L3 - Rename `shopify_total_revenue`**: A coluna `shopify_total_revenue` em `store_revenue_summary` armazena dados vindos do Klaviyo metric-aggregates (Placed Order), NAO de Shopify diretamente. O nome e enganoso. Renomear para `store_total_revenue` reflete melhor a semantica.

2. **M1 - Dual Cache Documentation**: O projeto usa duas fontes de cache:
   - `dashboard_cache` table: cache generico com JSON blob (usado para Shopify, GA4, Asaas)
   - `store_revenue_summary` + `klaviyo_flow_metrics` + `klaviyo_campaign_metrics`: cache estruturado para Klaviyo (populado pelo cron)

   Isso precisa ser documentado claramente para evitar confusao.

3. **L2 - Observability**: Structured logging de cache hits vs live fallback para monitorar eficacia da estrategia cache-first.

---

## Objetivo

Renomear coluna confusa, documentar arquitetura de cache, e adicionar structured logging para observability do sistema de cache.

  ```markdown
  # Cache Strategy — admin-convertfy

  ## Cache Sources

  ### 1. dashboard_cache (generic blob cache)
  - **Table:** dashboard_cache
  - **Used for:** Shopify reports, GA4, Asaas payments
  - **Populated by:** API routes on-demand (cache-aside pattern)
  - **TTL:** Configurable per cache_type (see src/lib/cache.ts)
  - **Format:** JSON blob with _cacheVersion field

  ### 2. Structured Klaviyo Cache (cron-populated)
  - **Tables:** store_revenue_summary, klaviyo_flow_metrics, klaviyo_campaign_metrics
  - **Used for:** Admin dashboard, Portal dashboard (Klaviyo data)
  - **Populated by:** Cron /api/cron/sync-reports (every 30min)
  - **TTL:** 6 hours (expires_at field)
  - **Format:** Typed columns, not JSON blob

  ### 3. Live Fetch Cooldown (Epic 10)
  - **Table:** live_fetch_cooldowns
  - **Used for:** Coordinating live fetches across serverless functions
  - **Populated by:** Admin/Portal endpoints on cache miss
  - **TTL:** 1 minute (cached periods) / 30 minutes (custom ranges)

  ## Which Cache Serves What

  | Data | Cache Source | Populated By |
  |------|-------------|-------------|
  | Klaviyo revenue, campaigns, flows | store_revenue_summary + detail tables | Cron + live fallback |
  | Shopify orders, products, customers | dashboard_cache (type=shopify) | API routes on-demand |
  | Audience metrics (leads, engaged) | store_revenue_summary columns | Cron only |
  | Klaviyo account info, metric IDs | dashboard_cache (type=klaviyo_metadata) | Cached helpers |
  ```

## Arquitetura Tecnica

### Migration: Rename Column

```sql
-- supabase/migrations/YYYYMMDD_rename_shopify_total_revenue.sql

-- Rename column to reflect actual data source
ALTER TABLE store_revenue_summary
  RENAME COLUMN shopify_total_revenue TO store_total_revenue;

COMMENT ON COLUMN store_revenue_summary.store_total_revenue
  IS 'Total store revenue from Klaviyo metric-aggregates (Placed Order). Not from Shopify API directly.';
```

**Nota:** `ALTER TABLE RENAME COLUMN` e uma operacao DDL atomica no PostgreSQL. Nao requer downtime. Queries em progresso podem falhar se referenciarem o nome antigo — mas como o deploy e atomico (Vercel redeploy), as novas functions usam o novo nome.

## Riscos e Mitigacoes

| Risco | Mitigacao |
|-------|-----------|
| Rename column quebra queries em progresso | Deploy atomico no Vercel — novo codigo e nova migration simultaneos |
| Migration falha se coluna nao existe | `ALTER TABLE RENAME COLUMN` falha com erro claro — facilmente detectavel |
| Frontend referencia `shopify_total_revenue` | Grep em `src/` antes da mudanca; frontend so acessa via API, nao diretamente do DB |
| Structured logging gera muito log volume | Usar `log.info` (nao `log.debug`) apenas para eventos significativos |
