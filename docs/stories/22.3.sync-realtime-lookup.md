# Story 22.3 -- Sync Real-Time no Lookup (Tracking sem Eventos)

## Status
Done

## Story

**Como** cliente que busca um pedido no widget de rastreamento,
**Quero** ver os eventos de rastreamento na primeira busca,
**Para que** eu nao precise esperar um cron ou voltar depois para ter informacao.

---

## Dependencia

> **Pre-requisito:** 22.1 e 22.2 ja implementadas (cascade reordenado, freshness guard, AbortController, provider_used).
> Esta story usa `syncTrackingCode()` que ja tem toda a logica de cascade e protecao.

## Contexto

Hoje o endpoint `/api/tracking/lookup` so le dados do banco. Se o tracking code existe mas nunca foi sincronizado (`tracking_events` vazio), o cliente ve o codigo sem nenhuma informacao de rastreamento.

Com esta story, quando o lookup encontra tracking codes sem eventos, faz sync real-time (espera o resultado) e retorna dados atualizados na mesma request. O custo de latencia (~2-5s) acontece apenas 1 vez por tracking code — buscas subsequentes usam cache.

### Fluxo proposto

```
Cliente busca tracking → lookup no DB
  ├─ tracking COM eventos → retorna cache (~50ms)
  └─ tracking SEM eventos → syncTrackingCode(id) em tempo real
                              → re-le do DB
                              → retorna com dados (~2-5s)
```

### Protecoes existentes (ja implementadas na 22.1)

- **Freshness guard**: se `last_checked_at` e recente, nao re-sync (previne retry storm)
- **AbortController 8s**: cada provider tem timeout, worst case ~16s para 17track
- **Short-circuit**: primeiro provider que retorna eventos vence

  function isWithinFreshness(lastCheckedAt: string | null, status: string | null, hasEvents: boolean): boolean {

    const thresholdMs = (!hasEvents && (status === "pending" || !status))

  }

## Dev Notes

### Onde implementar

Tudo em `src/app/api/tracking/lookup/route.ts`, no handler GET, apos montar `results` e antes de retornar.

### Pseudo-codigo

```typescript
import { syncTrackingCode } from "@/lib/services/tracking.service"

// ... apos montar results (antes da traducao de eventos):

// Detectar tracking codes sem eventos que nunca foram sincronizados
const staleIds: string[] = []
for (const result of results) {
  for (const track of result.tracking) {
    const hasEvents = Array.isArray(track.tracking_events) && track.tracking_events.length > 0
    const neverSynced = !track.last_checked_at
    if (!hasEvents && neverSynced && track.id) {
      staleIds.push(track.id)
    }
  }
}

// Sync real-time (max 3, timeout 15s)
if (staleIds.length > 0) {
  const t0 = Date.now()
  const syncController = new AbortController()
  const syncTimeout = setTimeout(() => syncController.abort(), 15000)
  let syncedCount = 0

  try {
    for (const id of staleIds.slice(0, 3)) {
      if (syncController.signal.aborted) break
      await syncTrackingCode(id)
      syncedCount++
    }
  } catch {
    // timeout ou erro — continua com dados parciais
  } finally {
    clearTimeout(syncTimeout)
  }

  log.info("Real-time sync triggered", {
    trackingStoreId,
    staleCount: staleIds.length,
    syncedCount,
    durationMs: Date.now() - t0,
  })

  // Re-ler tracking codes atualizados
  if (syncedCount > 0) {
    for (const result of results) {
      for (let i = 0; i < result.tracking.length; i++) {
        const track = result.tracking[i]
        if (staleIds.includes(track.id)) {
          const { data: updated } = await admin
            .from("tracking_codes")
            .select("id, tracking_number, carrier_name, status, status_detail, last_event, tracking_events, estimated_delivery")
            .eq("id", track.id)
            .single()
          if (updated) result.tracking[i] = updated
        }
      }
    }
  }
}
```

### Nota: select precisa incluir last_checked_at

Os selects de tracking_codes no lookup (linhas 196, 218, 225) precisam incluir `last_checked_at` para que o check `neverSynced` funcione. Adicionar ao `.select()`.

### Nota: syncTrackingCode e AbortController

`syncTrackingCode()` nao aceita AbortSignal — o timeout global funciona por tempo, nao por cancelamento do sync em andamento. Se o sync ja comecou, ele completa mesmo apos o timeout. O `break` no loop previne iniciar novos syncs.

### Nota: Limitacao conhecida — tempo real pode exceder 15s

O timeout global de 15s impede novos syncs de iniciarem, mas nao cancela um sync em andamento. Se o primeiro sync demora 14s, o segundo comeca e pode completar apos o timeout. O tempo real maximo e ~23s (14s primeiro sync + 8s segundo). Isso e aceitavel para v1 — o Vercel Pro permite 60s.

### Nota: Filtro de IDs sinteticos

O `mapLookupResults()` gera IDs no formato `${source}-${trackingCode}` (ex: `shopify-ABC123`). Esses IDs NAO existem no DB e fariam `syncTrackingCode()` falhar. Usar regex UUID (`/^[0-9a-f]{8}-...$/`) para filtrar apenas IDs reais do Supabase.
