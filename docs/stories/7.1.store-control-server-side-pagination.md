**Prioridade:** Alta

**Assignee:** @dev

**Epic:** 7 - Performance

---

## Contexto

O endpoint `GET /api/stores/control` carrega **todas as lojas da organizacao** de uma vez e faz chamadas externas (Klaviyo + Shopify) para cada uma delas. Com 20 lojas, o carregamento leva 30-60 segundos. Isso torna a aba de Lojas praticamente inutilizavel para agencias com muitas lojas.

A causa raiz: o endpoint busca todas as lojas, depois faz N chamadas de revenue (Klaviyo + Shopify) para cada loja em sequencia/chunks. Quanto mais lojas, mais tempo.

O frontend (`store-control-panel.tsx`) recebe todos os dados e faz filtragem client-side — search, status filter e link filter sao processados no browser. Isso significa que mesmo com filtros ativos, o backend carrega tudo.

---

## Objetivo

Implementar paginacao server-side no endpoint `/api/stores/control` para carregar apenas as lojas da pagina atual, reduzindo drasticamente o numero de chamadas externas e o tempo de carregamento. Mover toda a logica de filtragem (search, status, link) para o backend.

**Estimativa de melhoria:**
- Tempo de carga: 30-60s -> 15-30s (~50% reducao)
- API calls Klaviyo: ~60-80 -> ~30-40
- API calls Shopify: ~20-100+ -> ~10-50

#### Mudanca 1 — Parsing de Query Params (com Zod)

```typescript
import { paginationSchema } from "@/lib/schemas/common"
import { z } from "zod"

// Schema especifico para este endpoint
const storeControlQuerySchema = paginationSchema.extend({
  per_page: z.coerce.number().int().min(1).max(50).default(10), // override
  search: z.string().trim().optional().default(""),
  status: z.enum(["on_track", "due_soon", "overdue", "never", ""]).optional().default(""),
  link_filter: z.enum(["all", "avulsas", "vinculadas"]).optional().default("all"),
})

const { searchParams } = new URL(request.url)
const params = storeControlQuerySchema.parse(Object.fromEntries(searchParams))
const { page, per_page: perPage, search, status: statusFilter, link_filter: linkFilter } = params

// Backward compatible: se nenhum param de paginacao, retorna tudo
const isPaginated = searchParams.has("page") || searchParams.has("per_page")

// Params existentes continuam funcionando
const activeOnly = searchParams.get('active_only') !== 'false'
const skipCache = searchParams.get('fresh') === 'true'
```

#### Mudanca 2 — Query com Filtros (Search via client_id lookup separado)

**IMPORTANTE**: Supabase PostgREST NAO suporta `.ilike()` em colunas de foreign tables dentro de `.or()`. A busca por client name/company precisa ser feita em 2 etapas.

```typescript
// Etapa 1: Se search ativo, buscar client_ids que matcham
let matchingClientIds: string[] = []
if (search) {
  const { data: matchingClients } = await supabase
    .from("clients")
    .select("id")
    .eq("org_id", orgId)
    .or(`name.ilike.%${search}%,company.ilike.%${search}%`)

  matchingClientIds = (matchingClients || []).map(c => c.id)
}

// Etapa 2: Query principal
let query = supabase
  .from("client_stores")
  .select(`
    id, client_id, org_id, store_name, store_url, platform, is_active,
    shopify_access_token, klaviyo_private_key,
    feedback_frequency, last_feedback_date, next_feedback_date, last_feedback_by,
    clients!left(id, name, company, status),
    profiles:last_feedback_by(name)
  `, { count: "exact" })
  .eq("org_id", orgId)

if (activeOnly) {
  query = query.eq("is_active", true)
}

// Link filter
if (linkFilter === "avulsas") {
  query = query.is("client_id", null)
} else if (linkFilter === "vinculadas") {
  query = query.not("client_id", "is", null)
}

// Search filter: store_name direto OU client_id in matchingClientIds
if (search) {
  if (matchingClientIds.length > 0) {
    query = query.or(
      `store_name.ilike.%${search}%,client_id.in.(${matchingClientIds.join(",")})`
    )
  } else {
    // Nenhum client matchou, buscar so por store_name
    query = query.ilike("store_name", `%${search}%`)
  }
}
```

#### Mudanca 3 — Summary Cards (Query Leve Separada)

```typescript
// Query separada para contagens globais — SEM API calls externas
const { data: allStores } = await supabase
  .from("client_stores")
  .select("id, next_feedback_date, last_feedback_date, client_id")
  .eq("org_id", orgId)
  .eq("is_active", true)

const today = new Date()
today.setHours(0, 0, 0, 0)
const sevenDaysLater = new Date(today.getTime() + 7 * 24 * 60 * 60 * 1000)

const summary = { total: 0, overdue: 0, due_soon: 0, on_track: 0, never: 0 }
const linkCounts = { all: 0, avulsas: 0, vinculadas: 0 }

for (const store of allStores || []) {
  summary.total++
  linkCounts.all++

  if (!store.client_id) linkCounts.avulsas++
  else linkCounts.vinculadas++

  if (!store.last_feedback_date && !store.next_feedback_date) {
    summary.never++
  } else if (store.next_feedback_date) {
    const nextDate = new Date(store.next_feedback_date)
    nextDate.setHours(0, 0, 0, 0)
    if (nextDate < today) {
      summary.overdue++
    } else if (nextDate <= sevenDaysLater) {
      summary.due_soon++
    } else {
      summary.on_track++
    }
  } else {
    // tem last_feedback_date mas nao tem next — considerar overdue
    summary.overdue++
  }
}
```

#### Mudanca 4 — Status Filter + Paginacao (Fluxo Completo)

O `feedback_status` eh um campo computado (nao existe no banco). Quando `statusFilter` esta ativo, o fluxo precisa ser diferente para garantir count correto e sort consistente.

**Fluxo sem statusFilter:**
1. Aplicar filtros de search + link_filter na query Supabase
2. Aplicar `.range(from, to)` com `{ count: "exact" }`
3. Supabase retorna stores da pagina + count total
4. Computar feedback_status e sort em memoria (so da pagina)
5. Buscar revenue so para essas stores

**Fluxo com statusFilter:**
1. Aplicar filtros de search + link_filter na query Supabase (SEM `.range()`, SEM `{ count: "exact" }`)
2. Buscar TODOS os stores que passam nos filtros de search + link (query leve, sem revenue)
3. Computar feedback_status para cada store em memoria
4. Filtrar por statusFilter em memoria
5. Sort por status priority em memoria
6. Aplicar paginacao manual: `filteredStores.slice(from, to)`
7. Usar `filteredStores.length` como `total` na resposta
8. Buscar revenue so para os stores da pagina (slice)

```typescript
if (statusFilter) {
  // Buscar TODOS sem paginacao (query leve)
  const { data: allFilteredStores, error } = await query

  if (error) { /* handle error */ }

  // Computar feedback_status para cada store
  const withStatus = (allFilteredStores || []).map(store => ({
    ...store,
    feedback_status: computeFeedbackStatus(store), // helper function
  }))

  // Filtrar por status
  const statusFiltered = withStatus.filter(s => s.feedback_status === statusFilter)

  // Sort por priority
  const statusPriority = { overdue: 0, due_soon: 1, never: 2, on_track: 3 }
  statusFiltered.sort((a, b) => {
    const diff = statusPriority[a.feedback_status] - statusPriority[b.feedback_status]
    if (diff !== 0) return diff
    return 0
  })

  // Paginacao manual
  const total = statusFiltered.length
  const from = (page - 1) * perPage
  const pagedStores = isPaginated ? statusFiltered.slice(from, from + perPage) : statusFiltered

  // Revenue fetch apenas para pagedStores
  // ... enrich com revenue ...

  return NextResponse.json({
    success: true,
    stores: enrichedStores,
    summary,
    link_counts: linkCounts,
    ...(isPaginated && {
      pagination: { page, per_page: perPage, total, total_pages: Math.ceil(total / perPage) },
    }),
  })
} else {
  // Sem statusFilter — usar .range() do Supabase normalmente
  if (isPaginated) {
    const from = (page - 1) * perPage
    const to = from + perPage - 1
    query = query.range(from, to)
  }

  const { data: stores, count, error } = await query

  // Se range retornou 416, tratar como pagina vazia
  if (error?.code === 'PGRST103') {
    return NextResponse.json({
      success: true,
      stores: [],
      summary,
      link_counts: linkCounts,
      ...(isPaginated && {
        pagination: { page, per_page: perPage, total: 0, total_pages: 0 },
      }),
    })
  }

  // Computar feedback_status + sort em memoria
  // Revenue fetch apenas para stores da pagina
  // ...

  return NextResponse.json({
    success: true,
    stores: enrichedStores,
    summary,
    link_counts: linkCounts,
    ...(isPaginated && {
      pagination: {
        page,
        per_page: perPage,
        total: count || 0,
        total_pages: Math.ceil((count || 0) / perPage),
      },
    }),
  })
}
```

**Nota sobre sort sem statusFilter:** O sort por feedback_status priority em memoria so afeta a ordem dentro da pagina (nao cross-page). Para sort consistente cross-page sem statusFilter, manter o `.order('store_name')` no Supabase como sort primario e aplicar status priority sort apenas como sort secundario em memoria. Isso eh aceitavel porque o sort principal no Supabase garante determinismo na paginacao.

## Consideracoes de Seguranca

- **Sem alteracao de RLS**: `orgId` continua sendo resolvido via `resolveOrgId()` com `createClient()` (RLS-protected). Todas as queries usam `.eq("org_id", orgId)`. NAO usar `createAdminClient()`.
- **Input sanitization**: Parametros `search` devem ser tratados com `.ilike()` do Supabase (parameterizado, sem SQL injection).
- **Max per_page**: Limitado a 50 para evitar abuso.
- **Cache isolation**: Cache key inclui `orgId` para prevenir cache poisoning cross-tenant.

## Riscos e Mitigacoes

| Risco | Impacto | Mitigacao |
|-------|---------|-----------|
| Cache: cada combinacao page+filtro gera chave diferente | Memoria do server pode crescer | Cachear revenue por `storeId` separado e reutilizar entre paginas |
| Race condition ao mudar de pagina rapidamente | UI pode mostrar dados da pagina errada | AbortController cancela fetch anterior |
| Revenue continua lento (~15-30s por pagina) | UX ainda nao ideal | Aceitar como limitacao desta story; otimizacao futura com background job (Epic 8) |
| Status filter requer logica condicional (nao eh um campo direto) | Query mais complexa + count manual | Filtrar em memoria apos query leve (sem revenue), paginacao manual sobre IDs filtrados |
| `.or()` + `.ilike()` nao funciona em foreign tables no PostgREST | Search por client name/company quebraria | Buscar client_ids separadamente, usar `.in()` na query principal |
| `.range()` pode retornar 416 se pagina excede total | Erro nao tratado | Tratar status 416 retornando array vazio |
| Sort por feedback_status sem statusFilter nao eh cross-page | Ordem entre paginas pode variar | Sort primario por store_name no Supabase (determinisico), status priority como secundario em memoria |
