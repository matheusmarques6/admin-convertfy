# Story 33.5 — Fix Cron Lock Race Condition

## Story

**Como** engenheiro de infraestrutura,
**Quero** que a aquisicao do lock do cron `sync-reports` seja atomica,
**Para que** duas invocacoes concorrentes nao possam ambas adquirir o lock e executar em paralelo.

## Contexto

### Problema

A funcao `acquireSyncLock` no `sync-reports/route.ts` (linhas 54-79) usa operacoes separadas:

1. **SELECT** para verificar se `is_running = false`
2. **UPSERT** para setar `is_running = true`

Entre o SELECT e o UPSERT, outra invocacao pode ler `is_running = false` e tambem prosseguir. Isso e uma classic TOCTOU (Time-of-Check-to-Time-of-Use) race condition.

### Codigo atual (bug)

```typescript
async function acquireSyncLock(supabase: SupabaseClient): Promise<boolean> {
  // Step 1: READ (nao atomico com step 2)
  const { data: lock } = await supabase
    .from("cron_locks")
    .select("is_running, started_at")
    .eq("lock_name", "sync_reports")
    .single()

  if (lock?.is_running && lock.started_at) {
    const startedAt = new Date(lock.started_at).getTime()
    if (Date.now() - startedAt < STALE_LOCK_MS) {
      log.warn("[Cron] Another sync is running, skipping")
      return false
    }
    log.warn("[Cron] Stale lock detected, proceeding")
  }

  // Step 2: WRITE (race window between step 1 and step 2!)
  await supabase
    .from("cron_locks")
    .upsert({
      lock_name: "sync_reports",
      is_running: true,
      started_at: new Date().toISOString(),
    }, { onConflict: "lock_name" })

  return true
}
```

### Fix

Usar uma unica operacao SQL atomica: `UPDATE ... WHERE is_running = false RETURNING *`. Se nenhuma row e retornada, o lock ja estava held.

Para o caso de stale lock, usar a condicao `OR started_at < threshold` no WHERE.

## Acceptance Criteria

### 33.5.1 — Lock atomico via RPC (abordagem primaria)

- [x] Substituir a funcao `acquireSyncLock` por uma chamada RPC atomica
- [x] Criar a funcao PL/pgSQL `acquire_sync_lock` (ver AC 33.5.2)
- [x] Implementacao no route.ts:
  ```typescript
  async function acquireSyncLock(supabase: SupabaseClient): Promise<boolean> {
    const { data, error } = await supabase.rpc("acquire_sync_lock", {
      p_lock_name: "sync_reports",
      p_stale_ms: STALE_LOCK_MS,
    })

    if (error) {
      log.error("[Cron] Failed to acquire lock via RPC:", error.message)
      return false
    }

    if (data === true) {
      return true
    }

    log.warn("[Cron] Another sync is running, skipping")
    return false
  }
  ```
- [x] A funcao RPC retorna `true` se o lock foi adquirido, `false` caso contrario
- [x] A RPC usa `now()` do Postgres (server-side) para comparacao temporal — evita problemas de timezone

**Por que NAO usar Supabase client `.update().or()`:** Apos o UPDATE atomico, `.select()` retorna os valores NOVOS (ja atualizados). O codigo verificaria `updated[0].started_at` contra `staleThreshold`, mas `started_at` ja contem o novo timestamp escrito pelo UPDATE — a deteccao de stale lock nao funciona porque estamos lendo o valor recem-escrito, nao o valor anterior. A abordagem RPC evita esse problema pois trata tudo server-side.

**Arquivo:** `src/app/api/cron/sync-reports/route.ts`

### 33.5.2 — Criar migration com RPC

- [x] Criar migration `supabase/migrations/20260310_acquire_sync_lock_rpc.sql`
- [x] Conteudo da migration:
  ```sql
  CREATE OR REPLACE FUNCTION acquire_sync_lock(
    p_lock_name TEXT,
    p_stale_ms BIGINT DEFAULT 600000
  )
  RETURNS BOOLEAN
  LANGUAGE plpgsql
  SECURITY DEFINER
  SET search_path = public
  AS $$
  DECLARE
    v_updated INT;
    v_was_stale BOOLEAN := false;
  BEGIN
    -- Check if stale before update (for logging purposes)
    SELECT (is_running = true AND started_at < now() - (p_stale_ms || ' milliseconds')::interval)
    INTO v_was_stale
    FROM cron_locks
    WHERE lock_name = p_lock_name;

    -- Atomic UPDATE: acquire only if not running OR stale
    UPDATE cron_locks
    SET is_running = true,
        started_at = now()
    WHERE lock_name = p_lock_name
      AND (
        is_running = false
        OR started_at < now() - (p_stale_ms || ' milliseconds')::interval
      );

    GET DIAGNOSTICS v_updated = ROW_COUNT;

    IF v_updated > 0 AND v_was_stale THEN
      RAISE LOG '[Cron] Stale lock acquired for %', p_lock_name;
    END IF;

    RETURN v_updated > 0;
  END;
  $$;

  REVOKE ALL ON FUNCTION acquire_sync_lock FROM PUBLIC;
  GRANT EXECUTE ON FUNCTION acquire_sync_lock TO service_role;
  ```
- [x] A funcao deve ser `SECURITY DEFINER` com `SET search_path = public`
