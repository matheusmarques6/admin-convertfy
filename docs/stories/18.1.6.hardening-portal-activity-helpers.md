## Contexto

### Problema 1: client_portal_activity NAO EXISTE (GAP-6 do QA)

A tabela `client_portal_activity` e referenciada em 5+ rotas portal (auth, change-password, invoices, dashboard, report) mas **NAO EXISTE no banco**. Todas as insercoes falham silenciosamente. O P2-Step 1 original propunha criar policies, mas a tabela em si precisa ser criada primeiro.

### Problema 2: Falta helper de validacao de ownership

Varias rotas portal repetem o padrao de verificar se um `store_id` pertence ao `client_id` do portal user. Um helper centralizado reduz duplicacao e risco de erro.

### Problema 3: Tech debt nao documentado

- `client_notification_preferences` nao existe (dead code em settings routes)
- 50+ bypass policies em tabelas admin-only (escopo de Story 18.2 futura)

- [ ] **AC 18.1.6.1** — Criar migration `supabase/migrations/20260305_04_create_portal_activity.sql`:
  ```sql
  -- ============================================================
  -- Story 18.1.6: Create client_portal_activity table + policies
  -- GAP-6 do QA: tabela nao existia, inserts falhavam silenciosamente
  -- ============================================================

  CREATE TABLE IF NOT EXISTS client_portal_activity (
    id UUID DEFAULT gen_random_uuid() PRIMARY KEY,
    portal_user_id UUID NOT NULL REFERENCES client_portal_users(id) ON DELETE CASCADE,
    client_id UUID NOT NULL REFERENCES clients(id) ON DELETE CASCADE,
    action TEXT NOT NULL,
    resource_type TEXT,
    resource_id TEXT,
    metadata JSONB DEFAULT '{}',
    details JSONB DEFAULT '{}',
    created_at TIMESTAMPTZ DEFAULT now()
  );

  -- Indices para queries comuns
  CREATE INDEX IF NOT EXISTS idx_portal_activity_portal_user
    ON client_portal_activity(portal_user_id);
  CREATE INDEX IF NOT EXISTS idx_portal_activity_client
    ON client_portal_activity(client_id);
  CREATE INDEX IF NOT EXISTS idx_portal_activity_created_at
    ON client_portal_activity(created_at DESC);

  -- Enable RLS
  ALTER TABLE client_portal_activity ENABLE ROW LEVEL SECURITY;

  -- Service role: full access (para adminClient writes)
  CREATE POLICY "portal_activity_service_all" ON client_portal_activity
    FOR ALL TO service_role USING (true) WITH CHECK (true);

  -- Portal users: podem inserir activity propria
  CREATE POLICY "portal_activity_insert" ON client_portal_activity
    FOR INSERT TO authenticated
    WITH CHECK (
      portal_user_id IN (
        SELECT id FROM client_portal_users WHERE auth_user_id = auth.uid()
      )
    );

  -- Admin/org members: podem ler activities dos seus clients
  CREATE POLICY "portal_activity_select" ON client_portal_activity
    FOR SELECT TO authenticated
    USING (is_admin() OR can_access_client(client_id));
  ```

### Parte B: Helper verifyStoreOwnership

- [x] **AC 18.1.6.3** — Adicionar funcao `verifyStoreOwnership` ao arquivo `src/lib/portal/auth.ts`:
  ```typescript
  /**
   * Verify that a store belongs to a specific client.
   * Used as defense-in-depth in portal routes that receive store_id.
   */
  export async function verifyStoreOwnership(
    adminClient: ReturnType<typeof createAdminClient>,
    storeId: string,
    clientId: string
  ): Promise<boolean> {
    const { data } = await adminClient
      .from("client_stores")
      .select("id")
      .eq("id", storeId)
      .eq("client_id", clientId)
      .single()
    return !!data
  }
  ```

## Tech Debt Documentado

### TD-1: `client_notification_preferences` (dead code)
- **Onde:** `src/app/api/portal/settings/route.ts` (linha 45), `src/app/api/portal/settings/notifications/route.ts` (linha 75)
- **Problema:** Tabela nao existe. Queries falham silenciosamente.
- **Impacto:** Feature de notificacoes do portal nao funciona.
- **Solucao futura:** Criar tabela OU remover dead code (depende de decisao de produto).

### TD-2: 50+ bypass policies em tabelas admin-only (GAP-4)
- **Onde:** `activities`, `automation_logs`, `automations`, `client_briefings`, `contracts`, `custom_fields`, `deals`, `email_templates`, `integrations`, `onboarding_approvals`, `onboarding_history`, `onboarding_phase_transitions`, `pipeline_stages`, `pipelines`, `profiles`, `reports`, `settings`, `store_alerts`, `store_briefings`, `store_feedback_calls`, `store_onboarding_data`, `tags`, `task_checklists`, `task_comments`, `tasks`
- **Problema:** Qualquer usuario autenticado pode ler/modificar dados de qualquer org.
- **Impacto:** ALTO para seguranca, BAIXO para portal (portal nao acessa diretamente).
- **Solucao:** Story 18.2 futura para remediacao sistematica.

### TD-3: `integrations` bypass policy (GAP-3)
- **Onde:** Tabela `integrations`, policy `"Authenticated users can manage integrations"`
- **Problema:** Qualquer usuario autenticado pode ler todas as integracoes (credenciais Asaas encriptadas).
- **Impacto:** ALTO. Credenciais encriptadas expostas cross-org.
- **Solucao:** Incluir no escopo de Story 18.2.
