# Story 40.4 — Bi-directional Sync Service

## Story

**Como** membro da equipe,
**Quero** que ao completar uma tarefa no meu board pessoal, a etapa correspondente do onboarding avance automaticamente e vice-versa,
**Para que** eu nao precise atualizar manualmente em dois lugares.

## Contexto

Esta e a story central do epic. Cria o servico de sincronizacao bi-direcional:

- **Board -> Onboarding**: Membro completa task no board -> DB trigger updates step to `completed` -> DB trigger cascades waiting deps to `pending` -> App service (`OnboardingSyncService`) detects newly-pending steps, creates tasks for next members, sends notifications
- **Onboarding -> Board**: Manager move card no kanban de onboarding para completado -> task correspondente no board e atualizada

**HYBRID approach**: DB triggers handle the cascade (task completion -> step completion -> waiting deps to pending). The app service (`OnboardingSyncService`) handles task creation (needs board_config checks) and notifications. The service should NOT duplicate what triggers already do.

O servico coordena `TaskAutomationService` e `NotificationService`, reacting to changes already applied by DB triggers.

## Acceptance Criteria

- [x] **AC 40.4.1**: Servico `OnboardingSyncService` criado em `src/lib/services/onboarding-sync.service.ts`
- [x] **AC 40.4.2**: Metodo `onTaskCompleted(taskId)` — quando task com `source_type = 'auto_onboarding_step'` e completada no board:
  - DB trigger already updates the linked step to `completed` and cascades waiting deps to `pending`
  - The service should NOT manually update step status (trigger does this)
  - After the trigger fires, the service: resolves newly-`pending` steps, creates tasks via `TaskAutomationService.onOnboardingStepPending()`, sends notifications
- [x] **AC 40.4.3**: Metodo `onStepCompleted(stepId)` — quando step e completado diretamente no kanban de onboarding:
  - Se o step tem `task_id`, atualiza a task correspondente para `completed`
  - DB trigger cascades waiting deps to `pending`
  - For each newly-`pending` step, calls `TaskAutomationService.onOnboardingStepPending()`
- [x] **AC 40.4.4**: Metodo `onTaskStatusChanged(taskId, newStatus)` — sincroniza status intermediarios:
  - `in_progress` no board -> `in_progress` no step
  - `blocked` no board -> `blocked` no step
  - `review` no board -> `review` no step
- [x] **AC 40.4.5**: Protecao contra loop infinito: `_syncOrigin` metadata previne loops ONLY for the app->task direction. DB triggers are idempotent by design
- [x] **AC 40.4.6**: API route `PATCH /api/onboarding/[id]/steps/[stepId]` atualizada para chamar `onStepCompleted()` quando status muda para `completed`
- [x] **AC 40.4.7**: API route de tasks (`PATCH /api/tasks/[id]`) atualizada para chamar `onTaskCompleted()` quando task com `source_type = 'auto_onboarding_step'` e completada
- [x] **AC 40.4.8**: Todas as operacoes do sync sao atomicas — se qualquer parte falhar, logar erro mas NAO reverter as partes que ja foram (eventual consistency, nao transacao)
- [x] **AC 40.4.9**: Log estruturado para cada operacao de sync: `{ action, taskId, stepId, onboardingId, result }`
- [x] **AC 40.4.10**: Endpoint `POST /api/onboarding/[id]/seed-tasks` para criar tasks para steps ja `pending` em onboardings existentes (backfill para onboardings criados antes do sync)

## Technical Notes

### Interface do Servico

```typescript
// src/lib/services/onboarding-sync.service.ts

export class OnboardingSyncService {
  /**
   * Chamado quando uma task do board e completada.
   * Se a task e de onboarding step, sincroniza com o pipeline.
   */
  static async onTaskCompleted(taskId: string): Promise<void>

  /**
   * Chamado quando um step do onboarding e completado diretamente.
   * Sincroniza com a task do board (se existir) e desbloqueia proximos.
   */
  static async onStepCompleted(stepId: string, completedBy?: string): Promise<void>

  /**
   * Sincroniza status intermediarios (in_progress, blocked, review)
   */
  static async onTaskStatusChanged(taskId: string, newStatus: TaskStatus): Promise<void>

  /**
   * After DB trigger cascades deps, create tasks for newly-pending steps
   * and send notifications. Does NOT update step statuses (trigger handles that).
   */
  private static async handleNewlyPendingSteps(onboardingId: string): Promise<void>

  /**
   * Seed tasks for existing onboardings that already have pending steps
   * without linked tasks. Used for backfill via POST /api/onboarding/[id]/seed-tasks
   */
  static async seedTasks(onboardingId: string): Promise<string[]>
}
```

### Fluxo Board -> Onboarding (HYBRID)

```
Task completada no board
  │
  ├── task.source_type != 'auto_onboarding_step' → return (nao e onboarding)
  │
  ├── DB TRIGGER fires:
  │     ├── Updates linked step: status = 'completed', completed_at = now()
  │     └── Cascades: waiting deps whose ALL deps are completed/skipped → pending
  │
  ├── APP SERVICE (OnboardingSyncService.onTaskCompleted):
  │     ├── Query newly-pending steps (status = 'pending', task_id IS NULL)
  │     │
  │     ├── Para cada step pending sem task:
  │     │     ├── Buscar dados do step (name, assigned_to, etc.)
  │     │     ├── TaskAutomationService.onOnboardingStepPending(...)
  │     │     └── NotificationService (story 40.5)
  │     │
  │     └── Verificar se todos os steps completed → onboarding completed
  │
  └── Log resultado
```

### Fluxo Onboarding -> Board

```
Step completado no kanban
  │
  ├── step.task_id existe?
  │     ├── Sim → Atualizar task: status = 'completed', completed_at = now()
  │     │         (with _syncOrigin metadata to prevent loop)
  │     └── Nao → Nada a fazer no board
  │
  ├── DB trigger cascades deps (waiting → pending)
  │
  ├── handleNewlyPendingSteps(onboardingId) [create tasks + notify]
  │
  └── Log resultado
```

### Protecao contra loop

```typescript
// Usar um Set de operacoes em andamento
const activeSyncs = new Set<string>()

static async onTaskCompleted(taskId: string) {
  const syncKey = `task:${taskId}`
  if (activeSyncs.has(syncKey)) return // Prevenir loop
  activeSyncs.add(syncKey)
  try {
    // ... sync logic
  } finally {
    activeSyncs.delete(syncKey)
  }
}
```

**Nota**: Como o servico roda server-side em instancias stateless, o Set in-memory nao resolve across requests. Usar campo `metadata._syncOrigin` na task/step para prevenir loops cross-request:

```typescript
// Ao atualizar task a partir de step completion:
await supabase.from("tasks").update({
  status: "completed",
  metadata: { ...existing, _syncOrigin: "onboarding_step" }
})

// No handler de task completed, verificar:
if (task.metadata?._syncOrigin === "onboarding_step") return // Ja sincronizado
```
