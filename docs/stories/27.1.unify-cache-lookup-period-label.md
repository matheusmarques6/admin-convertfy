## Story

**Como** sistema que depende de cache para exibir dados de campanha,
**Quero** que todos os endpoints leiam o cache usando `period_label` (e nao `period_start/period_end`),
**Para que** os dados escritos pelo cron sejam encontrados pelos consumidores e os usuarios vejam metricas reais.

---

## Contexto

O cron escreve em `klaviyo_campaign_metrics` e `klaviyo_flow_metrics` com `period_label = "30d"`.

Os endpoints `/api/integrations/klaviyo/campaigns` e `/api/integrations/klaviyo/flows` leem o cache filtrando por `period_start` e `period_end` exatos (timestamps ISO). Como as datas sao calculadas com funcoes diferentes (timezone mismatch - ver story 27.3), o cache **nunca da hit**, forcando live fetch toda vez.

Alem disso, quando o live fetch escreve de volta no cache, **nao inclui `period_label` nem `org_id`**, criando rows orfas que o portal dashboard (que filtra por `period_label`) nunca encontra.

O portal dashboard ja usa `.eq("period_label", period)` e funciona corretamente — este e o padrao a seguir.

### Arquivos afetados

- `src/app/api/integrations/klaviyo/campaigns/route.ts` (linhas ~268-276: `readCampaignsFromCache`, linhas ~577-607: upsert)
- `src/app/api/integrations/klaviyo/flows/route.ts` (linhas ~256-262: `readFlowsFromCache`, linhas ~520-552: upsert)
- `src/app/api/portal/dashboard/route.ts` (referencia — ja usa `period_label` corretamente)
- `src/app/api/clients/[id]/performance/route.ts` (referencia — ja usa `period_label`)
- `src/lib/shared/data-status.ts` (constante `CACHED_PERIODS`)

## Acceptance Criteria

### 27.1.1 — Campaigns endpoint: cache read por `period_label`

- [x] Em `readCampaignsFromCache()`, trocar filtro de `.eq("period_start", X).eq("period_end", Y)` para `.eq("period_label", period)` onde `period` e o label (ex: "30d", "7d", "15d", "90d")
- [x] Atualizar a signature da funcao: trocar parametros `periodStart, periodEnd` por `period: string`
- [x] Atualizar o call site (linha ~427) para passar `period` ao inves de `periodStartISO, periodEndISO`
- [x] Manter filtro `.eq("store_id", storeId)`
- [x] Usar `isCachedPeriod(period)` de `@/lib/shared/data-status` para verificar se o period e cacheavel (NAO usar `.has()` — `CACHED_PERIODS` e array readonly, nao Set)
- [x] Importar `isCachedPeriod` e `CACHED_PERIODS` de `@/lib/shared/data-status`
- [x] Remover a constante local `CACHED_PERIODS = new Set(["7d", "15d", "30d", "90d"])` do arquivo

### 27.1.2 — Flows endpoint: cache read por `period_label`

- [x] Mesma mudanca do 27.1.1 aplicada em `readFlowsFromCache()` no endpoint de flows
- [x] Atualizar signature e call site analogamente
- [x] Importar `isCachedPeriod` e `CACHED_PERIODS` de `@/lib/shared/data-status`
- [x] Remover constante local duplicada se existir

### 27.1.3 — Campaigns endpoint: cache write com `period_label` e `org_id`

- [x] No upsert de `klaviyo_campaign_metrics` apos live fetch, incluir campo `period_label` com o valor do period (ex: "30d")
- [x] Incluir campo `org_id` — ja disponivel como `store.orgId` retornado por `requireStoreAccess()` (linha ~401). NAO fazer query extra.
- [x] Manter `period_start` e `period_end` no payload (necessarios para a API Klaviyo e para unique constraint)
- [x] Para periodos custom (nao em `isCachedPeriod`), usar `period_label = "custom"` ou nao escrever no cache

### 27.1.4 — Flows endpoint: cache write com `period_label` e `org_id`

- [x] Mesma mudanca do 27.1.3 aplicada no endpoint de flows
- [x] Incluir `period_label` e `org_id` no upsert de `klaviyo_flow_metrics`

### 27.1.5 — Validar cache hit funcional

- [x] Apos as mudancas, o endpoint de campaigns com `period=30d` deve retornar `fromCache: true` quando dados existem na tabela com `period_label = "30d"`
- [x] O endpoint de flows com `period=30d` deve retornar `fromCache: true` idem
- [x] Periodos custom continuam fazendo live fetch (sem cache)

## Notas Tecnicas

- O unique constraint de `klaviyo_campaign_metrics` e `(store_id, campaign_id, period_start, period_end)`. Adicionar `period_label` nao quebra o constraint — e apenas um campo adicional na row.
- O `org_id` ja esta disponivel como `store.orgId` via `requireStoreAccess()` — sem query adicional.
- `CACHED_PERIODS` em `data-status.ts` e um `readonly` array, NAO um Set. Usar `isCachedPeriod()` (ja existe em `data-status.ts` linha ~37) ao inves de `.has()`.
- Nao alterar como o cron escreve — ele ja esta correto.
- **Interacao com 27.3**: Apos esta story, cache lookup usa `period_label` e nao depende mais de `period_start/period_end` para encontrar dados. A story 27.3 (timezone) afeta apenas o live fetch path e os timestamps enviados ao Klaviyo.
