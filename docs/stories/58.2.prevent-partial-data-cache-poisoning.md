# Story 58.2 — Nao cachear dados parciais em custom ranges

## Executor Assignment

executor: "@dev"
quality_gate: "@qa"
quality_gate_tools: ["typecheck", "lint", "unit-tests"]

## Story

**Como** operador do admin,
**Quero** que o cache de periodos customizados NAO armazene dados quando um dos reports falhou,
**Para que** requests subsequentes busquem dados frescos da API em vez de servir dados envenenados.

## Contexto

### Problema

Em `report-summary.ts`, quando o flow-values-reports falha (retorna null) mas o campaign-values-reports funciona, o write-through cache salva:

```typescript
// Linhas 339-375 — write-through para custom ranges
await adminClient.rpc("upsert_custom_range_cache", {
  p_klaviyo_campaign_revenue: campaignRevenue,  // R$50.000 (correto)
  p_klaviyo_flow_revenue: flowRevenue,          // R$0 (ERRADO — API falhou, nao "zero real")
})
```

O RPC grava `sync_status = 'ok'` incondicionalmente. Na proxima request para o mesmo range:

```typescript
// Linhas 192-225 — cache read
if (row && row.sync_status !== "error") {  // 'ok' passa
  if (isCustomRangeCacheFresh(...)) {       // dentro do TTL, passa
    return cached  // flowRevenue=0 ENVENENADO servido como dado real
  }
}
```

### TTL do veneno

| Tipo de range | TTL | Tempo com dados errados |
|---------------|-----|------------------------|
| Historico (fim > 7d atras) | 30 dias | Ate 30 dias |
| Recente (fim 1-7d atras) | 6 horas | Ate 6 horas |
| Em andamento longo (>30d) | 2 horas | Ate 2 horas |
| Em andamento curto (<=30d) | 30 minutos | Ate 30 minutos |

### Contraste com o cron

O cron sync em `sync-persistence.service.ts` verifica `data.flowDataAvailable` e `data.campaignDataAvailable` antes de escrever, e usa `sync_status = 'partial'` para dados incompletos. O write-through custom NAO tem essa protecao.

## Acceptance Criteria

### 58.2.1 — Condicionar cache write a TODAS as fontes de dados terem sucesso

- [ ] Em `src/lib/integrations/klaviyo/report-summary.ts`:
  - Capturar sucesso de metric-aggregates como boolean separado (alem do valor numerico):
    ```typescript
    let storeRevenue = 0
    let metricAggSuccess = false
    try {
      const aggResult = await fetchStoreRevenueFromMetricAggregates(...)
      if (aggResult.success && aggResult.data) {
        storeRevenue = aggResult.data.storeRevenue
        metricAggSuccess = true
      }
    } catch { ... }
    ```
  - No bloco de write-through para custom ranges (linhas ~339-375):
    - Adicionar guard: so executar o upsert se `campaignReport !== null && flowReport !== null && metricAggSuccess`
    - Quando qualquer fonte falhar, logar warning: `Store ${storeId}: skipping custom range cache write (partial data: campaign=${campaignReport !== null}, flow=${flowReport !== null}, metricAgg=${metricAggSuccess})`
  - O return value da funcao NAO muda — ainda retorna os dados live (mesmo parciais) para o caller
  - NOTA: `KlaviyoPermissionError` causa `success: false` (ambos reports null) e NAO cai no caso parcial — o guard so se aplica a falhas transitorias (timeout, 500)

### 58.2.2 — Aplicar mesma protecao ao cache de 1d

- [ ] No bloco de write-through para 1d (linhas ~297-336):
  - Adicionar guard identico: so upsert se `campaignReport !== null && flowReport !== null && metricAggSuccess`
  - Logar warning quando pular
  - NOTA: O 1d path usa `.upsert()` direto (nao RPC) — o guard deve envolver o bloco inteiro do upsert

### 58.2.3 — Invalidar cache poisonado existente

- [ ] Criar migration SQL que limpa rows envenenadas:
  ```sql
  -- Limpar custom ranges onde flow=0 mas campaign>0 (provavelmente envenenados)
  -- Filtrar por sync_source para nao tocar rows do cron (que ja tem protecao parcial)
  DELETE FROM store_revenue_summary
  WHERE period_label LIKE 'custom:%'
    AND klaviyo_flow_revenue = 0
    AND klaviyo_campaign_revenue > 0
    AND sync_source IN ('live', 'report');
  ```
- [ ] Tambem limpar 1d rows potencialmente envenenadas:
  ```sql
  DELETE FROM store_revenue_summary
  WHERE period_label = '1d'
    AND klaviyo_flow_revenue = 0
    AND klaviyo_campaign_revenue > 0
    AND sync_source = 'live';
  ```
- [ ] **IMPORTANTE**: Deployar o codigo (guard do AC 58.2.1) ANTES de rodar esta migration, para evitar re-envenenamento
- [ ] NOTA: Essa heuristica pode deletar rows legitimas (lojas sem flows mas com campanhas). Isso e aceitavel porque a proxima request ira re-buscar da API e cachear dados corretos.

### Decisao de design

**Alternativa considerada e rejeitada**: Escrever no cache com `sync_status = 'partial'` (como o cron faz). Rejeitada porque:
1. O RPC `upsert_custom_range_cache` nao aceita `sync_status` como parametro
2. Modificar o RPC adicionaria complexidade sem ganho — e mais seguro simplesmente nao cachear dados incompletos
3. Custom ranges nao tem cron que re-sincroniza, entao `partial` nunca seria resolvido automaticamente

**Decisao**: Nao cachear = request seguinte vai live, busca dados completos, cacheia corretamente.

### Edge cases

- Se AMBOS reports falharem (`!campaignReport && !flowReport`), a funcao ja retorna `success: false` antes de chegar ao write-through — OK
- Se flow=null mas campaign=ok, o return value ainda inclui `campaignRevenue: X, flowRevenue: 0`. O caller (report processor) recebe dados parciais, mas o CACHE nao e envenenado
- Se uma loja realmente tem R$0 de flow revenue (nenhum flow ativo), `flowReport` retorna um resultado com `conversion_value: 0`, nao `null`. Portanto, `flowReport !== null` sera true e o cache sera escrito corretamente
