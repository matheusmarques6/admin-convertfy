## Contexto

O cron `sync-reports/route.ts` tem ~800 linhas com TODA a logica de sync Klaviyo embutida:
- `fetchStoreRevenueFromMetricAggregates()` (linhas 90-156)
- `syncStoreForPeriod()` (linhas 162-418) — fetch flows + campaigns + metric-aggregates, aggregate, upsert
- `fetchFlowNames()` / `fetchCampaignNames()` (linhas 440-476)
- `fetchAudienceForStore()` (linhas 496-567)

Para implementar live fallback (Stories 10.5/10.6), essas funcoes precisam ser chamadas de FORA do cron — diretamente pelos endpoints admin e portal. Se ficarem dentro do route.ts, nao sao importaveis.

Alem disso, o QA finding M3 aponta que `klaviyoRequest()` retorna `null` silenciosamente. O novo service deve usar `SyncResult<T>` (de Story 10.1) para retornar erros explicitos.

---

## Objetivo

Extrair a logica de sync Klaviyo do cron para `src/lib/services/klaviyo-sync.service.ts`, tornando-a reutilizavel pelo cron E pelos endpoints de live fallback. O cron passa a ser um orquestrador fino que chama o service.

async function syncStore(store, periods, supabase, startTime) {
  // ... get credentials, accountInfo, metricId ...
  const [flowNames, campNames] = await Promise.all([
    fetchFlowNames(apiKey),

  const audience = audienceResult.success ? audienceResult.data! : { totalLeads: 0, engagedLeads: 0, engagementRate: 0 }

      }

## Riscos e Mitigacoes

| Risco | Mitigacao |
|-------|-----------|
| Refactor grande (~400 linhas movidas) pode introduzir bugs | Mover funcao por funcao, testar cron apos cada move |
| Service importa klaviyoRequest que retorna null | Cada funcao do service checa null e retorna SyncResult.success=false |
| Cron perde performance com camada extra | Nenhuma — service e puro calculo, sem DB round-trips extras |
| flowNames/campNames sao Map — nao serializavel | OK, usado in-memory; callers ja lidam com isso |
