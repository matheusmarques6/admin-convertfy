# Story 34.4 — Guard Onboarding Phase Self-Transition

## Story

**Como** engenheiro responsavel pela observabilidade,
**Quero** evitar logs desnecessarios de "Invalid transition" quando o formulario de onboarding e resubmetido no mesmo estado,
**Para que** os logs de producao fiquem limpos e warnings sejam significativos.

## Contexto

### Problema observado em producao

Quando um formulario de onboarding e resubmetido enquanto o status ja e `pending_approval`, o codigo tenta transicionar para o mesmo estado. A state machine em `onboarding-phase.service.ts` (linha 70-71) rejeita com:

```
[WARN] Invalid transition: pending_approval → pending_approval
```

Isso ocorre em 2 arquivos que chamam `transition()` apos form submission:

**Arquivo 1:** `src/app/api/public/onboarding-form/route.ts` (linhas 191-202)
```typescript
try {
  await onboardingPhaseService.transition({
    onboardingId: onboarding.id,
    toPhase: "pending_approval",
    triggeredBy: "form_submission",
  }).catch(() => {
    // The onboarding is already in pending_approval, so transition may fail
    // That's ok, just manually notify
  })
} catch {
  // Non-blocking
}
```

**Arquivo 2:** `src/app/api/portal/stores/onboarding/route.ts` (linhas 202-210)
```typescript
try {
  await onboardingPhaseService.transition({
    onboardingId: onboarding.id,
    toPhase: "pending_approval",
    triggeredBy: "form_submission",
  }).catch(() => {})
} catch {
  // Non-blocking
}
```

Ambos tem `.catch(() => {})` que engole o erro, mas o `log.warn` no service ja foi emitido antes do reject.

### Bug funcional latente (encontrado pelo QA)

O self-transition NAO e apenas log noise. Ambos os callers fazem INSERT com `current_phase: "pending_approval"` e depois chamam `transition({ toPhase: "pending_approval" })`. Como a transicao falha, `executeSideEffects()` (que chama `notifyApprovers()` e `notifyClient()`) **NUNCA executa** em novas submissoes de formulario. Isso significa que **aprovadores nao estao sendo notificados** quando novos onboardings sao submetidos.

### Fix proposto

**Opcao A: Guard nos callers** — buscar a fase atual e so chamar `transition()` se for diferente:

```typescript
// Buscar fase atual
const { data: currentOnboarding } = await adminClient
  .from("client_onboardings")
  .select("current_phase")
  .eq("id", onboarding.id)
  .single()

if (currentOnboarding?.current_phase !== "pending_approval") {
  try {
    await onboardingPhaseService.transition({
      onboardingId: onboarding.id,
      toPhase: "pending_approval",
      triggeredBy: "form_submission",
    }).catch(() => {})
  } catch {
    // Non-blocking
  }
}
```

**Opcao B: No-op no service** — tratar self-transition como sucesso silencioso em `onboarding-phase.service.ts`:

```typescript
// Antes da validacao de transicoes validas (linha 69)
if (fromPhase === params.toPhase) {
  log.debug(`Self-transition ignored: ${fromPhase}`, { id: params.onboardingId })
  return { success: true, fromPhase, toPhase: params.toPhase }
}
```

**Opcao B e RECOMENDADA** pelo QA: mais limpa, previne o problema em qualquer caller futuro, e a analise de impacto confirmou que nenhum caller existente e prejudicado (7 callers verificados).

**IMPORTANTE:** Independente da opcao, o fix do log noise NAO resolve o bug funcional de notificacoes. Ver AC 34.4.4.
