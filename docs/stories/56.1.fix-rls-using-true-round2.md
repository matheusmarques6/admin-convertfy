# Story 56.1 — Fix RLS USING(true) em 7 Tabelas (Round 2)

## Story

**Como** engenheiro de seguranca,
**Quero** substituir as policies `USING(true)` restantes em 7 tabelas por checks org-scoped,
**Para que** usuarios autenticados nao possam ler/escrever dados de outras organizacoes via RLS.

## Contexto

### Problema

A migration `20250215_fix_rls_using_true.sql` corrigiu ~50 policies legacy, mas **7 tabelas** escaparam da auditoria original. Todas tem policies `USING(true)` para `TO authenticated`, permitindo que qualquer usuario autenticado acesse dados de qualquer organizacao.

### Tabelas afetadas

| Tabela | FK | Tipo de check necessario |
|--------|----|-----------------------|
| `store_feedback_calls` | `store_id` | `can_access_store(store_id)` |
| `store_onboarding_data` | `store_id` | `can_access_store(store_id)` |
| `store_briefings` | `store_id` | `can_access_store(store_id)` |
| `store_alerts` | `store_id` | `can_access_store(store_id)` |
| `onboarding_approvals` | `onboarding_id` | JOIN via `client_onboardings` |
| `onboarding_phase_transitions` | `onboarding_id` | JOIN via `client_onboardings` |
| `meeting_participants` | `meeting_id` | `is_org_member()` |

### Padrao a seguir

Usar o mesmo padrao da migration `20250215_fix_rls_using_true.sql`:

```sql
-- Tabelas com store_id direto
DROP POLICY IF EXISTS "old_policy_name" ON table_name;
CREATE POLICY "Users can view table_name"
  ON table_name FOR SELECT TO authenticated
  USING (can_access_store(store_id));

-- Tabelas com onboarding_id (JOIN)
CREATE POLICY "Users can view onboarding_approvals"
  ON onboarding_approvals FOR SELECT TO authenticated
  USING (
    EXISTS (
      SELECT 1 FROM client_onboardings co
      WHERE co.id = onboarding_approvals.onboarding_id
      AND is_org_member()
    )
  );

-- meeting_participants (org-level)
-- Ja foi corrigida na 20250215 mas pode ter sido recriada
```

### Impacto

- **service_role** (portal, cron): NAO afetado — bypassa RLS
- **authenticated** (admin UI): Passa a ver apenas dados da propria org
- **anon**: NAO afetado — nao tem acesso a essas tabelas

## Acceptance Criteria

### 56.1.1 — Tabelas com store_id direto (4 tabelas)

- [x] Para cada tabela (`store_feedback_calls`, `store_onboarding_data`, `store_briefings`, `store_alerts`):
  - DROP todas as policies existentes com `USING(true)` para `TO authenticated`
  - CREATE policy SELECT: `USING (can_access_store(store_id))`
  - CREATE policy INSERT: `WITH CHECK (can_access_store(store_id))`
  - CREATE policy UPDATE: `USING (can_access_store(store_id)) WITH CHECK (can_access_store(store_id))`
- [x] Policies para `TO service_role` NAO sao tocadas (devem permanecer como estao)

**Given-When-Then:**

```
GIVEN User A is authenticated in Org A
AND Store S1 belongs to Org B
WHEN User A queries store_feedback_calls WHERE store_id = S1
THEN RLS returns 0 rows (not an error, just empty — Postgres RLS behavior)

GIVEN User A is authenticated in Org A
AND Store S2 belongs to Org A
WHEN User A queries store_feedback_calls WHERE store_id = S2
THEN RLS returns the matching rows normally
```

### 56.1.2 — Tabelas com onboarding_id (2 tabelas)

- [x] Para `onboarding_approvals` e `onboarding_phase_transitions`:
  - DROP policies existentes com `USING(true)` para `TO authenticated`
  - CREATE policy SELECT com JOIN via `client_onboardings`:
    ```sql
    USING (
      EXISTS (
        SELECT 1 FROM client_onboardings co
        WHERE co.id = <table>.onboarding_id
        AND is_org_member()
      )
    )
    ```
  - CREATE policy INSERT/UPDATE com o mesmo pattern

**Given-When-Then:**

```
GIVEN User A is authenticated in Org A
AND Onboarding O1 belongs to Org B (via client_onboardings)
WHEN User A queries onboarding_approvals WHERE onboarding_id = O1
THEN RLS returns 0 rows

GIVEN User A is authenticated in Org A
AND Onboarding O2 belongs to Org A
WHEN User A queries onboarding_approvals WHERE onboarding_id = O2
THEN RLS returns the matching rows
```

### 56.1.5 — Validacao pos-migration

- [x] Nenhuma tabela no schema `public` tem policy `USING(true)` para `TO authenticated` (exceto tabelas intencionalmente abertas: `profiles`, `tags`)
- [x] Query de verificacao incluida como comentario:
  ```sql
  -- Verificacao: deve retornar 0 rows (exceto profiles, tags)
  SELECT schemaname, tablename, policyname, qual
  FROM pg_policies
  WHERE schemaname = 'public'
    AND roles::text LIKE '%authenticated%'
    AND qual = 'true'
    AND tablename NOT IN ('profiles', 'tags');
  ```
