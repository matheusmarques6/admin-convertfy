## Story

**Como** sistema que mantem cache de revenue,
**Quero** que dados validos nunca sejam sobrescritos com zeros por falhas temporarias,
**Para que** lojas mantenham suas metricas visiveis mesmo quando o cron falha.

---

## Contexto

Dois problemas causam perda de dados validos:

### Problema 1: `upsertSyncError` sobrescreve dados expirados com zeros

Em `src/app/api/cron/sync-reports/route.ts` (linha ~95), `upsertSyncError()` tem um guard:
```typescript
if (existing?.sync_status === "ok" && new Date(existing.expires_at) > new Date()) {
  return // preserva dados validos
}
```

Mas quando `expires_at` passa (>6h sem cron sucesso), o guard nao protege mais. A funcao entao escreve uma row com `klaviyo_total_revenue = 0`, `sync_status = "error"`.

### Problema 2: `clean_expired_revenue_summaries()` deleta rows expiradas

A funcao SQL deleta rows onde `expires_at < NOW() - INTERVAL '1 hour'`. Se o cron falha de novo, cria row zerada. Ciclo: dados bons → expira → deletado → cron falha → row zerada → repete.

---

## Acceptance Criteria

### 27.5.1 — Nunca sobrescrever revenue valida com zeros

- [x] Em `upsertSyncError()` (**arquivo**: `src/app/api/cron/sync-reports/route.ts`, linha ~95), remover a condicao de `expires_at` do guard
- [x] Nova logica: se `existing?.sync_status === "ok"` (independente de `expires_at`):
  - Preservar TODOS os campos de revenue (`klaviyo_total_revenue`, `klaviyo_campaign_revenue`, `klaviyo_flow_revenue`, `store_total_revenue`)
  - Atualizar apenas: `sync_status = "partial"`, `sync_error = errorMsg`, `expires_at = novo TTL`
  - Log: `"[CronSync] Preserving valid revenue for store {id}, marking as partial due to: {error}"`
- [x] Se `existing` nao existe ou `existing.sync_status` e "error": escrever normalmente (zeros OK para primeira vez)
- [x] Se `existing.sync_status` e "partial": aplicar mesma logica de preservacao (partial ja teve dados validos antes)

### 27.5.2 — Aumentar TTL de 6h para 24h

- [x] Em `upsertSyncResults()`, alterar `expires_at` de `Date.now() + 6 * 60 * 60 * 1000` para `Date.now() + 24 * 60 * 60 * 1000`
- [x] Extrair constante: `const CACHE_TTL_MS = 24 * 60 * 60 * 1000 // 24 hours`
- [x] Mesmo TTL em `upsertSyncError()` para rows novas

### 27.5.3 — Cleanup function: nunca deletar rows "ok"

- [x] Alterar a funcao SQL `clean_expired_revenue_summaries()` (via migration):
  - Adicionar condicao: `AND sync_status != 'ok'`
  - Rows com `sync_status = 'ok'` nunca sao deletadas automaticamente, mesmo expiradas
  - Rows com `sync_status = 'error'` continuam sendo limpas apos 1 hora de expiracao

### 27.5.4 — Renovar expires_at em leitura (touch pattern)

- [x] Quando um endpoint de leitura (`total-revenue`, `portal-dashboard`) encontra uma row "ok" mas expirada, renovar `expires_at` por mais 24h
- [x] Isso garante que dados acessados frequentemente nunca sao deletados
- [x] Implementar como UPDATE atomico usando `createAdminClient()` (service role — endpoints de leitura podem usar `createClient()` para reads, mas o UPDATE precisa de service role para bypassar RLS)
- [x] Query: `UPDATE store_revenue_summary SET expires_at = NOW() + INTERVAL '24 hours' WHERE id = ? AND sync_status = 'ok'`

## Notas Tecnicas

- O touch pattern adiciona 1 UPDATE por request, mas e muito barato (index hit) e previne perda de dados
- Com TTL de 24h e cron rodando a cada ~6h, ha 4 oportunidades de refresh antes de expiracao
- A migration SQL deve ser idempotente (`CREATE OR REPLACE FUNCTION`)
