# Story 31.1 - DB Migration: CREATE VIEW unified_invoices + Indexes + RLS

## Epic
Epic 31 - Unified Invoices: Portal Visibility for All Charges

## Contexto
As tabelas `invoices` e `client_charges` armazenam dados financeiros separadamente. O portal le apenas de `invoices`, tornando cobranças manuais invisiveis para o cliente. Esta story cria uma VIEW unificada que serve como contrato unico de leitura.

## Objetivo
Criar migration SQL que:
1. Adiciona `updated_at` em `invoices` (coluna baseline ausente)
2. Cria VIEW `unified_invoices` com UNION ALL normalizado
3. Adiciona indexes compostos para queries do portal
4. Adiciona RLS policy em `client_charges` para portal users

### Task 2: Criar VIEW unified_invoices
- [x] **2.1** `CREATE OR REPLACE VIEW unified_invoices` com UNION ALL:
```sql
CREATE OR REPLACE VIEW unified_invoices AS

-- Invoices from Asaas integration
SELECT
  i.id,
  i.client_id,
  i.amount,
  i.due_date,
  i.payment_date,
  i.status::TEXT            AS status,
  i.description,
  i.asaas_id,
  NULL::UUID                AS subscription_id,
  NULL::TEXT                AS payment_method,
  NULL::TEXT                AS actual_payment_method,
  NULL::TEXT                AS notes,
  i.created_at,
  COALESCE(i.updated_at, i.created_at) AS updated_at,
  'asaas'::TEXT             AS source
FROM invoices i

UNION ALL

-- Charges from admin UI / subscription auto-generation
SELECT
  cc.id,
  cc.client_id,
  cc.value                  AS amount,
  cc.due_date,
  cc.payment_date,
  cc.status,
  cc.description,
  NULL::TEXT                AS asaas_id,
  cc.subscription_id,
  cc.payment_method,
  cc.actual_payment_method,
  cc.notes,
  cc.created_at,
  COALESCE(cc.updated_at, cc.created_at) AS updated_at,
  'local'::TEXT             AS source
FROM client_charges cc;
```
- [x] **2.2** Adicionar `COMMENT ON VIEW` documentando proposito e a assimetria de status: `invoices` suporta `refunded` (5 valores), `client_charges` nao (4 valores). Filtrar por `status = 'refunded'` retorna apenas rows Asaas — comportamento esperado.
- [x] **2.3** `GRANT SELECT ON unified_invoices TO authenticated, service_role`

### Task 4: RLS policy para portal users em client_charges
- [x] **4.1** Verificar RLS policies atuais em `client_charges` (nao tem policy para portal users)
- [x] **4.2** Criar policy (com DROP IF EXISTS para idempotencia):
```sql
DROP POLICY IF EXISTS "Portal users can view own client_charges" ON client_charges;
CREATE POLICY "Portal users can view own client_charges"
  ON client_charges FOR SELECT
  TO authenticated
  USING (
    client_id IN (
      SELECT client_id FROM client_portal_users
      WHERE auth_user_id = auth.uid()
    )
  );
```

## Riscos
| Risco | Severidade | Mitigacao |
|-------|-----------|-----------|
| Funcao `update_updated_at()` nao existe | MEDIO | Verificar antes; se nao existir, criar na migration |
| VIEW nao acessivel pelo Supabase client | BAIXO | Portal usa `adminClient` (service_role) que bypassa RLS |
| Performance da UNION ALL | BAIXO | Volume de dados e pequeno; indexes compostos garantem performance |

## Notas Tecnicas
- A VIEW e read-only. Writes continuam nas tabelas originais
- `adminClient` (service_role) bypassa RLS, mas a policy e defense-in-depth
- `COALESCE(updated_at, created_at)` garante que registros antigos sem updated_at tenham valor
