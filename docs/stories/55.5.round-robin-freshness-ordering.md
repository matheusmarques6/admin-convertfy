# Story 55.5 — Round-Robin por Freshness (Lojas Mais Velhas Primeiro)

## Story

**Como** operador do sistema,
**Quero** que lojas com dados mais antigos (ou sem dados) sejam processadas primeiro no cron,
**Para que** mesmo com timeout, as lojas que mais precisam de refresh tenham prioridade e 100% de cobertura seja alcancada em 1-2 runs.

## Contexto

### Problema

Atualmente, as lojas sao processadas na ordem retornada pelo Supabase (sem ORDER BY explicito). Lojas que ficam no final da fila sao consistentemente skipadas por timeout. Com 42 lojas e limite de 240s, as ~22 ultimas nunca recebem dados frescos.

### Solucao

1. Fazer LEFT JOIN com `store_revenue_summary` para buscar `MIN(fetched_at)` de cada loja
2. Ordenar por `MIN(fetched_at) ASC, NULLS FIRST` — lojas novas e mais stale primeiro
3. Manter o agrupamento por API key (a ordenacao e DENTRO de cada grupo)
4. Aumentar `MAX_PARALLEL_GROUPS` de 2 para 3

### Comportamento Esperado

- **Run 1**: Processa as 20-25 lojas mais stale/novas
- **Run 2** (30min depois): As lojas processadas no run 1 estao frescas (55.1 skip), processa as restantes
- **Run 3+**: Todas as 42 lojas tem dados frescos; runs sao rapidos

### Combinado com outras stories

Com 55.1 (skip fresh) + 55.3 (remove sleeps) + 55.4 (metadata TTL), o tempo por loja cai de ~25s para ~4s. Com 3 grupos em paralelo, 42 lojas / 3 = 14 slots, 14 x 4s = ~56s. Margem ampla para 240s.

## Acceptance Criteria

### 55.5.1 — Query com freshness ordering

- [x] Alterar a query de stores no cron route para incluir freshness:
  ```sql
  SELECT
    cs.id, cs.store_name, cs.org_id,
    cs.klaviyo_has_reporting_access,
    cs.klaviyo_validated_at,
    cs.klaviyo_missing_scopes,
    MIN(srs.fetched_at) AS oldest_fetched_at
  FROM client_stores cs
  LEFT JOIN store_revenue_summary srs
    ON cs.id = srs.store_id
    AND srs.sync_status IN ('ok', 'partial')
  WHERE cs.org_id IS NOT NULL
    AND (cs.klaviyo_private_key IS NOT NULL OR cs.klaviyo_api_key IS NOT NULL)
  GROUP BY cs.id, cs.store_name, cs.org_id,
    cs.klaviyo_has_reporting_access,
    cs.klaviyo_validated_at,
    cs.klaviyo_missing_scopes
  ORDER BY oldest_fetched_at ASC NULLS FIRST
  ```
- [x] Implementado via two-query approach: `getGroupFreshness()` busca todos de uma vez, sorting em JS
- [x] Sem necessidade de RPC — query simples + sorting em memória é suficiente para ~42 stores

## Riscos

| Risco | Mitigacao |
|-------|----------|
| Query com LEFT JOIN e lenta | Tabela pequena (~42 rows x 4 periodos = ~168 rows); index em store_id ja existe |
| MAX_PARALLEL_GROUPS=3 causa rate limits | Cada grupo usa API key diferente; rate limiter e por chamada, nao por grupo |
| Ordenacao muda a cada run (nao deterministica) | Isso e desejavel — lojas mais stale sao priorizadas dinamicamente |
| RPC nao compativel com .or() filter | Query via RPC substitui o .or(); filtro de credentials feito internamente |

## Notes

- A query Supabase JS nao suporta LEFT JOIN nativamente. Opcoes:
  1. **RPC** (recomendado): Funcao PL/pgSQL que retorna a query completa
  2. **Two queries**: Buscar stores + buscar MIN(fetched_at) separadamente, merge em JS
  3. **View**: Criar view, mas views nao sao queryable via .or() facilmente
- Recomendacao: usar RPC por ser mais limpo e performante
- A story 55.1 adiciona `PERIOD_FRESHNESS_THRESHOLDS` — esta story usa `fetched_at` para ordering, que e complementar
