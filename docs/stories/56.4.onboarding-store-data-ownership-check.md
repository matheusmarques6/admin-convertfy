# Story 56.4 — Adicionar Ownership Check em /api/onboarding/store-data

## Story

**Como** engenheiro de seguranca,
**Quero** que o endpoint `/api/onboarding/store-data` valide ownership antes de ler/escrever dados,
**Para que** um usuario admin nao possa acessar dados de onboarding (incluindo PII) de lojas de outra organizacao.

## Contexto

### Problema

O endpoint `src/app/api/onboarding/store-data/route.ts` e o IDOR mais critico da auditoria (CVSS 8.1):

1. **GET**: Aceita `store_id` ou `client_id` dos query params, usa `adminClient` para buscar dados sem nenhum ownership check
2. **POST**: Aceita `store_id` ou `client_id` do body, cria/atualiza dados de onboarding sem validacao
3. **PII exposto**: Retorna `cpf_cnpj` (CPF/CNPJ — dado sensivel LGPD) sem controle de acesso
4. **Criacao cross-org**: POST com `client_id` de outra org permite criar lojas sob clientes alheios

### Rota usada APENAS pelo admin

Esta rota e usada pelo admin (onboarding kanban, tabs de onboarding). O portal usa `/api/portal/onboarding/wizard` que e uma rota separada com `getPortalUser()`. O fix desta story NAO afeta o portal.

### Helpers disponiveis

- `requireStoreAccess(storeId, userId)` — valida store ownership + retorna orgId
- `resolveOrgId(userId)` — resolve org do usuario (para cenario sem store_id)

### Codigo atual (vulneravel)

```typescript
// GET handler — aceita store_id ou client_id sem validacao
export async function GET(request: Request) {
  const supabase = await createClient()
  const user = await requireAuth(supabase) // so checa autenticacao, nao autorizacao
  const adminClient = createAdminClient()

  const { searchParams } = new URL(request.url)
  const storeId = searchParams.get("store_id")
  const clientId = searchParams.get("client_id")

  // Busca via adminClient sem ownership check!
  if (storeId) {
    const { data: store } = await adminClient
      .from("client_stores")
      .select("*")
      .eq("id", storeId)
      .single()
    // ... retorna dados incluindo PII do cliente
  }
}
```

## Acceptance Criteria

### 56.4.1 — GET com store_id: requireStoreAccess

- [x] Se `store_id` fornecido nos query params:
  ```typescript
  const storeAccess = await requireStoreAccess(storeId, user.id)
  ```
- [x] Se `requireStoreAccess` lanca erro, retornar 403:
  ```typescript
  try {
    const storeAccess = await requireStoreAccess(storeId, user.id)
  } catch (err) {
    return errorResponse(request, err, { handler: "GET /api/onboarding/store-data" })
  }
  ```
- [x] O `orgId` retornado pode ser usado para validacoes adicionais se necessario

**Given-When-Then:**

```
GIVEN User A is authenticated in Org A
AND Store S1 belongs to Org B
WHEN User A calls GET /api/onboarding/store-data?store_id=<S1_id>
THEN response is 403 Forbidden
AND no data from S1 is returned

GIVEN User A is authenticated in Org A
AND Store S2 belongs to Org A
AND User A has can_view on S2
WHEN User A calls GET /api/onboarding/store-data?store_id=<S2_id>
THEN response contains store, onboarding_data, and client data for S2
```

### 56.4.2 — GET com client_id: resolveOrgId + validacao

- [x] Se apenas `client_id` fornecido (sem store_id):
  ```typescript
  const userOrgId = await resolveOrgId(user.id)

  // Buscar client e verificar org_id
  const { data: client } = await adminClient
    .from("clients")
    .select("id, org_id")
    .eq("id", clientId)
    .single()

  if (!client || client.org_id !== userOrgId) {
    throw new ForbiddenError("Sem acesso a este cliente")
  }
  ```

**Given-When-Then:**

```
GIVEN User A is authenticated in Org A
AND Client C1 belongs to Org B
WHEN User A calls GET /api/onboarding/store-data?client_id=<C1_id>
THEN response is 403 Forbidden
AND no PII (name, email, phone, cpf_cnpj) from C1 is returned

GIVEN User A is authenticated in Org A
AND Client C2 belongs to Org A
WHEN User A calls GET /api/onboarding/store-data?client_id=<C2_id>
THEN response contains client data and stores for C2
```

### 56.4.3 — POST com store_id: requireStoreAccess

- [x] Se `store_id` fornecido no body:
  ```typescript
  const storeAccess = await requireStoreAccess(storeId, user.id)
  ```
- [x] Validacao ANTES de qualquer operacao com adminClient

**Given-When-Then:**

```
GIVEN User A is authenticated in Org A
AND Store S1 belongs to Org B
WHEN User A calls POST /api/onboarding/store-data with { store_id: S1_id, ... }
THEN response is 403 Forbidden
AND no data is modified

GIVEN User A is authenticated in Org A
AND Store S2 belongs to Org A
WHEN User A calls POST /api/onboarding/store-data with { store_id: S2_id, data: {...} }
THEN onboarding data is saved successfully
```

### 56.4.4 — POST com client_id (sem store_id): resolveOrgId + validacao

- [x] Se `client_id` fornecido sem `store_id`:
  ```typescript
  const userOrgId = await resolveOrgId(user.id)

  const { data: client } = await adminClient
    .from("clients")
    .select("id, org_id")
    .eq("id", clientId)
    .single()

  if (!client || client.org_id !== userOrgId) {
    throw new ForbiddenError("Sem acesso a este cliente")
  }
  ```
- [x] Store criada sob o client DEVE receber `org_id` do client (nao do usuario, para consistencia)

**Given-When-Then:**

```
GIVEN User A is authenticated in Org A
AND Client C1 belongs to Org B
WHEN User A calls POST /api/onboarding/store-data with { client_id: C1_id, store_name: "Evil Store" }
THEN response is 403 Forbidden
AND no store is created under C1

GIVEN User A is authenticated in Org A
AND Client C2 belongs to Org A
WHEN User A calls POST /api/onboarding/store-data with { client_id: C2_id, store_name: "New Store" }
THEN store is created under C2 with org_id = Org A
```
