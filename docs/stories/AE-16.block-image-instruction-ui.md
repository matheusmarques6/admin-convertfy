# Story AE-16 — UI de instrução por bloco no `BlockContentEditor` + endpoints regenerate/resolve-prompt

## User Story

**Como** designer (ou dev),
**quero** abrir um bloco `hero` ou `image` no `EmailDetailView`, digitar uma instrução opcional ("mostre a capa em couro vermelho esportivo") e clicar "Regenerar" para ver a nova imagem,
**para que** eu ajuste o resultado quando o niche-adaptive automático não captura uma nuance — sem precisar editar o prompt mestre global.

---

## Contexto

Hoje (após AE-10..14):
- Sistema niche-adaptive geral funciona: 6 prompts mestres versionados pra Welcome E1-E6, aspect ratio matriz, PRODUCT-REF mode, helpers de derivação
- `EmailDetailView` (`src/components/stores/producao/email-detail-view.tsx`, 3700+ linhas) tem `BlockContentEditor` (~L2676) inline pra editar `content` JSONB
- Botão "Gerar com IA" existe **no nível EMAIL** (não por bloco)
- AE-11 já preparou placeholder `{{#if INSTRUCAO_ADICIONAL}}` no template + `buildImagePromptVars` aceita `instrucaoAdicional?`
- `phase2-runner` já lê `blk.content.image_instruction` defensivamente (contrato com AE-16)

Esta story entrega:
1. Campo "Instrução adicional" em `BlockContentEditor` pra blocks `hero` e `image`
2. Botão "Regenerar imagem" por bloco
3. Botão "Ver prompt resolvido" (modal de debug)
4. 2 endpoints novos: `regenerate-image` e `resolve-prompt`

Decisões UX confirmadas com user (em sessão anterior):
- **Append**: instrução complementa prompt mestre (não substitui)
- **Botão explícito** (não auto-regen ao salvar — evita gasto de API)
- **Preview do prompt**: modal mostra prompt final renderizado (com vars substituídas)

## Dev Notes

### Reuso do helper de resolução de prompt
Pra evitar duplicar lógica entre `resolve-prompt` e `regenerate-image`:
```ts
// src/lib/agents/image/resolve-block-prompt.service.ts
export async function resolveBlockPrompt(blockId: string): Promise<{
  prompt: string
  vars: Record<string, string>
  aspect: AspectKey
  mode: ImageMode
  storeId: string
  topProductImageUrl: string | null
  overlayReserveBottom: boolean
}>
```
Ambos endpoints chamam isso; `regenerate-image` continua daqui pra `generateEmailImage`.

### Rate limit simples sem tabela nova
Reusa `image_last_generated_at` do próprio bloco. 1 query a mais, mas zero schema change.

### Por que mostrar "Vars used" no modal?
Designer pode entender por que a imagem saiu "errada" (ex: `PRODUTO_HEROI` veio com nome incorreto do catálogo). Útil pra debug colaborativo dev+designer.

### Compat com regeneração via AE-2 (mode=redo)
A regeneração por bloco substitui só **1 bloco específico**. O endpoint AE-2 (start-onboarding mode=redo) regera o flow inteiro. Os dois coexistem — escolha do designer/dev qual usar.

## Riscos

| Risco | Probabilidade | Mitigacao |
|-------|---------------|-----------|
| Designer regenera 20x = $20 perdido | Media | Rate limit 30s + cooldown visual + log de runs visíveis em AE-9 |
| Prompt resolvido vaza dados sensiveis (briefing) | Baixa | Endpoint restrito a admin/dev; modal nunca aparece pra outros roles |
| `image_last_prompt` infla JSONB do bloco (~2KB) | Baixa | Truncate a 2KB; aceitavel pra debug |
| Modal de preview chama API toda vez que abre | Baixa | Aceitavel (resolve-prompt eh barato ~5ms); pode cachear no client se vier issue |
| Concorrencia: 2 designers clicam regenerar ao mesmo tempo | Media | UPDATE atomico do image_url; ultimo vence (sem lock) — aceitavel |
