## Contexto

Esta eh a story central de performance. Os endpoints `/api/dashboard/total-revenue` e `/api/stores/control` atualmente fazem chamadas em tempo real para as APIs da Klaviyo e Shopify durante o carregamento de cada pagina. Com a tabela `store_revenue_summary` populada pelo cron (Stories 8.6 e 8.7), esses endpoints podem ser reescritos para ler diretamente do banco.

**Impacto esperado:**
- ANTES: 30 lojas x 4 API calls = 120 requests, ~72 segundos
- DEPOIS: 1 query Supabase, ~50ms

---

## Objetivo

1. Reescrever `/api/dashboard/total-revenue` para ler de `store_revenue_summary`
2. Reescrever o trecho de revenue em `/api/stores/control` para ler de `store_revenue_summary`
3. Remover cache in-memory (`Map`) de ambos os endpoints
4. Garantir que ambos usam `createClient()` (nao `createAdminClient()`) para leitura

## Arquitetura Tecnica

### total-revenue - Reescrita

```typescript
export async function GET(request: NextRequest) {
  const { user } = await requireAuth(request)
  const supabase = createClient()
  const orgId = await resolveOrgId(user.id)

  const { searchParams } = new URL(request.url)
  const period = searchParams.get("period") || "30d"

  // UMA UNICA QUERY — substitui 120+ API calls
  const { data: summaries, error } = await supabase
    .from("store_revenue_summary")
    .select(`
      store_id,
      klaviyo_total_revenue,
      klaviyo_campaign_revenue,
      klaviyo_flow_revenue,
      shopify_total_revenue,
      sync_status,
      fetched_at,
      client_stores!inner(id, store_name, client_id, clients(name))
    `)
    .eq("period_label", period)
    .eq("org_id", orgId)
    .gt("expires_at", new Date().toISOString())

  if (error) {
    return errorResponse(request, error, "total-revenue")
  }

  // Aplicar store_ids filter se presente
  const storeIds = searchParams.get("store_ids")?.split(",")
  const filtered = storeIds
    ? summaries?.filter(s => storeIds.includes(s.store_id)) || []
    : summaries || []

  // Agregar totais
  const totalRevenue = filtered.reduce((sum, s) => sum + Number(s.klaviyo_total_revenue), 0)
  const campaignRevenue = filtered.reduce((sum, s) => sum + Number(s.klaviyo_campaign_revenue), 0)
  const flowRevenue = filtered.reduce((sum, s) => sum + Number(s.klaviyo_flow_revenue), 0)

  // Formatar storeBreakdown, topStores, bottomStores
  const storeBreakdown = filtered.map(s => ({
    storeId: s.store_id,
    storeName: s.client_stores.store_name,
    clientName: s.client_stores.client_id
      ? s.client_stores.clients?.name || "Cliente desconhecido"
      : s.client_stores.store_name,
    totalRevenue: Number(s.klaviyo_total_revenue),
    campaignRevenue: Number(s.klaviyo_campaign_revenue),
    flowRevenue: Number(s.klaviyo_flow_revenue),
  }))

  const sorted = [...storeBreakdown].sort((a, b) => b.totalRevenue - a.totalRevenue)
  const topStores = sorted.slice(0, 5)
  const bottomStores = sorted.slice(-5).reverse()

  const hasPartialData = filtered.some(s => s.sync_status === 'error' || s.sync_status === 'partial')

  return successResponse(request, {
    period,
    totalRevenue,
    campaignRevenue,
    flowRevenue,
    storesCount: filtered.length,
    topStores,
    bottomStores,
    storeBreakdown,
    hasPartialData,
  })
}
```

## Riscos e Mitigacoes

| Risco | Mitigacao |
|-------|-----------|
| Tabela vazia no dia 1 (cron nao rodou) | Retornar revenue 0 com flag `hasPartialData`, nao erro |
| Formato de resposta diferente quebra frontend | Manter interface `TotalRevenueResponse` identica |
| Join com `client_stores` pode falhar se store deletada | `!inner` join garante que so retorna lojas existentes |
| Revenue com tipo `string` vs `number` | `NUMERIC(15,2)` retorna como string no Supabase; usar `Number()` |
